# 2026-07-27. dbt — 왜 "SQL 잘 짜는 것"과 "데이터 파이프라인을 짓는 것"은 다른가

> 우리는 SQL을 안다. `SELECT`, `JOIN`, `GROUP BY`. 그런데 현장에서 데이터브릭스 프로젝트에 들어가면 거의 예외 없이 **dbt(data build tool)**를 쓴다고 한다. SQL을 아는데 왜 또 다른 도구가 필요할까?
>
> 답은 이렇다. **SQL 한 방을 잘 짜는 것**과 **SQL 수백 개를 서로 의존하게 엮어 매일 안전하게 돌리는 것**은 완전히 다른 문제다. 앞은 '쿼리'의 문제고, 뒤는 **'소프트웨어 엔지니어링'의 문제**다. dbt는 바로 이 뒤쪽을 위한 도구다. 이번 주는 dbt가 무엇이고, 왜 데이터 변환의 사실상 표준이 됐는지를 밑바닥부터 뜯는다.

## 1. 도입: SQL 파일 수백 개의 지옥

가상의 장면 하나. 데이터 팀이 웨어하우스에 원본 데이터를 다 넣었다. 이제 분석용 테이블을 만들어야 한다. 처음엔 SQL 몇 개로 시작한다.

```sql
CREATE TABLE stg_orders AS SELECT ... FROM raw_orders;
CREATE TABLE stg_customers AS SELECT ... FROM raw_customers;
CREATE TABLE dim_customers AS SELECT ... FROM stg_customers JOIN ...;
CREATE TABLE fact_sales AS SELECT ... FROM stg_orders JOIN dim_customers ...;
```

몇 달 지나면 이 SQL 파일이 **200개**가 된다. 그리고 문제가 터진다.

- **실행 순서 지옥**: `fact_sales`는 `dim_customers`가 먼저 만들어져야 돌아간다. `dim_customers`는 `stg_customers`가 먼저다. 이 순서를 **사람이 손으로** 관리한다. 하나 끼어들면 전부 다시 배열.
- **"이거 고치면 뭐가 깨지지?" 공포**: `stg_orders`의 컬럼 하나를 바꾸면, 그걸 참조하는 하위 테이블 몇 개가 깨지는지 아무도 모른다. grep으로 테이블 이름을 검색하며 기도한다.
- **테스트 부재**: "고객 ID가 중복되면 안 된다", "매출은 음수면 안 된다" 같은 규칙을 검사하는 곳이 없다. 틀린 수치가 대시보드까지 조용히 흘러간다.
- **개발/운영 환경 뒤섞임**: 개발용으로 테이블 만들다가 실수로 운영 테이블을 덮어쓴다.
- **문서 부재**: `fact_sales`의 `amount`가 세전인지 세후인지, 아무 데도 안 적혀 있다. 만든 사람은 이미 퇴사했다.

이건 SQL을 못 짜서 생긴 문제가 **아니다.** 각 SQL은 완벽하다. 문제는 이 **수백 개를 하나의 시스템으로 엮고, 안전하게 반복 실행하고, 여럿이 협업**하는 방법이 없다는 것이다.

> 소프트웨어 엔지니어들은 이 문제를 수십 년 전에 풀었다. 버전 관리(Git), 모듈화, 자동 테스트, CI/CD, 의존성 관리, 문서화. **"이 검증된 방법론을 SQL 데이터 변환에도 그대로 가져오면 어떨까?"** — 이 질문의 답이 dbt다.

## 2. 한 문장 정의 — dbt는 ELT의 'T'다

dbt를 이해하는 가장 빠른 길은 **ELT**라는 3글자에 자리를 잡아주는 것이다.

옛날 방식은 **ETL**(Extract → Transform → Load)이었다. 데이터를 뽑아서(E), **웨어하우스 밖에서 변환한 뒤**(T), 완성본을 적재(L)했다.

지금 클라우드 시대의 방식은 **ELT**(Extract → Load → **Transform**)다. 저장·연산이 싸진 웨어하우스(Databricks, Snowflake, BigQuery…)에 **일단 원본을 다 적재하고(E·L)**, 변환(T)은 **웨어하우스 안에서 SQL로** 한다.

```
   [원본: 앱 DB, 로그, SaaS API...]
              │  E + L  (Fivetran, Airbyte, Databricks 인제스트 등이 담당)
              ▼
   [웨어하우스/레이크하우스에 원본 그대로 적재]
              │  ← ★ 여기가 dbt의 자리: T(Transform)
              ▼
   [분석용 테이블: 정제·조인·집계·차원 모델]
```

> **dbt는 이 마지막 'T' 한 글자만 담당한다.** 데이터를 뽑지도(E), 옮기지도(L) 않는다. 오직 **이미 웨어하우스에 들어온 데이터를, SQL `SELECT`로 변환해 새 테이블/뷰로 만드는 일**만 한다.

여기서 dbt를 처음 만나는 사람이 가장 많이 오해하는 지점을 못 박자.

> **핵심 통찰 — "dbt는 데이터를 옮기지 않는다. SQL을 생성해서 웨어하우스에 던질 뿐이다"**
>
> dbt 자체는 데이터를 1바이트도 처리하지 않는다. 무거운 연산(조인, 집계)은 **전부 Databricks/Snowflake 같은 엔진이** 한다. dbt가 하는 일은 (1) 우리가 쓴 `SELECT` 문들을 읽어서, (2) 의존성 순서를 계산하고, (3) 실행 가능한 완성된 SQL(`CREATE TABLE ... AS SELECT ...`)로 **컴파일**해서, (4) 순서대로 **웨어하우스에 보내 실행시키는 것**이다. 즉 dbt는 **"SQL 컴파일러 + 오케스트레이터"**이지, 데이터 처리 엔진이 아니다. 그래서 노트북 위에서 가볍게 돌아가고, 무거운 일은 강력한 엔진에 맡긴다 — 역할 분리가 아름답다.

그래서 dbt의 한 줄 정의는 이렇다.

> **dbt = SQL `SELECT` 문에 소프트웨어 엔지니어링(버전관리·의존성·테스트·문서)을 입혀, 데이터 변환을 하나의 관리 가능한 프로젝트로 만드는 도구.**

## 3. dbt의 심장 — Model과 `ref()`, 그리고 자동 DAG

dbt의 90%는 딱 두 가지 개념에서 나온다. **Model**과 **`ref()`**. 이 둘만 이해하면 "왜 dbt가 특별한가"가 단번에 보인다.

### 3.1 Model — "하나의 SELECT = 하나의 파일"

dbt에서 **Model**은 거창한 게 아니다. **`.sql` 파일 하나, 그 안에 `SELECT` 문 하나**다. 그게 전부다.

`models/stg_orders.sql`:
```sql
SELECT
    order_id,
    customer_id,
    amount,
    ordered_at
FROM raw.orders
WHERE amount > 0
```

주목할 점: `CREATE TABLE`도, `INSERT`도 없다. 그냥 **순수한 `SELECT`**다. "이 테이블은 이런 모양이어야 한다"만 선언하면, **어떻게 만들지(CREATE/INSERT/DROP)는 dbt가 알아서** 채워준다. 우리는 *무엇(what)*만 쓰고, *어떻게(how)*는 dbt에 맡긴다 — 이게 **선언형(declarative)**의 핵심이다.

### 3.2 `ref()` — dbt를 dbt로 만드는 단 하나의 함수

이제 마법이 시작된다. 한 Model이 다른 Model을 참조할 때, **테이블 이름을 직접 쓰지 않는다.** 대신 `ref()` 함수로 가리킨다.

`models/fact_sales.sql`:
```sql
SELECT
    o.order_id,
    c.customer_key,
    o.amount
FROM {{ ref('stg_orders') }}    AS o      -- 테이블명 직접 X, ref()로 참조
JOIN {{ ref('dim_customers') }} AS c
  ON o.customer_id = c.customer_id
```

`{{ ref('stg_orders') }}` — 이 한 줄이 dbt의 심장이다. 이게 왜 그렇게 중요한가?

**① dbt가 의존성을 자동으로 안다.** `fact_sales`가 `stg_orders`와 `dim_customers`를 `ref()`로 참조했으니, dbt는 **"fact_sales는 이 둘이 먼저 만들어져야 한다"**를 스스로 파악한다. 프로젝트 전체의 `ref()`를 다 훑으면 **의존성 그래프(DAG, 방향성 비순환 그래프)**가 통째로 그려진다.

```
raw.orders ──▶ stg_orders ──┐
                            ├──▶ fact_sales ──▶ (대시보드)
raw.customers ─▶ stg_customers ─▶ dim_customers ──┘
```

**② 실행 순서를 사람이 관리할 필요가 없다.** `dbt run` 한 방이면, dbt가 이 DAG를 위상 정렬해서 **올바른 순서로, 독립적인 건 병렬로** 알아서 실행한다. 2장의 "실행 순서 지옥"이 통째로 사라진다.

**③ 환경 분리가 공짜로 된다.** `ref('stg_orders')`는 실행 시점에 실제 이름으로 치환되는데, 개발 환경에선 `dev_me.stg_orders`로, 운영에선 `prod.stg_orders`로 **자동 치환**된다. 같은 코드가 환경에 따라 다른 테이블을 가리킨다. "실수로 운영 덮어쓰기"가 구조적으로 막힌다.

> **핵심 통찰 — "`ref()`는 하드코딩된 이름을 관계로 바꾼다"**
>
> 평범한 SQL에서 테이블 이름 `prod.stg_orders`는 **죽은 문자열**이다. 그게 어디서 왔는지, 뭘 부양하는지 코드는 모른다. dbt는 그 문자열을 `{{ ref('stg_orders') }}`라는 **살아있는 관계**로 바꾼다. 그 순간 200개의 흩어진 SQL 파일이 **하나의 연결된 그래프**가 된다. 실행 순서, 영향 범위("이거 고치면 뭐가 깨지나"), 환경 분리, 계보 추적 — 이 모든 게 `ref()` 하나에서 파생된다. dbt의 다른 모든 기능은 사실 이 그래프 위에 얹힌 부가물이다.

### 3.3 잠깐, 이 `{{ }}`는 뭔가 — Jinja

`{{ ref(...) }}`의 이중 중괄호는 **Jinja**라는 템플릿 언어다. dbt는 SQL에 Jinja를 섞어 **"SQL을 프로그래밍"**할 수 있게 한다. 변수, 반복문, 조건문, 함수(매크로)를 SQL 안에 쓸 수 있다. 예를 들어 결제수단 12개에 대해 컬럼 12개를 손으로 쓰는 대신, Jinja `for` 루프로 생성한다. dbt는 실행 전에 이 Jinja를 **순수 SQL로 렌더링(컴파일)**한 뒤 웨어하우스에 보낸다. 즉 우리가 보는 건 템플릿, 웨어하우스가 받는 건 완성된 SQL이다.

## 4. dbt가 공짜로 얹어주는 것 — 테스트·문서·계보

`ref()`로 그래프가 생기고 나면, 그 위에서 소프트웨어 엔지니어링의 도구들이 **거의 공짜로** 딸려온다. 이게 dbt를 "그냥 SQL 실행기"가 아니라 **개발 프레임워크**로 만든다.

### 4.1 데이터 테스트 — "틀린 수치를 대시보드 전에 잡는다"

Model 옆에 YAML로 **검증 규칙**을 선언하면, `dbt test`가 자동으로 검사한다.

```yaml
models:
  - name: dim_customers
    columns:
      - name: customer_key
        tests:
          - unique          # 중복 없어야
          - not_null        # 널 없어야
      - name: status
        tests:
          - accepted_values:   # 이 값들만 허용
              values: ['active', 'churned', 'prospect']
```

이 네 줄이 "고객키는 유일하고 널이 없어야 하며, 상태는 셋 중 하나여야 한다"를 **매 실행마다 자동 검사**한다. 규칙이 깨지면 파이프라인이 멈추고 알린다. **틀린 데이터가 하류로 흐르기 전에 차단**된다. 소프트웨어의 단위 테스트를, 데이터에 그대로 적용한 것이다.

### 4.2 문서 & 계보(Lineage) — 그래프의 부산물

`ref()` 그래프가 있으니, dbt는 **`dbt docs`** 명령 하나로 **인터랙티브 문서 사이트**를 자동 생성한다. 각 테이블/컬럼 설명(YAML에 적은 것)은 물론, **데이터 계보 그래프**를 시각적으로 보여준다 — "이 `fact_sales`는 어떤 원본에서 왔고, 어떤 대시보드를 부양하는가"가 클릭 몇 번에 드러난다.

> **핵심 통찰 — "계보는 만드는 게 아니라, `ref()`의 부산물로 생겨난다"**
>
> 많은 조직이 데이터 계보(lineage)를 그리려고 별도 도구를 산다. dbt에선 계보를 **따로 그릴 필요가 없다.** 개발자가 `ref()`로 코드를 짜는 순간, 계보는 **이미 코드 안에 존재**한다. dbt는 그걸 읽어서 그림으로 보여줄 뿐이다. "문서와 코드가 따로 놀다가 문서가 낡는" 고질병을, dbt는 **문서를 코드에서 유도**함으로써 원천 차단한다. 이게 dbt가 파는 진짜 가치다 — 기능 하나하나가 아니라, **코드가 곧 진실의 원천(single source of truth)**이 되는 구조.

## 5. Materialization — 같은 SELECT를 view로 굽나, table로 굽나, 쌓나

3장에서 "우리는 `SELECT`만 쓰고, `CREATE TABLE`은 dbt가 채운다"고 했다. 그러면 **정확히 어떻게** 물리화할지는 어떻게 정할까? 이게 **Materialization(구체화 전략)**이다. **같은 `SELECT` 문을, 설정 한 줄만 바꿔 다른 방식으로 물리화**한다.

| Materialization | dbt가 실제로 만드는 것 | 언제 쓰나 | 트레이드오프 |
|---|---|---|---|
| **view** | `CREATE VIEW` (쿼리만 저장, 데이터 X) | 가볍고 자주 안 읽는 중간 단계 | 저장 0, 하지만 읽을 때마다 재연산 |
| **table** | `CREATE TABLE AS SELECT` (매번 전체 재생성) | 자주 읽는 최종 소비 테이블 | 읽기 빠름, 하지만 매번 통째로 다시 만듦 |
| **incremental** | 처음엔 전체, 이후엔 **바뀐 행만** 추가/갱신 | 수십억 행 로그·거대 Fact 테이블 | 가장 효율적, 하지만 설정이 가장 복잡 |
| **ephemeral** | 테이블/뷰를 안 만들고, 상위 쿼리에 **CTE로 인라인** | 재사용하지만 물리화는 불필요한 조각 | 웨어하우스에 흔적 안 남김 |

바꾸는 법은 정말 이 한 줄이다:

```sql
{{ config(materialized='incremental') }}   -- view → table → incremental, 이 단어만 교체

SELECT ... FROM {{ ref('stg_orders') }}
{% if is_incremental() %}
  WHERE ordered_at > (SELECT MAX(ordered_at) FROM {{ this }})  -- 이미 처리한 이후 것만
{% endif %}
```

`incremental`이 특히 중요하다. 매일 수억 행이 쌓이는 로그 테이블을 매번 처음부터 다시 만들면 시간·비용이 폭발한다. incremental은 **"지난번 이후 새로 들어온 것만"** 처리해서, 이 비용을 극적으로 줄인다.

> **핵심 통찰 — "물리화를 코드에서 분리한 게 dbt의 우아함"**
>
> 평범한 SQL에선 "이걸 뷰로 할까 테이블로 할까"가 `CREATE VIEW` vs `CREATE TABLE`이라는 **문장 자체**에 박혀 있다. 바꾸려면 쿼리를 뜯어고쳐야 한다. dbt는 **비즈니스 로직(`SELECT`)과 물리화 전략(`config`)을 분리**했다. 로직은 그대로 두고 `view`→`table`→`incremental`만 갈아끼운다. 프로토타입 땐 싼 view로 빠르게 돌리다가, 운영 땐 incremental로 승격 — 로직 한 줄 안 건드리고. 이 **관심사의 분리**가 대규모 파이프라인을 유지보수 가능하게 만든다.

---

## 6. 실전 어휘 — source, seed, snapshot, macro

프로젝트에서 마주칠 나머지 핵심 어휘 넷을 짧게 정리한다.

- **Source(소스)**: 원본 테이블(dbt 밖에서 적재된 raw 테이블)을 `{{ source('raw', 'orders') }}`로 **선언**한다. 이러면 원본도 계보 그래프에 편입되고, "원본이 신선한가(freshness)"까지 검사할 수 있다. Model의 시작점을 명시하는 것.
- **Seed(시드)**: 작은 정적 CSV를 테이블로 올린다. 국가코드↔국가명 매핑, 환율 표 같은 **손으로 관리하는 참조 데이터**용. Git으로 버전 관리되는 게 장점.
- **Snapshot(스냅샷)**: **변화 이력을 자동으로 보존**한다. 소스의 어떤 행이 바뀌면, 옛 버전을 닫고 새 버전을 열어 히스토리를 남긴다. 이게 바로 차원 모델링의 **SCD Type 2**(느리게 변하는 차원, 이력 보존) — "그때 그 시점의 진실"을 지키는 기법 — 를 **dbt가 명령 하나로 자동화**한 것이다. 손으로 유효기간 컬럼을 관리하던 고된 작업을 `dbt snapshot`이 대신한다.
- **Macro(매크로)**: Jinja로 쓰는 **함수**. 여러 Model에서 반복되는 SQL 조각을 함수로 묶어 재사용한다. `{{ cents_to_dollars('amount') }}` 처럼. 소프트웨어의 "함수로 중복 제거(DRY)"를 SQL에 적용한 것. 남이 만든 매크로 묶음(**패키지**)을 가져다 쓸 수도 있다(dbt의 오픈소스 생태계).

> **핵심 통찰 — "dbt의 모든 기능은 '소프트웨어 엔지니어링을 SQL로 번역'한 것"**
>
> 여기까지 보면 패턴이 보인다. **테스트** = 단위 테스트, **매크로** = 함수, **패키지** = 라이브러리 의존성, **ref()** = 모듈 import, **환경 분리** = dev/prod 브랜치, **snapshot** = 변경 이력(감사 로그). dbt는 새로운 개념을 발명한 게 아니라, **소프트웨어 세계가 이미 검증한 관행들을 데이터 변환에 하나씩 이식**했다. "Analytics Engineering(분석 엔지니어링)"이라는 직군 이름 자체가 이 이식의 산물이다 — SQL을 아는 분석가가, 엔지니어처럼 일하게 만든 것.

## 7. dbt Core vs dbt Cloud, 그리고 2026년의 지각변동

### 7.1 두 얼굴 — Core와 Cloud

dbt는 두 형태로 존재한다.

- **dbt Core**: **오픈소스, 무료.** 커맨드라인 도구(`dbt run`, `dbt test`…)다. 우리가 지금까지 본 모든 개념(Model, ref, 테스트, 물리화)이 여기 다 있다. 실행 스케줄링·CI·협업 UI는 직접 붙여야 한다(예: Airflow, GitHub Actions).
- **dbt Cloud**: **상용 SaaS.** Core를 감싸서 웹 IDE, 스케줄러, CI/CD, 문서 호스팅, 권한 관리, 관측성을 얹은 것. 팀 규모가 커지면 이쪽으로 간다.

핵심은 **로직 자체는 둘이 동일**하다는 것. Core로 배운 게 Cloud에서 그대로 통한다. 학습은 Core로 시작하는 게 정석이다.

### 7.2 2026년, dbt 지형이 흔들렸다 — 꼭 알아야 할 두 가지

dbt를 지금 배우는 사람이라면 최근의 두 대형 변화를 반드시 알아야 한다.

**① dbt Fusion 엔진 (dbt Core v2.0).** 기존 dbt는 SQL을 **문자열로만** 다뤘다 — Jinja를 치환해 SQL 텍스트를 만들 뿐, 그 SQL의 *의미*는 몰랐다. 그래서 오타나 타입 오류는 실제로 웨어하우스에서 돌려봐야 터졌다. **Fusion**은 이걸 뒤집었다. **Rust로 새로 쓴, SQL을 진짜로 이해(파싱·분석)하는 엔진**이다. 덕분에 (1) 웨어하우스에 보내기 전에 **오류를 미리** 잡고, (2) 컴파일이 훨씬 빠르며, (3) 컬럼 수준 계보 같은 정밀 분석이 가능해졌다. 2026년 이 Fusion 엔진이 **Apache 2.0 라이선스로 오픈소스화(dbt Core v2.0)**되면서, 기존 dbt 사용자에게 더 빠르고 똑똑한 기반이 열렸다.

**② Fivetran + dbt Labs 합병.** 2025년 10월 발표되어 **2026년 6월 1일 완료**된 대형 사건. 데이터 **적재(EL)**의 강자 **Fivetran**과, **변환(T)**의 표준 **dbt Labs**가 한 회사가 됐다. 2장의 ELT 그림에서 **E·L을 Fivetran이, T를 dbt가** 맡고 있었는데, 그 둘이 하나로 합쳐진 것이다. 지향점은 "AI 에이전트가 신뢰할 수 있는, 하나로 통합된 오픈 데이터 인프라". 다만 **당장은 두 제품이 독립적으로 계속 돌아가므로**, 기존 dbt 파이프라인은 그대로 작동한다. 통합·번들 가격은 시간을 두고 진행될 전망이다. dbt는 전 세계 **8만 개 이상의 데이터 팀**이 쓰는 사실상 표준으로, 이 위상은 합병 뒤에도 유지된다.

> **핵심 통찰 — "T가 표준이 되자, E·L이 T를 사러 왔다"**
>
> 이 합병의 방향이 의미심장하다. 데이터 변환(T) 도구인 dbt가 어찌나 표준이 됐던지, **적재(EL) 회사가 변환 회사를 인수**해 파이프라인 전체를 손에 넣으려 한 것이다. "어떤 도구를 쓰든 변환은 dbt로 수렴한다"는 시장의 현실을, 이 딜 자체가 증명한다. 우리가 지금 dbt를 배우는 게 시류를 잘 탄 선택인 이유이기도 하다.

## 8. Databricks 위에서의 dbt

이제 이 글의 실전 목적지. **dbt와 Databricks는 어떻게 만나는가.** 현업에서 "데이터브릭스 프로젝트엔 dbt가 필수"라고 말하는 그 지점이다.

### 8.1 dbt-databricks 어댑터 — 둘을 잇는 다리

dbt는 특정 웨어하우스에 종속되지 않는다. 대신 **어댑터(adapter)**라는 플러그인으로 각 엔진에 연결된다. Databricks용은 **`dbt-databricks`** 어댑터인데, 중요한 건 이걸 **Databricks가 직접 만들고 유지보수**한다는 점이다. 그만큼 둘의 결합을 공식적으로 밀고 있다는 뜻이다. 이 어댑터의 기본 설계가 특히 절묘하다:

| dbt-databricks의 기본 동작 | 의미 |
|---|---|
| 테이블을 **기본적으로 Delta 포맷**으로 생성 | dbt Model이 곧 Delta 테이블. 트랜잭션·타임트래블을 그대로 얻는다 |
| **incremental** 모델을 **`MERGE`**로 구현 | "있으면 갱신, 없으면 삽입"(upsert)을 Delta의 강력한 `MERGE`로 처리 |
| 무거운 쿼리를 **Photon** 엔진으로 실행 | dbt가 생성한 SQL을 Databricks의 고속 엔진이 처리 |
| **Unity Catalog**의 3단 네임스페이스 지원 | `catalog.schema.table` 거버넌스 체계에 dbt Model이 그대로 얹힘 |

### 8.2 왜 이 조합이 강한가 — 역할 분담의 완성

여기서 dbt와 Databricks의 관계가 명확해진다. **dbt는 "무엇을 만들지"를 SQL로 선언하고, Databricks는 "그걸 어떻게 빠르고 안전하게 실행할지"를 책임진다.**

- dbt Model의 `SELECT` → Databricks가 **Photon으로 실행**.
- dbt `incremental` → Delta의 **`MERGE`**로 물리화. (dbt의 upsert 요구와 Delta의 MERGE 기능이 정확히 맞물린다.)
- dbt `snapshot`(SCD Type 2 이력 보존) → Delta의 `MERGE`가 **옛 행 닫고 새 행 여는** 그 upsert를 수행. 모델링 이론(이력 보존)과 저장 포맷 기능(MERGE)이 dbt를 매개로 한 줄기가 된다.
- dbt Model의 계층(정제 → 통합 → 소비) → 흔히 **Bronze→Silver→Gold의 Medallion 아키텍처**(원본→정제→소비용의 3단 파이프라인 설계)와 자연스럽게 포개진다. dbt 폴더 구조를 `staging / intermediate / marts`로 나누는 관행이 이 3단과 거의 1:1로 대응한다.

> **핵심 통찰 — "dbt는 로직의 언어, Databricks는 실행의 근육"**
>
> 2장에서 "dbt는 데이터를 처리하지 않고 SQL을 생성만 한다"고 했다. Databricks 조합에서 이 분업이 완성된다. dbt는 **파이프라인의 지도(로직·의존성·테스트·문서)**를 그리고, Databricks(Delta+Photon+Unity Catalog)는 **그 지도대로 대규모 데이터를 실제로 움직이는 엔진**이 된다. 하나는 *무엇을·왜*, 하나는 *어떻게·얼마나 빠르게*. 현업이 "Databricks엔 dbt가 필수"라 말하는 이유가 이것이다 — Databricks의 강력한 엔진에, **관리 가능하고 협업 가능하며 테스트되는 변환 로직 계층**을 씌우는 표준 방법이 dbt이기 때문이다.

### 8.3 실행되는 자리

dbt 프로젝트는 여러 방식으로 Databricks에 연결된다 — 로컬/CI에서 `dbt-databricks`로 Databricks SQL 웨어하우스에 붙여 돌리거나, **Databricks Workflows(잡)** 안에 dbt 태스크로 넣어 네이티브하게 스케줄링할 수도 있다. 어느 쪽이든 **연산은 전부 Databricks 클러스터/웨어하우스에서** 일어나고, dbt는 그 위에서 오케스트레이션과 컴파일을 맡는다.

## 9. 정리 & SI 관점의 시사점

**정리:**

- dbt가 푸는 문제는 "SQL을 잘 짜는 법"이 아니라 **"SQL 수백 개를 하나의 시스템으로 엮어 안전하게 반복 실행·협업하는 법"** — 즉 데이터 변환에 **소프트웨어 엔지니어링**을 입히는 것.
- dbt는 ELT의 **'T'만** 담당한다. 데이터를 옮기지 않고, **SQL을 컴파일해 웨어하우스에 던져 실행**시킨다. 무거운 연산은 엔진(Databricks 등)이 한다.
- 심장은 **Model(=하나의 SELECT 파일)**과 **`ref()`**. `ref()`가 흩어진 SQL을 **하나의 의존성 그래프(DAG)**로 묶고, 여기서 실행 순서·환경 분리·테스트·문서·계보가 전부 파생된다.
- **Materialization**(view/table/incremental)으로 로직은 그대로 둔 채 물리화 전략만 갈아끼운다. **snapshot**은 SCD Type 2 이력 보존을 자동화한다.
- **dbt Core**(무료 오픈소스)로 배우고, 팀이 커지면 **dbt Cloud**. 2026년엔 **Fusion 엔진(Rust 기반, SQL을 진짜 이해)**의 오픈소스화와 **Fivetran의 dbt Labs 합병**이라는 큰 변화가 있었다.
- Databricks와는 **`dbt-databricks` 어댑터**로 만나며, 기본이 Delta·MERGE·Photon·Unity Catalog에 정확히 맞물린다. dbt=로직, Databricks=실행 엔진.

**우리 SI 프로젝트에 주는 시사점 (토론 포인트):**

- **"변환 로직을 어디에 둘 것인가"의 표준 답**: Databricks 프로젝트에서 SQL 변환을 노트북에 흩뿌리면 6개월 뒤 유지보수가 지옥이 된다. dbt 프로젝트로 구조화하면 **버전관리·테스트·문서·계보가 코드에서 자동으로** 나온다. 초기에 dbt 폴더 구조(staging/intermediate/marts)와 네이밍 컨벤션을 표준으로 잡는 것이, 프로젝트 후반의 유지보수 비용을 결정한다.
- **테스트를 계약으로**: 고객에게 넘기는 데이터의 신뢰성은 **`dbt test`로 계약화**할 수 있다("고객키 유일", "매출 음수 불가"). 틀린 수치가 대시보드에 뜨기 전에 파이프라인이 멈춘다 — 이게 곧 SI의 품질 보증 수단이 된다.
- **분석가를 엔지니어로**: dbt의 진짜 힘은 **SQL만 아는 인력도 엔지니어처럼 협업**하게 만든다는 것. SI 팀 구성에서, 고급 Spark 엔지니어만이 아니라 **SQL 기반 분석 엔지니어**를 dbt 위에 태워 생산성을 끌어올리는 인력 전략이 가능하다.
- **부가가치의 지점**: 원본 적재는 도구가 해준다. 차별화는 **깨끗하게 구조화된 dbt 변환 계층 + 테스트 + 문서**를 설계해 넘기는 것 — "우리가 떠난 뒤에도 고객이 스스로 유지보수할 수 있는 파이프라인"이 SI의 진짜 산출물이다.

> **토론거리:** 우리 첫 Databricks 프로젝트에서 변환 계층을 **dbt로 표준화**할까, 아니면 Databricks 네이티브 선언형 파이프라인 도구로 갈까? dbt를 쓴다면 **Core를 CI로 직접 운영**할지 **dbt Cloud를 도입**할지, 그리고 Fusion 엔진·Fivetran 합병이라는 변화 속에서 어느 시점에 올라탈지가 초기 아키텍처 결정의 핵심이다.
