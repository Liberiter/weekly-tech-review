# 2026-08-03. 배치 vs 스트리밍 — "언제 처리하는가" 하나가 아키텍처 전체를 바꾼다

> 데이터 파이프라인을 설계할 때 가장 먼저 받는 질문은 대개 "무슨 데이터를 쓰나요?"가 아니라 **"얼마나 빨리 필요하세요?"**다. 이 한 마디의 답이 저장 포맷, 처리 엔진, 운영 방식, 비용, 심지어 팀 구성까지 연쇄적으로 결정한다.
>
> 그런데 이 주제는 오해가 많다. "스트리밍이 배치의 상위호환"이라는 오해, "실시간이니까 무조건 좋다"는 오해, 반대로 "우린 실시간 필요 없으니 스트리밍은 남 얘기"라는 오해까지. 이번 주는 배치와 스트리밍의 **본질적 차이**가 무엇이고, 왜 현대 엔진들은 이 둘의 경계를 지우는 방향으로 진화했는지를 밑바닥부터 뜯는다.

## 1. 도입: "실시간으로 해주세요"라는 요구가 실제로 뜻하는 것

현장에서 가장 자주 나오는 요구사항이 있다. **"실시간으로 보이게 해주세요."**

그런데 이 말은 사실 **하나의 요구가 아니다.** 파고들면 전혀 다른 세 가지가 섞여 있다.

- **"어제 데이터 말고 오늘 데이터를 보고 싶다"** → 사실은 **하루 1회 → 1시간 1회**면 충분하다. (지연 요구: 분~시간)
- **"대시보드를 열었을 때 최근 몇 분 상황이 보이면 좋겠다"** → **분 단위 마이크로배치**로 해결된다. (지연 요구: 분)
- **"결제 승인 나기 전에 사기 거래를 막아야 한다"** → 여기서만 **진짜 밀리초 실시간**이 필요하다. (지연 요구: 밀리초)

셋의 구현 난이도와 비용은 **자릿수가 다르다.** 그런데 요구사항 문서엔 똑같이 "실시간"이라고 적힌다.

여기서 이 글의 출발점이 나온다.

> **배치냐 스트리밍이냐는 기술 취향의 문제가 아니라, "데이터의 가치가 얼마나 빨리 소멸하는가"에 대한 비즈니스 판단의 문제다.**

월간 정산 리포트에서 5분 늦은 데이터는 아무 손해도 아니다. 사기 탐지에서 5분 늦은 판단은 **이미 돈이 나간 뒤**다. 같은 "지연 5분"이 한쪽에선 공짜고 한쪽에선 치명적이다. 그래서 이 결정은 엔지니어 혼자 내릴 수 없고, **"이 데이터가 늦으면 무슨 일이 벌어지나"**를 업무 담당자와 함께 따져야 한다.

## 2. 본질적 차이 — 경계 있는 데이터 vs 끝나지 않는 데이터

기술 이야기로 들어가자. 배치와 스트리밍을 가르는 진짜 경계는 "빠르다/느리다"가 아니다. **처리 대상에 끝이 있느냐**다.

| | **배치(Batch)** | **스트리밍(Streaming)** |
|---|---|---|
| 데이터의 성격 | **Bounded** — 시작과 끝이 있는 유한한 덩어리 | **Unbounded** — 끝이 없이 계속 도착 |
| 처리 단위 | "어제치 전부", "이 파일 전부" | "지금 막 도착한 것" |
| 실행 모델 | 시작 → 처리 → **종료** | 시작 → 처리 → 처리 → 처리 → **영원히** |
| 결과의 성격 | **한 번 확정** | **계속 갱신**(늦은 데이터로 과거 결과가 바뀔 수 있음) |
| 실패 시 | 그냥 **다시 돌린다** | 어디까지 처리했는지 **기억하고 이어서** 해야 한다 |
| 지연(latency) | 분 ~ 시간 ~ 일 | 밀리초 ~ 초 ~ 분 |

가장 중요한 줄은 **마지막에서 두 번째**다.

배치 잡은 실패하면 그냥 다시 돌리면 된다. 입력이 고정돼 있으니까. **"어제 데이터 전부"는 오늘 다시 읽어도 어제 데이터 전부다.** 이 단순한 성질이 배치를 압도적으로 쉽게 만든다. 재실행 = 복구다.

스트리밍은 그럴 수 없다. 처리 도중 죽었을 때 "처음부터 다시"란 개념이 없다. **처음이 어디인가?** 스트림엔 시작점이 없거나, 있어도 되돌아가면 몇 달치를 다시 처리해야 한다. 그래서 스트리밍 엔진은 **"어디까지 처리했는지"를 지속적으로 기록**해야 하고, 여기서 체크포인트·오프셋·상태 저장 같은 복잡도가 통째로 파생된다.

> **핵심 통찰 — "스트리밍의 어려움은 속도가 아니라 '끝이 없다'는 데서 온다"**
>
> 흔히 스트리밍이 어려운 이유를 "빨라야 해서"라고 생각한다. 틀렸다. 진짜 이유는 **끝이 없다**는 것이다.
>
> 끝이 없으면 (1) **"전부 다 모아서 집계"가 불가능**하다 — 영원히 다 안 모이니까. 그래서 시간 창(window)이라는 개념이 필요해진다. (2) **"결과가 확정됐다"고 말할 수 없다** — 늦게 도착한 데이터가 이미 낸 답을 바꿀 수 있으니까. 그래서 워터마크가 필요해진다. (3) **재실행으로 복구할 수 없다** — 그래서 체크포인트와 상태 관리가 필요해진다.
>
> 스트리밍 프레임워크의 복잡한 개념들은 전부 이 "무한함" 하나에서 유도된 결과물이다. 속도는 부산물이지 원인이 아니다.

## 3. 스트리밍이 어려운 진짜 이유 — 시간, 상태, 실패

2장에서 유도한 세 갈래를 하나씩 본다. 이 셋이 스트리밍 시스템 설계의 전부라고 해도 과언이 아니다.

### 3.1 시간이 두 개다 — 이벤트 시간 vs 처리 시간

배치에선 이 구분이 거의 안 중요하다. 어제치 파일을 오늘 읽으면 그만이니까. 스트리밍에선 이게 1번 난제다.

- **이벤트 시간(event time)**: 사건이 **실제로 일어난** 시각. (사용자가 결제 버튼을 누른 순간)
- **처리 시간(processing time)**: 그 데이터가 **우리 엔진에 도착한** 시각.

둘은 항상 어긋난다. 모바일 앱이 지하철 터널에서 오프라인이었다가 30분 뒤 로그를 한꺼번에 올린다. 네트워크가 밀린다. 중간 큐가 지연된다.

문제는 **"오후 2시대 매출"** 같은 집계를 낼 때 터진다. 어떤 시간으로 묶어야 하나?

- **처리 시간 기준**: 계산은 쉽지만 **답이 틀린다.** 2시 55분에 일어난 결제가 3시 5분에 도착하면 "3시대 매출"로 잡힌다. 게다가 같은 데이터를 재처리하면 **결과가 달라진다**(도착 시각이 달라지니까).
- **이벤트 시간 기준**: 답이 맞다. 재처리해도 같은 답이 나온다. 대신 **"2시대 집계를 언제 마감할 것인가"**라는 새 문제가 생긴다.

거의 항상 이벤트 시간이 정답이고, 그래서 마감 문제를 풀어야 한다.

### 3.2 워터마크 — "이제 그만 기다린다"는 선언

**워터마크(watermark)**는 그 마감 장치다. 정의는 이렇다.

> "지금까지 본 **가장 큰 이벤트 시간**에서 **N만큼 뺀 시점**보다 오래된 데이터는, 더 안 올 것으로 간주한다."

예를 들어 워터마크를 10분으로 잡으면: 3시 05분짜리 이벤트를 봤다면 → 2시 55분 이전 창은 **닫는다**. 그 뒤에 도착한 2시 50분 데이터는 **버린다(late data)**.

이게 왜 필요한가? **메모리 때문이다.** 워터마크가 없으면 엔진은 "혹시 어제 데이터가 지금 올지도 몰라"라며 **모든 시간 창의 중간 집계 상태를 영원히 들고 있어야** 한다. 상태가 무한히 자라 결국 터진다. 워터마크는 오래된 상태를 **버려도 된다고 허락**하는 장치다.

> **핵심 통찰 — "워터마크는 정확성과 지연 사이의 다이얼이다"**
>
> 워터마크 설정은 기술 파라미터가 아니라 **비즈니스 결정**이다.
>
> - 워터마크를 **길게**(1시간) 잡으면 → 늦은 데이터를 더 많이 포함해 **정확**해지지만, 결과 확정이 **1시간 늦어지고** 상태 저장 비용이 커진다.
> - **짧게**(1분) 잡으면 → **빠르지만**, 1분 넘게 늦은 데이터는 **소리 없이 버려진다.**
>
> 즉 "얼마나 늦은 데이터까지 기다려줄 것인가 = 얼마나 틀려도 되는가"를 숫자로 못 박는 일이다. 무한한 스트림에서 **완벽한 정확성과 낮은 지연은 동시에 가질 수 없고**, 워터마크는 그 트레이드오프를 명시적으로 선택하게 만드는 인터페이스다. 배치엔 이 고민 자체가 없다 — 데이터가 다 모인 뒤에 돌리니까.

### 3.3 상태(State) — 스트리밍 운영의 진짜 무게

스트리밍 연산은 두 종류로 갈린다.

- **Stateless(무상태)**: 각 레코드를 독립적으로 처리. 필터링, 컬럼 변환, 포맷 변경. **쉽다.** 이전 레코드를 기억할 필요가 없다.
- **Stateful(상태 유지)**: 이전 데이터를 기억해야 함. 집계(카운트·합계), 중복 제거, 스트림-스트림 조인, 세션화. **여기서 난이도가 급상승한다.**

상태가 있으면 그 상태를 **어딘가 안전하게 보관**해야 하고(장애 시 복구해야 하니까), 그 크기를 **관리**해야 하며(무한히 자라면 안 되니까 → 워터마크), 재시작 시 **정확히 복원**해야 한다.

현실의 스트리밍 운영 사고는 대부분 여기서 난다. "지연이 계속 늘어나요" → 상태가 비대해져 체크포인트가 느려진 것. "메모리가 터져요" → 워터마크 없는 집계나 카디널리티 폭발.

> **실무 감각**: 스트리밍 파이프라인을 설계할 때 가장 먼저 물어야 할 것은 "얼마나 빨라야 하나"가 아니라 **"상태를 얼마나 들고 있어야 하나"**다. 무상태 스트리밍은 배치보다 별로 안 어렵다. 상태가 큰 스트리밍은 배치와 완전히 다른 종목이다.

## 4. Structured Streaming — "스트림을 무한히 자라는 테이블로 본다"

이제 Spark가 이 문제를 어떻게 풀었는지 본다. Spark **Structured Streaming**의 발상은 놀랄 만큼 단순하고, 그 단순함이 곧 이 프레임워크의 전부다.

### 4.1 핵심 추상화

> **스트림 = 계속 새 행이 append되는, 무한히 자라는 테이블.**

```
    입력 스트림                     Unbounded Table
  ┌──────────────┐              ┌─────────────────────┐
  │ 이벤트 t=1   │  ───────▶    │ row 1               │
  │ 이벤트 t=2   │              │ row 2               │
  │ 이벤트 t=3   │              │ row 3               │
  │     ...      │              │ ...  (계속 append)  │
  └──────────────┘              └─────────────────────┘
                                         │
                        쿼리(그냥 평범한 DataFrame/SQL 연산)
                                         ▼
                                  ┌──────────────┐
                                  │  Result Table │ ← 새 데이터 올 때마다 갱신
                                  └──────────────┘
```

이 추상화가 주는 선물이 결정적이다. **"스트리밍용 API"를 따로 배울 필요가 없다.** 테이블에 대해 쓰던 `select`, `filter`, `groupBy`, `join`을 그대로 쓴다. 개발자는 "무한 테이블에 대한 쿼리"를 쓰고, **어떻게 증분으로 계산할지는 엔진이 알아서** 한다.

```python
# 배치
df = spark.read.format("delta").load(path)
result = df.filter("amount > 0").groupBy("region").sum("amount")
result.write.format("delta").save(out)

# 스트리밍 — read → readStream, write → writeStream. 로직은 글자 하나 안 바뀐다.
df = spark.readStream.format("delta").load(path)
result = df.filter("amount > 0").groupBy("region").sum("amount")
result.writeStream.format("delta").option("checkpointLocation", ckpt).start(out)
```

이 대칭성이 Structured Streaming의 판매 포인트다. 같은 비즈니스 로직을 배치로도 스트리밍으로도 돌릴 수 있다.

### 4.2 출력 모드 — "결과가 계속 바뀐다"는 문제의 답

무한 테이블에 대한 결과 테이블도 계속 변한다. 그럼 매번 **무엇을 밖으로 내보낼 것인가?** 이게 출력 모드다.

| 모드 | 내보내는 것 | 쓰이는 곳 |
|---|---|---|
| **Append** | **새로 추가된 행만** | 변하지 않는 결과. 단순 변환·필터, 워터마크로 확정된 창 집계 |
| **Update** | **이번에 값이 바뀐 행만** | 실시간 집계(카운터 갱신 등). 싱크가 upsert를 지원해야 함 |
| **Complete** | **결과 테이블 전체** | 결과가 작을 때만(전체 순위표 등). 크면 비현실적 |

여기서 초보자가 가장 자주 막히는 지점이 있다. **워터마크 없는 집계에는 Append를 쓸 수 없다.** 당연하다 — 창이 언제 닫힐지 모르는데 "이 행은 확정됐다"고 내보낼 수가 없다. 워터마크를 걸어야 비로소 "이 창은 끝났다"고 선언할 수 있고, 그때부터 Append가 가능해진다. 3.2절의 워터마크와 여기가 직접 맞물린다.

### 4.3 마이크로배치 — Spark의 실행 방식

Spark는 스트림을 **"아주 작은 배치의 연속"**으로 실행한다. 도착한 데이터를 짧은 주기로 모아 하나의 작은 배치 잡으로 처리하고, 그걸 무한 반복한다.

이 선택엔 명확한 트레이드오프가 있다.

- **장점**: 배치 엔진의 성숙한 최적화(카탈리스트 옵티마이저, 셔플, 내결함성)를 **그대로 재사용**한다. 처리량이 높고, 안정적이며, 배치와 코드가 같아진다.
- **단점**: **배치 경계가 곧 지연의 하한**이다. 아무리 줄여도 배치를 짜고 스케줄링하는 오버헤드 때문에 **수백 밀리초~초 단위**가 바닥이었다.

오랫동안 이게 Spark 스트리밍의 한계로 지적됐다(진짜 밀리초가 필요하면 Flink 같은 레코드 단위 엔진을 쓰라는 조언이 여기서 나왔다). 이 한계를 정면으로 깬 것이 최근의 **Real-Time Mode**인데, 8장에서 다룬다.

## 5. 트리거 — 배치와 스트리밍은 사실 하나의 다이얼이다

이 글에서 가장 중요한 장이다. **트리거(trigger)**는 "다음 마이크로배치를 언제 돌릴 것인가"를 정하는 설정인데, 이 하나가 배치와 스트리밍의 경계를 통째로 무너뜨린다.

| 트리거 | 동작 | 지연 | 비용 특성 |
|---|---|---|---|
| **기본(unspecified)** | 이전 배치가 끝나는 즉시 다음 배치 | 초 단위 | 클러스터 상시 가동 |
| **`processingTime="5 minutes"`** | 정해진 주기마다 배치 | 설정한 주기 | 상시 가동(주기가 길어도 클러스터는 떠 있음) |
| **`availableNow`** | **지금 있는 데이터를 다 처리하고 종료** | 스케줄 주기에 따름 | **처리 후 클러스터 종료 → 크게 절감** |
| **Real-Time Mode** | 마이크로배치 경계를 넘어선 저지연 처리 | **밀리초** | 전용 리소스 상시 점유 |

`availableNow`를 주목하자. 이건 **"스트리밍 코드를 배치처럼 돌리는"** 트리거다. 동작은 이렇다.

1. 체크포인트를 읽어 **지난번에 어디까지 처리했는지** 확인한다.
2. 그 이후 새로 들어온 데이터만 **증분으로** 처리한다(내부적으론 여러 마이크로배치로 나눠서).
3. 다 처리하면 **스스로 종료**한다.
4. 잡 스케줄러가 다음 날(혹은 다음 시간)에 다시 띄운다.

결과가 뭔가? **코드는 스트리밍인데, 운영은 배치다.** 클러스터는 처리하는 동안만 뜨니 비용은 배치급이고, "어디까지 처리했는지"는 체크포인트가 알아서 관리하니 배치 잡의 고질병인 **"어제 어디까지 넣었더라" 문제(워터마크 컬럼 수동 관리, 중복 적재, 누락)**가 사라진다.

> **핵심 통찰 — "배치는 스트리밍의 반대가 아니라, 스트리밍의 특수한 경우다"**
>
> 전통적으로 배치와 스트리밍은 **다른 코드, 다른 엔진, 다른 팀**이었다. 그래서 같은 비즈니스 로직을 두 번 구현하고, 두 결과가 안 맞아 대조하는 데 인력을 썼다.
>
> Structured Streaming의 진짜 성취는 "Spark로 스트리밍이 된다"가 아니라, **배치와 스트리밍을 하나의 모델 안에 통합**했다는 것이다. 데이터를 무한 테이블로 보고, **"얼마나 자주 처리할까"만 트리거로 조절**한다. 하루에 한 번 = 배치, 5분마다 = 마이크로배치, 계속 = 스트리밍, 밀리초 = 실시간. **이건 종류의 차이가 아니라 다이얼의 눈금 차이다.**
>
> 실무적 함의가 크다. **처음부터 스트리밍 스타일(증분 처리 + 체크포인트)로 짜두고 `availableNow`로 하루 한 번 돌리다가, 요구가 바뀌면 트리거만 바꿔 5분 주기로 승격**할 수 있다. 로직은 한 줄도 안 고친다. "나중에 실시간이 필요해지면 다 다시 짜야 한다"는 옛날 걱정이 사라진 것이다.

## 6. 정확성의 뒷받침 — 체크포인트와 정확히 한 번

5장의 마법("어디까지 처리했는지 알아서 안다")을 실제로 떠받치는 게 **체크포인트**다.

`checkpointLocation`에 지정한 경로에 엔진은 계속 기록을 남긴다.

- **오프셋 로그**: 각 마이크로배치가 소스의 **어디부터 어디까지**를 처리했는지 — *처리 전에* 먼저 기록.
- **커밋 로그**: 그 배치가 **성공적으로 끝났는지** — *처리 후에* 기록.
- **상태 저장소**: 집계 중간값 등 **stateful 연산의 상태**(대용량에선 RocksDB 기반으로 관리).

장애가 나면 재시작 시 이 로그를 읽어, 커밋되지 않은 배치를 **정확히 같은 입력 범위로 재실행**한다.

여기서 **정확히 한 번(exactly-once)**이 어떻게 성립하는지가 핵심이다. 흔한 오해는 "엔진이 데이터를 한 번만 읽는다"는 것인데, 아니다. 실제로는:

1. **소스가 재생 가능(replayable)**해야 한다 — 같은 오프셋 범위를 다시 읽으면 같은 데이터가 나와야 한다(Kafka, 클라우드 스토리지 파일, Delta 테이블 등).
2. **싱크가 멱등(idempotent)**해야 한다 — 같은 배치를 두 번 써도 결과가 한 번 쓴 것과 같아야 한다.

Delta Lake가 싱크로 강력한 이유가 여기 있다. Delta는 커밋할 때 **어느 스트림의 몇 번째 배치인지**를 트랜잭션 로그에 함께 기록한다. 그래서 같은 배치가 재시도로 다시 들어오면 **"이미 커밋된 배치"임을 알아보고 무시**한다. 처리는 두 번 됐어도 **결과는 정확히 한 번** 반영된다.

> **핵심 통찰 — "정확히 한 번은 엔진 혼자 못 만든다. 소스·엔진·싱크의 합작품이다"**
>
> "이 엔진은 exactly-once를 지원합니다"라는 문구는 절반만 참이다. 재생 가능한 소스와 트랜잭션 싱크가 함께 있어야 성립한다. 예컨대 Delta 테이블로 쓰면 정확히 한 번이지만, 같은 파이프라인이 외부 REST API를 호출하는 순간 그 호출은 **재시도 때 두 번 나간다.** 엔진은 API 호출을 되돌릴 수 없기 때문이다.
>
> 그래서 스트리밍 설계 리뷰에서 반드시 물어야 할 질문은 **"이 파이프라인의 종착지가 트랜잭션을 지원하는가, 아니면 부작용(side effect)이 있는가"**다. 후자라면 멱등성을 **우리가 직접** 설계해야 한다(고유 키 기반 upsert, 처리 이력 테이블 등). 체크포인트가 있으니 안전하다는 믿음이 사고로 이어지는 지점이 정확히 여기다.

## 7. 아키텍처 관점 — Lambda vs Kappa

개별 잡을 넘어 시스템 전체를 볼 때 등장하는 고전적 대립 구도다.

### 7.1 Lambda 아키텍처

과거의 표준 해법. **배치 레이어와 스트리밍 레이어를 둘 다** 운영한다.

```
              ┌─▶ [배치 레이어] ─▶ 정확하지만 느린 결과 ─┐
  원본 데이터 ─┤                                          ├─▶ [서빙] 둘을 합쳐서 응답
              └─▶ [스피드 레이어] ─▶ 빠르지만 근사한 결과 ─┘
```

발상은 합리적이다. 스트리밍은 빠르지만 늦은 데이터·장애로 부정확할 수 있으니, 배치가 주기적으로 **전체를 다시 계산해 진실을 정정**한다.

문제는 **비용**이다. 같은 로직을 **두 번 구현**하고(과거엔 엔진도 언어도 달랐다), 두 결과의 불일치를 계속 조사하고, 양쪽을 다 운영해야 한다. 유지보수 부담이 크다.

### 7.2 Kappa 아키텍처

"배치 레이어를 없애자"는 제안. **스트리밍 파이프라인 하나만** 두고, 과거 데이터를 다시 계산해야 하면 **같은 스트리밍 코드로 로그를 처음부터 재생(replay)**한다.

```
  원본 데이터(재생 가능한 로그) ─▶ [스트리밍 파이프라인 하나] ─▶ [서빙]
                                       ▲
                             재처리 필요 시 처음부터 replay
```

로직이 하나뿐이니 불일치가 원천적으로 없다. 대신 **재생 가능한 로그를 오래 보존**해야 하고, 대량 재처리를 스트리밍 엔진이 감당해야 한다.

### 7.3 2026년의 실제 답

현실은 어느 쪽 순수형도 아니다. **레이크하우스가 이 대립 자체를 상당 부분 무의미하게 만들었다.**

- 저장소(Delta 등)가 **배치 소스이자 스트리밍 소스이자 싱크**를 동시에 겸한다 → 같은 테이블을 배치로도 읽고 스트림으로도 읽는다.
- Structured Streaming이 **배치와 스트리밍 코드를 통합**했다 → Lambda의 "두 번 구현" 비용이 사라졌다.
- 트리거만 바꾸면 같은 파이프라인이 배치도 되고 스트리밍도 된다 → 레이어를 나눌 이유가 줄었다.

> **핵심 통찰 — "Lambda vs Kappa 논쟁은 이겨서 끝난 게 아니라, 전제가 무너져 사라졌다"**
>
> Lambda가 존재했던 이유는 **"배치 엔진과 스트리밍 엔진이 서로 다른 물건"**이었기 때문이다. 그래서 정확성은 배치에서, 속도는 스트리밍에서 따로 얻어야 했다.
>
> 레이크하우스는 그 전제를 깼다. **하나의 저장 포맷이 배치·스트리밍 양쪽의 소스이자 싱크가 되고, 하나의 엔진이 트리거만 바꿔 양쪽을 다 수행**하면, 두 레이어를 나눠 유지할 이유가 없다. 오늘의 실무적 답은 "Kappa가 이겼다"가 아니라 **"같은 코드·같은 테이블 위에서 처리 빈도만 다르게 가져간다"**에 가깝다. 아키텍처 다이어그램에 배치 경로와 스트리밍 경로를 나란히 그리고 있다면, **그걸 하나로 접을 수 있는지부터** 검토하는 게 요즘의 출발점이다.

## 8. Databricks 위에서의 배치와 스트리밍

이 글의 실전 목적지. 지금까지의 개념들이 Databricks에서 어떤 구체적 기능으로 나타나는지 정리한다.

### 8.1 Delta 테이블 = 배치 테이블이자 스트림

가장 중요한 사실 하나. **Delta 테이블은 스트리밍 소스로도, 스트리밍 싱크로도 쓸 수 있다.**

- **소스로**: `spark.readStream.format("delta").load(...)` — 테이블에 새로 커밋된 변경분을 스트림처럼 읽는다. 트랜잭션 로그의 버전이 곧 오프셋 역할을 하므로 재생이 가능하다.
- **싱크로**: 6장에서 본 배치 ID 기반 멱등 커밋으로 **정확히 한 번**을 보장한다.

이게 왜 결정적인가? Bronze→Silver→Gold처럼 **테이블을 여러 단계로 쌓는 파이프라인**에서, 각 단계 사이를 **스트림으로 이을 수 있다**는 뜻이기 때문이다. Bronze에 새 데이터가 커밋되면 Silver 스트림이 그 변경분만 증분 처리하고, 다시 Gold로 흐른다. 중간에 별도 메시지 큐가 필요 없다. **테이블 자체가 큐 역할을 겸한다.**

### 8.2 Auto Loader — "파일이 도착한다"는 스트림

현장에서 가장 많이 만나는 인제스트 패턴은 Kafka가 아니라 **클라우드 스토리지에 파일이 계속 떨어지는 것**이다. Auto Loader(`cloudFiles`)가 이걸 담당한다.

전통적 방식의 문제는 명확했다. "새로 온 파일만 처리"하려면 처리한 파일 목록을 어딘가 관리해야 하는데, 이게 손으로 하기 시작하면 지옥이다(중복 처리, 누락, 목록 테이블 비대화). Auto Loader는 **어떤 파일을 처리했는지 체크포인트로 자동 추적**해서 이 문제를 없앤다.

새 파일을 발견하는 방식은 둘이다.

- **디렉터리 목록 조회(directory listing)**: 주기적으로 디렉터리를 훑는다. 단순하지만, 파일이 수백만 개면 **목록 조회 자체가 비싸진다.**
- **파일 알림(file notification)**: 클라우드의 이벤트 알림 서비스를 구독해 **새 파일 알림을 받는다.** 대규모에서 훨씬 저렴하고 빠르다.

여기서 5장의 트리거가 실무 비용과 직결된다. **지연 요구가 낮은데 `processingTime`으로 상시 가동하면, 디렉터리 목록 조회 모드에서 특히 비용이 크게 새어나간다.** 공식 권장도 명확하다 — 저지연이 필요 없으면 **잡 스케줄러 + `availableNow`**로 증분 배치처럼 돌려라. 참고로 `Trigger.Once`는 DBR 11.3 LTS 이후 **폐기(deprecated)**되었고, 증분 배치는 모두 `availableNow`를 쓰는 게 현재 표준이다.

### 8.3 Lakeflow 선언형 파이프라인 — 스트리밍 테이블 vs 구체화 뷰

체크포인트, 트리거, 상태를 직접 다루지 않고 **"결과가 어때야 하는지"만 선언**하는 방식도 있다. Databricks의 선언형 파이프라인 프레임워크(Lakeflow Declarative Pipelines)가 그것이다. 참고로 이 프레임워크의 코어는 2025년 **Apache Spark에 Spark Declarative Pipelines로 기증**되어 오픈소스가 됐다.

여기서 우리 주제와 정확히 맞물리는 두 객체가 있다.

| | **스트리밍 테이블(Streaming Table)** | **구체화 뷰(Materialized View)** |
|---|---|---|
| 처리 방식 | 새로 들어온 데이터만 **append 증분 처리** | 소스가 바뀌면 결과를 **다시 계산**(가능하면 증분으로) |
| 적합한 곳 | 인제스트, 원본 정제 — **한 번 들어온 행은 안 바뀜** | 집계·조인 — **과거 행이 바뀌면 결과도 바뀌어야 함** |
| 대응 개념 | 스트리밍 | (증분) 배치 |

이 두 객체의 존재 자체가 이 글의 결론을 그대로 보여준다. **한 파이프라인 안에서 어떤 단계는 스트리밍답게, 어떤 단계는 배치답게 처리하는 게 자연스럽다.** 인제스트는 append-only라 스트리밍이 맞고, "지난 90일 재구매율" 같은 집계는 과거 데이터가 바뀌면 다시 계산해야 하니 구체화 뷰가 맞다. **파이프라인 전체를 한 가지로 통일할 필요가 없다.**

### 8.4 Real-Time Mode — 마이크로배치의 벽을 넘다

4.3절에서 "마이크로배치 경계가 지연의 하한"이라고 했다. 이 한계는 최근 정면으로 돌파됐다.

**Real-Time Mode(RTM)**는 Structured Streaming의 새로운 트리거 유형으로, **2026년 3월 Databricks에서 GA**됐다. 마이크로배치 스케줄링 대신 **연속적 데이터 흐름, 파이프라인 스케줄링, 스트리밍 셔플**로 구조를 바꿔, 종단 간 지연을 **최저 5ms 수준**까지 낮춘다(Databricks 내부 테스트 기준 p99가 변환 복잡도에 따라 수 ms~약 300ms).

실무적으로 중요한 점은 두 가지다.

- **코드를 갈아엎지 않는다.** 기존 Structured Streaming 코드에 **설정 변경 수준**으로 적용된다. 전용 저지연 엔진을 따로 도입해 로직을 이식할 필요가 없다.
- **대상 워크로드가 명확하다.** 사기 탐지, 실시간 개인화처럼 **즉각 대응이 곧 돈인 운영성 워크로드**다.

과거 실험적 기능이던 Continuous Processing이 제약이 많아 널리 쓰이지 못한 것과 달리, RTM은 정식 제품 경로에 올라온 선택지다.

> **핵심 통찰 — "실시간의 문턱이 '엔진 교체'에서 '설정 변경'으로 내려왔다"**
>
> 예전엔 밀리초 지연이 필요해지는 순간 **다른 엔진을 도입하고, 로직을 그 엔진의 API로 다시 짜고, 두 시스템을 함께 운영**해야 했다. 아키텍처 결정이자 조직 결정이었고, 그래서 "혹시 나중에 실시간이 필요할까 봐" 처음부터 과하게 설계하는 일이 잦았다.
>
> 이제 배치(`availableNow`) → 마이크로배치(`processingTime`) → 실시간(RTM)이 **같은 코드 위의 트리거 선택**이 됐다. 함의는 이것이다. **처음부터 실시간으로 설계할 이유가 오히려 줄었다.** 증분 처리 + 체크포인트라는 올바른 뼈대만 갖춰두면, 지연 요구가 실제로 올라왔을 때 그때 승격하면 된다. 조기 최적화의 비용이 사라졌으니, **"일단 싸게 시작하고 필요할 때 다이얼을 돌린다"**가 합리적 기본값이 된다.

## 9. 그래서 무엇을 고를 것인가 — 판단 기준

실무 판단을 표로 정리한다.

### 9.1 지연 요구에서 출발하기

| 실제 지연 요구 | 권장 접근 | 비용 감각 |
|---|---|---|
| 일/시간 단위 (리포트, 정산, ML 학습 데이터) | **`availableNow` 증분 배치** + 잡 스케줄 | 가장 저렴. 클러스터가 필요할 때만 뜬다 |
| 분 단위 (운영 대시보드, 모니터링) | **`processingTime` 마이크로배치**(1~5분) | 중간. 상시 가동이지만 리소스는 작게 |
| 초 단위 (실시간 대시보드, 알림) | **기본 트리거 연속 스트리밍** | 상시 가동 + 상태 관리 부담 |
| 밀리초 (사기 탐지, 실시간 개인화, 자동 대응) | **Real-Time Mode** | 가장 비쌈. 정말 필요한 곳에만 |

### 9.2 스트리밍을 **선택하지 말아야** 할 신호

- 소비자가 **하루 한 번 보는 리포트**다. → 실시간으로 만들어도 아무도 안 본다.
- 소스가 **하루 한 번 덤프**로 온다. → 하류를 실시간으로 만들어도 **소스가 병목**이다. 파이프라인의 신선도는 가장 느린 구간이 결정한다.
- 로직이 **전체 재계산을 요구**한다(예: 전 기간 리랭킹). → 증분 처리로 표현이 안 되면 억지로 스트리밍화할 이유가 없다.
- **운영 인력이 없다.** → 스트리밍은 24/7 살아있는 시스템이다. 새벽 3시에 죽으면 누가 보나? 배치는 아침에 재실행하면 되지만 스트리밍은 지연이 계속 쌓인다.

### 9.3 그래도 처음부터 챙겨둘 것

스트리밍을 안 쓰기로 했더라도 **증분 처리 뼈대**는 챙기는 게 이득이다.

- **체크포인트 기반 증분 인제스트**(Auto Loader `availableNow`)를 쓰면, 배치로 돌리면서도 "어제 어디까지 넣었더라" 문제에서 해방된다.
- 나중에 지연 요구가 올라와도 **트리거만 바꾸면 된다.**

> **가장 흔한 실패**는 "실시간을 안 해서" 생기지 않는다. **필요 없는 곳에 실시간을 넣어** 비용과 운영 부담만 늘리고, 정작 요구는 "어제 데이터 말고 오늘 데이터"였던 경우다. 반대 실패는 **수동 워터마크 컬럼으로 증분을 직접 관리**하다가 중복·누락을 반복하는 경우다. 둘 다 5장의 다이얼을 몰라서 생기는 일이다.

## 10. 정리 & SI 관점의 시사점

**정리:**

- 배치와 스트리밍을 가르는 본질은 속도가 아니라 **데이터에 끝이 있느냐(bounded vs unbounded)**다. 스트리밍의 모든 복잡도(시간 창, 워터마크, 상태, 체크포인트)는 이 **"끝이 없음"**에서 파생된다.
- 스트리밍의 세 난제는 **시간**(이벤트 시간 vs 처리 시간 → 워터마크로 마감), **상태**(stateful 연산이 진짜 무게), **실패**(재실행으로 복구 불가 → 체크포인트).
- **워터마크는 정확성과 지연의 다이얼**이다. 길면 정확하고 느리며, 짧으면 빠르고 늦은 데이터를 버린다. 기술 파라미터가 아니라 비즈니스 결정이다.
- Structured Streaming은 스트림을 **무한히 자라는 테이블**로 추상화해, **배치와 스트리밍의 코드를 통합**했다. 실행은 마이크로배치.
- **트리거가 배치/스트리밍의 경계다.** `availableNow`(증분 배치·처리 후 종료) → `processingTime`(주기적) → 기본(연속) → **Real-Time Mode**(밀리초, 2026년 3월 GA). **같은 코드, 다른 눈금.**
- **정확히 한 번은 소스(재생 가능)·엔진(체크포인트)·싱크(멱등)의 합작품**이다. Delta는 배치 ID를 트랜잭션 로그에 기록해 멱등 싱크가 된다. 외부 API 호출 같은 부작용은 우리가 직접 멱등성을 설계해야 한다.
- Lambda vs Kappa 논쟁은 **레이크하우스가 전제를 무너뜨려** 실효성이 줄었다. Delta 테이블이 배치·스트리밍의 소스이자 싱크를 겸하기 때문이다.

**우리 SI 프로젝트에 주는 시사점 (토론 포인트):**

- **요구사항 인터뷰의 표준 질문을 바꾸자**: "실시간 필요하세요?"는 항상 "네"를 부른다. 대신 **"이 데이터가 10분 늦으면 무슨 일이 벌어집니까? 1시간이면요?"**를 물어야 한다. 답이 "별일 없다"면 그 구간은 증분 배치로 간다. 이 질문 하나가 인프라 비용과 운영 난이도를 좌우한다.
- **기본값은 "증분 배치, 스트리밍 스타일 코드"**: 초기엔 Auto Loader + `availableNow`로 짜서 배치처럼 스케줄한다. 비용은 배치급인데, 체크포인트·정확히 한 번·증분 처리라는 자산은 미리 확보된다. 요구가 올라오면 **트리거만 승격**한다. "나중에 실시간 되면 다시 짜야 한다"는 협상 부담이 사라지므로, 고객 설득에도 강력한 논리가 된다.
- **파이프라인을 한 가지 색으로 칠하지 말 것**: 인제스트는 append-only라 스트리밍이 맞고, 상류 변경이 과거 결과를 뒤집는 집계 단계는 재계산(구체화 뷰)이 맞다. **단계별로 다른 처리 모델**을 쓰는 게 정상이며, 이를 설계 문서에 명시적으로 구분해 적는 것이 좋은 산출물이다.
- **스트리밍은 기술 결정이 아니라 운영 약속이다**: 상시 가동 파이프라인을 넘긴다는 건 **24/7 살아있는 시스템**을 넘긴다는 뜻이다. 장애 알림, 지연 모니터링, 재시작 절차, 상태 저장소 관리, 그리고 **누가 새벽에 보는가**까지 계약 범위에 들어와야 한다. 이 합의 없이 실시간을 약속하면 인수인계 후에 문제가 터진다.
- **차별화 지점**: 스트리밍을 구현할 줄 아는 것보다, **"여기는 실시간이 필요 없습니다"를 근거와 숫자로 설명하고 비용을 줄여주는 것**이 SI의 신뢰를 만든다. 그러면서 정말 필요한 한두 지점(사기 탐지 등)엔 정확히 실시간을 얹는 — 이 선별 능력이 산출물의 질을 가른다.

> **토론거리:** 우리 프로젝트에서 **정말로 초 단위 이하가 필요한 구간이 하나라도 있는가?** 있다면 그 근거는 무엇이고(늦으면 얼마의 손해인가), 없다면 전 구간을 `availableNow` 증분 배치로 설계하고 트리거 승격 경로만 열어두는 편이 낫지 않은가? 그리고 상시 가동 파이프라인을 고객에게 넘긴다면, **장애 대응 책임과 절차를 계약 어디에 명시**할 것인가?
