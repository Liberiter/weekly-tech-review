# 2026-08-04. DAB — 노트북을 "배포 가능한 프로젝트"로 바꾸는 YAML 한 장

> Databricks 프로젝트에서 개발은 대개 워크스페이스 UI에서 시작한다. 노트북을 만들고, UI로 잡을 걸고, 클러스터를 붙이고, 스케줄을 건다. 여기까지는 빠르고 즐겁다.
>
> 문제는 그다음이다. **개발 워크스페이스에서 만든 걸 운영 워크스페이스에 똑같이 올려야 할 때** 갑자기 할 일이 없어진다. UI로 만든 잡은 코드가 아니라서 복사할 수단이 없다. 누군가 스크린샷을 보며 손으로 다시 만들고, 클러스터 사양이 하나 어긋나고, 스케줄을 켜는 걸 잊고, 두 달 뒤 "운영이랑 개발이랑 왜 다르지?"가 시작된다.
>
> **DAB(Declarative Automation Bundles)**는 이 지점을 정확히 겨냥한 도구다. 잡·파이프라인·대시보드·카탈로그 같은 **워크스페이스 리소스를 YAML로 선언**하고, `databricks bundle deploy` 한 번으로 dev/staging/prod에 **같은 정의를 다르게 실체화**한다. 이 글은 DAB가 무엇을 어떻게 하는지, 그리고 왜 "그냥 배포 도구"가 아니라 **Databricks 프로젝트의 구조를 규정하는 물건**인지를 뜯는다.

## 1. 도입: UI로 만든 것은 왜 운영에 못 올라가는가

Databricks에서 만드는 산출물을 성격으로 나눠 보면 두 종류다.

- **코드**: 노트북, Python 파일, SQL. → Git에 들어간다. 리뷰도 되고, 이력도 남고, 되돌릴 수도 있다.
- **리소스 설정**: "이 노트북을 매일 새벽 3시에, 이런 사양의 클러스터에서, 이 순서로, 이 사람 권한으로 돌린다." → **어디에도 안 들어간다.** 워크스페이스 DB 안에만 있다.

두 번째가 문제의 전부다. 파이프라인이 실제로 어떻게 동작하는지를 결정하는 정보의 절반이 **버전 관리 밖**에 있다. 그래서 이런 일이 벌어진다.

- 운영 잡의 재시도 횟수를 누가 언제 왜 바꿨는지 **아무도 모른다.**
- dev에서 잘 되던 게 prod에서 안 된다. 원인은 코드가 아니라 **클러스터 런타임 버전 차이**였다.
- 인수인계 문서에 "잡 설정은 UI에서 확인하세요"라고 쓰게 된다.

전통적 해법은 두 가지였다. 하나는 **REST API를 직접 호출하는 배포 스크립트**를 짜는 것 — 만들 땐 되지만 "이미 있으면 업데이트, 없으면 생성, 지워진 건 삭제"를 제대로 구현하기 시작하면 금세 지옥이 된다. 다른 하나는 **Terraform**을 쓰는 것 — 정석이지만 데이터 엔지니어에게 HCL과 상태 파일 관리를 요구하는 건 진입 장벽이 높다.

DAB는 세 번째 답이다. **Databricks에 특화된, YAML 기반의 선언형 배포 도구**를, CLI 하나로 제공한다.

> **핵심 통찰 — "DAB의 진짜 가치는 배포 자동화가 아니라 '설정의 코드화'다"**
>
> DAB를 "배포를 편하게 해주는 도구"로 소개하면 절반만 맞다. 배포는 결과고, 원인은 **워크스페이스에만 존재하던 리소스 설정을 Git 안으로 끌어온 것**이다.
>
> 이게 되는 순간 따라오는 것들이 있다. 잡 설정 변경이 **PR과 코드 리뷰의 대상**이 된다. "누가 스케줄을 바꿨나"가 `git blame`으로 답이 된다. 장애 시 **직전 커밋으로 롤백**하면 리소스 설정까지 같이 되돌아간다. dev와 prod의 차이가 **YAML의 diff**로 보인다.
>
> 즉 DAB는 배포 시간을 줄이는 도구가 아니라, **Databricks 프로젝트를 소프트웨어 프로젝트처럼 다룰 수 있게 만드는** 전제 조건이다. 자동화는 그 위에 얹히는 부산물이다.

## 2. DAB 한 문장 정의 — 그리고 이름이 바뀐 이유

> **번들(bundle)이란: 프로젝트의 소스 코드 + 리소스 정의 + 배포 설정을 한 디렉터리에 묶고, YAML로 선언한 것.**

`databricks bundle init`으로 만든 표준 구조는 이렇다.

```
my-project/
├── databricks.yml          ← 번들의 진입점 (필수). 이름·타깃·include를 정의
├── resources/              ← 잡·파이프라인 등 리소스 정의 YAML
│   ├── ingest_job.yml
│   └── transform_pipeline.yml
├── src/                    ← 실제 코드 (노트북, Python 모듈)
│   └── transformations/
├── tests/                  ← 단위 테스트
└── fixtures/
```

핵심은 `databricks.yml`이 **프로젝트 루트에 있고, 코드와 같은 저장소에 산다**는 점이다. 공식 권장도 "코드와 번들 설정을 **하나의 저장소**에 둘 것"이다. 코드 변경과 그 코드를 돌리는 잡 설정 변경이 **같은 커밋, 같은 PR**에 들어가야 의미가 있기 때문이다.

### 이름 이야기: Asset Bundles → Declarative Automation Bundles

검색하면 두 이름이 섞여 나온다. 정리하면 이렇다.

- 원래 이름은 **Databricks Asset Bundles**였고, 줄임말 **DAB**로 자리 잡았다.
- **2026년 3월**(CLI v0.287 무렵) **Declarative Automation Bundles**로 공식 개명됐다. `asset`이라는 단어가 Databricks 안에서 다른 의미로도 쓰여 혼동을 준다는 게 이유다.
- **약칭 DAB는 그대로**고, **CLI 명령어(`databricks bundle ...`)도 그대로**다. 설정 파일도 안 바뀐다. **깨지는 변경이 전혀 없는 순수 명칭 변경**이다.

실무적으로는 "문서/블로그에서 두 이름이 같은 걸 가리킨다"만 알면 충분하다. 다만 팀 문서를 쓸 땐 최신 공식 명칭을 따르되 `(DAB)`를 병기하는 편이 검색성에 유리하다.

### 무엇을 선언할 수 있나

초기엔 잡·파이프라인 정도였지만 지금은 범위가 상당히 넓어졌다. `resources` 아래에 올 수 있는 타입들:

| 분류 | 리소스 타입 |
|---|---|
| 워크로드 | `jobs`, `pipelines`, `clusters`, `sql_warehouses` |
| 데이터 거버넌스 | `catalogs`, `schemas`, `volumes`, `external_locations`, `quality_monitors` |
| ML/AI | `experiments`, `models`, `registered_models`, `model_serving_endpoints`, `vector_search_endpoints`, `vector_search_indexes`, `genie_spaces` |
| 분석·앱 | `dashboards`, `alerts`, `apps` |
| OLTP(Lakebase) | `database_instances`, `database_catalogs`, `postgres_projects`, `postgres_branches`, `postgres_endpoints`, `synced_database_tables` 등 |
| 기타 | `secret_scopes` |

주목할 변화는 **`catalogs`, `schemas`, `volumes`, `external_locations` 같은 Unity Catalog 객체가 들어왔다**는 점이다. 이전엔 "잡은 DAB, 카탈로그·스키마는 Terraform"으로 도구가 갈렸는데, 이제 한 도구로 덮을 수 있는 범위가 커졌다. (단, 카탈로그·외부 위치·Genie 스페이스·AI Search 엔드포인트는 **뒤에서 볼 direct 엔진에서만** 지원된다.)

## 3. `databricks.yml` 해부 — 최상위 매핑 10가지

설정 파일의 최상위에 올 수 있는 키는 정해져 있다. 각각이 무슨 역할인지 알면 문서를 안 봐도 대략 쓸 수 있다.

| 매핑 | 역할 |
|---|---|
| `bundle` | 번들 이름, UUID, 요구 CLI 버전, 배포 엔진, Git 정보. **`name`은 필수** |
| `include` | 다른 YAML 파일을 끌어오는 glob 목록. `resources/*.yml` 패턴이 표준 |
| `variables` | 사용자 정의 변수. `${var.이름}`으로 참조. 기본값·복합 타입·**lookup**(이름으로 기존 객체 ID 조회) 지원 |
| `workspace` | 대상 워크스페이스 호스트, 인증 방식, 배포 루트 경로, 아티팩트 경로 |
| `artifacts` | Python wheel·JAR 등의 **빌드 방법**. 배포 전에 실행할 build 커맨드를 지정 |
| `resources` | **실제로 만들 리소스 정의.** REST API 페이로드 스키마를 그대로 YAML로 옮긴 형태 |
| `sync` | 워크스페이스로 올릴 로컬 파일 범위(`paths`/`include`/`exclude`). `.gitignore` 문법 |
| `targets` | 배포 환경(dev/staging/prod). **환경별 오버라이드가 들어가는 곳** |
| `permissions` / `run_as` | 배포된 리소스의 접근 권한 / 잡을 **실행할 주체(identity)** |
| `presets` / `scripts` | 이름 접두사·태그·스케줄 일시정지 등 일괄 설정 / `bundle run`으로 부를 셸 스크립트 |

작은 예시 하나로 감을 잡자.

```yaml
bundle:
  name: sales-pipeline
  databricks_cli_version: ">= 1.3.0"

include:
  - resources/*.yml

variables:
  catalog:
    description: 대상 Unity Catalog 카탈로그
    default: dev_catalog

resources:
  jobs:
    daily_ingest:
      name: daily-ingest
      tasks:
        - task_key: bronze
          notebook_task:
            notebook_path: ../src/ingest.py
            base_parameters:
              catalog: ${var.catalog}
      schedule:
        quartz_cron_expression: "0 0 3 * * ?"
        timezone_id: Asia/Seoul

targets:
  dev:
    default: true
    mode: development
    workspace:
      host: https://dev.cloud.databricks.com

  prod:
    mode: production
    workspace:
      host: https://prod.cloud.databricks.com
    variables:
      catalog: prod_catalog
    run_as:
      service_principal_name: ${var.sp_id}
```

여기서 눈여겨볼 구조가 **`resources`는 한 번만 쓰고, `targets`에서 필요한 부분만 덮어쓴다**는 점이다. dev용 잡 정의와 prod용 잡 정의를 따로 두지 않는다.

> **핵심 통찰 — "`resources`는 REST API 스키마를 그대로 베낀다 — 이게 학습 비용을 없앤다"**
>
> DAB의 `resources` 블록은 **자체 DSL이 아니다.** Jobs API가 받는 JSON 페이로드의 필드를 그대로 YAML로 옮긴 것이다. `tasks`, `task_key`, `notebook_task`, `job_clusters`, `max_concurrent_runs` — 전부 API 문서에 있는 이름 그대로다.
>
> 함의가 두 가지다. 첫째, **API 문서가 곧 DAB 문서**다. 새 잡 기능이 API에 추가되면 별도 지원 없이 대체로 그냥 쓸 수 있다. 둘째, **UI에서 만든 걸 그대로 가져올 수 있다.** UI로 잡을 완성한 뒤 `databricks bundle generate job`을 돌리면 그 잡의 YAML이 생성된다.
>
> 그래서 DAB 도입의 현실적 경로는 "처음부터 YAML로 짜기"가 아니라 **"UI로 만들고 → generate로 뽑고 → 그 뒤로는 YAML을 진실의 원천으로 삼기"**다. 팀에 "이제부터 YAML로 잡을 만드세요"라고 하면 저항이 크지만, "만들던 대로 만들고 명령어 하나로 코드화하세요"는 받아들여진다.

## 4. targets — 하나의 정의를 여러 환경으로 접는 법

DAB의 설계 중심은 `targets`다. **하나의 리소스 정의를 여러 환경에 다르게 실체화**하는 장치다.

```
                         ┌──────────────────────────┐
                         │  resources: (한 벌)      │
                         │    jobs.daily_ingest     │
                         └────────────┬─────────────┘
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
      targets.dev             targets.staging          targets.prod
   mode: development         mode: production        mode: production
   catalog: dev_catalog      catalog: stg_catalog    catalog: prod_catalog
   run_as: 나                run_as: SP              run_as: SP
              │                       │                       │
              ▼                       ▼                       ▼
   [dev jaehyeok] daily-ingest    daily-ingest            daily-ingest
   스케줄 일시정지               스케줄 활성             스케줄 활성
   /Users/나/.bundle/...        /Shared/.bundle/...     /Shared/.bundle/...
```

타깃이 오버라이드할 수 있는 것: `workspace`(호스트·경로), `variables`, `resources`(일부 필드만), `permissions`, `run_as`, `presets`, `mode`.

배포는 항상 타깃을 명시한다.

```bash
databricks bundle deploy -t dev     # 또는 default: true인 타깃이면 -t 생략 가능
databricks bundle deploy -t prod
```

여기서 중요한 규칙 하나. **각 타깃은 자기만의 배포 경로와 상태를 가진다.** dev에 배포한 것과 prod에 배포한 것은 서로 간섭하지 않는다. 같은 워크스페이스에 여러 개발자가 각자 dev 타깃으로 배포해도 충돌하지 않는데, 이건 다음 장의 `development` 모드가 이름에 사용자 접두사를 붙여주기 때문이다.

## 5. 배포 모드 — `development`와 `production`이 실제로 하는 일

`mode` 한 줄이 꽤 많은 기본 동작을 바꾼다. 이걸 모르면 "왜 잡 이름 앞에 이상한 게 붙지?", "왜 스케줄이 꺼져 있지?"에서 막힌다.

| | `mode: development` | `mode: production` |
|---|---|---|
| 리소스 이름 | **`[dev 사용자이름]` 접두사 자동 부착** | 그대로 |
| 태그 | 잡·파이프라인에 `dev` 태그 부착 | 없음 |
| 파이프라인 플래그 | `development: true`로 배포 | `development: false`여야 함 (**검증**) |
| 스케줄·트리거 | **전부 일시정지(PAUSED)** | 그대로 활성 |
| 동시 실행 | 기본 허용 | 정의대로 |
| 배포 잠금 | 비활성(빠른 반복용) | 활성 |
| 클러스터 오버라이드 | `--cluster-id`로 덮어쓰기 허용 | **금지** |
| Git 브랜치 | 검사 안 함 | **지정 브랜치와 현재 브랜치가 같아야 함** |
| 실행 주체 | 배포한 사람 | **서비스 프린시펄 권장** (`run_as`) |
| 경로 검증 | 없음 | 아티팩트/파일 경로가 개인 경로로 안 바뀌었는지 검증 |

`development` 모드의 세 가지가 특히 실무를 바꾼다.

1. **이름 접두사** — 팀원 5명이 같은 dev 워크스페이스에 각자 배포해도 `[dev jaehyeok] daily-ingest`, `[dev minsu] daily-ingest`로 갈려서 서로 안 덮어쓴다.
2. **스케줄 자동 일시정지** — 개발용으로 배포한 잡이 새벽 3시에 진짜로 돌아버리는 사고를 원천 차단한다. 이거 하나 때문에라도 dev 타깃은 반드시 `development` 모드여야 한다.
3. **배포 잠금 비활성** — 빠른 반복 배포에서 잠금 대기를 없앤다.

`production` 모드는 반대로 **막는 쪽**이다. 특히 Git 브랜치 검증(`git.branch`)이 강력하다.

```yaml
targets:
  prod:
    mode: production
    git:
      branch: main
```

이렇게 두면 feature 브랜치에서 실수로 `deploy -t prod`를 쳐도 **CLI가 거부**한다. (`--force`로 뚫을 수는 있다. 그래서 이건 실수 방지 장치지 보안 통제는 아니다 — 진짜 통제는 prod 배포 권한을 CI의 서비스 프린시펄에만 주는 것이다.)

> **핵심 통찰 — "`mode`는 편의 기능이 아니라 사고 방지 장치다"**
>
> `mode: development` / `mode: production`은 그럴듯한 기본값 묶음처럼 보이지만, 실제로 하는 일은 **"이 환경에서 하면 안 되는 일"을 물리적으로 막는 것**이다.
>
> dev에서 자주 나는 사고는 "개발 잡이 진짜로 돌아서 실데이터를 건드렸다"와 "동료 배포를 덮어썼다"인데, 두 가지 모두 development 모드가 기본으로 막는다. prod에서 자주 나는 사고는 "검증 안 된 브랜치가 운영에 나갔다"와 "개인 계정 권한으로 운영 잡이 돌다가 퇴사 후 멈췄다"인데, production 모드의 브랜치 검증과 `run_as` 요구가 이걸 막는다.
>
> **팀 규칙을 문서가 아니라 설정으로 강제할 수 있다**는 게 핵심이다. "prod에는 main에서만 배포합시다"는 위키에 적으면 지켜지지 않지만, `git.branch: main` 두 줄이면 지켜진다. 이 관점에서 보면 `databricks.yml`은 배포 스크립트라기보다 **팀의 운영 규약을 기계가 읽을 수 있게 적은 문서**에 가깝다.

## 6. 변수와 오버라이드 — 환경차를 흡수하는 세 가지 층

환경마다 다른 값(카탈로그 이름, 워크스페이스 호스트, 클러스터 크기, 웨어하우스 ID)을 어떻게 처리하느냐가 실무의 절반이다. DAB는 세 가지 수단을 준다.

### 6.1 사용자 정의 변수

```yaml
variables:
  catalog:
    description: 대상 카탈로그
    default: dev_catalog
  node_count:
    default: 2

targets:
  prod:
    variables:
      catalog: prod_catalog
      node_count: 8
```

`${var.catalog}`로 참조한다. CLI에서 `--var="catalog=sandbox"`로 덮어쓸 수도 있어서, CI에서 커밋 해시나 브랜치명을 주입하기 좋다.

### 6.2 lookup — 이름으로 ID 찾기

Databricks 리소스는 **ID로 참조**해야 하는 게 많은데(클러스터 ID, 웨어하우스 ID, 그룹 ID), ID는 환경마다 다르고 사람이 못 읽는다. `lookup`이 이걸 푼다.

```yaml
variables:
  warehouse_id:
    lookup:
      warehouse: shared-serverless-wh   # 이름으로 조회 → ID로 치환
```

환경마다 ID를 하드코딩하는 대신 **이름 규칙만 맞추면** 같은 YAML이 양쪽에서 동작한다.

### 6.3 substitution — 내장 값과 리소스 상호 참조

```yaml
${workspace.current_user.short_name}     # 배포자
${workspace.file_path}                   # 이번 배포의 파일 루트
${bundle.target}                         # 현재 타깃명
${resources.jobs.my_job.id}              # 다른 리소스의 ID (의존성 연결)
```

`${resources.*}`가 특히 유용하다. 잡 A가 끝나면 잡 B를 트리거하는 구성을 **ID를 몰라도** 선언할 수 있다.

### 6.4 병합 규칙 — 덮어쓰기가 아니라 병합이다

타깃에서 `resources`를 다시 쓰면 **통째로 교체되는 게 아니라 깊은 병합(deep merge)**된다.

```yaml
resources:
  jobs:
    daily_ingest:
      name: daily-ingest
      tasks: [...]
      job_clusters:
        - job_cluster_key: main
          new_cluster:
            num_workers: 2
            spark_version: 15.4.x-scala2.12

targets:
  prod:
    resources:
      jobs:
        daily_ingest:
          job_clusters:
            - job_cluster_key: main
              new_cluster:
                num_workers: 12      # 이 필드만 바뀐다
```

다만 **배열(리스트)의 병합 규칙은 직관과 다를 수 있다.** 위처럼 `job_cluster_key` 같은 키가 있는 항목은 키로 매칭되지만, 순수 리스트는 교체되는 경우가 있다. 그래서 실무 권장은 **환경차는 되도록 `variables`로 표현**하고, `resources` 오버라이드는 정말 구조가 달라야 할 때만 쓰는 것이다. 애매하면 `databricks bundle validate -t prod`로 **최종 병합 결과를 확인**하면 된다.

## 7. 배포 엔진 — Terraform에서 Direct로

DAB를 조금 깊게 쓰기 시작하면 마주치는 사실이 있다. **DAB는 원래 내부적으로 Terraform을 썼다.** `databricks bundle deploy`를 치면 CLI가 뒤에서 Terraform 바이너리와 Databricks Terraform Provider를 내려받아, YAML을 Terraform 설정으로 변환해 실행했다. `.databricks/` 아래에 `terraform.tfstate`가 생기는 이유다.

합리적인 선택이었다. 선언형 배포의 어려운 부분(현재 상태와 원하는 상태를 비교해 생성/수정/삭제를 결정)을 이미 검증된 엔진에 위임한 것이다. 대신 대가가 있었다.

- 배포할 때마다 **Terraform과 provider를 다운로드**해야 한다 → 폐쇄망·프록시·사내 레지스트리 환경에서 자주 깨진다. **한국 SI 현장에서 특히 아픈 지점**이다.
- 느리다.
- 에러 메시지가 Terraform 용어로 나와 디버깅이 어렵다.
- provider가 지원하는 리소스만 쓸 수 있다.

그래서 **direct 배포 엔진**이 나왔다. Terraform을 걷어내고 **Databricks Go SDK로 REST API를 직접 호출**하는 방식이다.

| | Terraform 엔진 | **Direct 엔진** |
|---|---|---|
| 의존성 | Terraform + provider 다운로드 필요 | **CLI 바이너리 하나로 완결** |
| 속도 | 기준 | **최대 40% 빠름** |
| 상태 파일 | `terraform.tfstate` | `resources.json` (자체 스키마) |
| plan | 제한적 | `bundle plan -o json`으로 **필드 단위 diff** |
| 재현 가능한 배포 | — | `bundle deploy --plan plan.json`으로 **승인된 plan만 실행** |
| 지원 리소스 | provider 범위 | 카탈로그·외부 위치·Genie 스페이스·AI Search 엔드포인트 **추가 지원** |

타임라인은 이렇다.

- **2025-12 (CLI 0.279.0)**: 두 엔진 병존 시작, `bundle deployment migrate` 제공
- **2026-06 (CLI 1.3.0)**: direct 엔진 **GA**, **신규 번들의 기본값**으로 전환
- 이후: Terraform 엔진은 **폐기 예정**. 공식 권장은 마이그레이션이다.

### 전환 방법

신규 번들이면 한 줄이다.

```yaml
bundle:
  engine: direct
```

(또는 환경 변수 `DATABRICKS_BUNDLE_ENGINE=direct`. 둘 다 있으면 설정이 이긴다.)

이미 Terraform으로 배포한 번들은 상태 파일을 변환해야 한다.

```bash
databricks bundle deploy -t my_target              # 1. 먼저 Terraform으로 완전 배포
databricks bundle deployment migrate -t my_target  # 2. tfstate → resources.json 변환
databricks bundle plan -t my_target                # 3. 검증: 변경 없음이 나와야 정상
databricks bundle deploy -t my_target              # 4. 확정
```

3번에서 변경이 잡히더라도 대부분은 플랫폼이 배포 후 채워 넣는 메타데이터 필드 차이(진짜 드리프트 아님)이고, 다음 배포에서 조정된다. 검증이 실패하면 `.databricks/bundle/<target>/resources.json`을 지워 되돌릴 수 있다.

### 주의: 동작이 미묘하게 다른 지점

**YAML에서 필드를 지웠을 때의 처리가 다르다.**

- **Terraform 엔진**: 설정에서 뺀 필드는 **플랫폼 값이 그대로 유지**된다.
- **Direct 엔진**: 설정에서 뺀 필드는 **리소스의 기본값으로 되돌아간다.**

Direct 엔진은 "로컬 설정 ↔ 직전 배포 스냅샷"을 비교하므로, 사라진 필드를 **변경으로 인식**하기 때문이다. 마이그레이션 직후 "왜 재시도 횟수가 초기화됐지?" 같은 일이 여기서 난다. 대응은 단순하다 — **유지하고 싶은 값은 명시적으로 적어라.** 이전 배포에 기대지 마라.

> **핵심 통찰 — "상태 파일을 가진 순간, DAB는 배포 스크립트가 아니라 인프라 관리 도구가 된다"**
>
> DAB를 처음 보면 "YAML을 API 호출로 바꿔주는 편의 도구"로 읽힌다. 하지만 **상태 파일(`resources.json`)이 있다**는 사실이 성격을 완전히 바꾼다.
>
> 상태가 있으면 CLI는 "무엇을 만들어야 하는가"뿐 아니라 **"내가 지난번에 무엇을 만들었는가"**를 안다. 그래서 YAML에서 잡 하나를 지우면 **워크스페이스에서도 그 잡이 사라진다.** 이건 강력한 동시에 위험하다. 스크립트라면 "안 만들 뿐"이지만, 상태 기반 도구는 **"지운다"**로 해석한다.
>
> 실무적 함의는 두 가지다. 첫째, **상태 파일이 진실의 절반**이므로 이게 꼬이면 배포가 꼬인다(그래서 타깃별로 격리되고, 워크스페이스에 동기화된다). 둘째, **Terraform을 다뤄본 사람의 직관이 대부분 그대로 통한다** — plan으로 먼저 보고, 상태와 실물의 드리프트를 의식하고, 삭제를 두려워하는 습관 말이다. DAB를 "쉬운 Terraform"으로 소개하는 게 정확한 이유다. Terraform을 걷어낸 direct 엔진에서도 **이 사고 모델 자체는 남아 있다.**

## 8. 명령어로 보는 라이프사이클

전체 흐름을 명령어로 훑으면 도구의 모양이 보인다.

```
  init ──▶ (개발) ──▶ validate ──▶ plan ──▶ deploy ──▶ run ──▶ summary
                                                          │
   generate ──▶ (기존 리소스를 YAML로 역수입)             ▼
   deployment bind ──▶ (기존 리소스를 번들이 인수)      destroy
```

| 명령 | 하는 일 | 언제 쓰나 |
|---|---|---|
| `bundle init` | 템플릿에서 프로젝트 생성 (`default-python`, `default-minimal` 등) | 시작할 때 한 번 |
| `bundle validate` | YAML 문법·스키마 검증 + **병합된 최종 설정 출력** | 커밋 전, CI 필수 |
| `bundle plan` | **무엇이 생성/수정/삭제될지 미리보기** | prod 배포 전 필수 |
| `bundle deploy` | 파일 동기화 + 리소스 생성/갱신 | 배포 |
| `bundle run` | 배포된 잡·파이프라인·스크립트 실행 | 배포 직후 스모크 테스트 |
| `bundle summary` | 배포된 리소스 목록 + 워크스페이스 링크 | "내가 뭘 올렸더라" |
| `bundle open` | 해당 리소스를 브라우저에서 열기 | 디버깅 |
| `bundle sync` | 코드 파일만 단방향 동기화(리소스 갱신 없음) | 노트북만 고쳤을 때 빠르게 |
| `bundle generate` | **워크스페이스의 기존 잡/파이프라인/대시보드 → YAML** | 도입 초기, UI 자산 흡수 |
| `bundle deployment bind` | 기존 워크스페이스 리소스를 번들 리소스에 **연결** | 이미 있는 운영 잡을 DAB로 인수 |
| `bundle destroy` | 배포한 리소스 삭제 | dev 정리 |

특히 **`generate` + `bind` 조합**이 현장 도입의 핵심이다.

```bash
# 1. 이미 운영 중인 잡을 YAML로 뽑는다
databricks bundle generate job --existing-job-id 1234567890

# 2. 그 YAML을 번들의 리소스로 "인수"한다 (새로 만들지 않고 기존 걸 관리 대상으로)
databricks bundle deployment bind daily_ingest 1234567890

# 3. 이제부터 deploy가 그 잡을 갱신한다
databricks bundle deploy -t prod
```

`bind`가 없으면 어떻게 되나? deploy가 **같은 이름의 잡을 새로 하나 더 만든다.** 그리고 원래 잡은 관리 밖에 남아 둘 다 스케줄대로 돌기 시작한다. 중복 적재의 전형적 시나리오다. **이미 돌고 있는 운영 리소스를 DAB로 가져올 땐 `bind`가 필수**라고 외워두는 게 좋다.

`bundle plan`도 새로 강조할 만하다. direct 엔진에서 `-o json`을 주면 **어떤 필드가 왜 변경으로 판정됐는지**까지 나온다. 그리고 그 plan을 파일로 저장해 `deploy --plan plan.json`으로 실행하면, **리뷰에서 승인된 계획만 정확히 운영에 반영**된다 — 계획과 실행 사이에 다른 게 끼어들 여지를 없애는 장치다.

## 9. CI/CD에 얹기

DAB의 목적지는 결국 파이프라인이다. 공식 권장 흐름은 단순하다.

```
  PR 생성/커밋
      │
      ├─▶ [CI]  코드 컴파일 + 단위 테스트
      │         databricks bundle validate -t staging
      │         (선택) databricks bundle plan -t prod  → PR에 diff 코멘트
      │
  main 병합
      │
      └─▶ [CD]  아티팩트(wheel/JAR) 빌드 → 볼륨/스토리지에 커밋 해시로 버전 업로드
                databricks bundle deploy -t staging
                databricks bundle run <통합테스트잡> -t staging
                (승인)
                databricks bundle deploy -t prod
```

핵심 원칙 몇 가지.

- **브랜치 = 타깃 매핑을 고정한다.** trunk 기반(main이 항상 배포 가능)이 권장이고, `git.branch` 검증으로 강제한다.
- **CI에서는 서비스 프린시펄로 인증한다.** 시크릿을 저장하는 대신 **워크로드 아이덴티티 페더레이션(OIDC)** 이 공식 권장이다. 토큰을 GitHub Secrets에 넣고 로테이션하는 부담이 사라진다.
- **`run_as`를 반드시 서비스 프린시펄로 둔다.** 개인 계정으로 운영 잡이 돌면 그 사람이 퇴사하거나 권한이 바뀌는 순간 파이프라인이 멈춘다. **인수인계 사고의 단골 원인**이다.
- **아티팩트는 커밋 해시로 버전을 붙인다.** "지금 운영에서 도는 코드가 정확히 어느 커밋인가"에 답할 수 있어야 한다.

GitHub Actions 골격은 이 정도로 짧다.

```yaml
- uses: databricks/setup-cli@main
- run: databricks bundle validate -t prod
- run: databricks bundle deploy -t prod
  env:
    DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
    DATABRICKS_CLIENT_ID: ${{ vars.DATABRICKS_CLIENT_ID }}
    DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }}
```

> **핵심 통찰 — "DAB는 CI/CD를 만들어주지 않는다. CI/CD를 '가능하게' 할 뿐이다"**
>
> "DAB 도입하면 CI/CD가 된다"는 기대는 절반만 맞다. DAB가 제공하는 건 **멱등한 배포 명령 하나**(`bundle deploy`)다. 그게 없으면 CI/CD를 만들 수 없으니 필수 조건은 맞지만, 충분 조건은 아니다.
>
> 나머지 절반은 **조직이 결정해야 하는 것들**이다. 브랜치 전략은 무엇인가. 어떤 테스트가 통과해야 staging으로 가는가. prod 배포에 사람의 승인이 필요한가, 필요하다면 누구인가. 서비스 프린시펄에 어떤 권한을 주는가. 실패하면 롤백인가 롤포워드인가.
>
> 실제 프로젝트에서 막히는 지점은 거의 항상 후자다. `databricks.yml`을 쓰는 데는 하루면 되지만, **"운영 배포를 누가 승인하는가"에 합의하는 데는 2주가 걸린다.** DAB 도입을 제안할 때 기술 작업량만 산정하면 반드시 일정이 밀린다.

## 10. 실무에서 밟는 지뢰들

### 10.1 `destroy`는 정말로 지운다

`bundle destroy`는 배포한 리소스를 삭제한다. 잡·파이프라인뿐 아니라 **번들이 만든 UC 스키마나 볼륨도 대상**이 될 수 있다 — 즉 **데이터가 날아갈 수 있다.**

방어책은 `lifecycle` 설정이다.

```yaml
resources:
  schemas:
    silver:
      name: silver
      catalog_name: ${var.catalog}
      lifecycle:
        prevent_destroy: true    # destroy가 이 리소스를 건드리면 에러로 중단
```

데이터를 담는 리소스(UC 스키마·볼륨), 운영 모델 등에는 기본으로 걸어두는 게 안전하다. 그리고 **운영 타깃에 대고 로컬에서 `destroy`를 치지 않는다**는 규칙 — prod 배포 권한 자체를 CI에만 주면 물리적으로 불가능해진다.

### 10.2 `bind` 없이 기존 리소스를 배포하면 중복이 생긴다

8장에서 본 그대로다. 이미 운영 중인 잡이 있는 상태에서 같은 정의를 배포하면 **쌍둥이 잡**이 생긴다. 도입 초기 가장 흔한 사고다.

### 10.3 상태 파일과 실제가 어긋난다(드리프트)

누군가 UI에서 잡 설정을 손으로 고치면 YAML과 실물이 어긋난다. 다음 배포에서 그 수정은 **말없이 덮어써진다.** 이건 버그가 아니라 의도된 동작이다 — YAML이 진실의 원천이니까.

문제는 **팀이 이걸 모를 때**다. "어제 UI에서 고친 게 오늘 사라졌어요"가 반복되면 도구 불신으로 이어진다. 그래서 DAB 도입 시 반드시 함께 선언해야 하는 규칙이 있다: **"DAB가 관리하는 리소스는 UI에서 고치지 않는다."** 필요하면 UI에서 실험하고, 확정되면 YAML에 반영한다.

불변 폴더(immutable folder) 옵션을 켜면 배포 산출물이 **읽기 전용 스냅샷 폴더**로 들어가 비관리자가 수정할 수 없게 된다. 운영 타깃에서 검토할 만한 강화책이다.

### 10.4 `development` 모드를 안 쓴 dev 배포

dev 타깃에 `mode: development`를 빼면 스케줄이 **활성 상태로 배포된다.** 개발용 잡이 실제로 새벽에 돌아 실데이터를 건드린다. 리뷰 체크리스트 1번에 올려둘 항목이다.

### 10.5 CLI 버전 편차

DAB는 기능 추가가 빠르다. 리소스 타입과 설정 필드가 CLI 버전에 따라 다르다(예: `lifecycle` 필드는 비교적 최근 CLI부터 인식된다). 로컬 CLI와 CI CLI 버전이 다르면 **"로컬에선 되는데 CI에서 안 되는"** 전형적 상황이 나온다.

```yaml
bundle:
  databricks_cli_version: ">= 1.3.0"   # 최소 버전을 번들이 강제
```

이 한 줄과, CI에서 **CLI 버전을 고정**하는 것 — 둘 다 하는 게 맞다.

### 10.6 DAB로 관리하면 안 되는 것

모든 걸 DAB에 넣고 싶어지지만, 선을 그어야 한다.

- **시크릿 값 자체** — `secret_scopes`로 스코프는 만들 수 있어도 **값을 YAML에 적으면 안 된다.** 값은 시크릿 관리자에 두고 참조만 한다.
- **워크스페이스·네트워크·IAM 같은 계정 레벨 인프라** — 이건 Terraform의 영역이다. DAB는 워크스페이스 **안**의 리소스를 다룬다.
- **분석가가 임시로 만드는 대시보드** — 실험적·일회성 자산까지 코드화하면 리뷰 비용이 가치를 넘는다.

## 11. 정리 & SI 관점의 시사점

**정리:**

- DAB는 **워크스페이스에만 존재하던 리소스 설정을 YAML로 코드화**하고, `databricks bundle deploy`로 환경별 배포를 자동화하는 도구다. 배포 자동화는 결과고, **설정의 버전 관리**가 본질이다.
- 2026년 3월 **Databricks Asset Bundles → Declarative Automation Bundles**로 개명됐다. 약칭 DAB, CLI 명령, 설정 파일 모두 그대로인 **비파괴적 변경**이다.
- `resources` 블록은 **REST API 스키마를 그대로 옮긴 형태**다. 그래서 API 문서가 곧 DAB 문서이고, `bundle generate`로 UI 자산을 YAML로 역수입할 수 있다.
- **`targets`가 설계 중심**이다. 리소스 정의는 한 벌만 쓰고, 환경차는 `variables` → `targets` 오버라이드로 흡수한다.
- **`mode: development` / `production`은 사고 방지 장치**다. dev는 이름 접두사·스케줄 자동 일시정지, prod는 Git 브랜치 검증·클러스터 오버라이드 금지·`run_as` 요구.
- **배포 엔진이 Terraform에서 direct로 넘어갔다.** 2026년 6월(CLI 1.3.0) GA이자 신규 번들 기본값. Terraform 다운로드가 사라져 **폐쇄망에서 유리**하고, 40% 빠르며, `bundle plan`의 필드 단위 diff와 승인된 plan 재실행이 가능하다. Terraform 엔진은 폐기 예정.
- **direct 엔진은 "YAML에서 지운 필드를 기본값으로 되돌린다"** — Terraform 엔진과 다른 지점이니 마이그레이션 시 주의.
- 도입 시 가장 흔한 사고는 **`bind` 누락(쌍둥이 리소스)**, **UI 수동 수정과의 충돌**, **`destroy`에 의한 데이터 손실**(→ `lifecycle.prevent_destroy`).

**우리 SI 프로젝트에 주는 시사점 (토론 포인트):**

- **DAB는 프로젝트 첫 주에 세팅해야 한다.** 나중에 도입하면 이미 UI로 만들어진 수십 개 리소스를 `generate` + `bind`로 일일이 인수해야 하고, 그 사이에 만들어진 것들은 계속 관리 밖으로 샌다. 저장소 뼈대(`databricks.yml` + `resources/` + 타깃 3개)를 **코드 한 줄 쓰기 전에** 만들어두는 게 비용이 가장 싸다.
- **"UI에서 고치지 않는다"는 팀 규약을 초기에 못 박자.** DAB의 최대 실패 원인은 기술이 아니라 이 규칙의 부재다. 한 명이 UI에서 고치고 다음 배포에 덮어써지는 일이 두어 번 반복되면 팀이 도구를 불신하게 된다. **불변 폴더 옵션**으로 운영 타깃을 물리적으로 잠그는 것도 검토할 만하다.
- **인수인계 산출물의 성격이 바뀐다.** 지금까지 "운영 가이드"에 스크린샷으로 남기던 내용(잡 구성, 스케줄, 클러스터 사양, 권한)이 **저장소 하나로 대체된다.** 고객에게 "이 저장소가 곧 운영 환경의 정의이며, 여기를 고치고 배포하면 반영됩니다"라고 넘길 수 있다는 건 SI 산출물로서 격이 다르다. 제안 단계에서 차별화 포인트로 쓸 만하다.
- **폐쇄망·프록시 환경이면 direct 엔진을 처음부터 지정하자.** 금융·공공 프로젝트에서 Terraform provider 다운로드가 막혀 배포가 안 되는 상황은 실제로 자주 발생한다. `bundle.engine: direct` 한 줄이 이 문제를 통째로 없앤다. 신규 프로젝트라면 어차피 기본값이지만, **명시적으로 적어두는 편**이 CLI 버전 편차로 인한 혼선을 막는다.
- **`run_as`는 계약 이슈다.** 운영 잡이 개인 계정으로 돌면 인력 교체·철수 시점에 파이프라인이 멈춘다. 프로젝트 초기에 **전용 서비스 프린시펄 생성과 권한 부여**를 고객사 인프라 담당과 합의해두지 않으면, 마지막에 가서 급하게 처리하다 사고가 난다.
- **DAB 도입의 난관은 YAML이 아니라 합의다.** 브랜치 전략, staging 존재 여부, 운영 배포 승인자, 서비스 프린시펄 권한 범위 — 이걸 정하는 데 기술 작업보다 훨씬 오래 걸린다. 일정 산정 시 **"CI/CD 파이프라인 구축"을 기술 작업으로만 잡으면 반드시 밀린다.**

> **토론거리:** 우리 프로젝트에서 **환경을 몇 개로 가져갈 것인가**(dev/prod 2단인가, staging을 넣어 3단인가)? 고객사 워크스페이스가 환경별로 분리돼 있는가, 아니면 하나의 워크스페이스에서 카탈로그로만 분리되는가 — 후자라면 `targets`를 어떻게 설계해야 안전한가? 그리고 **운영 배포 승인을 누가 하는가**, 우리인가 고객인가? 이 답에 따라 `databricks.yml`의 타깃 구조와 CI 파이프라인 모양이 통째로 달라진다.
