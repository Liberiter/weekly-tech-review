# 2026-08-04. SDP (Spark Declarative Pipelines) — "테이블이 어떠해야 하는지"만 쓰고 DAG는 안 쓴다

> 데이터 파이프라인 코드를 열어보면 대부분이 **본질과 무관한 코드**다. 어떤 테이블을 먼저 만들고 다음에 뭘 만들지 순서를 적는 코드, 실패하면 재시도하는 코드, 체크포인트 경로를 조립하는 코드, 스트리밍인지 배치인지에 따라 갈라지는 분기, 그리고 Airflow DAG에 이 순서를 한 번 더 베껴 쓰는 코드.
>
> 정작 비즈니스 로직 — "Bronze를 정제해 Silver를 만들고, Silver를 집계해 Gold를 만든다" — 는 전체의 몇 퍼센트도 안 된다. 나머지는 전부 **배관(plumbing)**이다.
>
> **SDP(Spark Declarative Pipelines)**는 이 배관을 통째로 프레임워크에 넘긴다. 개발자는 **"이 테이블은 이런 쿼리의 결과여야 한다"**만 선언하고, 실행 순서·병렬화·증분 처리·체크포인트·재시도는 엔진이 유도한다. Databricks가 DLT로 4년간 검증한 모델을 **Apache Spark에 기증해 오픈소스로 만든 것**이 SDP다. 이 글은 SDP의 개념 모델, 실제 문법, 그리고 "오픈소스 SDP와 Databricks 제품의 경계가 지금 어디인가"를 정리한다.

## 1. 도입: 우리가 파이프라인 코드에 쓰는 것의 대부분은 파이프라인이 아니다

전형적인 Spark ETL 잡 하나를 떠올려 보자. 실제로 코드에 들어가는 것들은 이렇다.

```python
# 1. 소스 읽기
bronze = spark.read.parquet(bronze_path)

# 2. 변환 (← 여기가 유일하게 "우리 것"이다)
silver = bronze.filter("status IS NOT NULL").withColumn(...)

# 3. 쓰기 — 모드는? 덮어쓰나 추가하나 병합하나?
silver.write.mode("overwrite").saveAsTable("silver_orders")

# 4. 그리고 gold는 silver가 끝난 다음에 돌려야 한다
#    → Airflow DAG에 의존성을 한 번 더 적는다
#    → 실패하면? 재시도? 부분 성공은?
#    → 증분으로 하려면? 어제 어디까지 했는지 어디에 적나?
#    → 스트리밍으로 바꾸려면? 코드를 다시 쓴다
```

문제는 2번을 뺀 전부다. 그리고 이 배관에는 **팀마다 다른 방언**이 생긴다. 어떤 잡은 `overwrite`, 어떤 잡은 `merge`, 어떤 잡은 수동 워터마크 컬럼. 새로 합류한 사람이 파이프라인 하나를 이해하는 데 며칠이 걸리는 이유다.

더 아픈 건 **의존성이 두 곳에 중복 기록**된다는 점이다. 코드 안에는 "gold는 silver를 읽는다"가 있고, Airflow DAG에는 "gold_task는 silver_task 다음"이 있다. 둘은 같은 사실을 다른 언어로 적은 것인데, **한쪽만 고치면 조용히 어긋난다.** 새 테이블을 추가하고 DAG에 등록하는 걸 잊어 며칠 뒤에 발견하는 일이 반복된다.

SDP의 출발점이 여기다.

> **핵심 통찰 — "선언형의 본질은 문법이 아니라 '의존성 그래프를 사람이 쓰지 않는다'는 것"**
>
> 선언형 파이프라인을 "데코레이터 붙이는 문법"으로 이해하면 가치를 놓친다. 진짜 변화는 **의존성 그래프의 소유권이 사람에게서 엔진으로 넘어간 것**이다.
>
> SDP에서 `gold`가 `silver`를 읽으면, 그 **읽는다는 사실 자체**가 의존성이다. 따로 등록하지 않는다. 등록할 수 없으니 **어긋날 수도 없다.** 코드가 곧 DAG이고, DAG는 항상 코드와 일치한다.
>
> 이건 단순한 편의가 아니라 **오류 계층 하나를 통째로 제거**한 것이다. "코드와 오케스트레이션 설정의 불일치"라는 버그 종류가 존재하지 않게 된다. 리팩터링할 때 테이블을 쪼개거나 합쳐도 DAG를 손대지 않아도 된다는 뜻이기도 하다.

## 2. SDP의 계보 — DLT에서 Apache Spark로

SDP는 새로 발명된 물건이 아니다. 4년간 프로덕션에서 굴러온 모델이 오픈소스로 옮겨온 것이다.

| 시점 | 사건 |
|---|---|
| 2022 | Databricks가 **Delta Live Tables(DLT)** 출시. 선언형 ETL 프레임워크 |
| 2025-06 | **Data + AI Summit 2025**에서 Databricks가 DLT의 코어를 **Apache Spark에 기증**한다고 발표. 이름은 **Spark Declarative Pipelines** |
| 2025 하반기 | Databricks 제품명이 DLT → **Lakeflow Declarative Pipelines**로 정리 |
| **Spark 4.1** | SDP가 **Apache Spark 정식 기능으로 탑재**. `spark-pipelines` CLI, `pyspark.pipelines` 모듈 |
| **Spark 4.2** (2026-07-14) | **Auto CDC(SCD Type 1)가 오픈소스 SDP로 진입.** `spark` 세션 자동 주입, DSv2 `CHANGES` 절 등 |

여기서 실무적으로 중요한 건 두 가지다.

첫째, **SDP는 Databricks 전용이 아니다.** Apache Spark만 있으면 EMR이든 온프레미스 YARN이든 로컬이든 돌아간다. 벤더 종속 없이 선언형 파이프라인을 쓸 수 있게 됐다.

둘째, **Databricks의 Lakeflow Declarative Pipelines는 SDP 위에 얹힌 구현**이다. 즉 Databricks에서 쓰던 파이프라인 코드가 원칙적으로 **다른 SDP 런타임으로 이식 가능**하다. 이건 SI 관점에서 상당히 큰 이야기라 10장에서 따로 다룬다.

## 3. 핵심 개념 넷 — 파이프라인, 플로우, 스트리밍 테이블, 구체화 뷰

SDP의 어휘는 넷뿐이다. 이걸 정확히 구분하는 게 전부다.

```
   ┌─────────────────────────── Pipeline ─────────────────────────────┐
   │ (개발·실행의 단위. spark-pipeline.yml 하나가 하나의 파이프라인)  │
   │                                                                  │
   │ [소스] ──Flow──▶ (Streaming Table) ──Flow──▶ (Materialized View) │
   │                          bronze                        gold      │
   │                                                                  │
   │ Flow = "읽어서, 변환해서, 쓴다"는 처리 로직 하나                 │
   │ Dataset = Flow가 채우는 결과물 (테이블 / 뷰)                     │
   └──────────────────────────────────────────────────────────────────┘
```

### 3.1 Pipeline

개발과 실행의 단위. 하나의 파이프라인이 여러 개의 플로우·스트리밍 테이블·구체화 뷰를 담는다. 실행하면 **정의된 객체들의 의존성을 분석해 실행 순서와 병렬도를 자동으로 결정**한다.

### 3.2 Flow

**SDP의 진짜 기본 단위.** 소스에서 읽고 → 사용자 로직을 적용하고 → 대상 데이터셋에 쓰는 **처리 로직 하나**를 가리킨다. 배치 의미론과 스트리밍 의미론을 모두 가질 수 있다.

대부분의 경우 플로우는 눈에 안 보인다. 테이블 하나를 정의하면 그 테이블을 채우는 플로우가 암묵적으로 하나 생기기 때문이다. 하지만 **하나의 테이블에 여러 플로우**를 붙일 수 있고, 여기서 SDP의 표현력이 나온다(7장).

### 3.3 Streaming Table

**증분 처리되는 테이블.** 새로 도착한 데이터만 처리한다. 하나 이상의 **스트리밍 플로우**가 채운다.

- 적합한 곳: **인제스트, 원본 정제.** 한 번 들어온 행이 나중에 바뀌지 않는 append-only 성격의 단계.
- 엔진이 체크포인트를 관리하므로 "어제 어디까지 처리했나"를 사람이 안 챙긴다.

### 3.4 Materialized View

**미리 계산되어 테이블로 저장된 뷰.** 소스가 바뀌면 결과를 다시 계산한다(가능하면 증분으로). **정확히 하나의 배치 플로우**가 채운다.

- 적합한 곳: **집계·조인.** 과거 행이 바뀌면 결과도 바뀌어야 하는 단계.
- "지난 90일 재구매율" 같은 건 상류가 수정되면 답이 달라져야 하므로 여기가 맞다.

### 3.5 Temporary View

파이프라인 **안에서만** 참조되는 중간 뷰. 밖으로 내보내지 않는다. 여러 곳에서 재사용하는 중간 변환을 이름 붙여 정리할 때 쓴다.

> **핵심 통찰 — "스트리밍 테이블이냐 구체화 뷰냐는 성능 선택이 아니라 '데이터의 성질' 선언이다"**
>
> 처음 SDP를 보면 이 둘을 "빠른 거 vs 느린 거"로 읽기 쉽다. 아니다. 이건 **"이 테이블의 과거 행이 나중에 바뀔 수 있는가"**에 대한 답이다.
>
> - 로그 인제스트: 어제 도착한 로그는 오늘 안 바뀐다 → **스트리밍 테이블**(증분이 항상 맞다)
> - 일별 매출 집계: 어제 거래가 취소되면 어제 매출이 바뀌어야 한다 → **구체화 뷰**(재계산이 필요하다)
>
> 잘못 고르면 **성능이 아니라 정답이 틀린다.** 집계를 스트리밍 테이블로 만들면 취소·정정이 반영 안 되고, 인제스트를 구체화 뷰로 만들면 매번 전체를 다시 읽어 비용이 폭발한다.
>
> 그래서 실무 판단 기준은 하나다. **"상류의 과거 데이터가 수정될 수 있는가?"** 그렇다면 구체화 뷰, 아니라면 스트리밍 테이블. 그리고 **한 파이프라인 안에서 두 종류를 섞는 게 정상**이다 — 브론즈는 스트리밍 테이블, 골드는 구체화 뷰처럼.

## 4. 의존성을 선언하지 않는다 — 그래프는 유도된다

SDP를 처음 쓸 때 가장 어색한 지점이자, 가장 핵심적인 지점이다.

```python
@dp.materialized_view
def gold_daily_sales():
    return spark.table("silver_orders").groupBy("order_date").sum("amount")
    #             ▲
    #             이 한 줄이 "gold_daily_sales는 silver_orders에 의존한다"이다.
    #             따로 등록하는 곳이 없다.
```

`spark.table("silver_orders")`를 호출하는 순간, SDP는 **분석 단계에서 이 참조를 발견**해 그래프에 간선을 추가한다. 그리고:

1. 파이프라인 전체의 **의존성 그래프를 구성**하고
2. **순서를 결정**하고 (silver 먼저, gold 나중)
3. **서로 무관한 것은 병렬로** 돌리고
4. 순환 참조가 있으면 **실행 전에 에러**를 낸다

여기서 나오는 실전 습관이 하나 있다. `spark-pipelines dry-run`이다.

```bash
spark-pipelines dry-run
```

데이터를 **한 줄도 읽거나 쓰지 않고** 파이프라인을 분석만 한다. 잡히는 것:

- Python/SQL **문법 오류**
- **분석 오류** — 존재하지 않는 테이블 참조, 없는 컬럼 참조
- **그래프 검증 오류** — 순환 의존성

3시간짜리 파이프라인이 2시간 50분 지점에서 오타로 죽는 상황을 몇 초 만에 막는다. **커밋 전과 CI에 반드시 넣을 명령**이다.

## 5. Python으로 쓰기

### 5.1 임포트와 세션

```python
from pyspark import pipelines as dp
from pyspark.sql import DataFrame, SparkSession

spark: SparkSession   # 타입 힌트만. 실제 세션은 SDP가 주입한다
```

Spark 4.2부터 프레임워크가 모듈 네임스페이스에 `spark`를 **자동 주입**한다. 4.1 스타일(`spark = SparkSession.active()`)도 여전히 동작한다. 위처럼 **타입 힌트만 선언**해두는 게 권장 패턴인데, 실행에는 영향이 없고 IDE·린터가 `spark`를 인식하게 해준다.

### 5.2 세 가지 데코레이터

```python
# 구체화 뷰 — 배치, 재계산
@dp.materialized_view
def customers() -> DataFrame:
    return spark.read.format("csv").option("header", True).load("/data/customers")

# 이름을 함수명과 다르게 주려면
@dp.materialized_view(name="trips_mv")
def basic_mv() -> DataFrame:
    return spark.table("samples.nyctaxi.trips")

# 스트리밍 테이블 — 증분
@dp.table
def orders() -> DataFrame:
    return (spark.readStream
        .format("kafka")
        .option("kafka.bootstrap.servers", "localhost:9092")
        .option("subscribe", "orders")
        .load())

# 임시 뷰 — 파이프라인 내부 전용
@dp.temporary_view
def cleaned() -> DataFrame:
    return spark.table("orders").filter("amount > 0")
```

규칙은 간단하다. **함수 이름이 곧 데이터셋 이름**이고, **함수는 DataFrame을 반환**하며, **쓰기는 하지 않는다.** `write`나 `save`를 부르지 않는 게 핵심이다 — 어디에 어떻게 쓸지는 프레임워크가 결정한다.

### 5.3 전체 파이프라인 예시

```python
from pyspark import pipelines as dp
from pyspark.sql import DataFrame, SparkSession
from pyspark.sql.functions import col

spark: SparkSession

@dp.table
def orders() -> DataFrame:
    return (spark.readStream
        .format("kafka")
        .option("kafka.bootstrap.servers", "localhost:9092")
        .option("subscribe", "orders")
        .load())

@dp.materialized_view
def customers() -> DataFrame:
    return spark.read.format("csv").option("header", True).load("/data/customers")

@dp.materialized_view
def customer_orders() -> DataFrame:
    return (spark.table("orders")
        .join(spark.table("customers"), "customer_id")
        .select("customer_id", "order_number", "state",
                col("order_datetime").cast("date").alias("order_date")))

@dp.materialized_view
def daily_orders_by_state() -> DataFrame:
    return (spark.table("customer_orders")
        .groupBy("state", "order_date")
        .count()
        .withColumnRenamed("count", "order_count"))
```

네 개의 함수만 있고, **실행 순서를 적은 곳이 없다.** SDP가 `orders`/`customers` → `customer_orders` → `daily_orders_by_state` 순서를 유도하고, 앞의 둘은 병렬로 돌린다.

## 6. SQL로 쓰기

같은 걸 SQL로도 쓸 수 있다. 파이프라인 소스 파일은 `.py`와 `.sql` 둘 다 가능하고, **한 파이프라인 안에서 섞어 쓸 수 있다.**

```sql
-- 구체화 뷰
CREATE MATERIALIZED VIEW customer_orders AS
SELECT c.customer_id, o.order_number, c.state
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;

-- 스트리밍 테이블 (STREAM 키워드가 증분 읽기를 지시한다)
CREATE STREAMING TABLE orders AS
SELECT * FROM STREAM orders_source;

-- 임시 뷰
CREATE TEMPORARY VIEW cleaned AS
SELECT * FROM orders WHERE amount > 0;
```

주목할 건 `STREAM` 키워드다. **같은 SQL에서 `FROM tbl`은 배치 읽기, `FROM STREAM tbl`은 증분 읽기**다. 배치와 스트리밍이 별개 API가 아니라 **한 언어 안의 한 단어 차이**로 표현된다.

실무 배분은 대체로 이렇게 갈린다.

| | SQL | Python |
|---|---|---|
| 잘 맞는 곳 | 정형화된 변환·조인·집계. **분석가도 읽고 고칠 수 있다** | 복잡한 로직, 반복 생성, 외부 라이브러리, UDF |
| 못 하는 것 | 동적 생성, `PIVOT` 미지원 | — |
| 싱크 정의 | 불가 | 가능 (`dp.create_sink`) |

**SQL로 쓸 수 있으면 SQL로 쓰는 게 낫다.** 리뷰 가능한 사람의 수가 다르고, 인수인계 후 유지보수 주체가 달라진다.

## 7. Flow를 직접 다루기 — 하나의 테이블에 여러 소스 합류시키기

3장에서 "플로우가 진짜 기본 단위"라고 했다. 그게 드러나는 게 이 패턴이다.

지역별로 나뉜 여러 소스를 하나의 테이블로 모아야 한다고 하자. 명령형으로 짜면 `union`으로 합치거나, 소스마다 잡을 따로 만들어 같은 테이블에 append하게 하고 순서를 조율해야 한다. SDP는 **테이블 하나에 플로우를 여러 개 붙인다.**

```python
# 빈 스트리밍 테이블을 먼저 선언
dp.create_streaming_table("customers_us")

# 여기에 흘려보내는 플로우들
@dp.append_flow(target="customers_us")
def append_customers_us_west() -> DataFrame:
    return spark.readStream.table("customers_us_west")

@dp.append_flow(target="customers_us")
def append_customers_us_east() -> DataFrame:
    return spark.readStream.table("customers_us_east")
```

SQL로도 같다.

```sql
CREATE STREAMING TABLE customers_us;

CREATE FLOW append_customers_us_west AS
INSERT INTO customers_us SELECT * FROM STREAM(customers_us_west);

CREATE FLOW append_customers_us_east AS
INSERT INTO customers_us SELECT * FROM STREAM(customers_us_east);
```

이 구조의 장점이 실무에서 크다. **소스가 하나 늘어도 기존 코드를 안 건드린다.** 새 지역이 추가되면 플로우 함수 하나를 추가하면 끝이고, 각 플로우는 **자기만의 체크포인트를 가지고 독립적으로 진행**한다. 한 소스가 늦어도 다른 소스는 계속 흐른다.

> **핵심 통찰 — "테이블 = 플로우 하나가 아니다. 이 분리가 SDP의 표현력을 만든다"**
>
> 대부분의 ETL 도구는 "출력 테이블 하나 = 잡 하나"를 전제한다. 그래서 여러 소스를 한 테이블에 모으려면 **먼저 합쳐서(union) 한 덩어리로 만들어야** 하고, 그러면 소스 하나가 실패할 때 전체가 멈추며, 소스를 추가할 때 기존 쿼리를 수정해야 한다.
>
> SDP는 **데이터셋(무엇이 존재해야 하는가)과 플로우(어떻게 채우는가)를 분리**했다. 그래서 하나의 테이블을 N개의 독립적인 플로우가 채울 수 있고, 각각이 자기 체크포인트를 갖는다.
>
> 실무에서 이게 빛나는 지점: **점진적 마이그레이션.** 레거시 소스와 신규 소스를 같은 대상 테이블에 각각의 플로우로 붙여두고, 레거시가 끝나면 그 플로우만 제거하면 된다. 하류(下流)는 아무것도 모른 채 계속 동작한다. "한 테이블에 여러 입력"을 자연스럽게 표현할 수 있느냐가 파이프라인 진화 비용을 크게 좌우한다.

## 8. 파이프라인 정의와 실행 — `spark-pipeline.yml`과 CLI

### 8.1 프로젝트 스펙

파이프라인 루트에 `spark-pipeline.yml`을 둔다. CLI는 현재 디렉터리부터 상위로 올라가며 이 파일을 찾는다.

```yaml
name: retail_pipeline

libraries:                      # 변환 소스 파일 위치 (.py / .sql)
  - glob:
      include: transformations/**

storage: /data/checkpoints      # 체크포인트 저장 디렉터리 (스트리밍 테이블용)

catalog: my_catalog             # (선택) 기본 출력 카탈로그
database: retail_db             # (선택) 기본 출력 데이터베이스 (schema로도 씀)

configuration:                  # (선택) Spark 설정
  spark.sql.shuffle.partitions: "1000"
```

`name`, `libraries`, `storage`가 필수다. `storage`가 필수인 이유가 의미심장하다 — **증분 처리에 필요한 상태를 어디에 둘지가 파이프라인 정체성의 일부**이기 때문이다. 이 디렉터리를 날리면 모든 스트리밍 테이블이 처음부터 다시 읽는다.

### 8.2 CLI

```bash
# 프로젝트 뼈대 생성
spark-pipelines init --name my_pipeline

# 검증만 (데이터 접근 없음)
spark-pipelines dry-run

# 실행 — 기본은 증분
spark-pipelines run

# 특정 스펙 파일 지정
spark-pipelines run --spec /path/to/my-pipeline.yaml

# 특정 데이터셋만 전체 재처리 (데이터·체크포인트 초기화)
spark-pipelines run --full-refresh orders,customers

# 전체 재처리
spark-pipelines run --full-refresh-all

# 데이터는 유지하고 갱신만
spark-pipelines run --refresh orders,customers

# 원격 Spark Connect 서버로
spark-pipelines run --remote sc://my-cluster:15002

# spark-submit 인자를 그대로 받는다 (--class 제외)
spark-pipelines run --conf spark.sql.shuffle.partitions=200 --driver-memory 4g
```

### 8.3 refresh 의미론 — 헷갈리면 사고 난다

| 플래그 | 하는 일 | 언제 |
|---|---|---|
| (없음) | **증분 갱신.** 새 데이터만 처리 | 평시 운영 |
| `--refresh <목록>` | 기존 데이터를 **지우지 않고** 갱신 | 일반 갱신 |
| `--full-refresh <목록>` | 해당 데이터셋의 **데이터와 체크포인트를 초기화**하고 처음부터 재계산 | 로직을 바꿨을 때 |
| `--full-refresh-all` | **전체 그래프 초기화** | 최후의 수단 |

`--full-refresh-all`은 `--full-refresh`/`--refresh`와 **함께 못 쓴다.** `--full-refresh`와 `--refresh`는 서로 다른 데이터셋에 대해 조합할 수 있다.

주의할 점: **`--full-refresh`는 데이터를 지운다.** 변환 로직을 고쳐서 과거분까지 다시 계산해야 할 때 필요한 명령이지만, 대상 테이블이 원본 데이터의 유일한 사본이라면(예: 이미 사라진 Kafka 토픽에서 적재한 브론즈 테이블) **복구 불가능한 손실**이 된다. 운영에서 이 플래그를 칠 땐 항상 "이 데이터를 다시 만들 수 있나?"를 먼저 물어야 한다.

## 9. 제약 — 여기서 대부분 넘어진다

SDP 코드에는 일반 Spark 코드와 다른 규칙이 있다. 모르면 반드시 걸린다.

### 9.1 데이터셋 함수 안에서 하면 안 되는 것

**SDP는 계획·실행 과정에서 파이프라인 코드를 여러 번 평가한다.** 그래서 데이터셋 정의 함수는 **순수해야** 하고, DataFrame만 반환해야 한다.

절대 쓰면 안 되는 것:

| 금지 | 이유 |
|---|---|
| `collect()`, `count()`, `toPandas()` | **액션.** 계획 단계마다 실행돼 성능이 무너지고, 결과에 따라 그래프가 달라지면 비결정적이 된다 |
| `save()`, `saveAsTable()`, `toTable()`, `start()` | **쓰기는 프레임워크의 일이다.** 직접 쓰면 이중 기록이 된다 |
| `pivot()` | 스키마가 **데이터에 따라 결정**되므로 그래프를 미리 확정할 수 없다 |

SQL에서도 **`PIVOT` 절은 지원되지 않는다.** 같은 이유다.

이 규칙들은 하나의 원리에서 나온다. **SDP는 실행 전에 전체 그래프와 스키마를 알아야 한다.** 데이터를 읽어봐야 구조가 정해지는 연산은 그 전제를 깬다.

### 9.2 반복문으로 데이터셋을 생성할 때

```python
for region in ["us", "eu", "apac"]:
    @dp.materialized_view(name=f"sales_{region}")
    def _(region=region) -> DataFrame:
        return spark.table("sales").filter(f"region = '{region}'")
```

이 패턴 자체는 가능하지만, **루프의 값이 항상 안정적(additive)이어야 한다.** 목록이 실행할 때마다 달라지면(예: DB에서 조회해서 만든 목록) 그래프가 매번 바뀌어 데이터셋이 사라졌다 나타났다 한다. 목록은 **설정 파일이나 상수**에서 오게 하고, 항목은 **추가만** 하는 게 안전하다.

### 9.3 싱크의 제약

파이프라인 결과를 Kafka 같은 외부로 내보내는 싱크를 정의할 수 있다.

```python
dp.create_sink(
    name="kafka_sink",
    format="kafka",
    options={"kafka.bootstrap.servers": "localhost:9092", "topic": "processed_orders"},
)

@dp.append_flow(target="kafka_sink")
def kafka_orders_flow() -> DataFrame:
    return (spark.readStream.table("customer_orders")
        .select(col("order_id").cast("string").alias("key"),
                to_json(struct("*")).alias("value")))
```

단, 제약이 뚜렷하다.

- **Python API 전용** — SQL로는 정의할 수 없다
- **스트리밍 + append 플로우만** 지원
- **append-only 의미론** — full refresh는 체크포인트를 초기화할 뿐, **이미 외부로 내보낸 결과를 되돌리지 않는다**

마지막 항목이 중요하다. 외부 시스템으로 나간 것은 프레임워크가 회수할 수 없다. 싱크를 쓰는 파이프라인에서 `--full-refresh`를 돌리면 **같은 데이터가 두 번 나간다.** 수신 측 멱등성을 우리가 설계해야 한다.

## 10. 오픈소스 SDP vs Databricks Lakeflow — 경계선은 어디인가

실무에서 가장 자주 받는 질문이다. Databricks의 **Lakeflow Declarative Pipelines**는 SDP 위에 만들어졌고, 성능 최적화된 Databricks Runtime에서 돌며, OSS SDP와 **상호 운용**된다.

2026년 8월 기준 경계선은 대략 이렇다.

| | **오픈소스 SDP** (Apache Spark 4.1+) | **Databricks Lakeflow** |
|---|---|---|
| 선언형 Python/SQL 저작 | ✅ | ✅ |
| 스트리밍 테이블 / 구체화 뷰 | ✅ | ✅ |
| 자동 의존성 해석·오케스트레이션 | ✅ | ✅ |
| 다중 플로우, 싱크 | ✅ | ✅ |
| **Auto CDC (SCD Type 1)** | ✅ **Spark 4.2에서 진입** | ✅ |
| **Auto CDC (SCD Type 2, 스냅샷 기반)** | ❌ | ✅ |
| **데이터 품질 expectations** | ❌ | ✅ |
| **조회 가능한 이벤트 로그** | ❌ | ✅ |
| **연속(continuous) 모드** | ❌ | ✅ |
| `foreachBatch` 싱크, update 플로우 | ❌ | ✅ |
| 서버리스 컴퓨트, UI, Unity Catalog 통합 | ❌ | ✅ |

여기서 **expectations**는 특히 아쉬운 항목이다. 행 단위로 참/거짓 SQL 식을 걸어 위반 시 정책(경고 / 행 폐기 / 파이프라인 실패)을 정하고, 결과를 이벤트 로그에 지표로 남기는 기능이다. 선언형 파이프라인에서 품질 검증을 **파이프라인 정의의 일부**로 표현할 수 있게 해주는 핵심 기능인데, 아직 오픈소스에는 없다.

> **핵심 통찰 — "오픈소스 경계선은 고정된 게 아니라 이동 중이다 — 그래서 '어느 쪽인가'보다 '이동 방향'을 봐야 한다"**
>
> Auto CDC를 보자. 기증 직후엔 명백히 Databricks 전용 기능이었다. 그런데 **Spark 4.2에서 SCD Type 1이 오픈소스로 넘어왔다.** 상용에 남은 건 Type 2와 스냅샷 기반이다.
>
> 이건 우연이 아니라 **관측 가능한 패턴**이다. Databricks는 DLT 코어를 통째로 기증했고, 이후 릴리스마다 상용 기능을 하나씩 상류로 올리고 있다. 상용 쪽은 **운영 편의(서버리스, UI, 이벤트 로그, 모니터링)**와 **최신 기능의 선행 제공**으로 차별화하는 방향이다.
>
> 기술 선택에 주는 함의가 크다. **"지금 오픈소스에 없다"를 영구적 제약으로 가정하면 안 된다.** expectations 하나 때문에 아키텍처를 뒤집기보다는, 없는 기간 동안의 우회로(별도 검증 단계, 품질 테이블)를 만들어두고 이식성을 유지하는 편이 낫다. 반대로 **"곧 오픈소스로 올 것"에 일정을 거는 것도 위험**하다. 시점은 아무도 보장하지 않는다.
>
> 실무 판단은 이렇게 정리된다. **저작 계층(테이블 정의, 변환 로직)은 표준 SDP 문법을 지켜 이식성을 확보하고, 운영 계층(모니터링, 스케줄링, 품질 게이트)은 플랫폼 것을 쓴다.** 종속은 운영 계층에서만 발생하고, 그건 대체로 감수할 만한 종속이다.

## 11. dbt·Airflow와는 무슨 관계인가

SDP를 소개하면 반드시 나오는 질문이다. 계층을 나눠 보면 명확하다.

```
  [스케줄링·외부 시스템 연동]  ← Airflow / Databricks Jobs
           │  "매일 3시에 이 파이프라인을 돌려라"
           │  "파이프라인 끝나면 API를 호출하고 슬랙에 알려라"
           ▼
  [파이프라인 내부 오케스트레이션]  ← SDP  ★
           │  "silver 다음 gold, 무관한 건 병렬로"
           │  "증분이냐 재계산이냐, 체크포인트는 어디에"
           ▼
  [실행 엔진]  ← Spark
```

- **SDP는 Airflow를 대체하지 않는다.** Airflow는 파이프라인 **바깥**을 조율한다 — 언제 시작할지, 외부 시스템과 어떻게 엮일지, 파이프라인 여러 개를 어떤 순서로 돌릴지. SDP는 파이프라인 **안**의 테이블 간 순서를 맡는다. 다만 SDP가 안쪽을 가져가면서 **Airflow DAG가 극적으로 단순해진다.** 테이블마다 태스크를 만들던 DAG가 "파이프라인 실행" 태스크 하나가 된다.
- **dbt와는 겹치는 면이 있다.** 둘 다 "테이블을 SELECT로 정의하고 의존성을 자동 유도한다"는 모델을 공유한다. 차이는 **스트리밍**이다. dbt는 배치 SQL 변환 도구이고, SDP는 **배치와 스트리밍을 같은 모델 안에서** 다룬다(`FROM` vs `FROM STREAM`). 또 dbt는 웨어하우스에 SQL을 밀어 넣는 방식이라 엔진 중립적인 반면, SDP는 Spark에 밀착돼 있어 Python UDF·Kafka 소스 같은 걸 자연스럽게 쓴다.

정리하면, **인제스트와 스트리밍이 섞인 파이프라인은 SDP가, 웨어하우스 위의 순수 배치 SQL 변환은 dbt가** 더 편한 경우가 많고, 둘을 함께 쓰는 구성도 드물지 않다.

## 12. 정리 & SI 관점의 시사점

**정리:**

- SDP는 **"어떤 테이블이 존재해야 하는가"만 선언**하면 엔진이 의존성 그래프·실행 순서·병렬화·증분 처리·체크포인트를 맡는 프레임워크다. **의존성을 사람이 적지 않는다**는 게 본질이다.
- Databricks가 2022년 DLT로 만든 것을 **2025년 Data + AI Summit에서 Apache Spark에 기증**했고, **Spark 4.1에 정식 탑재**됐다. 벤더 중립이다.
- 어휘는 넷: **파이프라인**(실행 단위), **플로우**(처리 로직, 진짜 기본 단위), **스트리밍 테이블**(증분), **구체화 뷰**(재계산).
- **스트리밍 테이블 vs 구체화 뷰**는 성능이 아니라 **"과거 행이 바뀔 수 있는가"**로 고른다. 인제스트는 스트리밍 테이블, 집계는 구체화 뷰. **한 파이프라인에 섞는 게 정상.**
- **데이터셋과 플로우가 분리**돼 있어, 하나의 테이블을 여러 개의 독립 플로우가 채울 수 있다(각자 체크포인트 보유). 점진적 마이그레이션에 강하다.
- Python(`@dp.table` / `@dp.materialized_view` / `@dp.temporary_view` / `@dp.append_flow`)과 SQL(`CREATE STREAMING TABLE` / `CREATE MATERIALIZED VIEW` / `CREATE FLOW`)을 **한 파이프라인에서 섞어 쓸 수 있다.** SQL에선 `FROM STREAM`이 증분 읽기를 뜻한다.
- 실행은 `spark-pipeline.yml` + `spark-pipelines` CLI. **`dry-run`은 데이터 접근 없이 문법·분석·그래프 오류를 잡는다** — CI 필수.
- 제약의 뿌리는 하나: **실행 전에 그래프와 스키마가 확정돼야 한다.** 그래서 `collect`/`count`/`toPandas`/`pivot`/직접 쓰기가 금지된다.
- **오픈소스와 상용의 경계는 이동 중이다.** Auto CDC(SCD Type 1)는 Spark 4.2에서 오픈소스로 넘어왔고, expectations·이벤트 로그·연속 모드·SCD Type 2는 아직 Databricks 쪽에 있다.

**우리 SI 프로젝트에 주는 시사점 (토론 포인트):**

- **선언형은 산출물의 성격을 바꾼다.** 명령형 파이프라인의 인수인계 산출물은 "코드 + 이 코드를 어떤 순서로 돌리는지 설명한 문서"인데, 문서는 반드시 낡는다. SDP에서는 **코드가 곧 순서**라 설명할 문서가 줄고 낡지도 않는다. 제안·인수인계 관점에서 이걸 명시적 이점으로 내세울 만하다.
- **저작은 표준 SDP 문법으로, 운영은 플랫폼 기능으로 — 이 선을 처음부터 그어두자.** Databricks에서 개발하더라도 테이블 정의와 변환 로직은 표준 SDP 범위를 지키면, 고객이 나중에 다른 Spark 환경을 검토할 때 **이식 가능성이 남는다.** "종속을 만들지 않았다"는 건 SI가 고객에게 줄 수 있는 강한 신뢰 신호다. 반대로 편의 기능을 깊게 쓰면 그만큼 이 카드를 잃는다는 것도 함께 인식해야 한다.
- **`dry-run`을 CI 게이트로 박자.** 파이프라인 코드는 실행 시간이 길어 "돌려봐야 아는" 오류가 비싸다. 테이블 오타·순환 의존·없는 컬럼을 PR 단계에서 수 초 만에 잡는 장치를 초기에 넣는 것이, 프로젝트 후반의 야간 배포 사고를 줄인다.
- **테이블 종류 선택을 설계 문서에 명시하자.** "이 테이블은 스트리밍 테이블 / 이건 구체화 뷰, 이유는 상류가 수정되는가"를 표로 남기면, 나중에 합류한 사람이 잘못된 선택을 하는 걸 막는다. 이건 성능 문서가 아니라 **정합성 문서**다 — 잘못 고르면 답이 틀리기 때문이다.
- **`--full-refresh`의 권한과 절차를 정해두자.** 이 명령은 데이터를 지운다. 원본이 이미 사라진 소스(보존 기간 지난 Kafka 토픽 등)에서 적재한 테이블이라면 **복구 불가능**하다. 누가 칠 수 있는지, 치기 전에 무엇을 확인하는지를 운영 절차에 넣어야 한다.
- **차별화 지점**: SDP를 쓸 줄 아는 것보다, **"어느 단계를 스트리밍 테이블로 하고 어느 단계를 구체화 뷰로 할지"를 데이터의 성질로부터 근거 있게 설명하는 것**이 실력으로 읽힌다. 그리고 오픈소스/상용 경계를 정확히 알고 **"이건 표준 기능이라 이식 가능, 이건 플랫폼 기능이라 종속"**을 구분해 말해줄 수 있는 것이 신뢰를 만든다.

> **토론거리:** 우리 파이프라인에서 **명령형으로 남겨야 할 구간이 있는가?** SDP의 제약(계획 단계에서 그래프 확정, 액션 금지, `PIVOT` 불가)에 걸리는 로직이 있다면, 그 부분만 별도 잡으로 빼고 나머지를 선언형으로 갈 것인가 아니면 전체를 명령형으로 유지할 것인가? 그리고 **데이터 품질 검증을 어디서 할 것인가** — 오픈소스 SDP에 expectations가 없는 지금, 플랫폼 기능을 쓸 것인가(종속 감수) 아니면 별도 검증 단계를 파이프라인에 넣을 것인가(이식성 유지)?
