## Q1. 데이터에 개인정보·민감정보가 포함되나요? 마스킹·암호화 요건이 있나요?

### 들은 답

- 개인정보의 정의는 **개인을 식별할 수 있는 정보**다.
- 우리 프로젝트는 **금융권과 같은 레벨**로 보안을 관리한다.
- **보수적으로 아이디(`mem_id`)도 개인정보에 포함**해서 다룬다.
- 마스킹에는 동적/정적이 있는데, **우리는 정적 마스킹**이다.
- **내부망**에서는 Redshift에서 `mem_id`를 받아 조회가 된다. 다운로드는 막혀 있고, PM님이 만들어두신 앱으로만 예외적으로 받을 수 있으며 **이력을 반드시 남겨야** 한다. **외부망에서는 아예 보이지 않는다.**
- `mem_id`는 **SHA-256 + salt**로 단방향 암호화한다. salt를 붙이면 **딕셔너리 어택으로 매칭되지 않는다.**

여섯 줄이지만, 이 안에 **법·조직·아키텍처·암호학**이 전부 들어 있다. 하나씩 푼다.

### 1) "개인을 식별할 수 있는 정보" — 이 한 줄이 왜 어려운가

개인정보보호법이 말하는 개인정보는 대략 세 갈래다.

| 유형 | 정의 | 예 |
|---|---|---|
| **그 자체로 식별되는 정보** | 단독으로 개인을 알아볼 수 있음 | 성명, 주민등록번호, 휴대폰번호, 이메일 |
| **결합하면 식별되는 정보** | 다른 정보와 **쉽게 결합**하여 알아볼 수 있음 | 회원ID, 사번, 기기ID, 상세 주소+생년 |
| **가명정보** | 추가 정보 없이는 못 알아보게 처리한 것. **여전히 개인정보다** | 해시된 `mem_id` |

초보자가 가장 많이 틀리는 지점이 **두 번째 줄**이다. `mem_id = 8813204`는 그 자체로는 숫자일 뿐이다. 하지만 회원 마스터 테이블과 조인하는 순간 이름·전화번호가 나온다. 그리고 그 조인은 **우리 회사 안에서 아주 쉽다.** 법이 말하는 "쉽게 결합"이 바로 이 상태다.

그래서 PM님이 "**보수적으로** 아이디도 포함"이라고 하신 것이다. 이건 과잉 대응이 아니라 정의에 충실한 판단이다. 실무 감각으로 정리하면 이렇다.

> **판단 규칙**: "이 컬럼만 보면 누군지 모른다"는 근거가 되지 않는다. **"우리 회사 안의 다른 테이블과 조인했을 때 누군지 아는가"**를 물어야 한다. 대부분의 ID 컬럼은 여기서 걸린다.

여기에 더해 법은 더 강한 보호를 요구하는 두 부류를 따로 둔다.

- **고유식별정보** — 주민등록번호, 여권번호, 운전면허번호, 외국인등록번호. 법령상 **암호화 저장 의무**가 있다.
- **민감정보** — 사상·신념, 노동조합 가입, 정치적 견해, 건강, 성생활, 유전정보, 범죄경력 등. 원칙적으로 처리 금지이고, 별도 동의가 있어야 한다.

`개인정보의 안전성 확보조치 기준`(개인정보보호위원회 고시)은 **비밀번호·바이오정보·고유식별정보를 안전한 알고리즘으로 암호화해 저장**하도록 하고, 그중 **비밀번호는 복호화되지 않는 일방향 암호화**를 요구한다. (조문은 개정이 잦으니 실제 요건은 국가법령정보센터의 최신 고시를 확인하는 게 맞다.)

> **핵심 통찰 — "개인정보인지 아닌지는 컬럼을 보고 정하는 게 아니라, 그 컬럼이 놓인 맥락을 보고 정한다"**
>
> 같은 `birth_ym` 컬럼이라도, 회원ID와 함께 있으면 개인정보고, 100만 명 집계 테이블에 통계값으로만 있으면 아니다. **컬럼 이름으로 자동 판정하는 규칙은 반드시 틀린다.**
>
> 실무적 함의: 데이터 카탈로그에 **컬럼 단위 분류 태그**를 붙이는 작업이 왜 필수인지가 여기서 나온다. 판단은 사람이 한 번 하고, 그 판단을 메타데이터로 남겨야 파이프라인이 자동으로 처리할 수 있다. Unity Catalog에서 태그를 지원하는 이유이기도 하다.

### 2) 금융권 레벨이라는 말의 무게

"금융과 같은 레벨로 관리한다"는 건 단순히 "빡세게 한다"가 아니다. 적용되는 규제 세트가 달라진다는 뜻이다.

| 축 | 일반 개인정보처리자 | 금융권 수준 |
|---|---|---|
| 근거 | 개인정보보호법 + 안전성 확보조치 기준 | + 신용정보법, 전자금융거래법, **전자금융감독규정** |
| 망 | 접근통제 중심 | **망분리**(업무망/인터넷망 물리·논리 분리) |
| 접속기록 | 보관 의무 | **더 긴 보관 + 정기 점검 의무** |
| 반출 | 정책에 따름 | **원칙 금지 + 예외 승인 + 이력** |
| 암호화 | 대상 지정 | **저장·전송·처리 전 구간** |

PM님 답변의 뒷부분(내부망·다운로드 차단·이력)은 전부 이 표의 오른쪽 열에서 나온 것이다. 즉 **"보안 정책이 까다롭다"가 아니라 "규제가 그렇게 요구한다"**가 정확한 인과다. 이걸 알면 통제를 우회할 방법을 찾는 대신 통제 안에서 일하는 방법을 찾게 된다.

### 3) 마스킹 — 동적과 정적의 진짜 차이

**마스킹(masking)** 은 값을 알아볼 수 없게 가리는 것이다. `010-1234-5678` → `010-****-5678`처럼. 핵심은 **언제 가리느냐**다.

```
[동적 마스킹]  원본을 그대로 저장하고, "읽을 때" 권한에 따라 가린다

   저장소                        조회
   ┌───────────────┐             ┌─ 관리자 → 010-1234-5678  (원본)
   │ 010-1234-5678 │ ─── 정책 ──▶│
   │  (원본 그대로)│             └─ 분석가 → 010-****-****  (가려짐)
   └───────────────┘

[정적 마스킹]  저장하는 시점에 물리적으로 바꿔서 넣는다  ← 우리 프로젝트

   원천                 변환(적재 시)          저장소
   ┌──────────────┐    ┌──────────────┐    ┌───────────────┐
   │ 010-1234-5678│───▶│ mask()/hash()│───▶│ 010-****-**** │
   └──────────────┘    └──────────────┘    │ (원본이 없음) │
                                           └───────────────┘
```

| | 동적 마스킹 | **정적 마스킹 (우리)** |
|---|---|---|
| 원본 저장 | **저장소에 원본이 있다** | **저장소에 원본이 없다** |
| 가리는 시점 | 쿼리 실행 시 | 적재(ETL) 시 |
| 되돌리기 | 권한만 있으면 가능 | **불가능** (그게 목적) |
| 저장소 유출 시 | **원본이 통째로 샌다** | 마스킹된 값만 샌다 |
| 우회 위험 | 파일 직접 읽기, 권한 설정 실수 | 낮음 |
| 정책 변경 | 즉시 반영 | **재적재 필요** |
| 구현 위치 | 카탈로그/DB 정책 | 파이프라인 코드 |

Databricks에서 동적 마스킹은 Unity Catalog의 **컬럼 마스크(column mask)** 와 **행 필터(row filter)** 로 구현한다. 개념을 잡아두면 좋으니 형태만 봐두자.

```sql
-- 1) 마스킹 함수를 만든다: 특정 그룹이면 원본, 아니면 가린 값
CREATE OR REPLACE FUNCTION gov.mask_phone(phone STRING)
RETURN CASE
  WHEN is_account_group_member('pii_readers') THEN phone
  ELSE regexp_replace(phone, '(?<=^\\d{3}-)\\d{4}', '****')
END;

-- 2) 컬럼에 정책으로 붙인다. 테이블 이름도 쿼리도 그대로 쓴다
ALTER TABLE silver.member ALTER COLUMN phone SET MASK gov.mask_phone;
```

`is_account_group_member()`는 **"지금 이 쿼리를 던진 사람이 그 그룹인가"**를 묻는 함수다. 정책은 카탈로그에 저장되고 자동으로 적용되므로, 사용자가 `SELECT phone FROM silver.member`를 그냥 실행해도 권한에 따라 다른 값이 나온다.

그런데 우리는 **정적**을 골랐다. 왜 그게 더 보수적인 선택인가?

동적 마스킹의 안전성은 **"접근 통제가 완벽하다"는 전제** 위에 서 있다. 권한 그룹을 잘못 넣으면, 정책 없는 새 뷰를 누가 만들면, 스토리지 경로를 직접 읽으면 — 전부 뚫린다. 원본이 거기 있기 때문이다. 반면 정적 마스킹은 **원본이 아예 없으므로 뚫릴 원본이 없다.** 통제의 신뢰도를 사람과 설정에 의존하지 않는 쪽으로 옮긴 것이다.

대가도 분명하다. **되돌릴 수 없다.** "3개월 뒤 원본 전화번호가 필요해졌다"가 되면 방법은 원천에서 다시 당기는 것뿐이다. 그래서 정적 마스킹을 쓸 땐 **무엇을 남기고 무엇을 버릴지를 설계 단계에서 확정**해야 한다.

> **핵심 통찰 — "정적 마스킹은 기술 선택이 아니라 신뢰 모델의 선택이다"**
>
> 동적 마스킹은 "저장소는 안전하다, 접근 통제만 제대로 하면 된다"고 가정한다. 정적 마스킹은 **"저장소도 언젠가 샐 수 있다"**고 가정한다.
>
> 이 가정의 차이가 곧 규제 수준의 차이다. 금융권이 정적을 선호하는 이유는 동적이 기술적으로 열등해서가 아니라, **사고가 났을 때 "우리는 원본을 갖고 있지 않았습니다"라고 말할 수 있는지**가 사후 책임을 완전히 바꾸기 때문이다.
>
> 그래서 이 선택은 데이터 엔지니어가 혼자 뒤집으면 안 된다. "동적으로 하면 나중에 편한데요"는 기술적으로는 맞고 **계약적으로는 틀린** 제안이다.

### 4) 단방향 vs 양방향 암호화 — 왜 `mem_id`는 단방향인가

먼저 용어를 정리한다.

| | **단방향 (해시)** | **양방향 (암호화)** |
|---|---|---|
| 되돌리기 | **불가능** | 키가 있으면 가능(복호화) |
| 대표 알고리즘 | SHA-256, SHA-3, bcrypt, Argon2 | AES-256(대칭), RSA(비대칭) |
| 키 관리 | salt/키 보관 | **키 보관이 생명** |
| 같은 입력 → 같은 출력 | 예 (결정적) | 보통 아니오 (IV/nonce로 매번 다름) |
| 쓰는 곳 | 비밀번호, **가명화된 조인 키** | 원본이 다시 필요한 값(주소, 계좌) |

`mem_id`를 단방향으로 처리하는 논리는 이렇다.

우리가 `mem_id`로 하는 일은 두 가지다 — **① 같은 사람의 행을 묶는 것(조인·집계)**, **② 그 사람이 누구인지 아는 것.** 데이터 분석 파이프라인에 필요한 건 ①뿐이다. ②는 필요 없다.

그런데 양방향 암호화를 쓰면 ②를 할 수 있는 능력이 시스템에 남는다. **필요 없는 능력을 갖고 있는 것 자체가 위험**이다(키가 새면 전부 복원된다). 그래서 필요한 만큼만 남기는 단방향을 고른다. 최소 권한 원칙의 데이터 버전이다.

해시의 성질을 기초부터 보면 왜 이게 되는지 보인다.

```
SHA-256("8813204")
  = a3f1c9...  (256비트 = 64자리 16진수, 항상 같은 길이)

성질 1. 결정적    같은 입력 → 항상 같은 출력    ← 이것 덕분에 조인이 된다
성질 2. 일방향    출력 → 입력 복원 불가          ← 이것 덕분에 안전하다
성질 3. 눈사태    입력 1비트만 바뀌어도 출력이 완전히 달라진다
성질 4. 충돌저항  다른 입력이 같은 출력을 내기 어렵다
```

**성질 1이 곧 성질 2를 무너뜨린다**는 게 이 이야기의 핵심이다.

### 5) salt — "딕셔너리 어택으로 매칭이 안 된다"의 정확한 의미

해시는 되돌릴 수 없다. 하지만 공격자가 되돌릴 필요가 없다면?

`mem_id`가 8자리 숫자라고 하자. 가능한 값은 1억 개다. 공격자는 이렇게 한다.

```
for i in range(10**8):
    table[ sha256(str(i)) ] = i     # 1억 개를 전부 미리 계산해 표로 만든다
```

이제 유출된 해시값을 이 표에서 **찾기만 하면** 원본이 나온다. 되돌린 게 아니라 **답을 미리 다 계산해둔 것**이다. 이게 **딕셔너리 어택**(사전 공격)이고, 표를 압축해 저장하는 기법이 **레인보우 테이블**이다. 1억 개 SHA-256은 요즘 GPU로 **초 단위**다. 휴대폰 번호(약 1억)도, 주민번호(약 10억 미만, 규칙까지 있어 더 적다)도 전부 이 사정권이다.

> 식별자 공간이 좁으면 해시는 보호가 되지 않는다. 이건 SHA-256이 약해서가 아니라 **원본의 경우의 수가 적어서**다.

**salt**는 여기에 공격자가 모르는 문자열을 끼워 넣는다.

```
before:  sha256("8813204")                     → 미리 계산 가능
after:   sha256("8813204" + "kZ9!p_vQ2mR#7x")  → salt를 모르면 계산할 표가 없다
```

공격자가 표를 만들려면 salt를 알아야 하고, salt가 유출되지 않는 한 1억 개 표는 쓸모가 없다. PM님이 "salt를 하면 딕셔너리 어택으로 매칭이 안 된다"고 하신 게 이 뜻이다.

여기서 **초보자가 반드시 구분해야 할 두 가지 salt 용법**이 있다. 자료마다 salt를 다르게 설명해서 헷갈리는 지점이다.

| | **비밀번호 저장용 salt** | **가명화용 salt (우리 경우)** |
|---|---|---|
| 값 | **레코드마다 다름** | **전체가 동일** |
| 보관 | 해시 옆에 **같이 저장**(공개돼도 됨) | **절대 비밀** — 별도 보관 |
| 목적 | 같은 비밀번호가 같은 해시로 보이지 않게 | 사전 공격 차단 |
| 조인 | 필요 없음 | **가능해야 함** ← 그래서 값이 같아야 한다 |
| 정확한 이름 | salt | **pepper / 비밀 키**에 가깝다 |

우리는 `mem_id`로 조인을 해야 한다. 그러려면 같은 `mem_id`가 언제 어디서 해시돼도 같은 값이 나와야 하고, 따라서 **salt가 하나로 고정**돼야 한다. 그 순간 salt는 "공개돼도 되는 무작위 값"이 아니라 **"유출되면 전체가 뚫리는 비밀 키"**가 된다.

**그래서 이 설계의 급소는 SHA-256이 아니라 salt 보관이다.**

```python
# ❌ 절대 하면 안 되는 것 — Git에 영원히 남는다
SALT = "kZ9!p_vQ2mR#7x"

# ✅ 시크릿 스코프에서 읽는다. 노트북 출력에도 [REDACTED]로 가려진다
salt = dbutils.secrets.get(scope="pii", key="mem_id_salt")

df = (df
      .withColumn("mem_key", F.sha2(F.concat(F.col("mem_id"), F.lit(salt)), 256))
      .drop("mem_id"))          # ← 원본 컬럼을 반드시 버린다
```

세 가지를 더 짚어둔다.

1. **`concat` 대신 HMAC이 정석이다.** `sha256(값 + 키)` 형태는 길이 확장 공격(length-extension attack) 계열의 이론적 약점이 있다. 키를 쓰는 해시는 **HMAC-SHA256**이 표준이다. 우리 용도(짧은 ID의 가명화)에서 실질 위험은 낮지만, 새로 설계한다면 HMAC을 고르는 게 맞다.
2. **비밀번호였다면 SHA-256은 오답이다.** SHA-256은 **빠르라고** 만든 함수다. 비밀번호 저장에는 일부러 느린 **bcrypt / scrypt / Argon2 / PBKDF2**를 쓴다. "느린 게 기능"인 드문 경우다. `mem_id` 가명화는 대량 처리라 빠른 해시가 맞다 — **용도가 다르면 알고리즘도 다르다.**
3. **해시했다고 개인정보가 아니게 되지 않는다.** salt와 원본 매핑이 존재하는 한 재식별이 가능하므로, 이 데이터는 법적으로 **가명정보**다. 가명정보도 개인정보보호법의 적용을 받는다. "암호화했으니 자유롭게 써도 된다"는 흔하고 위험한 오해다.

> **핵심 통찰 — "해시는 데이터를 안전하게 만들지 않는다. 위험을 salt 한 곳으로 모을 뿐이다"**
>
> SHA-256 + salt를 적용하면 테이블 수백 개에 흩어져 있던 위험이 **salt 하나**로 집중된다. 이건 개선이다 — 지켜야 할 대상이 수백 개에서 하나로 줄었으니까.
>
> 동시에 **단일 실패 지점**이 생긴 것이기도 하다. salt가 새면 `mem_id` 공간이 좁은 만큼 전 데이터가 한 번에 복원된다. 그러니 다음 질문은 자연스럽게 이렇게 이어져야 한다.
>
> **"salt는 누가 관리하고, 어디에 저장되며, 교체(rotation)한 적이 있나요? 교체하면 기존 해시와 조인이 깨지는데 그건 어떻게 처리하나요?"** ← 이게 오늘 배운 걸로 만들 수 있는 다음 질문이다.

### 6) 망분리 — 통제의 목적은 차단이 아니라 추적이다

PM님 답변의 마지막 축이다.

```
    [외부망 / 인터넷]                    [내부망 / 업무망]
    ─────────────────                    ──────────────────
    mem_id 자체가 보이지 않음      │     Redshift에서 mem_id 조회 가능
                                   │     화면으로는 볼 수 있음
                                   │     ┌────────────────────┐
                                   │     │ 다운로드: 차단     │
                                   │     │  └ 예외: 전용 앱   │
                                   │     │     → 이력 필수    │
                                   │     └────────────────────┘
```

여기서 배울 게 하나 있다. **"다운로드를 막았다"가 통제의 끝이 아니라는 것.** 완전히 막으면 업무가 안 돌아가므로 예외 경로가 반드시 생긴다. 그래서 진짜 설계는 이렇게 된다.

1. 기본 경로는 **막는다**.
2. 예외는 **한 곳으로만** 낸다 (그 전용 앱).
3. 그 한 곳에서 **누가·언제·무엇을·왜** 가져갔는지 남긴다.

**통제의 본질은 "못 하게 하는 것"이 아니라 "한 경로로 모아서 전부 기록하는 것"**이다. 사고가 났을 때 답할 수 있어야 하는 질문이 "막았습니까?"가 아니라 "누가 가져갔습니까?"이기 때문이다.

그래서 PM님이 "**이력을 잘 남겨야 한다**"고 하신 말은 절차적 잔소리가 아니다. 그 이력이 없으면 그 반출은 **정책 위반**이 된다. 내가 실제로 지켜야 할 규칙은 이것 하나다.

### 7) Databricks에서 내가 당장 조심할 것 (체크리스트)

법과 정책을 코드 레벨로 내리면 이렇게 된다. 전부 신입이 실제로 사고 내는 지점이다.

- [ ] **노트북 셀 출력에 원본이 박제된다.** `display(df)`, `df.show()` 결과는 노트북에 **저장**된다. Git에 커밋되면 PII가 리포지토리에 영구히 남는다. → 원본 컬럼은 확인 후 **셀 출력을 지우고 커밋**한다.
- [ ] **에러 메시지·로그에 값이 섞인다.** `raise ValueError(f"invalid mem_id: {mem_id}")` 같은 코드가 로그를 통해 PII를 유출한다.
- [ ] **샘플 CSV를 리포지토리에 넣지 않는다.** 테스트 픽스처는 합성 데이터로 만든다.
- [ ] **원본 컬럼을 `drop`했는지 확인한다.** 해시 컬럼을 추가만 하고 원본을 남겨두면 정적 마스킹이 아니다.
- [ ] **Bronze 계층 정책을 확인한다.** "Bronze는 원본 그대로"라는 일반론과 "원본을 저장하지 않는다"는 정책이 충돌한다. **우리 프로젝트는 어느 쪽인가**는 반드시 물어봐야 한다.
- [ ] **캐시·체크포인트·임시 테이블에도 원본이 남는다.** 스트리밍 체크포인트, `_delta_log`, `VACUUM` 전 이전 버전 파일까지 포함해서 본다.
- [ ] **시간여행(time travel)이 삭제를 무력화한다.** Delta 테이블에서 컬럼을 지워도 이전 버전을 조회하면 나온다. 실제 제거는 `VACUUM` 이후다.

마지막 두 항목은 특히 반직관적이라 따로 물어볼 가치가 있다.

## Q2. Jira 이슈 티켓 만드는 컨벤션이 있나요?

### 들은 답

> 컨벤션은 PM님과 수석님이 관리하시고, **개발자는 커밋할 때 이슈 ID만 넣으면 된다.**

### 이 답의 구조: 소유권과 접점의 분리

한 문장이지만 조직 설계가 들어 있다.

```
   [티켓 체계 설계·운영]              [개발자가 지켜야 할 것]
   PM · 수석                          나
   ────────────────────               ──────────────────────
   프로젝트/컴포넌트 구조             커밋 메시지에 이슈 ID
   이슈 타입 체계
   상태 워크플로
   에픽·스프린트 구성
   요구사항 추적 매트릭스
```

왜 이렇게 나누는가? SI 프로젝트에서 Jira는 **개발 도구가 아니라 관리 산출물**이기 때문이다. 티켓 구조가 곧 WBS이고, 공수 산정 근거이고, 고객 보고 자료이고, 요구사항 추적표다. 이건 프로젝트 관리자가 소유해야 하는 것들이다.

개발자에게 요구되는 건 딱 하나 — **추적성(traceability)**. 코드 변경과 요구사항을 연결하는 실 한 가닥. 그 실이 **커밋 메시지의 이슈 ID**다.

### 이슈 ID 한 줄이 만들어내는 것

`PROJ-123`을 커밋 메시지에 넣으면 이런 연쇄가 자동으로 생긴다.

```
  6개월 뒤: "이 마스킹 로직 왜 이렇게 짜여 있지?"

  git blame  →  커밋 abc1234  →  메시지의 PROJ-123  →  Jira 티켓
                                                        │
                     ┌──────────────────────────────────┘
                     ▼
        요구사항 원문 · 담당자 · 논의 코멘트 · 고객 승인 이력
```

이게 없으면 답은 "옛날에 누가 그렇게 했대요"에서 끝난다. 부가적으로 따라오는 것들도 있다.

- Jira 티켓 화면에서 **연결된 커밋·브랜치·PR이 자동으로 보인다** (Git 연동 시).
- 릴리스 노트를 커밋 로그에서 **자동 생성**할 수 있다.
- "이번 스프린트에 실제로 코드가 바뀐 티켓"을 기계적으로 뽑을 수 있다.

### 실무 포맷

팀 규칙이 최우선이지만, 일반적으로 통용되는 형태는 이렇다.

```bash
# 흔한 두 가지 — 팀이 쓰는 쪽을 따른다
PROJ-123 feat: 회원 ID 정적 마스킹 적용
feat(ingest): 회원 ID 정적 마스킹 적용 [PROJ-123]

# 브랜치 이름에도 넣으면 PR과 티켓이 자동 연결되는 경우가 많다
feature/PROJ-123-member-id-masking
```

Jira에는 **스마트 커밋(Smart Commits)** 이라는 기능도 있다. 커밋 메시지로 티켓을 조작한다.

```
PROJ-123 #comment 마스킹 로직 적용 완료 #time 3h #resolve
         └ 코멘트 추가        └ 작업시간 기록  └ 상태를 Resolved로
```

편리해 보이지만 **팀 합의 없이 쓰면 안 된다.** `#resolve`가 상태를 바꿔버리면, 티켓 상태로 진척을 보고하던 PM 입장에서는 "내가 안 옮겼는데 옮겨진 티켓"이 생긴다. **상태 전이는 관리자의 영역**이라는 게 오늘 들은 답의 핵심이었다는 걸 기억하자. 쓴다면 `#comment` 정도까지가 안전하다.

### 기초 — Jira 용어 최소 세트

처음이면 이 정도만 알면 대화가 된다.

| 용어 | 뜻 |
|---|---|
| **프로젝트 키** | `PROJ` 같은 접두사. 이슈 ID는 `키-번호` |
| **Epic** | 큰 덩어리의 목표. 여러 Story를 묶는다 |
| **Story / Task** | 실제 작업 단위. Story는 사용자 관점, Task는 실행 관점 |
| **Sub-task** | Task를 더 쪼갠 것 |
| **Bug** | 결함 |
| **워크플로** | `To Do → In Progress → In Review → Done` 같은 상태 흐름. 팀마다 다르다 |
| **스프린트** | 애자일에서 쓰는 고정 기간 단위. SI에서는 안 쓰는 곳도 많다 |

> **핵심 통찰 — "컨벤션이 없는 게 아니라, 내 접점이 하나로 좁혀져 있는 것이다"**
>
> "컨벤션 있나요?"에 "이슈 ID만 넣으면 된다"는 답이 오면, 초보자는 **"규칙이 느슨하구나"**로 오해하기 쉽다. 정반대다. 규칙은 촘촘하게 있고, **그중 개발자가 건드릴 수 있는 접점만 하나로 설계돼 있는 것**이다.
>
> 잘 설계된 프로세스의 특징이 이거다. 각 역할에게 **지켜야 할 것이 적게** 보인다. 적게 보이는 이유는 규칙이 없어서가 아니라 나머지를 다른 사람이 이미 흡수했기 때문이다.
>
> 그래서 실무적으로는 이렇게 행동하면 된다 — **티켓을 내가 만들어야 할 상황이 생기면 만들기 전에 물어본다.** 내 접점이 아닌 곳을 임의로 건드리는 게 이 구조에서 유일한 사고다.

## Q3. 배포가 실패하면 어디서 확인하나요? 로그는 어디서 보나요?

### 들은 답

- `databricks bundle deploy`는 **단순히 배포하는 명령**일 뿐이고, 실제 실행은 `run`을 해야 한다.
- `databricks bundle run`으로 **dry-run**을 할 수 있고, **UI에서 확인**할 수 있다.

### 이 답이 교정해준 것: deploy ≠ run

내 질문에는 잘못된 전제가 하나 깔려 있었다. **"deploy가 실패한다"** 안에 두 가지를 뭉뚱그린 것이다.

```
  로컬 databricks.yml
        │
        │  ① validate   YAML 문법·스키마가 맞나           (로컬에서 끝)
        │  ② plan       무엇이 생기고/바뀌고/지워지나      (워크스페이스 조회)
        ▼
  ③ deploy   파일 업로드 + 리소스 등록/갱신
        │              ↑ 여기까지가 "존재하게 만드는" 단계
        │                이 단계는 코드가 맞는지 전혀 모른다
        ▼
  ④ run      실제로 잡/파이프라인을 실행
                       ↑ 여기가 "일어나게 하는" 단계
                         비즈니스 로직 오류는 전부 여기서 난다
```

**배포가 성공했다는 건 "잡이 워크스페이스에 등록됐다"는 뜻이지, "그 잡이 돌아간다"는 뜻이 전혀 아니다.** SQL 오타, 없는 테이블, 권한 부족, 스키마 불일치 — 전부 deploy를 통과하고 run에서 터진다.

그래서 "실패를 어디서 보나"의 답도 둘로 갈린다.

| | **배포 실패 (deploy)** | **실행 실패 (run)** |
|---|---|---|
| 어디서 나나 | 내 터미널 | 워크스페이스 |
| 원인 | YAML 오류, 권한, 경로, 락, 네트워크 | 코드 오류, 데이터 오류, 리소스 부족 |
| 어디서 보나 | CLI 출력 / `--log-file` | **Workflows UI의 Job runs**, 파이프라인 UI |
| 흔한 증상 | `Error: cannot create job: ...` | 태스크가 빨간색, 스택트레이스 |

### 배포 실패를 파고들 때

CLI가 뱉는 한 줄로 부족하면 로그 레벨을 올린다.

```bash
# 배포 전 검증 — 여기서 걸리는 건 워크스페이스를 건드리기도 전이다
databricks bundle validate -t dev

# 무엇이 바뀔지 미리 본다 (운영 배포 전 필수)
databricks bundle plan -t prod

# 실패 원인이 안 보일 때: 디버그 로그를 파일로
databricks bundle deploy -t dev --log-level=debug --log-file=deploy.log

# 더 깊게 — 요청/응답까지 JSON으로
databricks bundle deploy -t dev --log-level=trace --log-format=json --log-file=trace.json
```

자주 만나는 배포 실패 원인 다섯 가지:

1. **권한** — 대상 경로나 카탈로그에 대한 권한이 없다. 서비스 프린시펄로 배포할 때 특히 자주 난다.
2. **경로** — `root_path`나 노트북 상대 경로가 어긋났다.
3. **스키마 오류** — YAML 필드 이름 오타. `validate`에서 대부분 잡힌다.
4. **배포 락** — 다른 배포가 진행 중이거나 이전 배포가 죽으면서 락이 남았다. (Q5에서 자세히)
5. **CLI 버전 차이** — 내 CLI와 CI의 CLI 버전이 달라 한쪽에서만 된다.

### 실행 실패를 볼 곳

워크스페이스 UI가 1차다. 계층을 알아두면 헤매지 않는다.

```
Workflows ─▶ Jobs ─▶ 해당 Job ─▶ Runs 탭 ─▶ 실패한 run 클릭
                                                │
                                                ├─ 태스크별 결과 (어느 태스크에서 죽었나)
                                                ├─ Output       (셀 출력, print, 예외 메시지)
                                                ├─ Logs         (stdout / stderr / log4j)
                                                └─ Spark UI     (스테이지·태스크·셔플, OOM 추적)

Pipelines ─▶ 해당 파이프라인 ─▶ Update 이력
                                  ├─ 그래프에서 실패한 데이터셋이 빨갛게
                                  ├─ 이벤트 로그 (기대 위반, 스키마 변경, 지표)
                                  └─ 데이터 품질 지표 (expectation 통과/실패 건수)
```

노트북 코드의 `print()`나 예외 메시지는 **Output**에, JVM/Spark 레벨의 문제(OOM, executor lost)는 **Logs의 log4j**에, 성능 문제는 **Spark UI**에 있다. 이 셋을 구분하지 못하면 매번 전부 뒤지게 된다.

### dry-run — 정확히 어디까지 되나

PM님이 말씀하신 dry-run은 **파이프라인**에 있는 기능이다.

```bash
# 파이프라인 검증 실행: 그래프·스키마·테이블/컬럼 참조를 확인하되
# 데이터는 적재하지 않는다
databricks bundle run my_pipeline --validate-only -t dev

# CLI 직접 호출 버전
databricks pipelines dry-run --pipeline-id <id>
```

무엇을 잡고 무엇을 못 잡는지 선을 그어두는 게 중요하다.

| dry-run이 잡는 것 | dry-run이 못 잡는 것 |
|---|---|
| 존재하지 않는 소스 테이블 | 데이터 값이 이상한 것 |
| 없는 컬럼 참조 | 조인 결과가 폭발하는 것 |
| 순환 의존성 | 성능·비용 문제 |
| SQL 파싱 오류 | 실제 스키마 진화 충돌 |

**잡(Job)에는 이런 dry-run이 없다.** 잡은 임의의 코드를 실행하므로 "실행하지 않고 검증"이 원리적으로 불가능하다. 그래서 잡의 리허설은 **dev 타깃에 배포해서 실제로 한 번 돌려보는 것**이 된다. 이게 `development` 모드가 존재하는 이유이기도 하다 — dev 배포는 리소스 이름에 사용자 접두사가 붙고 스케줄이 자동으로 꺼져서, 운영과 섞이지 않고 마음껏 돌려볼 수 있다.

```bash
databricks bundle deploy -t dev          # 내 전용 이름으로 배포됨
databricks bundle run my_job -t dev      # 실제 실행 (= 잡의 유일한 리허설)
databricks bundle summary -t dev         # 뭘 올렸는지 + UI 링크
databricks bundle open my_job -t dev     # 브라우저로 바로 열기
```

> **핵심 통찰 — "`deploy`는 명사를 만들고 `run`은 동사를 일으킨다"**
>
> `deploy`가 성공했다는 건 **"잡이라는 물건이 워크스페이스에 놓였다"**는 사실 하나뿐이다. 그 물건이 제대로 동작하는지에 대해서는 아무것도 말하지 않는다.
>
> 이걸 헷갈리면 **"배포 성공했으니 됐다"**고 보고했다가 다음날 새벽 스케줄에서 터진다. 초록불의 의미를 정확히 아는 게 CI/CD를 다루는 사람의 기본기다.
>
> 그래서 파이프라인의 최소 형태는 `deploy`가 아니라 **`validate → plan → deploy → run(스모크)`** 네 단계다. 마지막 `run`이 없으면 그 파이프라인은 "배포가 됐다"만 검증하는 파이프라인이다.

## Q4. terraform 엔진을 걷어내고 direct로 가는 최근 흐름의 영향도 있나요?

### 들은 답

> 앞으로는 direct로 한다. terraform 엔진은 이제 쓰지 않는다.

### 먼저: 왜 배포에 "엔진"이 필요한가

번들은 선언형이다. YAML에 "이런 잡이 있어야 한다"고 쓰면 CLI가 그 상태를 만든다. 그런데 이걸 실제로 하려면 매번 이 계산이 필요하다.

```
   원하는 상태(YAML)   vs   지금 워크스페이스 상태
            │                        │
            └────────  비교  ────────┘
                        │
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
   새로 만들기       고치기            지우기
```

이 "비교하고 결정하는 부분"이 **배포 엔진**이다. 그리고 이걸 하려면 **"내가 지난번에 무엇을 만들었는가"**를 기록한 상태 파일이 필요하다.

### terraform 엔진 → direct 엔진

Databricks는 처음에 이 어려운 부분을 **Terraform에 위임**했다. 합리적이었다 — 이미 검증된 엔진이 있는데 새로 만들 이유가 없다. CLI가 YAML을 Terraform 설정으로 변환하고, Terraform 바이너리와 Databricks Provider를 내려받아 실행했다. `.databricks/` 아래에 `terraform.tfstate`가 생기던 이유다.

대가가 있었다.

- 배포할 때마다 **Terraform과 provider를 다운로드**해야 한다 → **폐쇄망·프록시·사내 레지스트리 환경에서 자주 깨진다.** 한국 SI 현장에서 특히 아픈 지점이다.
- 느리다.
- 에러가 Terraform 용어로 나와서 디버깅이 어렵다.
- **provider가 지원하는 리소스만 쓸 수 있다.** ← 이게 뒤에서 중요해진다.

**direct 엔진**은 Terraform을 걷어내고 **Databricks Go SDK로 REST API를 직접 호출**한다.

| | Terraform 엔진 | **Direct 엔진** |
|---|---|---|
| 의존성 | Terraform + provider 다운로드 | **CLI 바이너리 하나로 완결** |
| 속도 | 기준 | **최대 40% 빠름** |
| 상태 파일 | `terraform.tfstate` | `resources.json` (자체 스키마) |
| 변경 미리보기 | 제한적 | `bundle plan`으로 **필드 단위 diff** |
| 지원 리소스 | provider 범위 | **더 넓다** (Genie 스페이스 등 포함) |

흐름은 이미 정해져 있다. CLI v0.279.0에서 direct가 등장했고, v1.3.0에서 GA + 신규 번들 기본값이 됐으며, 2026년 중반부터는 **기존 Terraform 번들을 배포 시 자동 마이그레이션**하는 방향이다. Terraform 백엔드는 폐기 예정이다. PM님 답변 그대로다.

전환은 한 줄이다.

```yaml
bundle:
  name: our_etl
  engine: direct        # (환경변수 DATABRICKS_BUNDLE_ENGINE=direct 도 가능. 설정이 우선)
```

이미 Terraform으로 배포한 번들은 상태 파일을 변환해야 한다.

```bash
databricks bundle deploy -t prod               # 1. 먼저 Terraform으로 완전 배포
databricks bundle deployment migrate -t prod   # 2. tfstate → resources.json 변환
databricks bundle plan -t prod                 # 3. 검증: "변경 없음"이 나와야 정상
databricks bundle deploy -t prod               # 4. 확정
```

**전환 후 반드시 알아야 할 동작 차이가 하나 있다.** YAML에서 필드를 지웠을 때:

- **Terraform 엔진**: 설정에서 뺀 필드는 **플랫폼의 기존 값이 유지**된다.
- **Direct 엔진**: 설정에서 뺀 필드는 **리소스 기본값으로 되돌아간다.**

Direct는 "로컬 설정 ↔ 직전 배포 스냅샷"을 비교하므로 사라진 필드를 **변경으로 인식**한다. 마이그레이션 직후 "왜 재시도 횟수가 초기화됐지?" 같은 일이 여기서 난다. 대응은 단순하다 — **유지하고 싶은 값은 전부 명시적으로 적는다.**

### 주석의 이유와 업계 흐름은 별개가 아니다

이제 내 질문으로 돌아온다. 주석에 적힌 이유(**Genie 스페이스**)와 업계 흐름(**Terraform 폐기**)은 서로 다른 두 개의 이유처럼 보인다. 그런데 파고들면 **같은 하나의 원인에서 갈라져 나온 두 얼굴**이다.

**Genie 스페이스**는 Databricks의 자연어 질의 인터페이스다. 현업 담당자가 SQL 대신 "지난달 지역별 매출 알려줘"라고 물으면, 지정된 테이블 집합과 설명·예시 쿼리를 근거로 답하는 기능이다. 데이터팀이 만든 테이블을 비개발자가 직접 쓰게 하는 통로라서, 요즘 프로젝트에서 산출물로 자주 들어간다.

그리고 **번들의 `genie_spaces` 리소스는 direct 엔진에서만 지원된다.** Terraform provider에 해당 리소스가 없기 때문이다. (Databricks 문서는 Genie 스페이스를 **"Genie 에이전트"**라고도 부르는데, 번들로 Genie 에이전트를 정의하는 건 direct 엔진에서만 가능하다고 명시하고 있다.)

```yaml
bundle:
  name: our_etl
  engine: direct          # ← genie_spaces를 쓰려면 선택이 아니라 필수

resources:
  genie_spaces:
    sales_genie:
      title: 매출 분석 Genie
      warehouse_id: ${var.warehouse_id}
      # ... 대상 테이블, 설명, 예시 쿼리 등
```

여기서 한 단계 더 들어가면 내 질문의 답이 나온다. **왜 Genie 스페이스는 direct에서만 지원되는가?**

Terraform provider에 리소스가 없기 때문인데, **앞으로도 추가되지 않을 것**이기 때문이다. Terraform 백엔드가 폐기 수순인 이상 신규 리소스는 direct 쪽에만 붙는다. 즉 인과는 이렇게 이어진다.

```
   [업계·제품 흐름]
   Databricks가 Terraform 백엔드를 걷어내기로 결정
            │
            ├─▶ Terraform provider에 신규 리소스를 더 추가하지 않는다
            │            │
            │            └─▶ genie_spaces 는 direct 엔진에만 존재
            │                         │
            │                         └─▶ [우리 주석] "genie space를 쓰므로 direct"
            │
            └─▶ direct가 신규 번들 기본값 · Terraform 번들은 자동 마이그레이션 예정
```

그래서 내 질문 **"그 흐름의 영향도 있는 건가요?"** 에 대한 답은 **"있다. 그런데 나란히 놓인 두 번째 이유가 아니라, 주석에 적힌 그 이유를 만들어낸 상위 원인이다"** 가 정확하다. PM님의 "앞으로는 direct로 한다, terraform은 이제 쓰지 않는다"는 답이 이 상위 원인을 그대로 확인해준 것이다.

이 구분이 실무에서 왜 의미가 있냐면, **되돌릴 수 있는 결정인지가 달라지기 때문**이다.

| 만약 이유가… | 그러면 |
|---|---|
| Genie 제약**만**이라면 | Genie를 안 쓰게 되면 Terraform으로 되돌릴 수 있다 |
| **제품 방향이 그쪽이라면** | Genie와 무관하게 되돌릴 이유가 없다. 되돌려도 곧 다시 와야 한다 |

6개월 뒤 누가 "폐쇄망 이슈 없는데 terraform으로 되돌리면 안 되나요?"라고 물으면, 답은 두 번째 줄이다.

> **핵심 통찰 — "기능이 한쪽에서만 지원된다는 사실 자체가 로드맵 신호다"**
>
> `genie_spaces`가 direct에서만 된다는 건 표면적으로는 **불편한 제약**이다. "왜 하필 이것만 안 되지"로 읽힌다.
>
> 하지만 벤더가 **신규 기능을 어느 쪽에만 붙이는가**는 그 벤더가 어느 쪽을 미래로 보는지에 대한 가장 정직한 신호다. 공식 블로그의 "권장합니다"보다 훨씬 강한 신호다 — 말이 아니라 **개발 리소스를 어디에 썼는가**이기 때문이다.
>
> 그래서 기술 선택을 할 때 볼 것이 하나 늘어난다. **"둘 다 되는가"가 아니라 "새로 나오는 것들이 어느 쪽에 붙고 있는가."** 지금 둘 다 되더라도, 신규 기능이 한쪽에만 붙고 있다면 나머지 한쪽은 이미 유지보수 모드다.
>
> 그리고 주석 쓰기의 교훈도 있다. 우리 주석은 **직접 제약(`genie space` → `direct`)** 을 적어둔 좋은 주석이다. 거기에 한 줄만 더 있으면 완벽하다 — `# Terraform provider에는 이 리소스가 추가되지 않음(백엔드 폐기 예정)`. **제약을 적으면 뒤집히지 않고, 제약의 배경까지 적으면 다시 묻지 않아도 된다.**

## Q5. 번들 규모가 커지면 나눠야 하는 시점이 오나요?

### 들은 답

- 번들은 **한 에이전트씩!** (에이전트 단위로 잡는다)
- 규모가 커지면 **도메인별로 나누면 되겠지만, 우리 프로젝트 규모에서는 그럴 일이 없을 것.**

### "한 에이전트씩" — 번들의 입자 크기를 정하는 원칙

이 답은 **"번들 하나에 무엇을 담을 것인가"**, 즉 **입자 크기(granularity)** 에 대한 것이다. 그리고 그 기준을 **에이전트 하나**로 잡으라는 말이다.

여기서 에이전트는 Databricks가 Genie 스페이스를 부르는 이름이기도 하고, 넓게는 **"독립적으로 배포되고 독립적으로 살아 있는 산출물 하나"**를 가리킨다. 어느 쪽으로 읽든 원칙의 모양은 같다.

```
   ✅ 번들 = 에이전트 하나 + 그 에이전트가 돌아가는 데 필요한 것 전부
      (잡 · 파이프라인 · 대시보드 · 설정 · 소스코드)

   ❌ 번들 = 조직에 있는 모든 것
   ❌ 번들 = 잡 하나 (너무 잘게 쪼갬)
```

왜 이 크기가 맞는가? **번들은 배포 단위이자 상태 단위이자 롤백 단위**이기 때문이다. 이 셋이 한 덩어리로 움직여야 하는 범위가 곧 번들의 경계다.

- 함께 배포돼야 하는 것들 → 같은 번들. (에이전트와 그 에이전트가 읽는 테이블을 만드는 잡이 따로 배포되면, 잡이 아직 안 올라간 상태의 에이전트가 존재하는 순간이 생긴다.)
- 함께 되돌려야 하는 것들 → 같은 번들. (`bundle destroy`나 이전 커밋 재배포의 사정거리가 곧 번들이다.)
- 함께 살고 함께 죽는 것들 → 같은 번들.

반대로 이 관계가 없는 것들을 한 번들에 넣으면, 관계없는 변경 하나가 전체 배포를 흔든다.

> 실무 감각: **"이걸 지울 때 저것도 같이 지워져야 하나?"** 답이 예면 같은 번들, 아니오면 다른 번들이다.

### 함께 알아둘 것: 배포 락 (deployment lock)

번들 크기와는 별개지만, "한 번에 하나씩"이라는 감각을 실제로 강제하는 장치가 하나 있다. 같은 번들·타깃에 대해 **동시에 두 개의 배포가 진행되지 못하도록 락**이 걸린다.

```
   CI 잡 A ──deploy──▶ 🔒 락 획득 ──▶ 배포 진행 ──▶ 락 해제
   CI 잡 B ──deploy──▶ ⏳ 대기 / 실패 ("deploy lock is held")
```

없으면 어떻게 되나? 두 배포가 같은 상태 파일을 동시에 쓰면서 **"만들었다는 기록은 있는데 실물이 없는"** 식으로 상태가 깨진다. 상태 기반 도구에서 가장 고치기 싫은 종류의 사고다.

알아둘 것 두 가지:

- **`development` 모드에서는 락이 기본으로 꺼져 있다.** dev는 사용자별로 리소스가 격리되므로 충돌 가능성이 낮고, 대신 반복 배포가 빨라진다. 필요하면 `bundle.deployment.lock.enabled: true`로 켤 수 있다.
- **`--force-lock`은 최후의 수단이다.** 이전 배포가 중간에 죽어서 **stale lock**이 남았을 때만 쓴다. 진짜로 다른 배포가 돌고 있는데 이걸 쓰면 위에서 말한 상태 손상이 그대로 일어난다.

```bash
databricks bundle deploy -t prod --force-lock   # 이전 배포가 죽은 게 확실할 때만
```

실무 규칙으로 옮기면: **CI에서 운영 타깃 배포는 동시 실행되지 않도록 묶는다.** (GitHub Actions라면 `concurrency` 그룹 하나로.)

### 규모가 커지면 실제로 뭐가 느려지나

"번들이 커진다"는 말은 세 가지 중 하나다. 각각 느려지는 이유가 다르다.

| 커지는 축 | 느려지는 이유 | 완화 |
|---|---|---|
| **파일이 많아진다** | 배포 때마다 워크스페이스로 동기화 | `sync.exclude`로 불필요한 파일 제외, `bundle sync`로 코드만 갱신 |
| **리소스가 많아진다** | 리소스 하나당 API 호출 + diff 계산 | direct 엔진이 유리 |
| **YAML이 길어진다** | 사람이 못 읽는다 | `include:`로 파일 분리 |

세 번째는 성능 문제가 아니라 **가독성 문제**인데, 실제로는 이게 가장 먼저 온다. 그리고 해결책은 번들 분할이 아니라 **파일 분할**이다.

```yaml
# databricks.yml — 여기는 뼈대만
bundle:
  name: our_etl
  engine: direct

include:
  - resources/jobs/*.yml
  - resources/pipelines/*.yml
```

**여기서 중요한 구분이 나온다. "파일을 나누는 것"과 "번들을 나누는 것"은 완전히 다르다.** 파일을 나눠도 번들은 하나고, 상태도 하나고, 배포도 한 번이다. 대부분의 "번들이 너무 커요"는 파일 분할로 해결된다.

### 번들을 진짜로 나눠야 할 때

그렇다면 번들 자체를 나누는 기준은 뭔가? PM님 말씀대로 도메인별이 일반적인데, 그 밑에 깔린 진짜 기준은 이거다.

| 나누는 축 | 언제 | 예 |
|---|---|---|
| **소유권** | 팀이 다르다 | 마케팅팀 번들 / 재무팀 번들 |
| **배포 주기** | 릴리스 리듬이 다르다 | 일 1회 vs 주 1회 |
| **위험도** | 실패 영향 범위를 분리하고 싶다 | 핵심 적재 / 실험 |
| **권한** | 배포 주체가 달라야 한다 | 운영 SP / 분석 SP |

분할의 대가도 알아야 한다. 공짜가 아니다.

- **번들 간 상호 참조가 안 된다.** `${resources.jobs.a.id}` 같은 참조는 번들 안에서만 된다. 번들 A의 잡이 번들 B의 파이프라인을 트리거하려면 ID를 하드코딩하거나 변수로 넘겨야 한다.
- **배포 순서를 사람이 관리해야 한다.** 하나였으면 CLI가 알아서 하던 것을 CI 스크립트가 떠안는다.
- **공통 설정이 중복된다.** 워크스페이스 호스트, 카탈로그 이름, 공통 변수가 여러 파일에 복사된다.

> **핵심 통찰 — "번들은 성능 때문에 나누는 게 아니라, 소유권 때문에 나눈다"**
>
> "느려지면 나눈다"는 직관은 대개 틀린다. 배포가 느려서 못 쓸 지경이 되는 번들은 현실에서 드물고, 그전에 **"이 YAML을 누가 고쳐도 되는가"**가 먼저 애매해진다.
>
> 그래서 판단 기준은 이렇게 세우는 게 맞다. **"두 팀이 같은 파일에서 충돌하기 시작했는가?" "A팀 배포가 B팀 리소스를 지울 수 있는가?"** 여기에 예가 나오면 그때 나눈다.
>
> PM님이 "우리 규모에서는 그럴 일 없다"고 하신 것도 정확히 이 뜻이다. **팀이 하나면 나눌 이유가 없다.** 그리고 나누면 위에 적은 세 가지 비용을 지금 당장 지불하게 된다.
>
> 그래서 "한 에이전트씩"과 "도메인별로 나눈다"는 서로 다른 두 규칙이 아니다. **함께 배포되고 함께 되돌아가는 범위**를 경계로 잡으라는 같은 말이고, 조직이 커지면 그 경계가 자연스럽게 도메인 경계와 겹치게 되는 것뿐이다.

## 부록. for each — 원천에서 당겨올 때의 반복문

메모에 한 줄로 남긴 것: *"원천에서 당겨올 때, 반복문."*

상황은 이렇다. 원천 시스템에서 테이블 30개를 같은 방식으로 당겨온다. 로직은 전부 똑같고 테이블 이름만 다르다. 태스크를 30개 복사해 붙여야 하나?

**반복을 어디에 둘 것인가**에 따라 답이 세 가지다. 그리고 이 선택이 운영 경험 전체를 바꾼다.

### 층위 0. YAML에는 반복문이 없다

먼저 확실히 해둘 것. **YAML은 데이터 포맷이지 프로그래밍 언어가 아니다.** `for` 문이 없다. 앵커(`&`)와 별칭(`*`)이 있지만 그건 **재사용**이지 **반복**이 아니다.

```yaml
# 이건 반복이 아니라 "같은 값 붙여넣기"다
defaults: &defaults
  max_retries: 3
  timeout_seconds: 3600

job_a:
  <<: *defaults
job_b:
  <<: *defaults
```

30번 반복하려면 30번 써야 한다. 그래서 실제 해법은 YAML 바깥에 있다.

### 층위 1. 런타임 반복 — `for_each_task`

Databricks Jobs가 제공하는 반복 태스크다. **입력 배열의 각 원소마다 중첩된 태스크를 실행**한다.

```yaml
resources:
  jobs:
    ingest_all:
      name: ingest_all_sources
      parameters:
        - name: source_list
          default: '["orders", "members", "payments", "coupons"]'
      tasks:
        - task_key: ingest_each
          for_each_task:
            inputs: "{{job.parameters.source_list}}"    # JSON 배열
            concurrency: 4                              # 동시 실행 개수
            task:
              task_key: ingest_one
              notebook_task:
                notebook_path: ../src/ingest.py
                base_parameters:
                  source_table: "{{input}}"             # 각 원소가 여기로
```

특징:

- **실행 UI에서 반복 하나하나가 개별 항목으로 보인다.** 3번째만 실패했으면 3번째만 보인다.
- **개별 재시도**가 된다.
- `concurrency`로 원천 DB에 가하는 부하를 조절할 수 있다. ← 원천에서 당겨올 때 이게 중요하다. 30개를 한 번에 때리면 소스 DB가 죽는다.
- **입력 목록을 잡 파라미터로 바꿀 수 있다.** 소스가 늘어도 YAML을 안 고친다.

### 층위 2. 정의 시점 반복 — Python으로 번들 설정 생성

"태스크 하나가 반복"이 아니라 "**잡 자체를 30개 만들고 싶다**"면 층위가 다르다. YAML로는 안 되고, 번들 설정을 파이썬으로 생성한다.

```yaml
# databricks.yml
experimental:
  python:
    resources:
      - "resources:load_resources"
    venv_path: .venv
```

```python
# resources/__init__.py
from databricks.bundles.core import Bundle, Resources
from databricks.bundles.jobs import Job

SOURCES = ["orders", "members", "payments"]

def load_resources(bundle: Bundle) -> Resources:
    resources = Resources()
    for src in SOURCES:                      # ← 진짜 반복문
        resources.add_job(
            f"ingest_{src}",
            Job.from_dict({
                "name": f"ingest_{src}",
                "tasks": [{
                    "task_key": "run",
                    "notebook_task": {
                        "notebook_path": "../src/ingest.py",
                        "base_parameters": {"source_table": src},
                    },
                }],
            }),
        )
    return resources
```

소스 목록을 CSV/JSON 설정 파일에서 읽어오면, **테이블이 추가될 때 설정 한 줄만 고치면 된다.** (이 기능은 비교적 새 기능이라 CLI 버전 요구사항이 있다. 쓰기 전에 팀 CLI 버전을 확인할 것.)

### 층위 3. 코드 안의 반복 — 파이프라인 정의를 루프로

선언형 파이프라인에서 테이블 정의 자체를 루프로 만드는 방법도 있다.

```python
SOURCES = ["orders", "members", "payments"]

for src in SOURCES:
    @dp.table(name=f"bronze_{src}")
    def _(src=src):        # ← 기본 인자로 값을 "고정"한다. 이게 없으면 전부 마지막 값이 된다
        return (spark.readStream
                .format("cloudFiles")
                .option("cloudFiles.format", "parquet")
                .load(f"/Volumes/raw/{src}"))
```

`src=src` 트릭을 빼먹으면 파이썬 클로저가 루프 변수를 **참조**로 잡아서 세 테이블이 전부 `payments`를 읽는다. 파이썬 초보자가 반드시 한 번은 밟는 지뢰다.

### 셋을 비교하면

| | **for_each_task** | **Python 번들 설정** | **코드 안 루프** |
|---|---|---|---|
| 반복 시점 | 실행할 때 | **배포할 때** | 파이프라인 정의할 때 |
| UI에서 보이는 단위 | 반복 항목별 | 잡/태스크별 | 테이블별 |
| 재시도 단위 | 개별 항목 | 잡 전체 | 데이터셋 |
| 목록 변경 | **파라미터만 바꾸면 됨** | 재배포 필요 | 재배포 필요 |
| 적합 | 소스 수가 자주 변함 | 소스별 스케줄·권한이 다름 | 같은 파이프라인 안의 다수 테이블 |

> **핵심 통찰 — "반복을 어디에 두느냐가 곧 관측·재시도의 단위를 정한다"**
>
> 세 방법 모두 "30개 테이블을 당긴다"를 해낸다. 차이는 **실패했을 때 무슨 일이 벌어지는가**에서 드러난다.
>
> - 코드 안 `for`문 → 3번째 테이블에서 죽으면 **잡 전체가 실패**하고, 재시도하면 1·2번을 다시 한다.
> - `for_each_task` → 3번째만 빨갛고, **3번째만 재시도**한다.
>
> 즉 반복문의 위치는 스타일 문제가 아니라 **운영 설계**다. "코드가 짧아지는 쪽"이 아니라 **"새벽 3시에 실패 알림을 받았을 때 내가 뭘 볼 수 있는가"**를 기준으로 고르는 게 맞다.

## 오늘의 정리

### 다섯 개의 답을 한 줄씩

1. **개인정보** — 컬럼 단독이 아니라 **조인 가능성**으로 판단한다. 우리는 원본을 저장하지 않는 **정적 마스킹**이고, `mem_id`는 SHA-256 + salt로 가명화한다. **모든 안전성이 salt 보관 한 곳에 걸려 있다.**
2. **Jira** — 티켓 체계는 관리자 소유, 개발자 접점은 **커밋의 이슈 ID 하나**. 규칙이 느슨한 게 아니라 잘 나뉜 것이다.
3. **배포 실패** — `deploy`는 "존재하게" 하고 `run`이 "일어나게" 한다. **배포 성공은 코드가 맞다는 뜻이 아니다.** 파이프라인은 `--validate-only`, 잡은 dev에서 실제 실행이 유일한 리허설.
4. **direct 엔진** — Terraform 백엔드는 폐기 수순이다. 주석에 적힌 이유(Genie 스페이스가 direct 전용)와 업계 흐름은 **별개가 아니라 같은 원인의 앞뒤**다 — 신규 리소스가 direct에만 붙는 것 자체가 그 흐름의 결과다. **되돌릴 이유가 없는 결정.**
5. **번들 분할** — 입자 크기는 **에이전트 단위**, 즉 함께 배포·롤백되는 범위가 곧 번들 경계다. 나누는 기준은 성능이 아니라 **소유권**. 우리 규모에서는 번들 분할이 아니라 파일 분할(`include:`)로 충분하다.

### 오늘 질문하면서 배운 것 (내용 말고 방법)

- **코드에 이미 적힌 답을 먼저 찾고, 그 "옆"을 물으면 질문의 질이 올라간다.** Q4가 그랬다. 주석에 `genie space 때문에 direct`라고 적혀 있었으니 "왜 direct인가요?"는 물을 필요가 없었고, 대신 **"그 제약 말고 다른 배경도 있나요?"**를 물었다. 그래서 "앞으로는 direct로 간다"는, 주석에는 없는 방향성을 얻었다. **문서에 있는 걸 묻지 말고, 문서에 있는 걸 근거로 물어야 한다.**
- **짧은 답은 정보가 적은 게 아니라 압축된 것이다.** "우리는 정적 마스킹"이라는 다섯 글자를 푸는 데 이 문서의 3분의 1이 들었다. 받아 적을 때 **"이 답이 전제하고 있는 게 뭐지"**를 표시해두면 나중에 풀기 쉽다.
- **모든 좋은 답은 다음 질문을 낳는다.** salt를 이해하고 나니 "salt는 누가 관리하고 교체 정책이 있나요"가 나왔다. 이게 질문의 질이 올라가는 방식이다.

### 다음에 물어볼 것

- **`mem_id` salt는 어디에 보관되고, 교체 정책이 있나요?** 교체하면 기존 해시와 조인이 깨지는데 그건 어떻게 다루나요?
- **Delta 시간여행과 `VACUUM` 보존 기간이 개인정보 삭제 요건과 어떻게 맞물리나요?**

- [개인정보의 안전성 확보조치 기준 (국가법령정보센터)](https://www.law.go.kr/%ED%96%89%EC%A0%95%EA%B7%9C%EC%B9%99/%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%EC%9D%98%EC%95%88%EC%A0%84%EC%84%B1%ED%99%95%EB%B3%B4%EC%A1%B0%EC%B9%98%EA%B8%B0%EC%A4%80) — 암호화 대상과 방법의 법적 근거. 개정이 잦으니 최신본 확인.
- [Row filters and column masks (Databricks 공식)](https://docs.databricks.com/aws/en/data-governance/unity-catalog/filters-and-masks/) — 동적 마스킹을 Unity Catalog에서 구현하는 방법. 우리가 안 쓰는 쪽이지만 비교 대상으로 알아둘 것.

**번들 배포**

- [Migrate to the direct deployment engine (Databricks 공식)](https://docs.databricks.com/aws/en/dev-tools/bundles/direct) — direct 엔진 전환 절차와 Terraform 대비 동작 차이.
- [bundle command group (Databricks CLI 레퍼런스)](https://docs.databricks.com/aws/en/dev-tools/cli/bundle-commands) — `validate`/`plan`/`deploy`/`run` 전체 옵션. `--force-lock`, `--validate-only`도 여기에 있다.
- [Declarative Automation Bundles 릴리스 노트](https://docs.databricks.com/aws/en/release-notes/dev-tools/bundles) — 엔진·리소스 지원 범위가 자주 바뀐다. 버전 이슈를 의심할 때 가장 먼저 볼 곳.
- [Troubleshoot the Databricks CLI](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/cli/troubleshooting) — `--log-level=debug`, `--log-file` 사용법.

**반복 처리**

- [Bundle configuration in Python (Databricks 공식)](https://docs.databricks.com/aws/en/dev-tools/bundles/python/) — 파이썬으로 번들 리소스를 루프 생성하는 방법.
- [Add tasks to jobs in bundles](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/bundles/job-task-types) — `for_each_task`를 포함한 태스크 타입 전체.
- [Genie Space 번들 예제 (databricks/bundle-examples)](https://github.com/databricks/bundle-examples/tree/main/knowledge_base/app_with_genie_space) — `genie_spaces` 리소스를 direct 엔진으로 배포하는 실제 예제.
