# 2026-08-05. YAML — 들여쓰기 두 칸으로 인프라를 기술하는 언어, 그리고 그 대가

> 요즘 내가 하루에 가장 많이 여는 파일 확장자는 `.py`도 `.sql`도 아니고 `.yaml`이다. 번들 설정, 파이프라인 정의, dbt 모델 스키마, CI 워크플로. **파이프라인이 무엇을 하는지는 코드에 있지만, 파이프라인이 어떻게 존재하는지는 전부 YAML에 있다.**
>
> 그런데 이 파일은 이상한 성질이 있다. 배울 게 없어 보인다. 들여쓰기하고 콜론 찍으면 끝인 것 같다. 그러다 어느 날 `version: 1.10`이 `1.1`로 읽히거나, 국가 코드 목록의 `NO`가 `false`가 되거나, cron 표현식 앞의 `*` 때문에 파서가 죽는다. 그제야 "이게 그냥 텍스트가 아니었구나"를 알게 된다.
>
> 이 글은 YAML이 **왜 이렇게 생겼는지**(유래), **무엇을 조심해야 하는지**(문법과 함정), 그리고 **Databricks 현장에서 실제로 어떻게 쓰이고 어디서 터지는지**를 정리한다.

## 1. 도입: 왜 YAML에서 매번 새로 물리는가

YAML의 문제는 **어려워서**가 아니라 **쉬워 보여서**다.

JSON을 처음 보면 중괄호와 대괄호가 있어서 "아, 구조가 있는 포맷이구나"를 인식한다. XML은 태그를 닫아야 해서 문법을 의식하게 된다. 반면 YAML은 이렇게 생겼다.

```yaml
name: daily-ingest
enabled: true
retries: 3
```

메모장이다. 그래서 아무도 문법을 공부하지 않고, 예제를 복사해 값만 바꾸며 쓴다. 90%는 그래도 돌아간다. 문제는 나머지 10%가 **조용히 잘못된 값으로 파싱되는** 형태로 온다는 것이다. 에러가 나면 차라리 낫다. 진짜 무서운 건 이런 것들이다.

```yaml
spark_version: 15.4          # 문자열 "15.4"가 아니라 실수 15.4
mode: no                     # 문자열 "no"가 아니라 false
mode2: 0644                  # 8진수/10진수 논쟁, 어느 쪽이든 "0644"는 아님
timeout: 12:30               # 어떤 파서에선 750 (60진법)
```

YAML을 배운다는 건 대부분 **"따옴표를 언제 쳐야 하는가"를 배우는 것**이고, 그 이유를 알려면 이 포맷이 왜 이렇게 설계됐는지를 알아야 한다.

> **핵심 통찰 — "YAML의 함정은 전부 하나의 설계 결정에서 파생된다"**
>
> 그 결정은 **"따옴표 없는 스칼라의 타입을 파서가 추론한다"**는 것이다. `true`는 불리언, `3`은 정수, `1.5`는 실수, `null`은 널. 사용자가 타입을 안 적어도 되게 만든 배려다.
>
> 이 배려의 대가가 이 글에 나오는 함정 **전부**다. Norway 문제도, 버전 번호가 실수가 되는 것도, `0644`가 깨지는 것도, `on:`이 `True`가 되는 것도 — 전부 "이 글자들이 무슨 타입인지 파서가 알아서 정한다"의 결과다.
>
> 그래서 YAML 함정을 개별 사례로 외울 필요가 없다. **규칙은 하나다: "문자열이길 원하는 값은 따옴표를 친다."** 사례를 외우는 대신 이 습관을 들이면 90%가 사라진다.

## 2. 유래 — "또 하나의 마크업 언어"에서 "마크업이 아님"으로

### 배경: 2000년경, XML이 모든 것이던 시대

2000년대 초는 XML이 설정·데이터 교환·문서·프로토콜을 전부 먹으려던 시기였다. 그런데 사람이 손으로 XML 설정 파일을 쓰는 경험은 좋지 않았다.

```xml
<job>
  <name>daily-ingest</name>
  <retries>3</retries>
  <tags>
    <tag>prod</tag>
    <tag>etl</tag>
  </tags>
</job>
```

내용은 네 줄인데 파일은 열 줄이고, 절반이 닫는 태그다. **XML은 문서(document)에 마크업을 다는 언어**로 설계됐는데, 사람들은 그걸 **데이터 구조를 적는 데** 쓰고 있었다. 도구와 용도가 어긋나 있었다.

### 2001년, YAML의 등장

**2001년 Clark Evans**가 처음 제안했고, **Ingy döt Net**, **Oren Ben-Kiki**가 함께 설계했다. 목표는 명확했다. *사람이 읽고 쓰기 쉬운 데이터 직렬화 포맷.*

이름의 반전이 이 포맷의 성격을 잘 보여준다.

- 처음 이름은 **"Yet Another Markup Language"** — 당시 온갖 `*ML`이 쏟아지던 세태를 비꼰 농담이었다.
- 나중에 **"YAML Ain't Markup Language"**라는 재귀적 약어로 다시 정의했다. 농담을 유지하면서, **"우리는 마크업이 아니라 데이터를 다룬다"**는 선언을 넣은 것이다.

이 개명이 실제 설계 철학이다. 마크업 언어는 "텍스트에 의미를 덧붙이는" 도구고, YAML은 "데이터 구조 자체를 적는" 도구다. 그래서 YAML에는 태그도 속성도 없고, 대신 **들여쓰기로 계층을 표현**한다. Python이 중괄호 대신 들여쓰기를 쓴 것과 같은 발상이며, 실제로 초기 YAML은 Python·Perl 커뮤니티에서 먼저 퍼졌다.

### 버전의 역사 — 여기가 실무에 중요하다

| 버전 | 시기 | 핵심 |
|---|---|---|
| 1.0 | 2004 | 첫 정식 명세 |
| **1.1** | **2005** | 널리 퍼진 버전. `yes/no/on/off`를 불리언으로, 60진수·8진수 지원 |
| **1.2** | **2009** | **JSON을 YAML의 부분집합으로** 만듦. 1.1의 헐거운 타입 추론(`yes/no/on/off`, 60진수)을 **core schema에서 제거** |
| 1.2.2 | 2021 | 명세 문서 정비(개정판). 문법 변경 없음 |

**1.2에서 JSON이 YAML의 부분집합이 됐다**는 건 실무적으로 큰 사건이다. 유효한 JSON 파일은 그대로 유효한 YAML이다. 그래서 YAML 파일 안에 JSON 스타일(flow style)을 섞어 써도 된다.

```yaml
tags: {env: prod, team: data}    # JSON처럼 써도 유효한 YAML
ports: [8080, 8443]
```

그런데 **여기서 이 글에서 가장 중요한 실무 사실이 나온다.**

> **핵심 통찰 — "당신이 쓰는 건 YAML 1.2가 아니라, 그 도구가 쓰는 파서의 YAML이다"**
>
> 명세는 2009년에 1.2로 올라갔지만, **현실의 파서 상당수는 여전히 1.1 기반**이다. 대표적으로 파이썬 생태계의 사실상 표준인 **PyYAML은 1.1만 지원**한다. Go의 `yaml.v2`도 1.1이고, `yaml.v3`에서야 1.2 쪽으로 움직였다.
>
> 결과가 뭐냐면, **"YAML 1.2에서는 `no`가 문자열입니다"라는 지식이 실무에서 자주 틀린다.** 당신이 쓰는 도구가 PyYAML로 파싱한다면 `no`는 여전히 `false`다. Ansible, dbt, 수많은 파이썬 기반 데이터 도구가 여기에 해당한다.
>
> 그래서 판단 기준을 "명세가 뭐라고 하나"가 아니라 **"이 파일을 누가 읽나"**로 바꿔야 한다. 같은 YAML 텍스트가 GitHub Actions(Go)와 dbt(Python)에서 다르게 읽힐 수 있다. 이 불확실성 전체를 없애는 방법은 앞에서 말한 그 하나 — **문자열은 따옴표로 감싼다** — 뿐이다.

## 3. 뼈대: 스칼라·시퀀스·매핑 세 가지가 전부다

YAML이 표현하는 자료형은 딱 세 가지다. 나머지는 전부 이 조합이다.

```yaml
# 1. 스칼라(scalar) — 단일 값
name: daily-ingest
retries: 3
enabled: true
owner: null

# 2. 시퀀스(sequence) — 순서 있는 목록. '- '로 시작
tags:
  - prod
  - etl

# 3. 매핑(mapping) — 키-값. '키: 값'
cluster:
  node_type: i3.xlarge
  num_workers: 4
```

### 알아둘 기본 규칙

**들여쓰기는 공백만. 탭은 문법 오류다.** YAML에서 탭은 들여쓰기로 절대 쓸 수 없다. 에디터가 탭을 넣으면 파일 전체가 깨진다. 관례는 **공백 2칸**이다.

**콜론 뒤에는 반드시 공백이 필요하다.**

```yaml
key: value      # 매핑 (키 'key', 값 'value')
key:value       # 문자열 스칼라 "key:value" — 매핑이 아니다!
```

**시퀀스 들여쓰기는 둘 다 유효하다.** 이게 처음 볼 때 헷갈린다.

```yaml
tags:
  - prod        # 들여쓴 형태
  - etl

tags:
- prod          # 안 들여쓴 형태 — 위와 완전히 동일하다
- etl
```

둘 다 같은 결과다. 팀 내에서 하나로 통일하면 되고, 대개 들여쓴 쪽을 쓴다.

**주석은 `#`.** 단, **`#` 앞에 공백이 있어야 주석**이다.

```yaml
retries: 3          # 이건 주석
url: http://a.com#x # 값은 "http://a.com#x" 전체 — #x는 주석이 아니다
```

**빈 값은 `null`이다.** 빈 딕셔너리도, 빈 문자열도 아니다.

```yaml
tags:               # → null (빈 리스트 [] 아님!)
labels: {}          # → 빈 딕셔너리
note: ""            # → 빈 문자열
```

이건 실무에서 `'NoneType' object is not iterable` 에러의 단골 원인이다. "키만 적고 값을 지웠는데 왜 죽지?"의 답이 여기 있다. 널을 명시하는 방법은 네 가지고 전부 같다: `null`, `Null`, `NULL`, `~`.

**문서 구분자.** `---`는 새 문서의 시작, `...`은 문서의 끝(생략 가능)이다. 한 파일에 여러 YAML 문서를 넣을 수 있다.

```yaml
---
name: doc-one
---
name: doc-two
```

Kubernetes 매니페스트에서 자주 보이는 패턴이고, **뒤에 나올 앵커의 유효 범위가 이 "문서" 단위**라 알아둘 필요가 있다.

## 4. 문자열 — 생각보다 어려운 부분

### 4.1 따옴표 세 종류

| 방식 | 예시 | 이스케이프 | 언제 쓰나 |
|---|---|---|---|
| 없음(plain) | `name: daily` | — | 평범한 값. **타입 추론 대상** |
| 홑따옴표 | `name: 'a: b'` | `''`만 (문자 그대로) | **경로·정규식·특수문자**. 백슬래시가 그대로 남는다 |
| 겹따옴표 | `name: "a\nb"` | `\n`, `\t`, `\"` 등 동작 | **개행·유니코드 등 이스케이프가 필요할 때** |

핵심 차이는 **홑따옴표 안에서는 백슬래시가 이스케이프 문자가 아니다**라는 점이다.

```yaml
a: 'C:\Users\data'      # → C:\Users\data (그대로)
b: "C:\Users\data"      # → \U는 유니코드 이스케이프로 해석되어 에러/오작동
c: "line1\nline2"       # → 진짜 개행 두 줄
d: 'line1\nline2'       # → 백슬래시-n 리터럴 그대로
```

**윈도우 경로, 정규식, 백슬래시가 들어간 값은 홑따옴표**가 기본이라고 외우면 된다.

### 4.2 따옴표를 반드시 쳐야 하는 경우

plain 스칼라로 시작할 수 없는 문자들이 있다. 이 문자로 **값이 시작하면** 파서가 다른 문법으로 해석한다.

| 시작 문자 | YAML이 이걸로 해석 | 실제 사례 |
|---|---|---|
| `*` | 별칭(alias) 참조 | `cron: */5 * * * *` → **파스 에러** |
| `&` | 앵커 정의 | |
| `-` (+공백) | 시퀀스 항목 | |
| `?` `:` | 복합 키 문법 | |
| `{` `[` | flow 컬렉션 시작 | `sql: {{ var('x') }}` → **에러** (dbt Jinja!) |
| `#` | 주석 | |
| `%` `@` `` ` `` | 예약 문자 | |
| `!` | 태그 | |

그리고 **값 안에 `: `(콜론+공백)가 들어가면** 매핑으로 오해받는다.

```yaml
msg: error: not found        # 에러 — 값 안의 ': '가 문제
msg: "error: not found"      # OK
```

### 4.3 블록 스칼라 — 여러 줄 문자열

SQL이나 스크립트를 YAML에 넣을 때 쓴다. 두 종류다.

```yaml
# | (literal) — 개행을 그대로 보존한다
query: |
  SELECT *
  FROM bronze.events
  WHERE dt = current_date()

# > (folded) — 개행을 공백으로 접어서 한 줄로 만든다
description: >
  이 잡은 매일 새벽에 원천 이벤트를
  브론즈 레이어로 적재한다.
```

`|`는 `SELECT *\nFROM bronze.events\n...`, `>`는 `이 잡은 매일 ... 적재한다.\n`이 된다. **SQL·셸 스크립트는 무조건 `|`**, 긴 설명문은 `>`다.

여기에 **chomping indicator**를 붙일 수 있다. 끝의 개행을 어떻게 처리할지 정한다.

| 표기 | 이름 | 마지막 개행 처리 |
|---|---|---|
| `\|` | clip (기본) | 개행 **하나만** 남긴다 |
| `\|-` | strip | 끝 개행을 **전부 제거** |
| `\|+` | keep | 끝의 빈 줄을 **전부 보존** |

```yaml
a: |-
  no trailing newline      # → "no trailing newline"
b: |
  one trailing newline     # → "one trailing newline\n"
```

셸 명령이나 토큰 값처럼 **끝 개행이 있으면 안 되는 값은 `|-`**를 쓴다. 인증 토큰을 `|`로 넣었다가 끝에 `\n`이 붙어 401이 나는 건 꽤 흔한 사고다.

## 5. 타입 추론이라는 지뢰밭

여기가 이 글의 핵심이다. 아래는 전부 **에러 없이 조용히 잘못 파싱되는** 사례들이다.

### 5.1 Norway 문제 (The Norway Problem)

YAML 세계에서 가장 유명한 버그다.

```yaml
countries:
  - GB
  - FR
  - NO      # → false !!!
  - DE
```

`NO`가 노르웨이가 아니라 **불리언 거짓**으로 파싱된다. YAML 1.1이 불리언으로 인정하는 표기가 이렇게 많기 때문이다.

```
true  True  TRUE  false False FALSE
yes   Yes   YES   no    No    NO
on    On    ON    off   Off   OFF
y     Y     n     N          (※ 명세엔 있으나 PyYAML은 제외)
```

`on`/`off`가 포함된 게 특히 아프다. **GitHub Actions 워크플로의 최상위 `on:` 키가 파이썬 파서에서 `True`라는 키로 읽히는** 유명한 사례가 여기서 나온다. GitHub 자체 파서는 처리하지만, 워크플로 YAML을 파이썬으로 읽어 검증하는 스크립트를 짜면 `workflow["on"]`이 `KeyError`가 난다.

### 5.2 버전 번호가 실수가 된다

```yaml
version: 1.10        # → 1.1 (float). "1.10"이 아니다
version: 1.2.3       # → "1.2.3" (점 두 개라 문자열로 남는다)
```

**점이 하나면 실수, 두 개면 문자열**이라는 일관성 없는 결과가 나온다. 버전·릴리스 번호는 무조건 따옴표다.

### 5.3 앞자리 0 — 8진수 문제

```yaml
mode: 0644           # YAML 1.1: 8진수 → 420 / YAML 1.2 core: 644
zipcode: 06241       # 앞의 0이 사라지거나 8진수로 해석됨
account: 0012345678  # 계좌번호가 숫자가 되면서 앞자리 0 소실
```

Ansible에서 파일 권한 `mode: 0644`가 엉뚱하게 적용되는 고전적 사고이자, **데이터 업무에서 더 위험한 케이스** — 계좌번호·우편번호·사번처럼 **앞자리 0이 의미 있는 식별자**가 숫자로 바뀌며 손상된다.

### 5.4 60진법 (sexagesimal)

YAML 1.1의 유물이다. 콜론으로 구분된 숫자를 **60진수 정수**로 해석한다.

```yaml
timeout: 12:30       # → 750  (12*60 + 30)
port_range: 22:22    # → 1342
```

YAML 1.2에서 제거됐지만 **PyYAML은 여전히 이렇게 파싱**한다. 시각, MAC 주소, 포트 표기에서 터진다.

### 5.5 그 밖에

```yaml
null_ish: ~          # null
empty:               # null
big: 12345678901234567890123   # 정밀도 손실 가능
date: 2026-08-05     # YAML 1.1에서 date 객체로 파싱 (문자열 아님)
tilde: ~/data        # 이건 문자열 (단독 ~만 null)
```

`2026-08-05`가 문자열이 아니라 **날짜 객체**가 되는 것도 자주 문제가 된다. 그대로 문자열로 API에 넘길 생각이었다면 타입이 안 맞는다.

### 5.6 중복 키 — 명세는 에러, 현실은 침묵

```yaml
retries: 3
timeout: 60
retries: 5      # 명세상 에러여야 하지만...
```

명세는 중복 키를 오류로 규정하지만, **PyYAML을 비롯한 여러 파서는 조용히 마지막 값을 채택**한다. 위 파일은 `retries: 5`가 된다. 긴 설정 파일에서 같은 키를 두 번 쓰고 "왜 안 먹지?"로 몇 시간을 태우는 시나리오다. **린터가 잡아주는 대표적 항목**이라 9장에서 다시 본다.

> **핵심 통찰 — "YAML은 '읽기 쉬운' 포맷이지 '안전한' 포맷이 아니다"**
>
> YAML의 홍보 문구는 항상 human-readable이다. 맞는 말이다. 하지만 여기서 빠진 절반이 있다 — **읽기 쉬움과 정확함은 다르다.**
>
> 위 사례들의 공통점은 **파일을 눈으로 봐서는 문제를 알 수 없다**는 것이다. `- NO`는 아무리 봐도 노르웨이고, `version: 1.10`은 아무리 봐도 1.10이다. 사람에게 읽히기 위해 문법을 줄인 결과, **사람이 읽은 것과 기계가 읽은 것이 달라질 여지**가 생겼다. JSON은 못생겼지만 `"NO"`는 언제나 문자열이다.
>
> 실무적 결론은 두 가지다. 첫째, **코드 리뷰로 YAML 버그를 잡을 수 없다.** 리뷰어도 사람이라 똑같이 속는다. 둘째, 그러므로 **YAML은 반드시 기계가 검증해야 한다** — 린터와 스키마 검증을 CI에 넣는 것이 선택이 아니라 필수인 이유다.

## 6. 재사용 — 앵커·별칭·병합 키

YAML에는 중복을 줄이는 장치가 있다. 설정 파일이 길어지면 유용하다.

```yaml
# &이름 으로 앵커를 걸고
defaults: &defaults
  spark_version: "15.4.x-scala2.12"
  node_type_id: i3.xlarge
  num_workers: 2

# *이름 으로 그대로 참조한다
dev_cluster: *defaults

# <<: 로 병합하고 일부만 덮어쓴다 (merge key)
prod_cluster:
  <<: *defaults
  num_workers: 12
```

결과적으로 `prod_cluster`는 `spark_version`, `node_type_id`를 물려받고 `num_workers`만 12가 된다.

**알아둘 제약이 셋 있다.**

1. **앵커의 유효 범위는 하나의 문서(document)다.** `---`로 나뉜 다음 문서에서는 참조할 수 없고, **다른 파일에서는 당연히 안 된다.** 이게 8장에서 볼 Databricks 실무 이슈로 직결된다.
2. **병합(`<<`)은 얕은 병합(shallow)이다.** 중첩 딕셔너리는 통째로 교체된다. 그리고 `<<`는 YAML 1.1 시절의 확장 문법이라 **1.2 core schema에는 없다.** 대부분의 파서가 지원하지만 보장은 아니다.
3. **가독성을 해칠 수 있다.** 앵커가 200줄 위에 있으면 파일을 위아래로 오가며 읽어야 한다. 그래서 설정 관리 도구들이 종종 앵커 대신 **자체 변수 기능**을 제공한다.

### 보안 각주: 앵커로 만드는 폭탄

앵커는 중첩 참조가 가능해서 **지수적으로 팽창**시킬 수 있다. 이른바 **billion laughs / YAML bomb**이다.

```yaml
a: &a ["x","x","x","x","x","x","x","x","x"]
b: &b [*a,*a,*a,*a,*a,*a,*a,*a,*a]
c: &c [*b,*b,*b,*b,*b,*b,*b,*b,*b]
# ... 몇 단만 더 쌓으면 수 GB로 팽창해 메모리를 터뜨린다
```

**신뢰할 수 없는 출처의 YAML을 서버에서 파싱한다면** 알아둬야 할 공격 벡터다. 같은 맥락에서 파이썬의 `yaml.load()`는 과거 임의 객체를 생성할 수 있어 원격 코드 실행으로 이어졌다. **`yaml.safe_load()`를 쓰는 것이 규칙**이고, 최신 PyYAML은 `Loader` 지정을 요구한다.

## 7. 확장자는 `.yaml`이 공식이다 — `.yml`은 왜 남았나

자주 나오는 질문이라 정리한다. 결론부터: **`.yaml`이 공식 권장이다.**

- **yaml.org가 2006년부터 `.yaml`을 권장 확장자로 명시**해 왔다. 공식 FAQ의 답이 그냥 "Please use `.yaml` when possible"이다.
- **`.yml`은 확장자를 3글자까지만 쓸 수 있던 시절(DOS의 8.3 파일명)의 유산**이다. 그 제약이 사라진 지 20년이 넘었는데도, 초기 도구들이 `.yml`로 자리를 잡아 관성으로 남았다.
- **기능적 차이는 전혀 없다.** 파서는 확장자를 보지 않는다. 내용만 본다.

그래서 **새로 만드는 파일은 `.yaml`로 쓰는 게 맞다.** 다만 현실에서 두 가지 예외를 알아둬야 한다.

**예외 ① 도구가 파일명을 고정한 경우.** 일부 도구는 특정 이름을 찾도록 하드코딩돼 있다. 대표적으로 dbt의 프로젝트 설정 파일은 **`dbt_project.yml`이라는 이름 자체가 규약**이라 `.yaml`로 바꾸면 dbt가 프로젝트를 못 찾는다. (반면 dbt의 모델 스키마 파일은 `.yml`/`.yaml` 둘 다 인식한다.) Databricks 번들 설정 파일은 **`databricks.yaml`과 `databricks.yml` 둘 다 유효**하다 — 다만 `bundle init` 템플릿이 `.yml`로 생성하므로, 팀 컨벤션을 `.yaml`로 정했다면 초기화 직후 이름을 바꿔주면 된다.

**예외 ② 이미 `.yml`로 굴러가는 저장소.** 중간에 섞기 시작하는 게 통일보다 나쁘다. 이유는 아래.

> **핵심 통찰 — "확장자 논쟁의 진짜 리스크는 취향이 아니라 glob 누락이다"**
>
> `.yml`이냐 `.yaml`이냐는 그 자체로는 아무것도 아니다. 문제는 **설정 파일들이 glob 패턴으로 수집된다**는 데 있다.
>
> ```yaml
> include:
>   - resources/*.yaml      # .yml로 저장된 파일은 조용히 무시된다
> ```
>
> 이 상황에서 누군가 `resources/new_job.yml`을 만들면 **에러도 경고도 없이 그냥 배포되지 않는다.** "분명히 잡을 정의했는데 워크스페이스에 없다"로 30분을 태우고, 원인이 확장자 한 글자라는 걸 알게 된다.
>
> 그래서 실무 규칙은 **"`.yaml`을 표준으로 삼되, 저장소 안에서는 예외 없이 하나로 통일한다"**이고, 안전장치로 **glob을 `resources/*.{yml,yaml}`처럼 양쪽 다 잡거나, 린트에서 어긋난 확장자를 실패로 처리**하는 편이 좋다. 컨벤션은 지켜지지 않을 때 조용히 실패하면 안 되고, 시끄럽게 실패해야 한다.

## 8. Databricks 실전 — 어디에 쓰이고 어디서 터지나

### 8.1 어디에 쓰이나

Databricks 프로젝트에서 YAML은 사실상 **인프라 기술 언어**다.

| 파일 | 역할 |
|---|---|
| `databricks.yaml` + `resources/*.yaml` | **번들(DAB)** — 잡·파이프라인·카탈로그·스키마·대시보드 등 워크스페이스 리소스 선언 |
| 파이프라인 정의 YAML | 선언형 파이프라인의 소스 경로·설정·스키마 지정 |
| `dbt_project.yml`(이름 고정), `profiles.yml`, `schema.yaml` | dbt 프로젝트 설정, 접속 정보, 모델 스키마·테스트·계약 |
| `.github/workflows/*.yaml` | 번들 배포 CI/CD |

즉 **"파이프라인이 무엇을 하는가"는 Python/SQL에, "파이프라인이 어떤 모습으로 존재하는가"는 전부 YAML에** 있다.

### 8.2 `${var.catalog}`는 YAML 문법이 아니다

DAB 설정을 보면 이런 게 나온다.

```yaml
variables:
  catalog:
    default: dev_catalog

resources:
  jobs:
    ingest:
      name: ingest-${bundle.target}
      tasks:
        - task_key: bronze
          notebook_task:
            base_parameters:
              catalog: ${var.catalog}
```

여기서 꼭 구분해야 할 것: **`${...}` 치환은 YAML 기능이 아니다.** YAML 명세에는 변수도, 참조도, 문자열 보간도 없다. 저건 **Databricks CLI가 YAML을 다 읽은 뒤 자기가 수행하는 후처리**다. dbt의 `{{ }}`(Jinja)도, GitHub Actions의 `${{ }}`도 전부 마찬가지로 각 도구의 기능이다.

> **핵심 통찰 — "YAML 파일에서 보이는 것의 절반은 YAML이 아니다"**
>
> 우리가 실무에서 만지는 `.yaml`은 대부분 **YAML(문법) + 그 도구의 스키마(무슨 키가 유효한가) + 그 도구의 템플릿 엔진(`${}`, `{{}}`)**이라는 세 겹이다.
>
> 이걸 구분하지 못하면 학습이 꼬인다. `${var.x}`가 안 먹혀서 YAML 문서를 뒤지거나, 반대로 `NO`가 `false`가 된 걸 도구 버그로 신고하게 된다. **디버깅의 첫 질문은 항상 "이건 세 겹 중 어느 층의 문제인가"여야 한다.**
>
> 층을 나누면 대처법도 갈린다. **문법 오류**는 린터가 잡는다. **스키마 오류**(없는 키, 잘못된 타입)는 그 도구의 검증 명령(`databricks bundle validate`, `dbt parse`)이 잡는다. **치환 오류**는 최종 병합 결과를 출력해서 눈으로 확인해야 한다. 도구마다 이 세 가지를 어떻게 확인하는지만 알면 YAML 디버깅의 대부분이 끝난다.

### 8.3 앵커는 파일 경계를 못 넘는다 → 복합 변수를 쓴다

DAB에서 흔히 하고 싶은 일: 여러 잡이 공유하는 클러스터 사양을 한 곳에 정의하기. 앵커로 시도하면 이런 벽에 부딪힌다.

```yaml
# resources/common.yaml
_defaults: &cluster          # 여기서 앵커를 걸어도...
  spark_version: "15.4.x-scala2.12"
  num_workers: 2

# resources/ingest_job.yaml
job_clusters:
  - new_cluster: *cluster    # ← 다른 파일이라 참조 불가. 6장의 그 제약이다
```

**앵커의 유효 범위가 문서 하나**이기 때문이다. `include`로 여러 YAML을 끌어오는 구조에서는 각각이 별개 문서다.

DAB가 주는 답은 **복합 변수(complex variable)**다.

```yaml
variables:
  base_cluster:
    type: complex            # 값이 스칼라가 아니라 맵/리스트
    default:
      spark_version: "15.4.x-scala2.12"
      node_type_id: i3.xlarge
      num_workers: 2

resources:
  jobs:
    ingest:
      job_clusters:
        - job_cluster_key: main
          new_cluster: ${var.base_cluster}    # 파일 경계를 넘는다

targets:
  prod:
    variables:
      base_cluster:                            # 환경별로 통째 교체
        spark_version: "15.4.x-scala2.12"
        node_type_id: i3.2xlarge
        num_workers: 12
```

**정리하면: 한 파일 안의 반복은 앵커, 파일·환경을 넘는 공유는 복합 변수.** 이 구분이 DAB 설정 구조를 깔끔하게 유지하는 핵심이다.

### 8.4 실제로 터지는 Databricks YAML 사고 5선

**① `spark_conf` 값은 문자열이어야 한다**

Clusters API에서 `spark_conf`는 **문자열 → 문자열 맵**이다. 그런데 YAML은 친절하게 타입을 추론한다.

```yaml
spark_conf:
  spark.sql.shuffle.partitions: 200      # → 정수 200. API는 문자열을 원한다
  spark.databricks.delta.optimizeWrite.enabled: true   # → 불리언

# 안전한 형태
spark_conf:
  spark.sql.shuffle.partitions: "200"
  spark.databricks.delta.optimizeWrite.enabled: "true"
```

**`spark_conf`, `spark_env_vars`, `custom_tags`의 값은 전부 따옴표**로 감싸는 습관을 들이면 된다.

**② cron 표현식은 따옴표 필수**

```yaml
schedule:
  quartz_cron_expression: */15 * * * * ?      # 파스 에러! '*'가 별칭 지시자
  quartz_cron_expression: "0 0 3 * * ?"       # OK
```

`*`로 **시작하는** 순간 YAML은 별칭 참조로 읽는다. cron은 예외 없이 따옴표.

**③ 런타임 버전이 실수가 된다**

```yaml
spark_version: 15.4                  # → 실수 15.4. 문자열이어야 함
spark_version: "15.4.x-scala2.12"    # OK
```

**④ dbt의 Jinja는 반드시 따옴표 안에**

```yaml
# dbt_project.yml(이름 고정) / schema.yaml
vars:
  start_date: {{ var('start') }}       # 에러! '{'가 flow 매핑 시작으로 읽힘
  start_date: "{{ var('start') }}"     # OK
```

값이 `{{`로 시작하면 YAML은 flow 컬렉션으로 해석한다. **문장 중간에 있는 Jinja는 괜찮지만, 값 맨 앞에 오면 무조건 따옴표.** dbt를 처음 쓸 때 반드시 한 번은 밟는 지뢰다.

**⑤ 시크릿을 YAML에 쓰지 않는다**

당연하지만 반복할 가치가 있다. `databricks.yaml`은 Git에 들어간다. 토큰·비밀번호는 시크릿 스코프나 CI 시크릿에 두고 **참조만** 한다. 한 번 커밋된 시크릿은 이력에서 지우기 어렵고, 실질적으로 유출된 것으로 간주해야 한다.

## 9. 안전하게 다루기 — 도구와 습관

YAML은 눈으로 검증할 수 없으므로 기계에 맡긴다. 비용이 거의 안 드는 것부터.

### 9.1 에디터에 스키마를 물린다 (가장 효과가 큼)

DAB는 자기 JSON 스키마를 뽑아준다.

```bash
databricks bundle schema > bundle_schema.json
```

VS Code의 YAML 확장(Red Hat)에 이 스키마를 연결하면 **오타 난 키, 잘못된 타입, 없는 필드를 타이핑하는 즉시** 빨간 줄로 알려주고 자동완성까지 된다. 파일 첫 줄에 이렇게 넣어도 된다.

```yaml
# yaml-language-server: $schema=./bundle_schema.json
```

문서를 뒤지는 시간을 가장 크게 줄여주는 조치다.

### 9.2 린터를 CI에 넣는다

`yamllint`는 **중복 키, 탭 들여쓰기, 줄 끝 공백, 따옴표 스타일 불일치** 등을 잡는다. 5장에서 본 중복 키 문제를 잡는 실질적인 유일한 방법이다.

```bash
yamllint databricks.yaml resources/
```

### 9.3 도구 자체의 검증 명령을 쓴다

문법이 맞아도 **의미가 틀릴 수 있다.** 각 도구가 주는 검증·미리보기 명령이 그 층을 담당한다.

```bash
databricks bundle validate -t prod   # 스키마 검증 + 병합된 최종 설정 출력
dbt parse                            # dbt YAML 파싱·참조 검증
```

특히 `bundle validate`가 출력하는 **최종 병합 결과**를 확인하는 습관이 중요하다. 변수 치환과 타깃 오버라이드가 다 적용된 뒤의 값을 보면 "내가 의도한 게 이건가"를 눈으로 확인할 수 있다.

### 9.4 습관 다섯 개

1. **문자열이길 원하면 따옴표를 친다.** 버전, 식별자, cron, 국가/통화 코드, `spark_conf` 값, 계좌·우편번호.
2. **백슬래시가 있으면 홑따옴표**, 이스케이프가 필요하면 겹따옴표.
3. **탭 금지, 공백 2칸.** 에디터에 `.editorconfig`로 못 박는다.
4. **파일을 짧게 쪼갠다.** 300줄짜리 YAML은 사람이 검토할 수 없다. DAB의 `include`, dbt의 디렉터리 분리를 적극 쓴다.
5. **의심되면 파싱해서 출력해 본다.** `python -c "import yaml,sys;print(yaml.safe_load(open(sys.argv[1])))" f.yaml` 한 줄이면 파서가 실제로 뭘 읽었는지 바로 보인다.

## 10. 정리 & SI 관점의 시사점

**정리:**

- YAML은 **2001년 XML의 장황함에 대한 반동**으로 나왔다. 이름을 *Yet Another Markup Language*에서 ***YAML Ain't Markup Language***로 바꾼 것 자체가 "우리는 마크업이 아니라 **데이터 구조**를 다룬다"는 선언이다.
- **1.2(2009)부터 JSON은 YAML의 부분집합**이다. 하지만 **현실의 파서 다수(PyYAML 등)는 여전히 1.1**이라, 명세보다 "이 파일을 어떤 파서가 읽나"가 중요하다.
- 자료형은 **스칼라·시퀀스·매핑** 셋뿐이다. **탭 금지, 콜론 뒤 공백 필수, 빈 값은 `null`**.
- 문자열은 **plain/홑따옴표/겹따옴표** 세 가지이고, **홑따옴표는 백슬래시를 보존**한다. 여러 줄은 `|`(개행 보존)와 `>`(접기), 끝 개행 제어는 `|-` / `|+`.
- 모든 함정의 근원은 **plain 스칼라의 자동 타입 추론**이다. Norway 문제(`NO`→false), 버전 실수화(`1.10`→1.1), 앞자리 0 소실, 60진법(`12:30`→750), 날짜 자동 변환, 그리고 **조용히 마지막 값을 채택하는 중복 키**.
- **앵커·별칭·병합 키**로 중복을 줄일 수 있지만 **문서 하나를 벗어나지 못하고**, 병합은 얕다. 신뢰할 수 없는 YAML은 **YAML 폭탄·역직렬화 취약점** 대상이므로 `safe_load`를 쓴다.
- **확장자는 `.yaml`이 공식 권장**이다(yaml.org, 2006~). `.yml`은 8.3 파일명 시절의 유산이고 **기능 차이는 없다.** 다만 `dbt_project.yml`처럼 **이름이 고정된 파일**은 예외이며, 진짜 리스크는 확장자 선택이 아니라 **혼용으로 인한 glob 누락**이다.
- Databricks에서 YAML은 **인프라 기술 언어**다. `${var.x}`는 YAML이 아니라 CLI 기능이며, 파일을 넘는 재사용은 **앵커가 아니라 복합 변수(`type: complex`)**로 한다. 실전 지뢰는 **`spark_conf` 값 타입, cron의 `*`, 런타임 버전 실수화, dbt Jinja `{{`**.

**우리 SI 프로젝트에 주는 시사점 (토론 포인트):**

- **YAML 컨벤션을 프로젝트 첫 주에 문서 한 장으로 못 박자.** 들여쓰기 2칸, 확장자 `.yaml` 통일(공식 권장이자 glob 사고 예방), "문자열은 따옴표", 파일 최대 길이. 나중에 정하면 이미 수십 개 파일이 제각각이라 일괄 수정이 리뷰 불가능한 크기의 diff가 된다. `.editorconfig` + `yamllint` 설정 파일을 저장소 뼈대에 넣는 것이 실질적인 강제 수단이다.
- **YAML 린트·스키마 검증을 CI 필수 단계로 넣자.** YAML 버그는 **코드 리뷰로 못 잡는다.** 리뷰어도 `- NO`를 노르웨이로 읽는다. 사람이 못 잡는 것을 사람에게 맡기는 프로세스는 언젠가 반드시 사고를 낸다. `yamllint` + `databricks bundle validate`는 합쳐서 CI 10초짜리다.
- **신규 인력 온보딩에 "YAML 30분"을 넣을 가치가 있다.** 아무도 안 가르치는데 모두가 매일 쓴다. 실제로 팀에서 반복해 나는 사고(따옴표 누락, 중복 키, 탭)는 **한 번 설명하면 안 나는** 종류다. 학습 비용 대비 사고 감소 효과가 프로젝트 통틀어 가장 좋은 항목 중 하나다.
- **고객사 데이터의 식별자 컬럼을 특히 주의하자.** 계좌번호·사업자번호·우편번호·상품코드처럼 **앞자리 0이 의미를 갖는 값**을 설정이나 매핑 테이블에 YAML로 넣을 일이 생긴다. 여기서 앞자리 0이 사라지면 조인이 조용히 실패하고, 발견은 몇 주 뒤 정합성 검증에서 된다. **금융·공공 도메인에서 이건 이론이 아니라 실제 사고 유형**이다.
- **인수인계 문서의 성격이 달라진다.** 설정이 YAML로 코드화되면 "운영 가이드 스크린샷" 대신 저장소를 넘기게 된다. 다만 **YAML을 읽을 줄 아는 고객 담당자가 있어야** 그 산출물이 의미가 있다. 인수인계 계획에 "YAML/번들 구조 설명 세션"을 명시적으로 넣어두는 편이 안전하다.

> **토론거리:** 우리 프로젝트에서 **YAML 검증을 어느 수준까지 CI에 강제할 것인가?** 린트 실패를 경고로 둘 것인가 빌드 실패로 둘 것인가 — 초기에는 경고로 시작해도, 한 번 사고가 나면 실패로 올려야 한다는 게 대체적 경험이다. 그리고 **공통 설정(클러스터 사양, 태그 정책, 공통 파라미터)을 어디에 둘 것인가?** 복합 변수 하나로 모을지, 환경별로 따로 쓸지에 따라 나중에 사양을 바꿀 때 고쳐야 할 파일 수가 1개와 20개로 갈린다. 마지막으로, **`.yaml` 파일도 코드 리뷰 대상인가?** 잡 스케줄과 클러스터 사양 변경은 코드 변경보다 사고 영향이 큰 경우가 많은데, 실제로는 "설정이니까" 하고 가볍게 승인되는 경향이 있다.
