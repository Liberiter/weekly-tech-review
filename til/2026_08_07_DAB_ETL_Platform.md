# 2026-08-07. 배포·ETL·플랫폼 구조 — 하루치 교육을 근본부터 다시 세우기

> 오늘 들은 내용은 세 덩어리였다. **번들 단위 배포(DAB)**, **ETL 파이프라인 설계**, **Databricks 플랫폼 자체의 구조**.
>
> 겉보기엔 따로 노는 주제지만, 정리해보니 전부 같은 질문 하나로 수렴했다 — **"이 결정의 실체가 어디에 있는가."** 코드에 있는가 워크스페이스 DB에 있는가, 우리 클라우드 계정에 있는가 벤더 계정에 있는가, 쿼리 시점에 계산되는가 미리 물리적으로 만들어져 있는가.
>
> 받아 적은 메모 + 공식 문서로 다시 확인한 내용을 합쳐서 적었다. **메모가 틀렸던 지점은 숨기지 않고 따로 표시**했다. 회사 고유 명칭은 일반 명사로 바꿨다.

|---|---|---|---|
| 1 | **번들 단위 작업** | 잡·파이프라인·설정을 디렉터리 하나로 묶어 YAML로 선언 | 워크스페이스 DB에만 있던 설정을 **Git 안으로** 끌어오는 것 |
| 2 | **도구 세트** | CLI + 에이전트용 skill + MCP 서버 | skill = **어떻게**의 지식, MCP = **무엇을 할 수 있나**의 능력. 층이 다르다 |
| 3 | **artifacts = 공용 wheel** | 팀이 함께 쓰는 파이썬 패키지를 wheel로 빌드해 배포 | 공통 코드를 **버전이 붙은 배포 단위**로 만들어야 재현성이 생긴다 |

| 5 | **lookup** | 이름으로 ID를 찾아주지만 배포 시 API를 한 번 탄다 | 편의의 대가는 **배포 시점 의존성**. 이름 규약이 계약이 된다 |
| 6 | **브랜치 통일** | 앞으로 `dev`/`qa`/`master` 세 개만 | 브랜치 = 환경. **배포 target과 1:1**로 맞춰야 오배포가 구조적으로 막힌다 |
| 7 | **write_mode 3종** | overwrite / append / merge | 진짜 축은 성능이 아니라 **재실행 안전성(멱등성)** |
| 8 | **cache로 두 벌 쓰기** | 원본·마스킹본을 만들 때 `cache()`로 재계산 방지 | Spark는 **action마다 처음부터 다시 읽는다.** cache는 그 재계산을 끊는 것 |
| 9 | **Metric View → MV** | `materialization` 필드로 물리 MV를 만들고 자동 rewrite | 에이전트가 **매번 조인을 다시 하지 않게** 미리 계산해 두는 것 |
| 10 | **원천 연결** | JDBC 직접 vs Lakehouse Federation | 제어권과 운영 부담의 교환. **드라이버를 누가 관리하느냐** |
| 11 | **암호화 대상 지정** | Unity Catalog 태그로 "이 컬럼은 마스킹 대상" 표시 | 태그는 **정책의 입력값**. 규칙과 대상 목록을 분리하는 장치 |
| 12 | **Catalog 4종** | Tables / Volumes / Models / Shares | 정형·비정형·모델·외부공유를 **하나의 권한 체계** 아래 놓는 것 |
| 13 | **Control/Compute Plane** | 뇌는 벤더 계정, 손발은 계정이 갈린다 | 서버리스가 빠른 이유가 곧 **우리 VPC 밖에 있는 이유**다 |

### 메모가 틀렸던 곳 — 먼저 정정

내가 받아 적은 것 중 **문서와 어긋난 세 가지**를 먼저 박아둔다. 이걸 그대로 믿고 설계하면 시간을 날린다.

| 메모 | 실제 | 왜 중요한가 |
|---|---|---|
| "DBU = **Data**Base Unit, 일반적으로 2~4 core" | **Databricks Unit**. 코어 수가 아니라 **시간당 정규화된 소비 단위**. 인스턴스 타입별 계수가 따로 정해져 있다 | "코어 수"로 이해하면 비용 추정이 통째로 틀린다. DBU는 **성능 지표가 아니라 과금 지표**다 |
| "Metastore와 Workspace는 **M:N**" | **Workspace : Metastore = N:1** (워크스페이스 하나는 정확히 메타스토어 하나에 배정). M:N인 건 **Catalog ↔ Workspace** 관계(workspace-catalog binding) | "워크스페이스를 지워도 카탈로그는 남는다"는 결론은 **맞다.** 다만 그 이유가 M:N이어서가 아니라 **카탈로그의 소유주가 메타스토어(계정 레벨)이기 때문**이다 |
| "서버리스는 Redshift에 **연결하지 못한다**" | **기본 상태로는** 못 한다. NCC(Network Connectivity Configuration)로 고정 egress IP를 받아 방화벽에 허용하거나 PrivateLink 사설 엔드포인트를 걸면 된다 | "불가능"과 "계정 레벨 설정이 필요하다"는 완전히 다른 결론이다. 전자는 설계를 포기하게 만들고 후자는 티켓 하나를 만든다 |

# Part 1. 배포 — 번들이라는 작업 단위

## 1. 번들 단위로 일한다는 것의 의미

### 문제부터

데이터 플랫폼에서 만드는 산출물을 성격으로 나누면 두 종류다.

- **코드** — 노트북, 파이썬 파일, SQL. Git에 들어간다. 리뷰되고, 이력이 남고, 되돌릴 수 있다.
- **리소스 설정** — "이 노트북을 매일 03시에, 이런 사양의 클러스터에서, 이 순서로, 이 권한으로 돌린다." **어디에도 안 들어간다.** 워크스페이스 내부 DB에만 있다.

두 번째가 문제 전체다. 파이프라인이 **실제로 어떻게 동작하는지를 결정하는 정보의 절반**이 버전 관리 밖에 있다. 그래서 이런 일이 생긴다.

```
   운영 잡의 재시도 횟수가 3 이다.
   누가?  언제?  왜 바꿨나?
        └─▶ 답할 방법이 없다. 로그도 없고 diff도 없다.

   dev 에서 되던 게 prod 에서 안 된다.
   코드는 동일하다.
        └─▶ 원인은 클러스터 런타임 버전 차이였다.
            그런데 그 사실을 알아내는 데 반나절이 걸린다.
```

**번들(bundle)** 은 이 지점을 정확히 겨냥한다.

> **번들 = 프로젝트의 소스 코드 + 리소스 정의 + 배포 설정을 한 디렉터리에 묶고, YAML로 선언한 것.**

```
my_project/
├── databricks.yml          ★ 번들의 뿌리. 이름·타깃·워크스페이스 설정
├── resources/
│   ├── jobs/
│   │   └── daily_batch.yml     "이 잡은 이렇게 생겼다"
│   └── variables/
│       └── variables.yml       환경별로 달라지는 값
├── src/
│   ├── ingest.py
│   └── transform.py
└── pyproject.toml          artifacts 빌드 대상
```

`databricks bundle deploy -t prod` 한 번이면 이 디렉터리 전체가 대상 워크스페이스에 **선언된 모양 그대로** 실체화된다.

### "번들 단위로 작업한다"가 바꾸는 습관

이건 도구 사용법이 아니라 **작업 단위의 정의**가 바뀌는 일이다.

| | 번들 이전 | 번들 이후 |
|---|---|---|
| 작업 시작 | 워크스페이스에서 노트북을 연다 | 로컬에서 리포를 클론한다 |
| 잡 수정 | UI에서 필드를 바꾸고 저장 | YAML을 고치고 PR을 올린다 |
| 검증 | 돌려보고 눈으로 확인 | `bundle validate` → 스키마 검사 |
| 환경 이관 | 스크린샷 보며 손으로 재현 | `deploy -t qa` |
| 롤백 | ??? | `git revert` 후 재배포 |
| "누가 바꿨나" | 모른다 | `git blame` |

> **핵심 통찰 — "번들의 진짜 가치는 배포 자동화가 아니라 '설정의 코드화'다"**
>
> 번들을 "배포를 편하게 해주는 도구"로 소개하면 절반만 맞다. 배포 자동화는 **결과**이고, 원인은 **워크스페이스에만 존재하던 리소스 설정을 Git 안으로 끌어온 것**이다.
>
> 이게 되는 순간 따라오는 것들이 있다. 스케줄 변경이 **PR과 코드 리뷰의 대상**이 된다. 장애 시 직전 커밋으로 롤백하면 **리소스 설정까지 같이** 되돌아간다. dev와 prod의 차이가 **YAML의 diff**로 보인다.
>
> 즉 번들은 배포 시간을 줄이는 도구가 아니라, **데이터 프로젝트를 소프트웨어 프로젝트처럼 다룰 수 있게 만드는 전제 조건**이다. 자동화는 그 위에 얹히는 부산물이다.

### 번들 경계는 어떻게 정하나

"번들 단위로 작업한다"는 말이 나오면 곧바로 따라오는 질문이 있다 — **번들 하나에 뭘 넣나?**

기준은 크기가 아니다. **함께 배포되고 함께 롤백되는 것들**이 한 번들이다.

```
   [같은 번들에 넣어야 하는 신호]
   · 같이 배포하지 않으면 깨진다     (잡 A가 잡 B의 산출물을 읽는다)
   · 같이 롤백해야 의미가 있다       (스키마 변경 + 그걸 쓰는 잡)
   · 소유 팀이 같다                  (장애 시 같은 사람이 본다)

   [번들을 나눠야 하는 신호]
   · 배포 주기가 다르다              (일 1회 vs 분기 1회)
   · 권한 경계가 다르다              (개인정보 취급 vs 일반)
   · 실패해도 서로 무관하다
```

번들을 지나치게 크게 잡으면 **한 곳의 배포 실패가 전부를 막고**, 지나치게 잘게 쪼개면 **의존 관계가 번들 경계를 넘나들면서** 배포 순서를 사람이 기억해야 한다. 후자가 더 위험하다.

## 2. 도구 세트 — CLI · skill · MCP는 각각 무슨 층인가

오늘 세 가지 도구가 나란히 언급됐다. **CLI**, **에이전트용 skill**, **MCP 서버**. 이름만 들으면 다 "도구"지만, 실제로는 **완전히 다른 층에 있다.** 이걸 구분하는 게 앞으로 도구를 고를 때 계속 쓰인다.

```
 ┌────────────────────────────────────────────────────────────┐
 │  사람 / 에이전트                                           │
 └────────────────────────────────────────────────────────────┘
        │                         │
        │ 절차 지식               │ 능력(도구 접근)
        ▼                         ▼
 ┌───────────────┐        ┌──────────────────┐
 │    skill      │        │   MCP 서버       │
 │               │        │                  │
 │ "이 상황에서  │        │ "이 시스템을     │
 │  이렇게 한다" │        │  호출할 수 있다" │
 │               │        │                  │
 │ = 문서 + 절차 │        │ = 도구 스펙 +    │
 │   + 예시      │        │   실행 엔드포인트│
 └───────────────┘        └──────────────────┘
        │                         │
        └────────────┬────────────┘
                     ▼
            ┌─────────────────┐
            │      CLI        │
            │  실제 API 호출  │
            └─────────────────┘
                     ▼
              플랫폼 REST API
```

세 층의 역할을 한 문장씩 정리하면:

| 층 | 무엇인가 | 없으면 생기는 일 |
|---|---|---|
| **CLI** | 플랫폼 API를 명령으로 감싼 것. 사람도 스크립트도 CI도 쓴다 | 배포를 REST 호출로 직접 짜야 한다 |
| **skill** | "이 작업은 이런 순서와 규약으로 한다"는 **절차 지식**을 에이전트에 주입 | 에이전트가 도구는 쓸 줄 알아도 **우리 팀 규약을 모른다** |
| **MCP** | 에이전트가 외부 시스템을 **호출할 수 있게** 하는 표준 프로토콜 | 에이전트가 알아도 **실행할 손이 없다** |

> **핵심 통찰 — "skill은 '어떻게'를, MCP는 '무엇을 할 수 있나'를 준다. 둘 다 있어야 자동화가 된다"**
>
> 에이전트에게 MCP만 붙이면 **능력은 있는데 규약을 모르는 신입**이 된다. 배포는 할 수 있는데 우리 팀이 어느 타깃에 어떤 순서로 배포하는지는 모른다. 반대로 skill만 주면 **규약은 아는데 손이 없는 컨설턴트**가 된다.
>
> 그래서 도구를 붙일 때 물어야 할 질문은 "이 도구가 좋은가"가 아니라 **"이건 지식인가 능력인가, 그리고 나머지 반쪽은 있는가"** 다.
>
> 실무적으로는 **skill이 더 중요하고 더 어렵다.** 능력은 벤더가 주지만, 규약은 우리가 써야 하고 우리 조직에만 있다. 그리고 그 규약은 대개 **아무 데도 안 적혀 있고 사람 머릿속에만 있다.** skill을 쓰는 작업은 사실상 **암묵지를 문서로 꺼내는 작업**이다.

한 가지 실무 감각을 덧붙이면 — **skill을 쓰는 건 팀 온보딩 문서를 쓰는 것과 거의 같은 일**이다. 신입에게 설명해야 하는 것과 에이전트에게 설명해야 하는 것의 목록이 놀랄 만큼 겹친다. 그래서 skill이 잘 정비된 팀은 대개 온보딩도 빠르다. 역도 성립한다.

## 3. artifacts — 공용 wheel이 번들에 들어가는 이유

### 무엇인가

메모: *"artifact는 팀원들이 공통으로 사용하는 python 패키지 wheel 파일들의 모음"*

정확하다. 여기서 파고들 지점은 **왜 하필 wheel인가**다.

팀이 공통 코드를 공유하는 방법은 여러 가지다.

```
 ① 복붙                       — 최악. 열 군데에 열 개의 버전이 산다
 ② 공용 노트북을 %run 으로 호출 — 경로 결합, 버전 없음, 테스트 불가
 ③ 리포에 공용 디렉터리 두고 sys.path 조작 — 로컬에선 되는데 잡에선 깨진다
 ④ wheel 로 빌드해서 라이브러리로 설치  ★
```

wheel이 이기는 이유는 셋이다.

| | 왜 |
|---|---|
| **버전이 붙는다** | `mylib-1.4.2-py3-none-any.whl`. "어제 돌던 그 코드"를 특정할 수 있다 |
| **의존성이 선언된다** | `pyproject.toml`에 적힌 의존이 설치 시 같이 해결된다 |
| **일반 파이썬 패키지가 된다** | 로컬에서 `pip install -e .` 하고 **pytest로 테스트**할 수 있다. 노트북 안에 있는 코드는 이게 안 된다 |

세 번째가 가장 크다. **노트북에 있는 코드는 테스트할 수 없다.** 공통 로직을 wheel로 빼는 순간, 그 로직은 **유닛 테스트가 붙는 소프트웨어**가 되고 노트북은 **그걸 호출하는 얇은 껍데기**가 된다.

```
   [before]                          [after]
   notebook (500줄)                  notebook (20줄)
   ├ 설정 파싱                        └ from mylib import run_daily
   ├ 원천 접속                            run_daily(date=dbutils.widgets...)
   ├ 변환 로직 200줄
   ├ 검증                            mylib/  ← wheel. pytest 있음.
   └ 적재                            ├ config.py     테스트 O
                                     ├ io.py         테스트 O
   테스트 불가. 재사용 불가.         ├ transform.py  테스트 O ★
   리뷰도 diff 가 깨진다             └ validate.py   테스트 O
```

### 번들에서의 선언

번들은 wheel 빌드까지 배포 파이프라인 안으로 끌어온다.

```yaml
artifacts:
  my_lib:
    type: whl
    path: ./libs/my_lib
    build: poetry build          # 또는 python -m build

resources:
  jobs:
    daily_batch:
      tasks:
        - task_key: transform
          python_wheel_task:
            package_name: my_lib
            entry_point: run_daily
          libraries:
            - whl: ../libs/my_lib/dist/*.whl
```

`bundle deploy` 시 **빌드 → 업로드 → 잡 정의에 라이브러리로 연결**까지 한 번에 일어난다. 업로드 위치는 번들의 `artifact_path` 아래 `.internal` 디렉터리다.

### 밟기 쉬운 지뢰

**같은 버전 번호로 wheel을 다시 배포하면, 이미 떠 있는 클러스터가 새 코드를 못 볼 수 있다.** 파이썬 패키지 설치는 "이미 그 버전이 있으면 건너뛴다"가 기본 동작이기 때문이다. 코드는 바꿨는데 결과가 그대로여서 한참 헤매게 되는 전형적인 함정이다.

대응은 둘 중 하나다.

```
 ① 빌드마다 버전을 올린다 (개발 중엔 dev 버전 접미사로 자동 증가)
 ② 배포 후 클러스터를 재시작한다 (잡 클러스터·서버리스는 매 실행 새로 뜨므로 무관)
```

**잡 클러스터나 서버리스를 쓰면 이 문제 자체가 없다.** 매 실행마다 환경이 새로 구성되기 때문이다. 이건 "전용 클러스터를 계속 띄워두는 것"이 왜 개발 편의 이상의 비용을 갖는지를 보여주는 예이기도 하다.

> **핵심 통찰 — "공통 코드를 wheel로 빼는 결정은 재사용이 아니라 테스트 가능성을 위한 것이다"**
>
> "여러 잡에서 같은 함수를 쓰니까 라이브러리로 뺀다"는 흔한 설명은 부수적인 이유다. 진짜 이유는 **노트북 안의 코드에는 테스트를 붙일 수 없다는 것**이다.
>
> 데이터 파이프라인의 버그는 대부분 **예외가 아니라 조용히 틀린 값**으로 나타난다. 잡은 초록불인데 숫자가 이상하다. 이런 버그를 잡는 유일한 방법이 **로직 단위 테스트**인데, 그러려면 로직이 먼저 **호출 가능한 함수**여야 한다.
>
> 그래서 wheel로 빼는 작업의 성과는 "코드 중복이 줄었다"가 아니라 **"파이프라인의 핵심 변환 로직에 처음으로 테스트가 생겼다"** 로 측정해야 한다.

## 4. 배포 위치 — `root_path`가 기본값이면 안 되는 이유

메모: *"배포 방법 두 가지 — ① CI/CD 계정으로 배포 ② root_path에 배포"*

이 둘은 사실 **대립하는 선택지가 아니라 서로 다른 축**이다. 정확히 풀면 배포에는 **독립적인 세 가지 정체성**이 있다.

```
   ┌──────────────────────────────────────────────────────┐
   │ ① 배포 주체 (누가 deploy 명령을 실행했나)            │
   │    → 내 계정?  CI/CD 서비스 프린시펄?                │
   ├──────────────────────────────────────────────────────┤
   │ ② 배포 위치 (파일이 워크스페이스 어디에 놓이나)      │
   │    → root_path                                       │
   ├──────────────────────────────────────────────────────┤
   │ ③ 실행 주체 (돌아갈 때 누구 권한으로 도나)           │
   │    → run_as                                          │
   └──────────────────────────────────────────────────────┘
        이 셋은 서로 독립이다. 구별 못 하면 사고 난다.
```

### 기본값이 무엇인지가 핵심이다

`root_path`를 지정하지 않으면 기본값은 이렇다.

```
   ~/.bundle/${bundle.name}/${bundle.target}

   실제로 풀리면:
   /Workspace/Users/<배포한 사람의 이메일>/.bundle/daily_etl/prod
                     ▲
                     └─ 여기가 문제다
```

즉 **번들의 정체성 = 배포자 + 번들명 + 타깃**이다. 이 기본값이 개발에는 훌륭하다. 팀원 다섯 명이 같은 번들을 각자 배포해도 서로 안 밟는다.

그런데 **운영에서는 이게 정확히 사고의 형태**다.

```
   [기본 root_path 로 운영 배포했을 때]

   김OO 이 8월에 배포  → /Workspace/Users/kim@.../.bundle/etl/prod
   김OO 퇴사          → 계정 비활성화
                        └─▶ 운영 잡의 소스 파일이 사라진 계정 홈에 있다
   이OO 이 재배포     → /Workspace/Users/lee@.../.bundle/etl/prod
                        └─▶ ★ 같은 이름의 잡이 두 개가 된다
                            (state 파일이 달라서 서로를 모른다)
```

그래서 운영 타깃에는 **결정적(deterministic)인 공용 경로를 명시**한다.

```yaml
targets:
  prod:
    mode: production
    workspace:
      host: https://<prod-workspace>
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    run_as:
      service_principal_name: <application-id>
    permissions:
      - level: CAN_MANAGE
        group_name: data-platform
```

`root_path` 아래에는 자동으로 하위 경로들이 파생된다.

```
   root_path/
   ├── files/      ← 소스 코드 (file_path)
   ├── artifacts/  ← wheel 등 (artifact_path)
   ├── state/      ← 배포 상태 파일 (state_path)  ★ 가장 중요
   └── resources/
```

`state/`가 결정적이다. 번들은 여기 있는 상태 파일로 **"내가 지난번에 뭘 만들었는지"** 를 기억한다. 그래서 **경로가 바뀌면 기억을 잃고, 기억을 잃으면 기존 리소스를 자기 것으로 인식하지 못해 중복 생성**한다.

### `mode: production`이 대신 잡아주는 것

번들에는 이 실수를 막는 안전장치가 이미 들어 있다. `mode: production`을 켜면 배포 시 이런 검증이 돈다.

- 서비스 프린시펄로 배포하지 않는 경우, **`root_path`·`artifact_path`·`file_path`·`state_path`가 특정 개인에게 묶여 있지 않은지** 검증한다.
- `run_as`와 `permissions`를 **명시하도록 요구**한다.
- 파이프라인이 `development: false`인지 확인한다.
- `git.branch`를 지정했다면 **현재 브랜치가 그 브랜치인지** 확인한다(`--force`로 우회 가능).

반대로 `mode: development`는 정반대로 움직인다. 리소스 이름에 `[dev <사용자>]` 접두사를 붙이고, **모든 스케줄과 트리거를 일시정지**하고, 동시 실행을 허용한다. dev 워크스페이스에서 개인 배포가 새벽 3시에 알림을 쏘지 않는 게 이 덕분이다.

> **핵심 통찰 — "'누가 배포했나'가 '배포된 것의 정체성'에 섞여 들어가면 운영이 사람에 묶인다"**
>
> 번들의 기본 정체성에 **배포자**가 들어 있다는 사실은 개발 편의를 위한 훌륭한 기본값이면서, 동시에 **운영에서 반드시 걷어내야 할 기본값**이다.
>
> 판단 기준은 단순하다 — **"이 배포물의 수명이 특정 사람의 재직 기간보다 긴가?"** 길면 사람에 묶으면 안 된다. 운영 파이프라인은 언제나 그렇다.
>
> 그래서 "CI/CD 계정으로 배포한다"와 "root_path를 명시한다"는 둘 중 하나를 고르는 게 아니라 **같은 목표(사람에서 분리)를 향한 두 개의 조치이고, 운영에서는 둘 다 해야 한다.** 서비스 프린시펄로 배포하되 `root_path`를 안 박으면 이번엔 **서비스 프린시펄의 홈**에 놓일 뿐이다.

## 5. lookup — 편의의 정확한 청구서

메모: *"lookup: 편리하고 하드코딩 하지 않아도 되지만, databricks api를 한 번 거쳐야 한다."*

이 한 줄에 트레이드오프가 정확히 들어 있다. 풀어본다.

### 문제

번들 YAML에는 **환경마다 다른 ID**를 써야 하는 자리가 계속 나온다. 클러스터 ID, 웨어하우스 ID, 인스턴스 풀 ID, 알림 대상 ID.

```yaml
# 하드코딩
existing_cluster_id: 0801-123456-abcd1234
```

이 값의 죄는 "값이 예쁘지 않다"가 아니다. **이 YAML이 특정 워크스페이스에 결합됐다**는 것이다. 다른 워크스페이스에 배포하면 그 ID는 존재하지 않거나, 더 나쁘게는 **엉뚱한 클러스터를 가리킨다.**

### lookup

```yaml
variables:
  batch_cluster_id:
    description: 배치용 공용 클러스터
    lookup:
      cluster: "shared-batch-cluster"     # ID가 아니라 이름으로 참조

resources:
  jobs:
    daily_batch:
      tasks:
        - task_key: t1
          existing_cluster_id: ${var.batch_cluster_id}
```

배포 시점에 CLI가 API를 호출해 그 **이름**의 오브젝트 ID를 찾아 채운다. 지원 대상은 cluster, warehouse, job, pipeline, instance_pool, cluster_policy, dashboard, query, metastore, service_principal, notification_destination, alert 등이다.

### 대가를 정확히 계산하면

| 얻는 것 | 치르는 것 |
|---|---|
| YAML이 워크스페이스에 독립적이 된다 | **배포가 대상 워크스페이스 상태에 의존**한다 |
| 클러스터를 재생성해 ID가 바뀌어도 YAML 불변 | 이름이 **없으면 배포 실패**. 이름이 **둘 이상이어도 실패** |
| 사람이 읽을 수 있는 값이 코드에 남는다 | 배포 주체에게 **그 오브젝트 조회 권한**이 필요하다 |
| | API 왕복만큼 **배포가 느려진다** (리소스가 많으면 체감된다) |

**"이름이 둘 이상이면 실패한다"** 는 조건이 실무에서 가장 자주 문다. 누군가 클러스터를 복제하면서 이름을 그대로 두면, 그날 밤 CI 배포가 깨진다. 코드는 한 줄도 안 바뀌었는데.

> **핵심 통찰 — "lookup은 하드코딩을 없애는 게 아니라, 결합의 대상을 ID에서 이름으로 옮기는 것이다"**
>
> lookup을 쓰면 "하드코딩을 제거했다"고 느끼기 쉽지만, 사실은 **결합이 사라진 게 아니라 옮겨간 것**이다. 이제 우리 YAML은 `"shared-batch-cluster"`라는 **이름의 존재와 유일성**에 결합돼 있다.
>
> 이 교환이 남는 장사인 이유는 하나다 — **이름은 사람이 관리할 수 있고 ID는 못 한다.** ID는 재생성 때마다 바뀌고 아무도 못 외우지만, 이름은 명명 규약을 세우고 지킬 수 있다.
>
> 다만 그 순간 **이름 규약이 문서가 아니라 계약**이 된다. "환경마다 같은 이름의 클러스터가 정확히 하나씩 존재한다"가 지켜져야 배포가 성립한다. lookup을 도입하면서 이 규약을 안 세우면, 편의를 얻고 **원인 파악이 어려운 배포 실패**를 얻는다.
>
> 그리고 더 나은 답이 있는 경우가 많다 — **애초에 기존 클러스터를 참조하지 않는 것.** `job_clusters`로 잡 전용 클러스터를 번들 안에 정의하거나 서버리스를 쓰면, 참조할 외부 오브젝트가 없으니 lookup도 필요 없다. **가장 좋은 의존성은 없는 의존성이다.**

## 6. 브랜치 전략을 셋으로 줄인다는 결정

메모: *"인프라 조직과 우리 조직이 관리하는 브랜치 전략이 다르다. 앞으로는 dev, qa, master 세 브랜치만 쓴다."*

### 왜 통일이 필요했나

브랜치 전략이 조직마다 다르면, **문제는 각 조직 안이 아니라 경계에서 터진다.**

```
   조직 A: main / develop / feature/* / release/* / hotfix/*   (Git Flow)
   조직 B: master / dev / qa                                   (환경 브랜치)

   경계에서 벌어지는 일:
   · "release 브랜치는 어디에 배포되나요?"  → 대응되는 환경이 없다
   · "qa 로 머지했는데 왜 안 올라가죠?"      → A쪽 CI는 qa 를 모른다
   · hotfix 를 어느 브랜치에서 따야 하나     → 답이 조직마다 다르다
```

브랜치 전략은 **취향이 아니라 인터페이스**다. 조직이 다른 인터페이스를 쓰면 통합 지점마다 변환기가 필요하고, 그 변환기는 대개 **사람의 기억**으로 구현된다.

### `dev` / `qa` / `master` 세 개의 의미

이건 **환경 브랜치 모델(environment branching)** 이고, 번들의 `targets`와 **1:1로 대응시키는 게 핵심**이다.

```
   브랜치        타깃         워크스페이스        배포 트리거
   ──────────────────────────────────────────────────────────
   dev      →   dev      →   개발 워크스페이스    push 시 자동
   qa       →   qa       →   검증 워크스페이스    merge 시 자동
   master   →   prod     →   운영 워크스페이스    merge 시 자동 (승인 필요)

   ★ 대응이 1:1 이면, "브랜치를 머지한다" = "환경에 배포한다" 가 된다.
     배포는 별도의 행위가 아니라 머지의 결과다.
```

여기에 앞에서 본 `mode: production`의 **git 브랜치 검증**을 붙이면 마지막 안전장치가 완성된다.

```yaml
targets:
  prod:
    mode: production
    git:
      branch: master     # 현재 브랜치가 master가 아니면 배포 거부
```

로컬에서 실험하다가 실수로 `deploy -t prod`를 쳐도 막힌다. **규칙을 사람의 주의력이 아니라 도구가 강제**하게 만드는 것이다.

### 세 개가 적당한 이유

브랜치 수를 정하는 진짜 기준은 **"실제로 존재하는 환경의 수"** 다.

```
   브랜치 > 환경  →  어떤 브랜치는 배포될 곳이 없다.
                     "이 브랜치는 뭐 하는 거죠?" 가 반복된다.
   브랜치 < 환경  →  한 브랜치가 여러 환경에 배포된다.
                     "지금 qa에 올라간 게 어느 커밋이죠?" 에 답할 수 없다.
   브랜치 = 환경  →  브랜치 이름이 곧 "지금 어디에 뭐가 떠 있는지"의 답.  ★
```

Git Flow의 `release/*`나 `hotfix/*`가 통합 환경에서 유독 애물단지가 되는 이유가 여기 있다. **대응되는 환경이 없는 브랜치**이기 때문이다.

> **핵심 통찰 — "브랜치 전략은 코드 관리 규칙이 아니라 배포 인터페이스다"**
>
> 브랜치 전략을 "우리 팀이 코드를 어떻게 관리할지"의 문제로 보면 조직마다 달라도 괜찮아 보인다. 실제로 각 조직 안에서는 괜찮다.
>
> 그런데 **브랜치가 배포 타깃과 묶이는 순간 브랜치는 공개 인터페이스가 된다.** "master에 머지하면 운영에 나간다"는 사실은 그 리포를 건드리는 **모든 사람이 공유해야 하는 지식**이다. 인터페이스가 조직마다 다르면 통합 비용은 조직 수의 제곱으로 늘어난다.
>
> 그래서 통일의 이득은 "깔끔해진다"가 아니라 **"머지한 사람이 자기가 뭘 했는지 안다"** 는 것이다. 그리고 그 대응이 1:1일 때, **배포는 별도의 행위가 아니라 머지의 결과**가 된다. 배포를 잊어버릴 방법이 없어진다.

# Part 2. ETL — 데이터를 어떤 상태로 만들 것인가

## 7. write_mode 세 가지 — 진짜 축은 멱등성이다

`overwrite` / `append` / `merge`. 보통 성능과 편의로 설명되지만, **실무에서 이걸 고르는 진짜 기준은 "같은 배치를 두 번 돌렸을 때 무슨 일이 나는가"** 다.

파이프라인은 **반드시 두 번 돌게 되어 있다.** 실패 후 repair, 상류 지연으로 인한 재실행, 백필. 그래서 write_mode 선택은 **재실행 안전성 선택**이다.

### 세 가지 정면 비교

| | `overwrite` | `append` | `merge` |
|---|---|---|---|
| 동작 | 대상 범위를 지우고 다시 씀 | 뒤에 붙임 | 키로 매칭해 update/insert |
| **두 번 돌리면** | ✅ 같은 결과 (멱등) | ❌ **행이 두 배** | ✅ 같은 결과 (멱등) |
| 상류 수정 반영 | ✅ 자동 | ❌ 안 됨(중복) | ✅ 자동 |
| 상류 삭제 반영 | ✅ 자동 | ❌ 안 됨 | △ 별도 절 필요 |
| 비용 | 범위가 크면 비쌈 | **가장 쌈** | 조인 비용. 키 분포에 민감 |
| 이력 보존 | ❌ 지워짐 | ✅ 그대로 | △ 덮어씀 |
| 적합 | 일 단위 스냅샷, 소규모 팩트 | append-only 로그·이벤트 | 변경분(CDC) 반영, SCD |

**`append`만 멱등하지 않다.** 그런데 가장 싸고 가장 단순해서 가장 많이 선택된다. 이 조합이 위험하다.

```
   [append 로 짠 일 배치의 전형적 사고]

   03:00  배치 시작 → 8/6 데이터 100만 행 append → 04:00 성공
   09:00  "어제 데이터가 이상하다" → 담당자가 repair 버튼
          → 8/6 데이터 100만 행 다시 append
          → 총 200만 행. 잡은 초록불. 대시보드 숫자만 두 배.  ★
```

**잡이 실패하지 않는다는 게 이 사고의 핵심**이다. 아무도 알림을 못 받는다. 숫자를 보는 사람이 이상함을 느낄 때까지 아무 일도 일어나지 않는다.

### `overwrite`를 안전하게 쓰는 법

전체 테이블 덮어쓰기는 멱등하지만 비싸고, 실패하면 **테이블이 비어 있는 순간**이 생긴다. 그래서 실무에서는 **범위를 좁힌 덮어쓰기**를 쓴다.

```python
# 특정 조건 범위만 원자적으로 교체 — 나머지 파티션은 건드리지 않는다
(df.write
   .format("delta")
   .mode("overwrite")
   .option("replaceWhere", "dt = '2026-08-07'")
   .saveAsTable("catalog.schema.daily_fact"))
```

이러면 **"오늘치만 다시 만든다"** 가 되어 재실행이 싸고 안전해진다. Delta의 쓰기는 트랜잭션이라 **성공하기 전까지 독자에게는 이전 버전이 보인다.** 실패해도 빈 테이블이 노출되지 않는다.

### `merge`의 함정

`merge`는 멱등하고 강력하지만 **조인**이다. 즉 비용이 데이터 크기가 아니라 **매칭 대상의 크기**에 비례한다.

```sql
MERGE INTO tgt t
USING src s
  ON t.id = s.id AND t.dt >= '2026-08-01'   -- ★ 이 조건이 없으면 전체 스캔
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
```

`ON` 절에 **파티션/범위 조건을 넣어 스캔 범위를 자르는 것**이 merge 튜닝의 8할이다. 이게 없으면 매일 전체 테이블을 다시 읽는다.

그리고 삭제 반영이 필요하면 절을 하나 더 써야 한다.

```sql
WHEN NOT MATCHED BY SOURCE AND t.dt >= '2026-08-01' THEN DELETE
```

이 절을 빼먹으면 **"원천에서 지운 데이터가 우리 쪽에는 영원히 남는다."** 조용히 틀리는 종류의 버그다.

> **핵심 통찰 — "write_mode는 성능 선택이 아니라 재실행 정책 선택이다"**
>
> 배치는 반드시 두 번 돈다. 실패해서 돌고, 백필로 돌고, 누가 버튼을 잘못 눌러서 돈다. 그러니 write_mode를 고를 때 첫 질문은 성능이 아니라 **"두 번 돌아도 괜찮은가"** 여야 한다.
>
> 이게 중요한 이유는 **repair 버튼의 의미가 write_mode에 따라 정반대가 되기 때문**이다. 멱등한 태스크에서 repair는 **복구**지만, `append` 태스크에서 repair는 **데이터 오염**이다. 그런데 UI의 버튼은 똑같이 생겼다.
>
> 실무 규칙 하나로 압축하면 — **"repair를 눌러도 되는가"를 코드가 아니라 사람의 기억에 의존시키지 마라.** 멱등하지 않은 태스크를 만들 거면, 최소한 **잡 이름이나 태스크 이름에 그 사실이 드러나야** 한다.

## 8. cache — 두 벌로 나눠 쓸 때 왜 안 느려지나

메모: *"원본과 암호화본 두 개로 나눠서 넣을 때는 cache(spark의 persist)를 사용하기 때문에 오래 걸리지 않는다."*

이걸 제대로 이해하려면 **Spark가 왜 그냥 두면 두 번 일하는지**부터 봐야 한다.

### Spark는 action마다 처음부터 다시 한다

Spark의 변환(`select`, `filter`, `join`…)은 **게으르다(lazy).** 실행 계획만 쌓고 아무것도 안 한다. 실제 계산은 **action**(`write`, `count`, `collect`…)이 호출될 때 일어난다.

문제는 여기다 — **action마다 그 계획을 처음부터 다시 실행한다.**

```
   df = 원천 읽기 → 필터 → 조인 → 파생컬럼        (계획만 쌓임)

   df.write... mart          ← action ① : 원천부터 전부 다시 계산
   df_enc.write... mart_enc  ← action ② : 원천부터 ★ 또 다시 계산

   결과: 원천을 두 번 읽고, 조인을 두 번 하고, 시간도 두 배.
```

**"같은 df니까 한 번만 계산하겠지"는 틀린 직관**이다. Spark는 그렇게 동작하지 않는다. df는 데이터가 아니라 **계산 방법의 설명서**이기 때문이다.

### cache가 하는 일

```python
df = (spark.read.table("src.raw_tbl")
        .filter("dt = current_date()")
        .join(dim, "member_id"))

df.cache()          # "이 결과는 계산해두고 재사용해라"
df.count()          # ★ action 을 한 번 태워서 실제로 적재시킨다

# 이제 아래 두 개는 원천을 다시 읽지 않는다
df.write.mode("overwrite").saveAsTable("gold.mart")
mask_columns(df).write.mode("overwrite").saveAsTable("gold.mart_enc")

df.unpersist()      # 다 썼으면 반드시 놓아준다
```

```
   [cache 없이]                    [cache 있음]

   원천 읽기 ─┐                    원천 읽기 ──┐
   조인      │→ mart               조인       │→ 캐시에 적재 ★
   파생      ─┘                    파생       ─┘
                                        │
   원천 읽기 ─┐                         ├──▶ mart
   조인      │→ mart_enc                └──▶ mart_enc
   파생      ─┘                              (캐시에서 바로)

   원천 2회, 조인 2회               원천 1회, 조인 1회
```

### 알아둬야 할 세부

| 사실 | 왜 중요한가 |
|---|---|
| **`cache()` = `persist(MEMORY_AND_DISK)`** | `cache()`는 기본 스토리지 레벨의 축약형일 뿐이다. 메모리가 모자라면 디스크로 흘린다 |
| **cache도 lazy다** | `cache()`만 부르면 아무 일도 안 일어난다. **action이 한 번 돌아야** 실제로 적재된다 |
| **메모리 압박 시 evict된다** | 쫓겨나면 **조용히 재계산**한다. 느려질 뿐 실패하지 않아서 원인을 못 찾는다 |
| **`unpersist()`를 해야 한다** | 안 하면 뒤에 오는 태스크가 쓸 메모리를 계속 물고 있는다 |
| **두 번 이하로 쓸 거면 손해** | 캐시 적재 자체가 비용이다. **재사용이 2회 이상**일 때만 이득 |

### 대안도 알고 있어야 한다

캐시가 유일한 답은 아니다. 특히 **결과가 아주 클 때**는 오히려 나쁘다.

```
 ① cache            — 중간 결과가 메모리에 들어갈 만할 때. 재사용 2회 이상.
 ② 중간 테이블로 실체화 — 결과가 클 때. 한 번 쓰고 두 번 읽는다.
                       느리지만 예측 가능하고, 디버깅도 쉽다.
 ③ mart 를 먼저 쓰고, mart_enc 를 mart 에서 파생
                       ★ 원천이 아니라 이미 저장된 테이블에서 읽으므로
                         재계산 자체가 없다. 대신 두 테이블에 순서 의존이 생긴다.
```

③은 특히 눈여겨볼 만하다. **마스킹본은 원본의 함수**이므로, 원본을 먼저 만들고 거기서 파생하면 캐시 없이도 재계산이 사라진다. 대신 **두 테이블 사이에 실행 순서 의존**이 생기고, 원본이 실패하면 마스킹본도 못 만든다. 무엇을 더 중요하게 볼지의 문제다.

> **핵심 통찰 — "cache는 저장이 아니라 계산 그래프를 자르는 가위다"**
>
> `cache()`를 "데이터를 메모리에 담아두는 것"으로 이해하면 언제 써야 하는지 감이 안 온다. 정확히는 **"이 지점부터 위쪽은 다시 계산하지 마라"고 계산 그래프에 표시하는 것**이다.
>
> 그래서 판단 기준이 명확해진다. 물어야 할 것은 "이 데이터가 큰가"가 아니라 **"이 지점 위쪽의 계산이 비싼가, 그리고 그 아래로 갈래가 둘 이상인가"** 다. 갈래가 하나면 캐시는 순손해다. 위쪽이 싸면(단순 파일 읽기) 역시 손해다.
>
> **원본/마스킹본처럼 하나의 계산에서 여러 산출물이 갈라지는 구조가 캐시의 교과서적 사례**인 이유가 여기 있다. 비싼 계산(원천 읽기 + 조인)이 갈림길 위에 있고, 갈래가 둘이다. 정확히 가위를 대야 할 자리다.

## 9. fact + dim 조인이 튜닝 지점이 되는 이유

메모에 튜닝 대상으로 **일별 팩트 테이블(+ 마스킹본) + 회원 차원 + 날짜 차원**이 지목됐다. 왜 하필 여기인가 — 우연이 아니다. **별 스키마에서 성능이 무너지는 자리는 거의 항상 정해져 있다.**

```
              ┌──────────────┐
              │  dim_date    │  작다 (수천 행)
              └───────┬──────┘
                      │
   ┌──────────┐  ┌────┴──────────────┐
   │dim_member│──│  daily_fact       │  크다 (수억 행)
   │  중간    │  │  일별 집계 팩트   │
   └──────────┘  └───────────────────┘
        ▲                 ▲
        │                 └── 여기가 셔플의 진원지
        └── 카디널리티가 높다 = 조인 키가 흩어진다
```

### 무엇이 실제로 느린가

| 증상 | 원인 | 대응 |
|---|---|---|
| 조인이 오래 걸린다 | 큰 테이블 양쪽을 셔플(sort-merge join) | **작은 차원은 브로드캐스트**되게 유도 |
| 특정 태스크만 안 끝난다 | **데이터 스큐** — 특정 회원/날짜에 행이 몰림 | AQE의 skew join 처리, salting |
| 파일이 너무 많다 | 작은 파일 문제. 메타데이터 읽는 데 시간 다 씀 | OPTIMIZE / 자동 압축 |
| 매일 전체를 다시 읽는다 | 파티션 프루닝이 안 걸림 | 조인·필터 조건을 **파티션 컬럼 기준**으로 |

가장 먼저 확인할 건 **작은 차원 테이블이 브로드캐스트되고 있는지**다.

```
   [sort-merge join]  양쪽을 키로 셔플 → 정렬 → 병합
                      네트워크로 데이터가 전부 이동한다. 비싸다.

   [broadcast join]   작은 쪽을 모든 익스큐터에 복사해두고
                      큰 쪽은 제자리에서 처리 → ★ 셔플 없음
```

`dim_date`는 거의 항상 브로드캐스트 대상이다(수천 행). `dim_member`는 규모에 따라 갈린다. 실행 계획에서 `BroadcastHashJoin`이 아니라 `SortMergeJoin`이 보이면 그 지점이 첫 번째 용의자다.

**단, 브로드캐스트를 손으로 강제할 때는 주의해야 한다.** 차원 테이블이 예상보다 커지면 드라이버 메모리가 터진다. 회원 차원처럼 **계속 자라는 테이블**은 특히 그렇다. 오늘 맞는 힌트가 6개월 뒤에 장애가 된다.

> **핵심 통찰 — "튜닝 대상은 성능 측정으로 발견하는 게 아니라 모델 구조에서 예측된다"**
>
> "느린 곳을 찾아서 고친다"는 순서는 맞지만, 별 스키마에서는 **어디가 느릴지 대체로 미리 안다.** 큰 팩트와 카디널리티 높은 차원이 만나는 지점, 그리고 그 결과를 다시 두 벌로 쓰는 지점이다.
>
> 이게 실무에서 갖는 의미는 **설계 시점에 튜닝 후보를 목록으로 만들 수 있다**는 것이다. 그러면 성능 문제가 "터진 뒤에 찾는 일"에서 "이미 지켜보고 있던 곳이 예상대로 커진 일"로 바뀐다.
>
> 그리고 이 목록은 **모니터링 대상 목록과 거의 같다.** 어디가 느려질지 아는 것과 무엇을 지켜봐야 하는지 아는 건 같은 지식이다.

## 10. Metric View를 Materialized View로 구현한다는 것

오늘 던진 질문 중 가장 깊게 들어간 것.

> **질문**: Metric View를 Materialized View로 구현한다는 게 어떤 의미일까요?
>
> **답변**:
> - Catalog에서 Metric View detail을 보면 된다.
> - cache할 때, **조인을 먼저 해놓고(MV로 만들어놓고)** 만들겠다는 것. 그래야 매번 metric view를 다 계산하지 않고 에이전트가 대답할 수 있다.
> - **`materialization` 필드**에 정의하면 물리적인 MV를 만든다.
> - MV에서 **걸리는 건 그걸 참고하고, 아니면 다시 원래 metric view로 넘어간다.**

들은 답이 문서와 거의 정확히 일치한다. 문서로 확인한 세부를 붙여서 완성한다.

### 먼저: metric view가 무엇인가

metric view는 **"지표의 정의"를 카탈로그 객체로 만든 것**이다. 테이블도 아니고 일반 뷰도 아니다.

```yaml
version: 1.1
source: prod.gold.orders_enriched
filter: revenue > 0
fields:                        # 차원 (dimensions와 동의어)
  - name: category
    expr: substring(category, 5)
measures:                      # 지표 — ★ 여기가 핵심
  - name: total_revenue
    expr: SUM(revenue)
  - name: number_of_suppliers
    expr: COUNT(DISTINCT supplier_id)
```

일반 뷰와 결정적으로 다른 점: **집계를 미리 확정하지 않는다.** `total_revenue`는 "SUM(revenue)"라는 **규칙**으로만 정의되어 있고, 어떤 차원으로 자를지는 질의하는 쪽이 정한다.

```sql
-- 카테고리별
SELECT category, MEASURE(total_revenue) FROM metric_view GROUP BY category
-- 월별
SELECT month,    MEASURE(total_revenue) FROM metric_view GROUP BY month
--                      ▲ 같은 정의를 다른 축으로 자른다
```

**이게 semantic layer의 정체다.** "매출이 뭐냐"를 한 번만 정의하고, 자르는 방법은 무한히 열어두는 것.

### 그래서 materialization이 왜 필요한가

문제는 **매번 계산해야 한다는 것**이다. metric view는 논리적 정의이므로, 질의가 들어올 때마다 원본 테이블을 읽고 조인하고 집계한다.

```
   에이전트: "이번 달 카테고리별 매출 알려줘"
        │
        ▼
   metric view → source 테이블 읽기 → joins 수행 → filter → 집계
        │            ▲
        │            └── 매번. 조인이 비싸면 매번 비싸다.
        ▼
   답변 (10초 후)
```

**사람이 대시보드를 볼 때는 10초를 기다린다. 에이전트와 대화하는 사람은 안 기다린다.** 이게 materialization이 필요한 실제 이유다.

### `materialization` 필드

```yaml
materialization:
  schedule: every 6 hours        # 갱신 주기
  mode: relaxed                  # 현재 지원되는 유일한 모드
  materialized_views:
    - name: baseline
      type: unaggregated         # ★ source + joins + filter 까지만 미리
    - name: revenue_breakdown
      type: aggregated           # ★ 특정 조합까지 미리 집계
      dimensions: [category]
      measures:   [total_revenue]
      partition_by: [category]
```

두 타입의 차이가 메모에 적힌 **"조인을 먼저 해놓고"** 와 정확히 대응한다.

| 타입 | 무엇을 미리 만드나 | 언제 쓰나 |
|---|---|---|
| **unaggregated** | source + joins + filter까지 처리된 **데이터셋 전체** | **조인이 비쌀 때.** 어떤 질의가 올지 모를 때. 커버리지가 넓다 |
| **aggregated** | 특정 차원×지표 조합까지 **집계 완료** | 자주 오는 질의 패턴이 뻔할 때. 가장 빠르다 |

**"조인을 먼저 해놓는다" = `unaggregated`** 다. 질의가 어떻게 들어올지 모르는 에이전트 시나리오에서 특히 잘 맞는다. 무엇을 물어보든 **비싼 조인은 이미 끝나 있는** 상태에서 출발하기 때문이다.

### "걸리면 MV, 아니면 원본" — 쿼리 재작성 4단계

메모의 마지막 줄이 이 부분이다. 문서상 옵티마이저는 이 순서로 매칭을 시도한다.

```
   질의 도착
      │
      ├─① Exact Match       요청한 게 정확히 미리 계산돼 있다
      │                     → 저장된 결과를 그대로 읽는다.        가장 빠름
      │
      ├─② Rollup Match      더 굵은 단위를 요청했다 (일별 MV → 월별 질의)
      │                     → 미리 집계된 걸 한 번 더 굳힌다
      │                     ※ 가법적(additive) 지표여야 한다   ★
      │
      ├─③ Unaggregated Match 집계 조합은 안 맞지만
      │                     조인·필터가 끝난 데이터셋에서 시작한다
      │
      └─④ Fallback          아무것도 안 맞는다
                            → ★ 원본 테이블로 그대로 질의한다
```

**④가 메모의 "아니면 다시 원래 metric view로 넘어간다"** 다. 이 설계의 중요한 성질은 — **materialization은 성능 최적화일 뿐, 정답의 정의를 바꾸지 않는다는 것**이다. MV가 없어도, 갱신이 늦어도, 조합이 안 맞아도 **답은 나온다. 느릴 뿐이다.**

②의 단서를 놓치면 안 된다. **Rollup은 가법적 지표에서만 성립한다.** `SUM`은 일별을 더해 월별이 되지만, `COUNT(DISTINCT ...)`는 안 된다. 일별 고유 방문자를 30개 더해도 월별 고유 방문자가 아니다. 그래서 위 예시의 `number_of_suppliers`는 rollup으로 답할 수 없고 ③이나 ④로 내려간다.

### 제약 — 그리고 마스킹 설계와의 연결

문서가 명시한 중요한 제약이 하나 있다.

> **행 수준 보안(RLS), 컬럼 마스크, 또는 ABAC 정책을 사용하는 metric view나 그 소스 테이블은 materialize할 수 없다.**

이게 **13장의 정적 마스킹 이야기와 정확히 맞물린다.** 마스킹을 컬럼 마스크(질의 시점 동적 마스킹)로 구현하면 그 테이블 위의 metric view는 **materialize가 불가능**해진다. 반면 마스킹본을 **별도 물리 테이블(`_enc`)로 미리 만들어두면** 컬럼 마스크 정책이 없으므로 materialization이 가능하다.

즉 오늘 들은 두 이야기 — "마스킹은 정적으로 한다"와 "metric view를 MV로 만든다" — 는 **독립된 결정이 아니라 서로를 가능하게 하는 결정**이다.

그 외 제약도 알아둘 것:
- **파라미터를 쓰는 metric view는 materialize 불가.**
- materialization 생성 후에는 **소유자를 바꿀 수 없다.** 개인 계정으로 만들면 나중에 곤란해진다(4장과 같은 문제).
- 서버리스 파이프라인이 활성화돼 있어야 하고, 최신 런타임이 필요하다.
- **1:N 조인은 exact match에서만** 재작성이 걸린다.

> **핵심 통찰 — "materialization은 '지표의 정의'와 '지표의 계산 시점'을 분리한다"**
>
> 전통적으로 "미리 집계해두기"에는 큰 대가가 따랐다. 집계 테이블을 만드는 순간 **그게 새로운 진실이 되고**, 원본과 어긋나기 시작하며, "어느 걸 봐야 하나"라는 질문이 생긴다. 요약 테이블이 늘어날수록 지표 정의가 여러 벌로 갈라진다.
>
> metric view의 materialization은 이 대가를 **구조적으로 제거**한다. 정의는 metric view **한 곳에만** 있고, MV는 그 정의의 **캐시일 뿐**이다. 이름조차 사용자에게 노출되지 않는다 — 질의하는 쪽은 언제나 metric view를 부르고, 옵티마이저가 알아서 고른다.
>
> 그래서 판단 기준이 뒤집힌다. 전통적 집계 테이블에서는 "이걸 만들면 진실이 갈라질 위험을 감수할 만한가"를 물어야 했지만, 여기서는 **순수하게 비용/속도 문제**만 남는다. **틀릴 위험 없이 빠르게 만들 수 있는 몇 안 되는 최적화**다.
>
> 다만 공짜는 아니다. `schedule: every 6 hours`는 **최대 6시간 낡은 답을 허용하겠다는 선언**이다. 그리고 그 사실이 답변 어디에도 표시되지 않는다. **에이전트가 "이 수치는 N시 기준입니다"를 말하게 하는 건 별도의 설계 과제**다.

## 11. 15분 주기 대시보드는 어디서 데이터를 받아오나

> **질문**: 전사 지표 대시보드는 15분마다 refresh하도록 해놨다. 그러면 이건 데이터를 어떻게 받아오나?
>
> **답변**: 원천 DW(Redshift)에서 받아오는 건데, **우리가 할 건 아니다. 이미 구현되어 있는 것이다.**

답 자체는 짧지만, 이 답이 알려주는 **경계 정보**가 값지다.

### 무엇을 알게 되는가

```
   [우리 파이프라인]                    [별도로 이미 존재하는 경로]

   원천 DW ──일 배치──▶ Databricks      원천 DW ──15분──▶ 전사 대시보드
                          │
                          ▼
                   metric view → 에이전트

   ★ 두 경로는 같은 원천을 보지만 서로 독립이다.
     주기도 다르고, 소유 조직도 다르고, 우리 배포가 저기에 영향을 주지 않는다.
```

이걸 알고 나면 판단이 달라지는 지점이 실제로 있다.

| 착각 | 실제 |
|---|---|
| "우리 배치를 15분으로 줄여야 하나?" | 아니다. **그 요구는 다른 경로가 이미 충족**하고 있다 |
| "우리 배치가 늦으면 전사 대시보드가 멈추나?" | 아니다. 독립 경로다 |
| "우리가 만든 지표와 전사 대시보드 숫자가 다르면?" | ⚠️ **있을 수 있다.** 신선도가 다르니까 |

세 번째가 남는 숙제다. **같은 원천을 보지만 주기가 다른 두 경로**는 언제든 서로 다른 숫자를 보여줄 수 있다. 오전 10시에 전사 대시보드는 09:45 기준을 보여주고, 에이전트는 어제 03시 기준을 보여준다. **둘 다 맞는데 다르다.**

이런 상황에서 필요한 건 숫자를 맞추는 게 아니라 **기준 시각을 답변에 명시하는 것**이다. "8월 매출은 X입니다"가 아니라 "8월 6일 03시 기준 X입니다"가 되어야 한다.

> **핵심 통찰 — "'우리가 할 게 아니다'라는 답은 범위 축소가 아니라 경계 정보다"**
>
> 이런 답을 들으면 "아, 그럼 안 봐도 되겠네"로 끝내기 쉽다. 그런데 실제로 얻은 정보는 **"같은 원천을 보는 다른 소비 경로가 존재하고, 그것의 신선도는 우리와 다르다"** 는 사실이다. 이건 우리 설계에 직접 영향을 준다.
>
> SI에서 특히 그렇다. **모르는 시스템이 같은 데이터를 보고 있다는 사실 자체가 리스크**다. 우리가 원천에 부하를 주면 그쪽이 느려지고, 우리가 지표 정의를 다르게 잡으면 **회의실에서 두 개의 숫자가 충돌**한다. 그리고 그 회의에서 설명해야 하는 사람은 대개 우리다.
>
> 그래서 "우리가 할 게 아니다"를 들었을 때 이어서 물어야 할 것은 **"그럼 그건 어느 주기로, 어느 정의로 도나요?"** 다. 담당이 아니어도 **인접 시스템의 신선도와 지표 정의는 알아야 한다.**

## 12. 원천 연결 — JDBC 직접이냐 Federation이냐

메모: *"원천 연결 방식 ① JDBC 방법: 세밀한 제어, 튜닝 용이. but jar나 spark 버전 관리가 어렵다. ② Lakehouse Federation (우리 방법)"*

정확한 요약이다. 두 방식이 실제로 무엇인지 채워 넣는다.

### ① JDBC 직접 연결

Spark가 JDBC 드라이버로 직접 붙어서 읽는다.

```python
df = (spark.read
      .format("jdbc")
      .option("url", "jdbc:redshift://...")
      .option("dbtable", "(SELECT ... FROM t WHERE dt = '2026-08-07') AS q")
      .option("partitionColumn", "id")     # ★ 병렬 읽기 제어
      .option("lowerBound", 1)
      .option("upperBound", 10000000)
      .option("numPartitions", 32)
      .option("fetchsize", 10000)
      .load())
```

**세밀한 제어가 가능하다는 게 정확히 이 옵션들**이다. 몇 개의 병렬 연결로 나눌지, 어느 컬럼으로 쪼갤지, 한 번에 몇 행을 받을지 — 전부 직접 정한다. 원천에 부하를 얼마나 줄지도 우리가 결정한다.

대가도 정확히 메모대로다.

```
   드라이버 jar 를 클러스터에 설치해야 한다
        │
        ├─ 어느 버전을?           원천 DB 버전과 맞아야 한다
        ├─ 런타임 올리면?          Spark/Scala 버전 호환성 재확인
        ├─ 클러스터마다 설치?      init script 또는 라이브러리 정책
        └─ 자격 증명은 어디에?     노트북에 쓰면 안 되고, 시크릿으로
```

**"jar 관리가 어렵다"는 건 한 번 설치하면 끝나는 문제가 아니라, 런타임을 올릴 때마다 되돌아오는 문제**라는 뜻이다.

### ② Lakehouse Federation

카탈로그 레벨에서 외부 DB를 **연결(connection)** 로 등록하고, 그 DB를 **외래 카탈로그(foreign catalog)** 로 미러링한다.

```sql
CREATE CONNECTION redshift_conn TYPE redshift
  OPTIONS (host '...', port '5439', user secret(...), password secret(...));

CREATE FOREIGN CATALOG src_dw USING CONNECTION redshift_conn
  OPTIONS (database 'analytics');
```

이후에는 **그냥 카탈로그의 테이블처럼 보인다.**

```sql
SELECT * FROM src_dw.public.orders WHERE dt = '2026-08-07';
--            ▲ 실제로는 원천에 질의가 푸시다운된다. 복사본이 없다.
```

내부적으로는 여전히 JDBC를 쓰지만, **드라이버는 런타임에 번들되어 있고 자격 증명은 카탈로그가 관리**한다.

### 정면 비교

| | JDBC 직접 | Lakehouse Federation |
|---|---|---|
| 드라이버 | **우리가 설치·버전 관리** | 런타임에 포함 |
| 자격 증명 | 시크릿에 넣고 코드에서 참조 | **카탈로그 connection 객체가 소유** |
| 권한 관리 | Spark 밖. 별도 관리 | **카탈로그 권한 체계에 편입** |
| 읽기 병렬도 제어 | ✅ 완전히 우리 손에 | △ 제한적 |
| 카탈로그 탐색 | ❌ 코드로만 접근 | ✅ **UI에서 스키마·테이블이 보인다** |
| 리니지 | ❌ 끊긴다 | ✅ 원천까지 추적된다 |
| 쓰기 | 가능 | **읽기 전용** |
| 운영 부담 | 높다 | 낮다 |

### 왜 Federation을 골랐나 — 그리고 언제 뒤집히나

Federation이 이기는 이유는 **성능이 아니라 운영 부담과 거버넌스**다. 드라이버 관리에서 해방되고, 자격 증명이 코드에서 사라지고, **누가 어느 원천 테이블에 접근할 수 있는지가 카탈로그 권한 하나로 관리**된다.

그런데 뒤집히는 경우가 있다.

```
   Federation 이 불리해지는 상황:
   · 매우 큰 테이블을 통째로 읽어야 한다 (병렬도 제어가 필요)
   · 원천에 주는 부하를 정밀하게 통제해야 한다 (운영 DB라 민감)
   · 원천에 써야 한다                        (Federation 은 읽기 전용)
   · 원천이 지원 목록에 없다
```

**"어느 하나가 언제나 옳다"가 아니라 "적재 방식이 대량 벌크 로드냐 조회형이냐"** 로 갈린다.

> **핵심 통찰 — "연결 방식 선택의 진짜 축은 성능이 아니라 '드라이버를 누가 관리하느냐'다"**
>
> JDBC와 Federation을 비교할 때 처음 눈에 들어오는 건 성능 제어권이지만, **6개월 뒤에 실제로 아픈 건 jar 관리**다. 런타임 업그레이드마다 호환성을 확인하고, 클러스터마다 설치 상태를 맞추고, 드라이버 버전이 원천 DB 업그레이드를 따라가는지 확인해야 한다. 이 비용은 **개발할 때는 안 보이고 운영할 때만 보인다.**
>
> Federation은 그 부담을 벤더에게 넘기는 대신 제어권을 일부 포기하는 거래다. 그리고 **대부분의 적재는 정밀 제어가 필요 없다.**
>
> 실무 규칙 — **기본값은 Federation, 예외는 측정된 병목이 있을 때.** "혹시 나중에 튜닝이 필요할까 봐" JDBC를 고르는 건 **오늘 확실한 운영 비용을 내고 내일 불확실한 유연성을 사는 것**이다.

## 13. 암호화 대상 컬럼을 태그로 정한다는 설계

메모: *"암호화 대상 컬럼 결정 방식 — Unity Catalog 태그를 사용해서 **정적 마스킹을 하기 위한 컬럼으로만** 사용"*

이 문장에서 중요한 단어는 **"정적"** 과 **"~으로만"** 이다. 둘 다 의도적인 선택이다.

### 정적 마스킹 vs 동적 마스킹

마스킹을 구현하는 방법은 근본적으로 두 가지다.

```
 [동적 마스킹]  질의 시점에 정책이 값을 바꾼다
 ─────────────────────────────────────────────
   테이블 1개. 실제 값이 저장돼 있다.
   SELECT phone FROM t
        │
        ▼  컬럼 마스크 정책 평가
   권한 있으면 → 010-1234-5678
   권한 없으면 → 010-****-****

   장점: 저장소 1벌. 정책 바꾸면 즉시 반영.
   단점: 모든 질의에 정책 평가 비용. ★ metric view materialize 불가.


 [정적 마스킹]  적재 시점에 마스킹된 복사본을 만든다
 ─────────────────────────────────────────────
   테이블 2개.
   mart      : 실제 값 — 권한 있는 소수만 접근
   mart_enc  : 마스킹된 값 — 나머지 전부

   장점: 질의 시 추가 비용 0. 마스킹본은 평범한 테이블이라
        ★ materialize·공유·복제에 아무 제약이 없다.
   단점: 저장소 2벌. 정책이 바뀌면 재적재 필요.
        ★ 잘못된 테이블을 보여줄 위험이 항상 존재한다.
```

**정적 마스킹을 고르면 "성능·호환성"을 얻고 "접근 통제의 실수 여지"를 떠안는다.** 마스킹본을 봐야 할 사람이 원본에 접근하면 그냥 실제 값이 보인다. 동적 마스킹에서는 그 사람이 같은 테이블을 봐도 마스킹된 값이 나온다.

그래서 정적 마스킹을 쓰면 **권한 설계가 곧 마스킹 설계**가 된다. 두 테이블의 권한 부여를 틀리면 마스킹은 아무 의미가 없다.

### 태그가 하는 일 — 그리고 하지 않는 일

Unity Catalog 태그는 **키-값 메타데이터**를 카탈로그·스키마·테이블·컬럼에 붙이는 기능이다.

```sql
ALTER TABLE gold.mart ALTER COLUMN phone   SET TAGS ('pii' = 'phone');
ALTER TABLE gold.mart ALTER COLUMN email   SET TAGS ('pii' = 'email');
ALTER TABLE gold.mart ALTER COLUMN name    SET TAGS ('pii' = 'name');
```

여기서 결정적인 점 — **태그 자체는 아무것도 막지 않는다.** 태그를 붙였다고 값이 가려지지 않는다. 태그는 **"이 컬럼은 이러이러한 성격이다"라는 사실의 선언**일 뿐이고, 그 사실을 **무언가가 읽어서 행동해야** 효과가 생긴다.

우리 설계에서 그 "무언가"는 **적재 파이프라인**이다.

```
   ① 태그 조회      시스템 카탈로그에서 pii 태그가 붙은 컬럼 목록을 읽는다
                    (information_schema / system 테이블)
        │
        ▼
   ② 마스킹 적용    그 컬럼들에 해시·부분마스킹·토큰화를 적용
        │
        ▼
   ③ mart_enc 생성  마스킹된 복사본을 쓴다

   ★ 대상 목록(태그)과 처리 규칙(코드)이 분리되어 있다.
     새 PII 컬럼이 생기면 코드가 아니라 태그를 추가한다.
```

**이게 태그를 쓰는 진짜 이유다.** 대상 목록을 코드에서 빼내는 것.

```python
# 태그를 안 쓰면 — 컬럼 목록이 코드에 박힌다
PII_COLUMNS = ["phone", "email", "name", "address", ...]
#              ▲ 컬럼이 추가될 때마다 코드 수정 → 리뷰 → 배포

# 태그를 쓰면 — 목록은 카탈로그가 갖고, 코드는 규칙만 갖는다
pii_cols = spark.sql("""
    SELECT column_name FROM system.information_schema.column_tags
    WHERE table_name = 'mart' AND tag_name = 'pii'
""").collect()
#              ▲ 컬럼이 추가되면 태그만 붙이면 된다. 배포 불필요.
```

### "~으로만" 이라는 단서

메모의 *"정적 마스킹을 하기 위한 컬럼으로만 사용"* 은 **태그의 용도를 의도적으로 좁혔다**는 뜻으로 읽힌다. 이건 실무적으로 현명한 선택이다.

태그는 아무 데나 붙일 수 있어서 **금방 쓰레기장이 된다.** `owner`, `domain`, `layer`, `pii`, `deprecated`, `temp`, `2024_migration`… 누구도 전체 목록을 모르고, 붙었는지 안 붙었는지 아무도 확인하지 않으며, 결국 **아무도 신뢰하지 않는 메타데이터**가 된다.

용도를 **"파이프라인이 실제로 읽어서 동작이 달라지는 것"** 하나로 제한하면, 태그가 틀렸을 때 **즉시 표가 난다.** 태그를 빠뜨리면 마스킹이 안 되고, 그건 검증에서 잡힌다. **틀리면 티가 나는 메타데이터만 신뢰할 수 있다.**

### 플랫폼이 제공하는 다른 길 — ABAC

참고로, 플랫폼에는 **태그를 정책에 직접 연결하는 기능**이 있다(ABAC, 속성 기반 접근 제어). 거버넌스 태그(governed tags)를 정의하고, 카탈로그·스키마 레벨에 정책을 걸면 **그 태그가 붙은 모든 컬럼에 마스킹이 자동 적용**된다. 테이블마다 설정할 필요가 없고, 테이블 소유자가 임의로 해제할 수도 없다.

우리가 이 길을 안 간 이유가 앞서 나왔다 — **ABAC/컬럼 마스크가 걸린 소스는 metric view를 materialize할 수 없다.** 성능이 걸린 문제라 정적 마스킹을 골랐고, 대신 태그는 정책 연결이 아니라 **파이프라인 입력**으로만 쓴다.

> **핵심 통찰 — "태그는 정책이 아니라 정책의 입력이다. 규칙과 대상 목록을 분리하는 장치다"**
>
> 태그를 "메타데이터를 예쁘게 정리하는 기능"으로 보면 왜 쓰는지 잘 안 와닿는다. 정확히는 **"어떻게 처리할지(규칙)"와 "무엇을 처리할지(목록)"를 다른 곳에 두는 장치**다.
>
> 규칙은 코드에 있어야 한다. 리뷰가 필요하고, 테스트가 필요하고, 자주 안 바뀐다. 목록은 계속 바뀐다. 새 컬럼이 생기고, 새 테이블이 생기고, 개인정보 판정이 갱신된다. **둘을 같은 곳에 두면 자주 바뀌는 쪽이 안 바뀌는 쪽의 배포 주기에 갇힌다.**
>
> 그리고 목록을 카탈로그에 두면 **개발자가 아닌 사람도 관리할 수 있다.** "이 컬럼은 개인정보다"는 개발 판단이 아니라 **업무·법무 판단**이다. 그 판단을 코드에 박아두면, 판단할 자격이 있는 사람은 못 고치고 고칠 수 있는 사람은 판단할 자격이 없는 상태가 된다.
>
> 대가도 분명하다. **태그가 곧 보안 경계가 되므로, 태그를 붙일 권한이 곧 개인정보 통제 권한이 된다.** 태그 자체에도 통제가 필요해진다.

# Part 3. 플랫폼 — 내 코드가 실제로 도는 곳

## 14. Catalog의 네 가지 얼굴

카탈로그 화면에는 성격이 전혀 다른 네 가지가 나란히 있다. 이게 **우연이 아니라 이 플랫폼의 핵심 주장**이다.

| 구분 | 무엇 | 실체 |
|---|---|---|
| **Tables** | 정형 데이터 | Delta/Parquet 테이블. 관리형 또는 외부 |
| **Volumes** | 비정형 원본 | **클라우드 스토리지 경로에 이름과 권한을 씌운 것** |
| **Models** | AI 모델 | MLflow 모델을 카탈로그 객체로 등록 |
| **Shares Received** | 공유받은 것 | Delta Sharing으로 **다른 조직/계정에서 받은 데이터** |

### Volumes — "S3 연결"의 정확한 의미

메모: *"Volumes: 비정형의 원본(S3 연결)"*

정확하다. 조금 더 정밀하게 말하면 — **볼륨은 테이블이 아닌 파일을 카탈로그 권한 체계 안으로 들여오는 장치**다.

```
   [볼륨 없이]                        [볼륨]

   s3://our-bucket/raw/               catalog.schema.raw_files
        ▲                                   ▲
        └─ 접근 통제는 IAM 정책             └─ 카탈로그 권한(GRANT READ VOLUME)
           클라우드 콘솔에서 관리              테이블과 같은 체계
           데이터 담당자가 못 본다             카탈로그 UI에서 보인다
           리니지 없음                        리니지에 잡힌다
```

관리형(managed)과 외부(external)로 나뉜다. **기존 스토리지 경로를 그대로 감싸면 external, 카탈로그가 위치까지 관리하면 managed.** 외부 시스템이 같은 경로에 읽고 쓴다면 external이 맞다.

파일 경로 표기도 통일된다.

```python
# 볼륨 경로는 일반 파일 경로처럼 쓸 수 있다
df = spark.read.json("/Volumes/catalog/schema/raw_files/2026/08/07/*.json")
```

### Shares Received — Delta Sharing

메모: *"Shares Received: 공유 받은 것(내부망에서 외부망으로 공유)"*

Delta Sharing은 **데이터를 복사하지 않고 공유하는 오픈 프로토콜**이다. 공유하는 쪽은 `share`를 만들어 테이블을 담고 수신자(recipient)를 지정한다. 받는 쪽에는 카탈로그로 마운트되어 **읽기 전용 테이블처럼 보인다.**

핵심 성질 두 가지:

```
 ① 복사가 아니다
    받는 쪽은 실제로 원본 스토리지를 읽는다.
    → 공유자가 데이터를 갱신하면 수신자에게 즉시 반영된다.
    → "언제 적 데이터인가" 문제가 없다.

 ② 상대가 같은 플랫폼일 필요가 없다
    오픈 프로토콜이라 다른 스택에서도 읽을 수 있다.
    → 망이 다르거나 조직이 다른 상대와의 공유에 쓰인다.
```

**망 분리 환경에서 특히 의미가 크다.** 데이터를 파일로 떠서 전달하는 방식은 사본이 생기고, 사본은 낡고, 낡은 사본은 언젠가 잘못된 판단의 근거가 된다. Delta Sharing은 사본 없이 경계를 넘는다.

> **핵심 통찰 — "카탈로그의 야심은 '데이터 목록'이 아니라 '모든 자산에 대한 단일 권한 평면'이다"**
>
> Tables·Volumes·Models·Shares를 한 화면에 둔 게 UI 편의처럼 보이지만, 실제 주장은 이것이다 — **"테이블이든 파일이든 모델이든 외부 공유든, 접근 통제는 한 곳에서 한 가지 방식으로 한다."**
>
> 이게 왜 큰 문제인지는 안 그런 조직을 보면 안다. 테이블 권한은 DW에서, 파일 권한은 클라우드 IAM에서, 모델 권한은 MLOps 도구에서, 외부 공유는 담당자 메일로 관리된다. **네 개의 서로 다른 시스템, 네 개의 서로 다른 담당자, 그리고 "누가 이 데이터를 볼 수 있나"에 대한 네 개의 부분적인 답.**
>
> 감사 대응에서 이 차이가 드러난다. **"이 개인정보 컬럼에 접근 가능한 사람 전체 목록"을 뽑을 수 있는가.** 통합돼 있으면 질의 하나다. 아니면 프로젝트 하나다.

## 15. Metastore · Workspace · Catalog의 진짜 관계

메모: *"Meta Store와 Workspace는 주종관계가 아니다. Mapping 관계이다. M:N 관계. Workspace를 지워도 Catalog는 남는다."*

**결론은 맞는데 관계도가 한 칸 어긋나 있다.** 정확히 그리면 이렇다.

```
   ┌──────────────────────────────────────────────────────────┐
   │  Account (계정 레벨)                                     │
   │                                                          │
   │   ┌────────────────────────────────────────────┐         │
   │   │  Metastore  (리전당 1개 권장)              │         │
   │   │                                            │         │
   │   │   catalog_a   catalog_b   catalog_c        │         │
   │   └──────┬────────────┬───────────┬───────────┘          │
   │          │            │           │                      │
   │      binding      binding     binding     ← ★ 여기가 M:N │
   │          │            │           │                      │
   │   ┌──────┴───┐   ┌────┴─────┐  ┌──┴───────┐              │
   │   │Workspace1│   │Workspace2│  │Workspace3│              │
   │   └──────────┘   └──────────┘  └──────────┘              │
   │        │              │            │                     │
   │        └──────────────┴────────────┘                     │
   │              모두 같은 Metastore 에 배정  ← ★ 여기는 N:1 │
   └──────────────────────────────────────────────────────────┘
```

- **Workspace : Metastore = N:1.** 워크스페이스 하나는 **정확히 하나의** 메타스토어에 배정된다. 리전당 메타스토어는 하나만 만들 수 있다.
- **Catalog : Workspace = M:N.** 카탈로그 하나를 여러 워크스페이스가 볼 수 있고, 워크스페이스 하나가 여러 카탈로그를 본다. 이 대응을 정하는 게 **workspace-catalog binding**이다.

### 그런데 메모의 결론은 왜 맞나

*"주종관계가 아니다"*, *"워크스페이스를 지워도 카탈로그는 남는다"* — 둘 다 사실이다. 다만 이유가 M:N이어서가 아니라 **소유 주체가 다르기 때문**이다.

```
   Workspace 는 "작업 환경"        — 컴퓨트·노트북·잡이 사는 곳
   Catalog   는 "데이터 자산"      — 메타스토어(계정 레벨)가 소유

   ★ 워크스페이스는 카탈로그를 소유하지 않는다. 볼 권한을 얻을 뿐이다.
     그래서 워크스페이스를 지워도 카탈로그는 그대로 있다.
     "지운 것"은 창문이지 방이 아니다.
```

이게 예전 방식(워크스페이스마다 독립된 Hive metastore)과의 결정적 차이다. 예전에는 **워크스페이스가 데이터 정의를 소유**했다. 그래서 워크스페이스가 늘어나면 테이블 정의가 갈라지고, 워크스페이스 간에 데이터를 보려면 복사해야 했다.

### "Outside this workspace"의 정체

메모: *"Outside this workspace: 이 워크스페이스에 연결되지 않은 카탈로그들"*

정확하다. 이 목록에 뜨는 건 **메타스토어에는 있지만 이 워크스페이스에 바인딩되지 않은 카탈로그**다.

- 메타스토어 관리자나 카탈로그 소유자에게는 **바인딩과 무관하게 보인다.**
- 다만 **회색으로 표시되고, 자식 객체는 보이지도 질의되지도 않는다.**

즉 "존재는 알지만 열 수는 없다"는 상태다. 이 구분이 있는 이유는 **관리자가 전체를 파악할 수 있어야 하기 때문**이다. 안 보이면 "우리 계정에 어떤 카탈로그가 있나"를 답할 수 없다.

### "카탈로그만 관리하는 UI가 없다"

메모의 이 관찰은 체감상 정확하다. 정확히 말하면:

- **메타스토어 자체**의 관리(생성, 워크스페이스 배정)는 **계정 콘솔**에서 한다.
- **카탈로그 안**의 탐색·권한 관리는 **워크스페이스의 Catalog Explorer**를 통해서만 한다.

그래서 **"카탈로그를 보려면 워크스페이스가 하나는 있어야 한다"** 는 상황이 생긴다. 데이터는 워크스페이스에 속하지 않는데, 데이터를 보는 창문은 워크스페이스뿐인 구조다.

> **핵심 통찰 — "데이터의 수명이 작업 환경의 수명보다 길다는 전제로 설계된 구조다"**
>
> 왜 카탈로그를 계정 레벨로 올렸는지를 한 문장으로 답하면 이것이다. **워크스페이스는 만들어지고 없어지지만 데이터는 남는다.**
>
> 실제로 워크스페이스는 생각보다 자주 생기고 없어진다. 프로젝트별로 만들고, 팀별로 나누고, 실험용으로 만들었다가 지운다. 만약 데이터 정의가 워크스페이스에 묶여 있다면 **워크스페이스를 지우는 결정이 곧 데이터를 지우는 결정**이 되고, 그러면 아무도 워크스페이스를 못 지운다. 죽은 워크스페이스가 계속 쌓인다.
>
> 분리하면 **워크스페이스는 가볍게 만들고 가볍게 지울 수 있는 것**이 된다. 이건 거버넌스 이야기이면서 동시에 **조직 구조 이야기**다. 팀이 바뀌고 프로젝트가 끝나도 데이터 자산은 조직에 남는다는 사실을, 구조가 반영한 것이다.

## 16. Control Plane과 Compute Plane — 계정이 갈리는 지점

메모의 이 부분이 오늘 배운 것 중 **가장 실무 영향이 큰 내용**이다.

```
 ┌───────────────────────────────────────────────────────────────┐
 │  CONTROL PLANE  — 벤더 계정                                   │
 │  ─────────────────────────────────────────────                │
 │  · 웹 UI, REST API                                            │
 │  · 잡 스케줄러, 클러스터 매니저                               │
 │  · Unity Catalog 메타데이터                                   │
 │  · 질의 히스토리, 노트북 코드                                 │
 │                                                               │
 │  ※ 여기에 "데이터"는 없다. 데이터에 대한 "정보"만 있다.  ★    │
 └───────────────────────────────────────────────────────────────┘
              │                            │
   secure tunnel (443)              cloud backbone
              │                            │
 ┌────────────┴───────────────┐  ┌──────────┴───────────────────┐
 │ CLASSIC COMPUTE PLANE      │  │ SERVERLESS COMPUTE PLANE     │
 │ = 우리 클라우드 계정 VPC   │  │ = 벤더 계정                  │
 │ ────────────────────────   │  │ ──────────────────────────   │
 │ · EC2 인스턴스가 직접 뜸   │  │ · 미리 warm 상태인 풀에서    │
 │ · 우리 VPC 안              │  │   즉시 할당                  │
 │ · 우리 보안 그룹 적용  ★   │  │ · 우리 VPC 밖  ★             │
 │ · 기동에 수 분             │  │ · 기동 수 초                 │
 │ · EC2 비용은 우리 계정 청구│  │ · 인프라 비용이 DBU 에 포함  │
 └────────────────────────────┘  └──────────────────────────────┘
              └──────────┬───────────────┘
                         ▼
              ┌─────────────────────────┐
              │  STORAGE                │
              │  = 우리 계정 S3     ★   │
              │  데이터는 언제나 우리 것│
              └─────────────────────────┘
```

### 세 문장으로 압축하면

1. **뇌(제어)는 벤더 계정에 있다.** UI, 스케줄러, 메타데이터.
2. **손발(컴퓨트)은 두 종류이고 계정이 다르다.** classic은 우리 계정, serverless는 벤더 계정.
3. **데이터는 언제나 우리 계정에 있다.** 어느 컴퓨트를 쓰든 스토리지는 우리 S3다.

**3번이 이 아키텍처의 핵심 상품성**이다. "우리 데이터가 벤더 계정으로 넘어가는가"에 대한 답이 "아니다"이기 때문에 이 구조가 성립한다.

### "워크스페이스를 연결한다"의 의미

메모: *"Workspace를 연결한다는 것은 두 계정을 연결하는 것이다."*

정확히 그렇다. 워크스페이스를 만들 때 실제로 하는 일은:

```
   우리 클라우드 계정에서:
   ① IAM 역할을 만들어 벤더 계정이 assume 할 수 있게 신뢰 관계 설정
   ② VPC / 서브넷 / 보안 그룹 지정 (classic compute 가 뜰 곳)
   ③ S3 버킷과 접근 권한 부여

   → 벤더의 control plane 이 우리 계정 안에 EC2 를 띄울 수 있게 되는 것
```

**즉 워크스페이스 생성은 "계정 하나 만들기"가 아니라 "우리 계정에 대한 위임 설정"** 이다. 이걸 이해하면 왜 워크스페이스 생성이 네트워크·보안 조직의 협조를 필요로 하는지가 자명해진다.

### 보안 터널

classic compute를 쓸 때 클러스터가 어떻게 control plane과 통신하는지도 알아둘 만하다.

```
   [예전 방식]  control plane 이 클러스터로 인바운드 접속
                → 클러스터에 공인 IP 필요, VPC 에 인바운드 포트 개방

   [현재 기본]  secure cluster connectivity
                클러스터가 control plane 으로 아웃바운드 터널을 연다 (443)
                → ★ 공인 IP 불필요, 인바운드 포트 전부 닫힘
```

**연결 방향을 뒤집어서 인바운드 개방을 없앤 것**이다. 보안 검토에서 반드시 나오는 질문("클러스터에 외부에서 들어올 수 있나요")에 대한 답이 여기 있다.

> **핵심 통찰 — "'서버리스'는 성능 옵션이 아니라 네트워크 경계의 위치를 바꾸는 결정이다"**
>
> classic과 serverless를 "느리고 싸다 vs 빠르고 비싸다"로만 비교하면 진짜 차이를 놓친다. 결정적 차이는 **컴퓨트가 우리 VPC 안에 있느냐 밖에 있느냐**다.
>
> 이게 바꾸는 것들:
> - **우리 VPC 안의 자원(원천 DB, 내부 API)에 기본 도달 가능한가** — classic은 예, serverless는 아니오
> - **우리 보안 그룹·NACL·프록시 정책이 적용되는가** — classic은 예, serverless는 아니오
> - **네트워크 로그가 우리 VPC 플로우 로그에 남는가** — classic은 예, serverless는 아니오
> - **EC2 비용이 우리 클라우드 청구서에 뜨는가** — classic은 예, serverless는 아니오(DBU에 포함)
>
> 그래서 "서버리스 쓰면 되지 않나요"는 성능 질문이 아니라 **네트워크·보안·비용 배분 질문**이다. 답하려면 네트워크 담당자가 방에 있어야 한다.

## 17. 서버리스는 왜 우리 계정에 없는가

메모에 답을 못 적고 남겨둔 질문이 이거였다.

> *"Redshift에는 EC2만 보안 그룹 방화벽 설정으로 연결될 수 있고, 서버리스는 연결하지 못한다. **그러면 왜 서버리스는 우리 계정에 담지 않는가?**"*

좋은 질문이다. 답은 **서버리스의 경제성이 성립하는 조건 자체가 "공유"이기 때문**이다.

### 서버리스가 빠른 이유 = 우리 계정에 못 두는 이유

```
   서버리스가 몇 초 만에 뜨는 이유:
   ────────────────────────────────
   미리 부팅해둔 컴퓨트 풀(warm pool)이 대기하고 있다가
   요청이 오면 거기서 하나 떼어준다.

   그런데 그 풀은 누가 유지하나?
   → 놀고 있는 동안에도 비용이 든다.
   → 그 비용을 감당하려면 ★ 여러 고객이 그 풀을 공유해야 한다.
      (한 고객의 유휴 시간이 다른 고객의 사용 시간으로 메워진다)

   만약 우리 계정에 전용 풀을 둔다면?
   ────────────────────────────────
   · 우리가 안 쓰는 시간의 유휴 비용을 ★ 우리가 전부 낸다
   · 결국 "그냥 클러스터를 계속 띄워두는 것"과 같아진다
   · 그러면 서버리스가 아니다
```

**"즉시 기동"과 "쓴 만큼만 과금"은 멀티테넌트 풀링 없이는 동시에 성립하지 않는다.** 그리고 멀티테넌트 풀은 정의상 고객 계정 안에 둘 수 없다. 다른 고객의 워크로드가 우리 VPC 안에서 돌 수는 없으니까.

부차적인 이유도 있다.

| 이유 | 설명 |
|---|---|
| **운영 주체** | 패치, 스케일링, 장애 대응을 벤더가 한다. 우리 계정에 두면 우리 책임 범위가 애매해진다 |
| **자원 한도** | 대규모 풀은 클라우드 계정의 인스턴스 쿼터·용량 예약을 크게 먹는다 |
| **버전 관리** | 런타임을 벤더가 통제해야 "항상 최신"이 유지된다 |

### 그럼 원천 DB에 못 붙나 — 여기서 메모를 정정한다

**메모의 "서버리스는 연결하지 못한다"는 기본 상태 한정으로 맞고, 최종 결론으로는 틀리다.** 방법이 있다.

```
 ① NCC 고정 egress IP
    ─────────────────────
    계정 레벨에서 Network Connectivity Configuration 을 만들면
    서버리스가 사용할 고정 공인 IP 목록이 부여된다.
    → 그 IP 를 원천 DB 보안 그룹/방화벽에 허용하면 연결된다.
    · 설정이 간단하다
    · 다만 트래픽이 공용 네트워크를 경유한다

 ② PrivateLink 사설 엔드포인트
    ─────────────────────
    NCC 에 private endpoint rule 을 추가해
    우리 VPC 안의 자원(또는 NLB 뒤의 자원)으로 사설 연결을 뚫는다.
    → ★ 공용 인터넷을 안 탄다. 보안 검토에서 가장 선호된다.
    · 리전당 엔드포인트 100개, NCC 당 워크스페이스 50개 같은 한도가 있다

   두 방법 모두 ★ 계정 관리자 권한이 필요하다.
   개발자가 혼자 해결할 수 있는 문제가 아니다.
```

**이 구분이 실무에서 중요한 이유**는 결론이 완전히 달라지기 때문이다.

```
   "서버리스는 원천 DB에 못 붙는다"
        → 전체 파이프라인을 classic 클러스터로 설계한다.
          운영 부담과 비용을 계속 진다.

   "서버리스는 기본 상태로는 못 붙고, NCC 설정이 필요하다"
        → 인프라 조직에 티켓 하나를 넣는다.
          그 다음부터는 서버리스로 간다.  ★
```

앞의 결론을 믿고 설계하면, **한 번 하면 끝날 설정 작업을 피하려고 영구적인 운영 부담을 떠안게 된다.**

> **핵심 통찰 — "'못 한다'와 '기본값이 아니다'를 구별하지 못하면 설계가 통째로 잘못된 쪽으로 간다"**
>
> 플랫폼을 배우는 초기에 가장 비싼 실수가 이거다. 시도해봤는데 안 되면 **"이 플랫폼은 이걸 지원하지 않는다"** 로 결론 내리고, 그 결론 위에 아키텍처를 쌓는다. 나중에 사실이 아니었음을 알아도 **이미 그 전제로 만든 것들이 있어서 되돌리기 어렵다.**
>
> 특히 네트워크·권한 영역에서 이 실수가 잦다. 이 영역의 기능은 대부분 **기본적으로 꺼져 있고, 계정 관리자만 켤 수 있으며, 개발자 화면에서는 아예 안 보이기** 때문이다. 개발자 시야에서는 "존재하지 않음"과 "권한이 없어 안 보임"이 똑같이 생겼다.
>
> 그래서 규칙 하나 — **"안 된다"는 결론을 내리기 전에 반드시 공식 문서에서 그 기능의 존재 여부를 확인하고, 없으면 인프라 담당에게 묻는다.** "안 되더라"는 시도 결과이지 사양이 아니다.

## 18. DBU — 성능 단위가 아니라 과금 단위

메모: *"DBU: DataBase Unit → 바로 돈으로 과금되는 단위는 아니고, 서비스마다 가격이 다르다. 일반적으로는 2~4 core"*

**앞 절반은 맞고 뒤 절반은 정정이 필요하다.**

### 정정

**DBU = Databricks Unit.** DataBase Unit이 아니다. 그리고 **코어 수와의 고정 대응이 없다.**

> DBU는 **시간당 소비되는 정규화된 컴퓨트 용량 단위**다. 인스턴스 타입과 클라우드 제공자 간의 차이를 추상화한다. **CPU 코어 수·메모리 크기·GPU 개수와 직접 대응하지 않는다.**

"2~4 core"라는 감각이 아예 근거 없는 건 아니다. 흔히 쓰는 인스턴스 타입들의 DBU 계수가 대략 그 근처에 오는 경우가 있어서다. 하지만 **이건 관찰이지 정의가 아니고, 인스턴스 타입을 바꾸면 곧바로 깨진다.**

### "바로 돈이 아니다"가 맞는 이유

메모의 이 부분은 정확하다. 실제 비용은 **곱셈 두 개의 합**이다.

```
   총 비용 = (소비 DBU × SKU 단가) + (클라우드 인프라 비용)
              ▲                        ▲
              벤더에게 청구             우리 클라우드 계정에 직접 청구
                                        (EC2, EBS, 네트워크 …)
```

그리고 **SKU 단가가 워크로드 종류마다 크게 다르다.** 같은 인스턴스에서 같은 시간을 돌려도 청구액이 몇 배 차이 난다.

```
   All-Purpose Compute   ← 가장 비쌈. 대화형 개발용.
        │                   ★ 여기서 배치를 돌리면 몇 배를 더 낸다
   Jobs Compute          ← 훨씬 쌈. 잡 실행 전용.
   SQL Warehouse         ← 별도 체계
   Serverless            ← 인프라 비용이 단가에 포함되어 있음
```

**여기서 가장 실전적인 교훈 하나** — 개발할 때 쓰던 all-purpose 클러스터에 그대로 잡을 걸어두면, 같은 일을 하면서 몇 배를 낸다. 잡은 **잡 클러스터나 서버리스**로 돌려야 한다. 이건 성능 최적화가 아니라 **가격표를 읽는 문제**다.

### 두 개의 청구서

classic과 serverless의 비용 구조 차이도 짚어둘 만하다.

```
   [classic]     DBU 청구(벤더)  +  EC2/EBS 청구(우리 클라우드 계정)
                 ────────────────────────────────────────────
                 ★ 청구서가 두 장이라 총액을 보려면 합쳐야 한다.
                   그리고 대개 두 청구서를 보는 사람이 다르다.

   [serverless]  DBU 청구(벤더) 한 장. 인프라 비용이 단가에 포함.
                 ────────────────────────────────────────────
                 ★ DBU 단가가 비싸 보이는 이유가 여기 있다.
                   비교할 때 classic 쪽 EC2 비용을 빼놓으면 잘못된 비교다.
```

> **핵심 통찰 — "DBU는 성능을 재는 자가 아니라 가격을 매기는 자다"**
>
> DBU를 "코어 몇 개쯤"으로 이해하면 **성능 단위**로 착각하게 되고, 그러면 "DBU를 늘리면 빨라지나?" 같은 잘못된 질문을 하게 된다. DBU는 벤더가 **서로 다른 하드웨어에 하나의 가격을 매기기 위해 만든 정규화 단위**다.
>
> 이걸 제대로 이해했을 때 바뀌는 실무 행동은 명확하다 — **비용을 줄이려면 인스턴스를 만지기 전에 SKU를 본다.** all-purpose에서 도는 배치를 jobs로 옮기는 게, 인스턴스 타입을 몇 시간 고민하는 것보다 대체로 훨씬 큰 절감이다.
>
> 그리고 비용 비교를 할 때는 **반드시 두 청구서를 다 보고** 비교해야 한다. classic이 싸 보이는 건 대개 EC2 비용을 안 세었기 때문이다.

## 19. Vector Search · Apps · LTAP

메모 마지막에 나란히 적힌 세 가지. 각각 **플랫폼이 어느 방향으로 넓어지고 있는지**를 보여주는 신호라서 같이 본다.

### Vector Search — 벡터 스토어

```
   Delta 테이블 (문서, 설명, 청크)
        │
        │  ★ Delta Sync 인덱스
        │     트랜잭션 로그를 보고 변경분만 증분 반영
        ▼
   Vector Search Index  ──────▶  유사도 검색
        ▲
        └─ 엔드포인트(서빙 클러스터)가 인덱스를 호스팅
```

주목할 점은 **동기화가 자동이라는 것**이다. 소스 Delta 테이블에 행이 추가/수정/삭제되면 인덱스가 **트랜잭션 로그를 통해 감지해 증분 반영**한다. 별도 파이프라인을 안 짜도 된다.

그리고 **인덱스도 카탈로그 객체**라 권한이 상속된다. RAG 시스템에서 흔히 생기는 문제 — "벡터 DB에는 권한 개념이 없어서, 검색 결과로 볼 권한 없는 문서가 딸려 나온다" — 를 구조적으로 다룰 수 있다는 뜻이다.

### Apps — 데이터를 보여주는 앱

메모: *"Javascript, Python으로 FE, BE를 올릴 수 있다. 데이터를 보여줄 수 있는 앱을 만들기 위해 시작."*

정확하다. **서버리스로 호스팅되는 내부용 웹 앱 플랫폼**이고, Streamlit·Dash·Gradio·Flask·FastAPI·Node.js·Shiny 같은 흔한 프레임워크를 지원한다.

의미 있는 건 **인증과 권한이 이미 붙어 있다는 것**이다.

```
   [전통적 내부 대시보드 앱]         [Apps]

   앱 서버 띄우기                    코드 올리면 끝
   + SSO 붙이기                      + 로그인은 이미 붙어 있다 (OIDC/OAuth)
   + DB 접속 자격증명 관리           + 카탈로그 권한이 그대로 적용
   + 배포 파이프라인                 + 번들로 같이 배포
   + 인프라 운영                     + 서버리스

   ★ "데이터를 보여주는 사내 앱"에서 반복되는 잡일이 전부 사라진다
```

대시보드로는 부족하고(입력을 받아야 한다, 워크플로가 있다), 그렇다고 제대로 된 웹 서비스를 만들 만큼은 아닌 — **그 사이의 넓은 구간**을 겨냥한 물건이다. 데이터 팀이 가장 자주 요청받는 게 정확히 이 구간이다.

### LTAP — OLAP + OLTP

메모: *"LTAP: OLAP + OLTP"*

**맞다.** 다만 이름이 흥미롭다. **LTAP = Lake Transactional/Analytical Processing.** 기존에 통용되던 HTAP(Hybrid TAP)과 의도적으로 다른 이름을 쓴다.

```
   [HTAP]     하나의 엔진이 트랜잭션과 분석을 동시에 처리하려 한다
              → 두 워크로드의 요구가 정반대라 타협이 생긴다
                (OLTP: 짧은 지연, 행 단위 / OLAP: 큰 스캔, 열 단위)

   [LTAP]     ★ 저장 계층에서 통합하고, 엔진은 각자 최적인 것을 쓴다
              쓰기는 Postgres 호환 계층(Lakebase)에 커밋되고,
              백그라운드로 열 기반 오픈 포맷에 반영되어
              분석 엔진이 같은 데이터를 읽는다
              → ETL·복제본·CDC 파이프라인을 설계상 제거하겠다는 주장
```

**"엔진을 합친다"가 아니라 "저장소를 합치고 엔진은 나눈다"** 는 게 차이다. 다만 이 구조에서도 **반영에 지연이 있다**(보고된 수치로는 1분 이상 수준). "하나의 데이터"라는 표현이 "완전히 동일 시점"을 뜻하지는 않는다는 걸 알아둬야 한다.

> **핵심 통찰 — "세 기능은 전부 '데이터가 있는 곳으로 애플리케이션을 끌어온다'는 같은 방향이다"**
>
> Vector Search, Apps, LTAP는 서로 무관한 기능처럼 보이지만 방향이 하나다.
>
> - **Vector Search** — 벡터 DB를 따로 두지 말고 **데이터가 있는 곳에서 검색**하라
> - **Apps** — 앱 서버를 따로 두지 말고 **데이터가 있는 곳에서 서빙**하라
> - **LTAP** — 운영 DB를 따로 두지 말고 **데이터가 있는 곳에서 트랜잭션**하라
>
> 공통 논리는 **"데이터를 옮기는 순간 사본이 생기고, 사본이 생기는 순간 동기화·권한·비용 문제가 따라온다"** 는 것이다. 그래서 옮기지 말고 애플리케이션 쪽을 데이터로 가져오자는 주장이다.
>
> 이 주장이 우리에게 주는 실질적 판단 기준 하나 — **새 컴포넌트를 도입할 때 "이걸 위해 데이터를 또 복사해야 하는가"를 먼저 묻는 것.** 답이 예라면, 플랫폼 안에 같은 일을 하는 기능이 이미 있는지 확인할 값어치가 있다. 대개 있다.
>
> 물론 반대 면도 봐야 한다. **이 방향은 곧 락인(lock-in)이기도 하다.** 벡터 검색도, 앱도, 운영 DB도 한 플랫폼 안에 넣으면 나가기가 그만큼 어려워진다. 편의와 종속은 같은 것의 양면이다.

## 20. 오늘의 정리

### 배운 것 한 줄씩

**배포**

1. **번들 단위 작업** — 워크스페이스 DB에만 있던 리소스 설정을 Git 안으로 끌어오는 것. 자동화는 부산물이고 본질은 **설정의 코드화**다. 번들 경계는 **함께 배포되고 함께 롤백되는 것**으로 정한다.
2. **CLI · skill · MCP** — 층이 다르다. **MCP는 능력, skill은 규약.** 능력은 벤더가 주지만 규약은 우리만 갖고 있고, 대개 사람 머릿속에만 있다. skill 작성은 사실상 **암묵지를 문서화하는 작업**이다.
3. **artifacts = 공용 wheel** — 재사용이 아니라 **테스트 가능성**이 진짜 이유. 노트북 안의 코드에는 테스트를 붙일 수 없다. 함정은 **같은 버전 재배포 시 갱신 안 됨**.
4. **배포 위치** — 기본 `root_path`는 **배포자 개인 홈**이다. 운영 배포물의 수명은 사람의 재직 기간보다 기니까 **서비스 프린시펄 + 명시적 공용 경로** 둘 다 해야 한다. `mode: production`이 이 검증을 대신 해준다.
5. **lookup** — 하드코딩을 없애는 게 아니라 **결합 대상을 ID에서 이름으로 옮기는 것.** 그 순간 이름 규약이 계약이 된다. 더 나은 답은 대체로 **참조 자체를 없애는 것**(job_clusters·서버리스).
6. **브랜치 3개** — 브랜치 전략은 취향이 아니라 **배포 인터페이스**다. 브랜치 = 환경 = 타깃을 1:1로 맞추면 **배포가 머지의 결과**가 되어 잊을 방법이 없어진다.

**ETL**

7. **write_mode** — 진짜 축은 성능이 아니라 **재실행 안전성**. `append`만 멱등하지 않고, 하필 가장 싸고 단순해서 가장 많이 선택된다. `append` 태스크에서 repair는 복구가 아니라 **데이터 오염**이다.
8. **cache** — 저장이 아니라 **계산 그래프를 자르는 가위**. 물어야 할 건 "데이터가 큰가"가 아니라 **"위쪽 계산이 비싸고 아래로 갈래가 둘 이상인가"**. 원본/마스킹본 분기가 교과서적 사례다.
9. **fact + dim 튜닝** — 튜닝 지점은 측정으로 발견하는 게 아니라 **모델 구조에서 예측**된다. 그래서 설계 시점에 후보 목록을 만들 수 있고, 그건 **모니터링 대상 목록과 같다.**
10. **Metric View → MV** — `materialization` 필드로 물리 MV를 만들고, 옵티마이저가 **exact → rollup → unaggregated → fallback** 순으로 매칭한다. "조인을 미리"가 `unaggregated`이고, "안 걸리면 원래대로"가 fallback. **정의는 한 곳, MV는 캐시**라서 진실이 갈라지지 않는다. 대가는 **신선도**이고, 그건 답변에 표시되지 않는다.
11. **15분 대시보드** — 우리 경로와 독립된 별도 경로. "우리가 할 게 아니다"는 범위 축소가 아니라 **경계 정보**다. 같은 원천을 다른 주기로 보는 소비자가 있으면 **숫자가 다를 수 있고**, 그때 필요한 건 숫자를 맞추는 게 아니라 **기준 시각을 명시하는 것**이다.
12. **JDBC vs Federation** — 진짜 축은 성능 제어권이 아니라 **드라이버를 누가 관리하느냐**. jar 관리 비용은 개발할 때 안 보이고 운영할 때 보인다. 기본값은 Federation, 예외는 **측정된 병목**이 있을 때.
13. **태그 기반 마스킹** — 태그는 정책이 아니라 **정책의 입력**. 규칙(코드)과 대상 목록(카탈로그)을 분리해, 자주 바뀌는 쪽이 안 바뀌는 쪽의 배포 주기에 갇히지 않게 한다. **정적 마스킹을 고른 것과 metric view를 materialize하는 것은 서로를 가능하게 하는 한 쌍의 결정**이다.

**플랫폼**

14. **Catalog 4종** — 야심은 데이터 목록이 아니라 **모든 자산에 대한 단일 권한 평면**. 판별 질문은 "이 컬럼에 접근 가능한 사람 전체 목록을 뽑을 수 있는가".
15. **Metastore · Workspace · Catalog** — Workspace:Metastore는 **N:1**, Catalog:Workspace가 **M:N**. 워크스페이스를 지워도 카탈로그가 남는 이유는 **데이터의 수명이 작업 환경의 수명보다 길다**는 전제로 설계됐기 때문이다.
16. **Control/Compute Plane** — 뇌는 벤더 계정, **데이터는 언제나 우리 계정**. classic/serverless 선택은 성능 옵션이 아니라 **네트워크 경계의 위치를 바꾸는 결정**이다.
17. **서버리스가 우리 계정에 없는 이유** — "즉시 기동 + 쓴 만큼 과금"은 **멀티테넌트 풀링 없이 성립하지 않고**, 그 풀은 정의상 고객 계정 안에 못 둔다. 원천 DB 연결은 **불가능한 게 아니라 NCC 설정이 필요**한 것이다.
18. **DBU** — Databricks Unit. **성능 단위가 아니라 과금 단위.** 비용을 줄이려면 인스턴스 타입보다 **SKU(all-purpose vs jobs)를 먼저** 본다. 비교할 땐 두 청구서를 다 봐야 한다.
19. **Vector Search · Apps · LTAP** — 전부 **"데이터를 옮기지 말고 애플리케이션을 데이터로 가져와라"** 는 한 방향. 새 컴포넌트를 볼 때 **"이걸 위해 데이터를 또 복사해야 하나"** 를 먼저 묻는다. 그리고 그 방향은 동시에 **락인**이다.

### 오늘 전체를 관통한 하나의 질문

정리하고 나서 보니, 열아홉 개가 전부 같은 질문의 변주였다.

> **"이 결정의 실체가 어디에 있는가."**

| 영역 | 실체가 어디에 있나 | 그래서 무엇이 달라지나 |
|---|---|---|
| 번들 | 워크스페이스 DB → **Git** | 리뷰·롤백·`git blame`이 가능해진다 |
| root_path | 개인 홈 → **공용 경로** | 사람이 떠나도 운영이 산다 |
| lookup | ID → **이름** | 사람이 관리할 수 있는 것에 결합된다 |
| 브랜치 | 팀 규칙 → **배포 인터페이스** | 머지가 곧 배포가 된다 |
| write_mode | 성능 선택 → **재실행 정책** | repair 버튼의 의미가 결정된다 |
| metric view | 질의 시점 계산 → **미리 만든 MV** | 정의는 한 곳, 속도는 별개 |
| 마스킹 대상 | 코드의 상수 → **카탈로그 태그** | 판단할 사람이 직접 관리한다 |
| 카탈로그 | 워크스페이스 → **계정 레벨** | 환경보다 데이터가 오래 산다 |
| 컴퓨트 | 우리 VPC → **벤더 풀** | 네트워크 경계가 이동한다 |

**전부 "어디에 두느냐"의 문제이고, 답의 형태도 같다** — 자주 바뀌는 것과 안 바뀌는 것을 분리하고, 사람에 묶인 것을 조직에 묶고, 실행 시점에 하던 걸 배포 시점이나 사전 계산 시점으로 당긴다.

### 교육을 들으면서 배운 것 (내용 말고 방법)

- **"우리가 할 게 아니다"는 답을 그냥 넘기면 안 된다.** 담당이 아니라는 사실보다 **인접 시스템이 존재한다**는 사실이 중요하다. 이어서 물어야 할 건 "그럼 그건 어느 주기로, 어느 정의로 도나요?"다.
- **메모에 남은 미해결 질문("왜 서버리스는 우리 계정에 없나")이 가장 값진 항목이었다.** 답을 못 들은 질문을 그날 안에 문서로 찾아보는 게, 답을 들은 질문 열 개를 정리하는 것보다 이해를 많이 남겼다.
- **약어는 반드시 원어를 확인한다.** DBU를 "DataBase Unit"으로 적어뒀는데 실제로는 Databricks Unit이었고, 그 오해 하나가 "코어 수"라는 잘못된 모델로 이어졌다. **약어를 잘못 풀면 그 위에 쌓는 이해가 전부 기운다.**
- **관계도는 화살표 방향과 카디널리티까지 적어야 한다.** "M:N"이라고만 적어두니 무엇과 무엇 사이인지가 사라졌다. `A : B = N : 1` 형태로 적었으면 나중에 검증할 수 있었다.
- **서로 다른 세션에서 들은 것들이 연결되는 지점을 찾아야 한다.** 정적 마스킹(ETL 세션)과 metric view materialization(질의응답)이 **제약으로 연결**되어 있다는 건 둘을 나란히 놓고 나서야 보였다. 메모를 주제별로만 정리하면 이런 연결이 안 보인다.

### 다음에 확인할 것

- **적재 태스크의 write_mode가 실제로 무엇인가?** `append`가 하나라도 있으면 repair 버튼의 의미가 태스크마다 다르다는 뜻이다.
- **metric view에 `materialization`이 이미 정의되어 있나?** 있다면 갱신 주기가 몇 시간이고, 그 신선도가 에이전트 답변에 어떻게 표시되나.
- **서버리스용 NCC가 이미 설정되어 있나?** 없다면 신청 리드타임이 얼마나 되나. 이게 컴퓨트 선택을 좌우한다.
- **PII 태그를 붙일 권한을 누가 갖고 있나?** 태그가 마스킹 대상을 결정한다면, 태그 권한이 곧 개인정보 통제 권한이다.
- **공용 wheel의 버전 관리 규칙이 있나?** dev 배포마다 버전을 올리는가, 아니면 클러스터를 재시작하는가.
- **차원 테이블이 실행 계획에서 브로드캐스트되고 있나?** `SortMergeJoin`이 보이면 첫 번째 튜닝 후보다.
