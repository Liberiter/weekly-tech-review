## Q1. 테이블을 만드는 노트북이 비어 있습니다 — 초기 생성은 어디서 하나요?

내가 본 구조는 이랬다. **테이블 목록이 행(row)으로 등록된 관리용 테이블**이 하나 있고, 거기에 `배치 대상 여부` 같은 플래그 컬럼이 있다. 그리고 "대상 테이블을 실제로 만드는" 역할처럼 보이는 노트북이 하나 있는데 — **열어보니 비어 있었다.**

그래서 물었다. "이 노트북이 관리 테이블을 읽어서 플래그가 켜진 테이블들을 실제로 생성하는 것으로 이해하면 될까요?"

### 들은 답

> **그냥 빈 노트북이다.** 초기 세팅할 때 테이블 만드는 것은 그냥 CTAS 문으로 만들었다.

> **CTAS**는 `CREATE TABLE ... AS SELECT ...` 의 약자다. 컬럼 목록과 타입을 일일이 적는 대신, **SELECT 결과의 스키마를 그대로 따라 테이블을 만드는** 방식이다. 원천 테이블의 구조를 그대로 옮겨올 때 가장 손이 덜 가는 방법이라, 초기 세팅에 자주 쓰인다.

답은 한 줄인데, 여기서 배울 게 세 덩어리다. **① 메타데이터로 파이프라인을 돌린다는 게 무슨 뜻인지, ② 왜 "처음 만드는 일"만 코드 밖에 있는지, ③ 빈 노트북이 남아 있다는 사실 자체가 무엇을 뜻하는지.**

### 1) 먼저 — 테이블 목록이 행으로 들어 있는 테이블의 정체

이건 특정 프로젝트의 별난 구조가 아니라 이름이 붙어 있는 패턴이다. **메타데이터 주도 파이프라인(metadata-driven pipeline)**, 그 목록 테이블은 흔히 **컨트롤 테이블(control table)** 이라고 부른다.

무엇을 해결하는 패턴인지부터 보면 이해가 빠르다.

```
   [메타데이터를 안 쓸 때]

   src/ingest_orders.py       ─┐
   src/ingest_members.py      ─┤  30개 테이블 = 30개 파일
   src/ingest_payments.py     ─┤  내용은 테이블 이름만 다르고 99% 동일
   ...  (27개 더)             ─┘
                                  ↓
        테이블 하나 추가 = 파일 추가 + 잡 정의 수정 + PR + 배포
        공통 로직 한 줄 수정 = 30개 파일 전부 수정  💥


   [메타데이터를 쓸 때]

   컨트롤 테이블                            노트북 1개
   ┌───────────┬─────────┬──────────┐
   │ 테이블명  │ 적재방식│ 배치대상 │      for each 대상:
   ├───────────┼─────────┼──────────┤   ─▶    파라미터로 받아서
   │ orders    │ append  │   Y      │         똑같은 코드로 처리
   │ members   │ merge   │   Y      │
   │ payments  │ append  │   Y      │
   │ coupons   │ merge   │   N      │  ← 플래그만 끄면 배치에서 빠진다
   └───────────┴─────────┴──────────┘
                                  ↓
        테이블 하나 추가 = 행 하나 INSERT  (배포 없음)
        공통 로직 수정 = 파일 하나 수정
```

**핵심은 "무엇을 처리할지(what)"와 "어떻게 처리할지(how)"를 분리한 것**이다. `how`는 코드에, `what`은 데이터에 둔다. 이렇게 하면 처리 대상이 늘어나도 코드는 안 늘어난다.

이 패턴에서 컨트롤 테이블이 흔히 들고 있는 정보들:

| 컬럼 | 역할 |
|---|---|
| 원천/대상 테이블명 | 무엇을 읽고 어디에 쓸지 |
| 적재 방식 | `append` / `merge` / `overwrite` |
| 병합 키 | `merge`일 때 무엇을 기준으로 매칭할지 |
| 증분 기준 컬럼 | 무엇을 보고 "변경분"을 판단할지 |
| **활성화 플래그** | **이 테이블을 이번 배치에 포함할지** |
| 마지막 성공 시각 | 다음 실행의 시작점(워터마크) |

내가 본 `배치 대상 여부` 플래그는 저 목록의 다섯 번째다. 그리고 이 플래그의 진짜 가치는 **"배포 없이 끌 수 있다"** 는 데 있다. 새벽 3시에 특정 테이블 적재가 계속 실패해서 배치 전체를 물고 늘어질 때, PR을 올리고 리뷰받고 배포하는 대신 **행 하나를 `N`으로 바꾸면 된다.** 운영에서 이 차이는 매우 크다.

> 다만 반대 면도 있다. **배포 없이 바꿀 수 있다는 건 리뷰 없이 바뀔 수 있다는 뜻**이기도 하다. 누가 언제 왜 껐는지가 Git 히스토리에 안 남는다. 그래서 성숙한 팀은 컨트롤 테이블에 `변경자`, `변경시각`, `변경사유` 컬럼을 같이 둔다. **코드 밖으로 뺀 설정은 코드가 주던 추적성도 같이 잃는다는 걸 인정하고 보완하는 것**이다.

### 2) 그런데 왜 "테이블 만드는 일"은 이 구조 밖에 있나

여기가 내 질문이 빗나간 지점이다. 나는 자연스럽게 "컨트롤 테이블을 읽어서 → 대상 테이블을 자동 생성" 하는 흐름을 상상했다. 실제로는 **손으로 CTAS를 날려서 만들었다.**

왜 그래도 되는지는 **부트스트랩(bootstrap) 작업과 정상 운영(steady state) 작업의 차이**로 설명된다.

| | **부트스트랩** | **정상 운영** |
|---|---|---|
| 실행 횟수 | **딱 한 번** | 매일 |
| 반복성 | 없음 | 있음 |
| 자동화 이득 | 거의 없음 | 매우 큼 |
| 실패 시 | 사람이 보고 있음 | 새벽에 아무도 없음 |
| 예 | 스키마·테이블 최초 생성, 초기 이력 적재 | 일 배치 적재, 갱신 |

**자동화의 가치는 반복 횟수에 비례한다.** 30개 테이블을 매일 도는 일은 자동화가 압도적으로 남는 장사지만, **평생 한 번 하는 일을 자동화하는 건 대체로 손해**다. 자동화 코드를 짜는 시간 + 그 코드를 나중에 읽고 유지보수하는 비용이, 손으로 한 번 하는 것보다 크기 때문이다.

그리고 초기 테이블 생성은 특히 자동화가 안 어울리는 성질을 가지고 있다.

```
   [매일 도는 적재]
   같은 일을 30번, 그리고 내일 또 30번
      → 파라미터화된 하나의 코드가 명백히 이득

   [최초 테이블 생성]
   30개 테이블의 스키마가 전부 다르다
   파티션 컬럼도, 클러스터링 키도, 코멘트도 전부 다르다
   그리고 다시는 안 한다
      → "공통 코드 + 파라미터"로 뽑아내려면
        결국 파라미터가 스키마 전체가 된다  💥
        = 추상화해도 줄어드는 게 없다
```

마지막 줄이 핵심이다. **추상화는 "다른 부분보다 같은 부분이 많을 때"만 이득**이다. 테이블 30개의 DDL은 다른 부분이 대부분이라, 이걸 하나의 생성기로 짜면 "SQL을 쓰기 위한 또 하나의 언어"를 발명하는 꼴이 된다.

### 3) 그래도 — 손으로 만든 DDL이 남기는 빚

PM님 답은 실용적으로 맞다. 다만 **공짜는 아니고, 무엇을 지불했는지는 알고 있어야 한다.**

```
   [DDL이 코드에 없을 때]

   운영 환경                     개발 환경
   ┌───────────────┐            ┌───────────────┐
   │ 테이블 30개   │            │ 테이블 ??개   │
   │ (손으로 생성) │            │ (누가 언제    │
   │               │            │  뭘 만들었지?)│
   └───────────────┘            └───────────────┘
          ↑
   "이 테이블 스키마가 왜 이렇지?" → 물어볼 사람이 퇴사했다
   "개발 환경을 새로 만들어야 한다" → 무엇을 만들어야 하는지 아무도 모른다
   "운영과 개발 스키마가 같나?"     → 확인할 방법이 눈으로 비교하는 것뿐
```

구체적인 손실은 네 가지다.

1. **재현 불가능.** 새 환경(dev/staging)을 처음부터 세우려면 무엇을 만들어야 하는지가 어디에도 안 적혀 있다.
2. **드리프트를 감지 못 한다.** 운영과 개발의 스키마가 조용히 갈라져도 알 수 없다.
3. **변경 이력이 없다.** "이 컬럼 언제 추가됐죠?"에 답할 수 없다.
4. **의도가 사라진다.** 파티션 컬럼을 왜 그걸로 골랐는지, 왜 이 타입인지가 남지 않는다.

그래서 실무의 절충은 대개 이렇다. **자동 생성 파이프라인은 안 만들되, DDL 자체는 리포에 저장한다.**

```
   ❌ 최악:  손으로 만들고 아무 데도 안 남긴다

   △ 현실:  손으로 만들고, 실행한 DDL 을 리포의 SQL 파일로 남긴다
            → 재현 가능, 리뷰 가능, 이력 남음
            → 실행은 여전히 수동 (그래도 된다)

   ✅ 이상:  스키마 관리 도구가 선언적으로 관리
            (dbt 모델, 마이그레이션 도구, 파이프라인 선언 등)
            → 다만 초기 프로젝트에 이걸 강요하는 건 과할 수 있다
```

**"자동으로 실행되지 않는 것"과 "코드로 남지 않는 것"은 다른 문제다.** 부트스트랩은 자동 실행할 이유가 없지만, 코드로 남지 않을 이유는 없다.

### 4) 빈 노트북이 남아 있다는 사실 자체에 대해

마지막으로, 이건 기술이 아니라 **협업**의 문제다.

내가 그 노트북을 열고 "아 비어 있네, 아직 안 만들었나 보다" 하고 넘어갔다면 아무 일도 없었다. 그런데 **나는 그것을 "테이블을 생성하는 노트북"이라고 읽었다.** 이름이 그렇게 붙어 있었기 때문이다.

```
   빈 파일이 사람에게 주는 신호

   "이건 앞으로 채워질 자리다"      ← 대부분의 신입이 이렇게 읽는다
   "이건 실패한 시도의 잔해다"
   "이건 그냥 안 지운 것이다"        ← 실제
        ↑
   셋 중 무엇인지 파일 자체는 말해주지 않는다
```

**이름이 있는 빈 껍데기는 거짓 약속을 한다.** 그리고 그 약속을 믿은 사람이 시간을 쓴다. 처리 비용은 둘 중 하나다.

- **지운다.** 필요 없어졌다면 그게 정답이다. Git에 남아 있으니 사라지는 게 아니다.
- **한 줄 적어둔다.** `이 노트북은 사용하지 않습니다. 초기 테이블은 최초 세팅 시 CTAS로 수동 생성했습니다.` — 5초면 쓰는 문장이 다음 사람의 30분을 아낀다.

> **핵심 통찰 1 — "자동화의 가치는 작업의 어려움이 아니라 반복 횟수에 비례한다"**
>
> 초보자가 코드를 배울 때 생기는 반사 신경이 있다. **"손으로 하고 있네? 자동화해야지."** 대부분의 경우 맞지만, 이 반사 신경은 **"몇 번 하는 일인가"를 안 묻는다**는 결함이 있다.
>
> 자동화의 손익은 단순하다. `(수동 1회 비용 × 실행 횟수)` 대 `(자동화 개발 비용 + 유지보수 비용 × 남은 수명)`. **실행 횟수가 1이면 왼쪽은 거의 항상 작다.** 게다가 오른쪽의 "유지보수 비용"은 사람들이 계산에서 자주 빼먹는데, 실제로는 이게 제일 크다. 아무도 안 쓰는 자동화 코드도 리포에 있는 한 읽히고, 의심받고, 리팩터링 때 걸린다.
>
> 그래서 판단 질문은 "이걸 자동화할 수 있나"가 아니라 **"이걸 몇 번 더 할 것인가"** 다. 답이 "한 번"이면 손으로 하는 게 엔지니어링이다. 대신 **한 것을 기록으로 남기는 것**은 횟수와 무관하게 항상 남는 장사다.

> **핵심 통찰 2 — "설정을 데이터로 빼면 유연성을 얻고 추적성을 잃는다"**
>
> 처리 대상 목록을 코드에서 테이블로 옮기면 대단히 편해진다. 배포 없이 대상을 늘리고, 장애 중에 특정 테이블을 즉시 끌 수 있다. 이건 진짜 이득이다.
>
> 그런데 **코드가 공짜로 주던 것들이 같이 사라진다는 걸 인식해야 한다** — 변경 이력, 코드 리뷰, PR 승인, 롤백, "누가 왜 이렇게 했는가". 코드에 있을 땐 Git이 알아서 해주던 일이다.
>
> 그래서 설정을 데이터로 뺄 때는 **잃어버린 기능을 명시적으로 다시 만들어야 한다.** 변경 이력 컬럼, 변경 사유 필수 입력, 변경 시 알림 같은 것들. 이걸 안 하면 유연성만 남고 통제가 사라진 상태가 되는데, 그 상태는 **"바꾸기는 쉬운데 왜 그렇게 됐는지 아무도 모르는 시스템"** 이다.

### 내가 확인할 것

- [ ] 실행했던 초기 DDL이 리포 어딘가에 남아 있는지. 없다면 지금이라도 현재 스키마를 덤프해 파일로 남길 수 있는지
- [ ] 개발 환경과 운영 환경의 테이블 스키마가 실제로 동일한지 확인할 방법이 있는지
- [ ] 컨트롤 테이블에 변경 이력(변경자·시각·사유)이 남는지. 안 남는다면 플래그를 끈 사실을 누가 어떻게 아는지
- [ ] 그 빈 노트북 — 지워도 되는지 물어보고, 지우거나 최소한 한 줄 설명을 넣기
- [ ] 테이블을 새로 추가할 때의 표준 절차가 문서화돼 있는지 (DDL 실행 → 컨트롤 테이블 INSERT 순서와 주의점)

## Q2. 파라미터는 위젯으로 받는데, 시크릿은 어디서 오나요?

배치 노트북을 읽다가 두 종류의 "밖에서 값을 가져오는" 호출을 봤다.

```python
target_table = dbutils.widgets.get("table_name")     # ← 잡 정의에서 넘어오는 값
password     = dbutils.secrets.get(scope, key)       # ← 이건 어디서 오지?
```

앞의 것은 이해했다. 잡 정의(리소스 YAML)에서 태스크에 넘긴 파라미터가 위젯으로 들어온다. 그런데 뒤의 것은 **어디에도 정의된 곳이 안 보였다.** 그래서 물었다.

### 들은 답

- **Secrets Scope에 있는 값**이고, **admin만 가능**하다.
- **UI에서 넣을 수도 있지만, 대체로는 Python 코드로 API를 통해 넣는다.**
- 요즘은 **Unity Catalog 안에 넣을 수 있는 기능**이 생겼다.

방향은 다 맞다. 다만 **세부에 짚고 갈 게 몇 개 있다.** 순서대로 간다.

### 1) 기초 — 파라미터와 시크릿은 왜 갈라져 있나

둘 다 "코드 밖에서 값을 주입한다"는 점은 같다. 갈라지는 이유는 하나다. **하나는 보여도 되고, 하나는 보이면 안 된다.**

| | **파라미터 (위젯)** | **시크릿** |
|---|---|---|
| 값의 성격 | 대상 테이블명, 처리 날짜, 환경 이름 | 비밀번호, 토큰, 접속 키 |
| 어디에 정의 | 잡 정의 YAML, UI, 실행 시 입력 | 별도의 시크릿 저장소 |
| **로그에 남나** | **남는다** (실행 이력에 파라미터가 그대로 보임) | **자동으로 가려진다** |
| 버전 관리 | 코드에 그대로 커밋 | **절대 커밋 금지** |
| 누가 보나 | 잡을 볼 수 있는 사람 전부 | 권한을 명시적으로 받은 사람만 |
| 바뀌는 주기 | 실행마다 | 몇 달~몇 년 |

**핵심 차이는 "로그에 남는가"** 다. 배치 실행 이력을 열면 그 실행에 어떤 파라미터가 들어갔는지 다 보인다. 만약 비밀번호를 위젯으로 넘기면, **잡 실행 이력을 볼 수 있는 모든 사람이 그 비밀번호를 보게 된다.** 이건 보안 사고다.

그래서 시크릿 API는 **출력 자동 마스킹**이라는 방어 장치를 갖고 있다.

```python
pw = dbutils.secrets.get(scope="my_scope", key="db_password")
print(pw)
# 출력:  [REDACTED]        ← 노트북 출력에서 자동으로 가려진다
```

이게 꽤 강력하다. 시크릿에서 읽어온 문자열은 노트북 출력·로그에서 자동으로 `[REDACTED]`로 치환된다. 실수로 출력해도 노출되지 않는다.

> ⚠️ **다만 만능은 아니다.** 문자열을 변형하면(슬라이싱, 인코딩, 문자 사이에 뭘 끼워 넣기 등) 마스킹을 우회할 수 있다. 마스킹은 **실수를 막는 장치이지 악의를 막는 장치가 아니다.** 진짜 방어선은 아래에 나올 **권한(ACL)** 이다.

### 2) 시크릿 스코프의 구조

이름이 "스코프(scope)"인 이유는 **시크릿들을 묶는 네임스페이스**이기 때문이다.

```
   워크스페이스
   └─ 시크릿 스코프: "prod-source-db"
       ├─ key: "host"        → value: (숨김)
       ├─ key: "username"    → value: (숨김)
       └─ key: "password"    → value: (숨김)
   └─ 시크릿 스코프: "dev-source-db"
       ├─ key: "host"        → value: (숨김)
       └─ ...

   dbutils.secrets.get(scope="prod-source-db", key="password")
                            └─ 어느 묶음 ─┘      └─ 그 안의 어느 값 ─┘
```

권한은 **스코프 단위로** 붙는다. 세 단계다.

| 권한 | 할 수 있는 일 |
|---|---|
| `READ` | 값 읽기, 키 목록 조회 |
| `WRITE` | + 시크릿 추가·수정·삭제 |
| `MANAGE` | + 권한(ACL) 자체를 관리 |

스코프의 종류는 두 가지다.

| | **Databricks 백엔드** | **클라우드 키 저장소 백엔드** |
|---|---|---|
| 값이 실제로 저장되는 곳 | Databricks가 관리하는 암호화 저장소 | Azure Key Vault 등 외부 키 관리 서비스 |
| 값 갱신 | Databricks 쪽에서 | **외부 저장소에서 갱신하면 자동 반영** |
| 감사 로그 | Databricks | 외부 저장소의 감사 기능도 함께 |
| 언제 쓰나 | 기본 선택지 | 전사 키 관리 정책이 이미 있을 때 |

**후자는 "시크릿의 단일 진실원을 조직 전체가 이미 갖고 있을 때"** 쓴다. 회사가 키 저장소를 운영하고 있는데 Databricks에만 비밀번호 사본을 또 두면, 비밀번호를 교체할 때 두 곳을 고쳐야 하고 결국 한 곳을 빼먹는다.

### 3) ⚠️ "admin만 가능하다"와 "UI에서 넣을 수도 있다"를 정확히

여기가 메모와 문서가 미묘하게 어긋나는 지점이라 정확히 적어둔다.

**① "admin만 가능하다"** — 조직 정책으로는 대개 맞지만, 플랫폼의 기본 제약은 아니다.

Databricks 백엔드 스코프는 **원칙적으로 워크스페이스 사용자가 생성할 수 있고, 만든 사람이 그 스코프의 `MANAGE` 권한을 갖는다.** 다만 실무에서는 거의 항상 이렇게 운영한다.

```
   [플랫폼이 허용하는 것]        [조직이 실제로 하는 것]
   ─────────────────────        ────────────────────────
   사용자가 스코프 생성 가능      플랫폼/보안 팀만 스코프 생성
   생성자가 MANAGE 보유           개발자에게는 READ 만 부여
                                  운영 자격증명은 아예 접근 불가
```

**왜 이렇게 조이나?** 누구나 스코프를 만들 수 있으면 **비밀번호가 여기저기 흩어진다.** 개발자마다 자기 스코프를 만들어 같은 DB 비밀번호를 복사해두면, 비밀번호 교체 시 몇 개를 고쳐야 하는지 아무도 모르는 상태가 된다. 그래서 "admin만"은 **플랫폼의 제약이 아니라 조직의 규율**이고, 그 규율의 목적은 **자격증명이 한 곳에만 있게 하는 것**이다.

**② "UI에서 넣을 수도 있다"** — 이 부분은 조심해야 한다.

**시크릿 스코프의 생성과 시크릿 값의 입력은 기본적으로 CLI 또는 REST API로 하는 작업이다.** 워크스페이스 UI 화면에서 "새 시크릿 만들기" 버튼을 눌러 값을 타이핑하는 흐름은 일반적인 경로가 아니다. (Azure Key Vault 백엔드를 쓰는 경우, **값 자체는 Key Vault의 UI에서** 넣게 되는데 — 아마 PM님이 말씀하신 "UI"가 이쪽일 가능성이 크다.)

그러니 표준 경로는 이렇다.

```bash
# CLI
databricks secrets create-scope my_scope
databricks secrets put-secret my_scope db_password
```

```python
# SDK / API — PM님이 "Python 코드로 API로 넣는다"고 하신 것
from databricks.sdk import WorkspaceClient

w = WorkspaceClient()
w.secrets.create_scope(scope="my_scope")
w.secrets.put_secret(scope="my_scope", key="db_password", string_value=pw)
w.secrets.put_acl(scope="my_scope", principal="data-eng-group", permission="READ")
```

**왜 코드로 넣는 게 낫나?** 이유가 셋이다.

1. **재현 가능하다.** 새 워크스페이스를 세울 때 같은 스크립트를 돌리면 같은 구조가 만들어진다.
2. **권한 부여를 빼먹지 않는다.** UI에서 손으로 하면 "스코프는 만들었는데 ACL을 안 줘서 배치가 실패"가 흔하다. 스크립트에 넣어두면 항상 같이 실행된다.
3. **자동화 파이프라인에 넣을 수 있다.** 자격증명 교체(rotation)를 주기적으로 돌리려면 결국 코드여야 한다.

> 참고로, 배포 번들에서 **시크릿 스코프와 그 권한을 리소스로 선언**하는 것도 지원된다. 다만 **선언할 수 있는 건 "스코프와 ACL"이지 "값"이 아니다.** 값을 YAML에 적으면 그게 바로 Git에 커밋되는 비밀번호가 되기 때문이다. 이 설계 자체가 좋은 교훈이다 — **"구조는 코드로, 값은 코드 밖으로."**

### 4) "요즘은 Unity Catalog 안에 넣을 수 있다"는 말의 의미

이 부분은 **정확히 무슨 기능을 가리키는지 확인이 필요하다.** 최근 Databricks가 자격증명 관리를 Unity Catalog 쪽으로 끌어오는 흐름이 분명히 있고, 대표적인 것이 둘이다.

| 기능 | 무엇 | 언제 |
|---|---|---|
| **서비스 자격증명 (service credentials)** | 외부 클라우드 서비스에 접근할 때 쓰는 인증을 UC 객체로 관리 | 노트북에서 외부 API·클라우드 서비스를 호출할 때 |
| **커넥션 (connections)** | 외부 데이터베이스 접속 정보를 UC 객체로 관리 | Q5에 나올 **Lakehouse Federation**의 접속 정보가 바로 이것 |

두 기능의 공통점이 중요하다.

```
   [전통적 방식]                        [UC 방식]
   ───────────────                     ─────────────────────────
   시크릿 스코프에 값 저장               UC 객체(커넥션/자격증명)로 저장
        ↓                                    ↓
   코드가 값을 "읽어서"                  코드는 값을 아예 안 본다
   직접 접속 문자열을 조립                객체 이름만 참조
        ↓                                    ↓
   ⚠️ 값이 코드의 변수에 들어온다        ✅ 값이 코드에 노출되지 않는다
   ⚠️ 권한 관리가 UC 밖에 따로 있다      ✅ UC 권한 체계에 통합된다
```

**방향의 핵심은 "시크릿을 안전하게 읽는 것"에서 "시크릿을 아예 읽지 않는 것"으로 옮겨가는 것**이다. 값을 코드가 만지지 않으면 유출 경로가 원천적으로 줄어든다.

> ⚠️ 다만 **어떤 기능이 정확히 무엇을 대체하는지, 우리 환경에서 쓸 수 있는지는 직접 확인해야 한다.** 이 영역은 최근 변화가 빠르고, 클라우드(AWS/Azure/GCP)마다 지원 범위가 다르며, "미리보기(Preview)" 딱지가 붙었다 떨어졌다 한다. **"요즘 되더라"를 그대로 설계에 넣으면 안 되고, 공식 문서에서 현재 상태를 확인하는 게 맞다.**

### 5) 실무에서 꼭 알아둘 것 — 시크릿을 다룰 때의 지뢰

```python
# ❌ 절대 하면 안 되는 것들

# 1. 코드에 직접
password = "P@ssw0rd123"

# 2. 위젯으로 받기 — 실행 이력에 그대로 남는다
password = dbutils.widgets.get("password")

# 3. 환경 변수로 클러스터에 박아두기 — 클러스터를 보는 사람 모두가 본다
#    (단, 시크릿을 "참조"하는 방식의 환경변수 주입은 지원되는 안전한 방법이다)

# 4. 로그로 확인하려는 시도
print(f"pw len = {len(password)}, starts with {password[:3]}")
#     ↑ 변형했으므로 마스킹이 안 걸릴 수 있다
```

```python
# ✅ 표준 형태
scope = dbutils.widgets.get("secret_scope")     # 스코프 "이름"은 파라미터로 (비밀이 아님)
user  = dbutils.secrets.get(scope, "username")
pw    = dbutils.secrets.get(scope, "password")
```

마지막 줄의 패턴이 좋은 이유가 있다. **스코프 이름을 파라미터로 받으면 환경 분리가 자동으로 된다.** 같은 노트북이 개발 환경에서는 `dev-source-db`를, 운영에서는 `prod-source-db`를 보게 되고, **코드는 한 줄도 안 바뀐다.**

> **핵심 통찰 1 — "설정과 비밀의 차이는 민감도가 아니라 '어디에 남는가'다"**
>
> "비밀번호는 민감하니까 따로 관리한다"는 설명은 맞지만 실행에 도움이 안 된다. 무엇이 민감한지 판단이 사람마다 다르기 때문이다.
>
> 실행 가능한 기준은 이거다. **"이 값이 실행 이력·로그·에러 메시지에 찍혀도 괜찮은가?"** 파라미터로 넘긴 값은 **반드시 어딘가에 기록된다.** 잡 실행 상세 화면에, 감사 로그에, 스택 트레이스에. 시크릿 API는 정확히 그 경로들을 막기 위해 존재한다.
>
> 그래서 새 값을 코드 밖으로 뺄 때 물어야 할 질문은 "이거 비밀인가?"가 아니라 **"이게 로그에 남아도 되나?"** 다. 후자는 답이 명확하고, 판단이 사람마다 갈리지 않는다.

> **핵심 통찰 2 — "자격증명 관리의 발전 방향은 '안전하게 읽기'가 아니라 '읽지 않기'다"**
>
> 시크릿 저장소의 1세대 가치는 **값을 코드에서 분리한 것**이었다. 코드에는 스코프 이름만 남고, 값은 권한이 있는 사람만 접근 가능한 곳에 있다. 큰 진전이다.
>
> 그런데 여전히 남는 구멍이 있다 — **결국 런타임에는 값이 프로세스 메모리의 변수에 들어온다.** 그 변수를 누군가 로그로 찍을 수 있고, 예외 메시지에 섞여 나갈 수 있고, 접속 문자열로 조립되다가 새어나갈 수 있다.
>
> UC 커넥션 같은 방식은 이 마지막 구멍을 닫는다. **코드가 값을 참조하지 않고 "객체를 참조"한다.** 인증은 플랫폼이 대신 하고, 애플리케이션 코드는 비밀번호가 존재한다는 사실조차 모른다. 일반화하면 이렇다 — **보안에서 가장 확실한 방어는 "조심해서 다루기"가 아니라 "손에 쥐지 않기"다.** 손에 없는 것은 떨어뜨릴 수 없다.

### 내가 확인할 것

- [ ] 우리 프로젝트가 쓰는 스코프가 Databricks 백엔드인지 클라우드 키 저장소 백엔드인지
- [ ] 스코프 이름이 코드에 하드코딩돼 있는지, 파라미터로 주입되는지 (환경 분리가 되는 구조인지)
- [ ] 스코프를 만들고 권한을 준 스크립트가 리포에 남아 있는지. 없다면 새 환경을 어떻게 세우는지
- [ ] 자격증명 교체 주기와 절차가 정해져 있는지. 교체하면 배치가 자동으로 새 값을 쓰는지
- [ ] UC 커넥션 방식으로 옮길 계획이 있는지, 있다면 지금 시크릿 기반 코드가 어떻게 되는지

## Q3. 상태 테이블은 왜 하루 중 특정 시간대만 읽나요?

배치 코드를 보니 **시간 범위를 계산하는 함수와 쿼리를 만드는 함수가 각각 두 벌씩** 있었다. 두 벌로 나뉜 기준은 알겠는데 — 한쪽은 계속 쌓이는 **사실(fact) 테이블**이라 `append`, 다른 한쪽은 **거래 상태 테이블**이라 `merge` — **두 번째 계열의 시간 범위가 이상했다.** 다른 날짜 범위가 아니라 **당일 00시부터 07시까지**로 고정돼 있었다.

그래서 물었다. "원천 쪽 ETL이 00~07시 사이에 도는 건가요?"

### 들은 답

> ETL 시간이 잡히도록만 해놓으면, **상태 테이블은 어차피 최종 상태만 원하니까 이력이 필요 없다.**

이 답은 맞다. 그런데 **한 문장 안에 두 개의 서로 다른 이야기가 압축돼 있고, 그중 하나에는 조건이 붙는다.** 갈라서 본다.

- **① "최종 상태만 원한다 = 이력이 필요 없다"** → 데이터 모델링 이야기. 전적으로 맞다.
- **② "ETL 시간만 잡히면 된다"** → 증분 추출 이야기. **맞지만 위험한 가정이 하나 깔려 있다.**

### 1) 기초 — 왜 테이블마다 적재 방식이 다른가

먼저 append와 merge가 갈리는 근본 이유부터. **데이터가 "불변인가 가변인가"** 다.

```
   [사실(fact) — 일어난 일]

   2026-08-09 14:32  주문 #1001 생성됨
   2026-08-09 14:35  주문 #1002 생성됨
   2026-08-09 14:41  주문 #1003 생성됨
         ↑
   과거의 사건은 바뀌지 않는다. 14:32에 일어난 일은 영원히 14:32에 일어난 일이다
         ↓
   ✅ append — 새로 일어난 것만 뒤에 붙이면 된다


   [상태(state) — 지금 어떤가]

   주문 #1001 :  결제대기 → 결제완료 → 배송중 → 배송완료
                    ↑           ↑          ↑         ↑
                 같은 행이 계속 갱신된다
         ↓
   ✅ merge — 이미 있으면 갱신, 없으면 삽입 (upsert)
```

여기서 갈라지는 건 적재 방식만이 아니다. **"무엇이 변경분인가"의 정의도 같이 갈라진다.**

| | **사실 테이블 (append)** | **상태 테이블 (merge)** |
|---|---|---|
| 행이 바뀌나 | ❌ 한 번 쓰이면 끝 | ✅ 계속 갱신됨 |
| 변경분 판단 기준 | **생성 시각** | **최종 수정 시각** |
| 놓치면 생기는 일 | 그 사건이 영영 안 들어옴 | **오래된 상태가 남아 있음** |
| 중복 적재하면 | **행이 두 배가 됨** 💥 | 같은 값으로 덮어씀 (무해) |
| 멱등성 | 별도 장치 필요 | **구조적으로 멱등** ★ |

마지막 두 줄이 실무에서 매우 중요하다. **merge는 같은 데이터를 두 번 넣어도 안전하다.** 키가 같으면 그냥 같은 값으로 덮어쓰기 때문이다. 반면 **append는 두 번 넣으면 그대로 중복**이 된다.

이 비대칭이 다음 절의 결론을 만든다.

### 2) "최종 상태만 원한다"의 정확한 의미 — SCD

PM님 답의 첫 부분, **"어차피 최종 상태만 원하니까 이력이 필요 없다"** 는 데이터 웨어하우스에 정식 명칭이 있는 설계 결정이다. **SCD(Slowly Changing Dimension, 천천히 변하는 차원)** 유형 선택이다.

```
   주문 #1001 의 상태가 "배송중"에서 "배송완료"로 바뀌었다


   [Type 1 — 덮어쓴다]  ← 우리가 선택한 것
   ┌──────┬──────────┬─────────────┐
   │ 주문 │  상태    │ 수정시각    │
   ├──────┼──────────┼─────────────┤
   │ 1001 │ 배송완료 │ 08-10 06:00 │   ← 이전 값은 사라짐
   └──────┴──────────┴─────────────┘
   "지금 어떤가"에만 답한다. 단순하고 작다


   [Type 2 — 이력을 남긴다]
   ┌──────┬──────────┬─────────────┬─────────────┬────────┐
   │ 주문 │  상태    │  시작       │  종료       │ 현재행 │
   ├──────┼──────────┼─────────────┼─────────────┼────────┤
   │ 1001 │ 결제완료 │ 08-08 10:00 │ 08-09 14:00 │   N    │
   │ 1001 │ 배송중   │ 08-09 14:00 │ 08-10 06:00 │   N    │
   │ 1001 │ 배송완료 │ 08-10 06:00 │  (없음)     │   Y    │
   └──────┴──────────┴─────────────┴─────────────┴────────┘
   "그때는 어땠나"에도 답한다. 대신 행이 몇 배로 늘고 쿼리가 복잡해진다
```

Type 2를 선택하면 답할 수 있게 되는 질문들이 있다.

- "배송중 상태에 평균 몇 시간 머물렀나?"
- "지난달 말일 기준으로 미배송 주문이 몇 건이었나?"
- "결제완료에서 취소로 간 비율이 지난주 대비 어떤가?"

**전부 "시간에 따른 변화"에 대한 질문**이다. Type 1을 선택했다는 건 **이런 질문에는 답하지 않기로 했다**는 뜻이다.

> 그리고 이건 기술 결정이 아니라 **업무 결정**이다. "상태 전이 소요 시간 분석이 필요한가?"는 개발자가 판단할 문제가 아니다. 지금 필요 없다고 해서 영원히 필요 없는 것도 아니고, **나중에 필요해졌을 때 과거 이력은 복원할 수 없다.** Type 1로 덮어쓴 순간 그 정보는 영영 사라진다.
>
> 그래서 이 결정에는 **비대칭이 있다.** Type 2로 쌓아두면 나중에 안 써도 손해는 저장 비용뿐이지만, Type 1로 버리면 나중에 필요해도 못 만든다. 상태 전이 이력이 업무적으로 중요할 가능성이 조금이라도 있다면, **최소한 원천 쪽에 이력이 남는지는 확인해둬야 한다.**

### 3) ★ "특정 시간대만 읽는다"의 진짜 의미 — 그리고 그 밑의 가정

이제 내 질문의 원래 지점이다. **왜 하필 00~07시인가?**

답은 이렇다. **상류 시스템의 ETL이 그 시간대에 돈다.** 그러니 **"그 시간대에 수정된 행"이 곧 "어제 이후 변경된 행 전부"** 라는 것이다.

```
   [상류 시스템의 하루]

   00:00 ─────────── 07:00 ─────────────────────────── 24:00
     │                   │                                 │
     └── ETL 수행 구간 ──┘                                 │
         이 시간에만 상태 테이블이 갱신된다                │
                        │                                  │
                        └──── 나머지 시간엔 변경 없음 ─────┘

   [우리 배치]
   07시 이후에 실행 → "오늘 00~07시에 수정된 행"만 뽑아 MERGE
                       = 하루치 변경분 전부
```

논리 자체는 맞다. 그런데 **이 논리는 하나의 가정 위에 서 있다.**

> **가정: 상류의 상태 테이블은 00~07시 밖에서는 절대 바뀌지 않는다.**

이 가정이 깨지는 경우를 세어보면 생각보다 많다.

| 상황 | 무슨 일이 생기나 |
|---|---|
| **상류 ETL이 지연돼 08시에 끝남** | 07시 이후 수정분을 못 읽는다 → **그 행들은 영원히 옛날 상태로 남는다** |
| **상류가 배치 시간을 변경함** | 우리 코드는 그대로 → 조용히 유실 |
| **운영자가 낮에 데이터를 수동 수정** | 우리 창 밖 → 놓침 |
| **긴급 핫픽스 배치가 저녁에 돎** | 우리 창 밖 → 놓침 |
| **타임존이 다름** | 상류가 KST 기준 00~07시인데 우리가 UTC로 계산하면 **9시간 어긋난다** 💥 |

**전부 조용히 실패한다는 게 핵심이다.** 배치는 초록불로 끝나고, 에러도 없고, 알림도 안 온다. 다만 **일부 주문의 상태가 며칠 전 값으로 멈춰 있을 뿐**이다. 그리고 그 데이터를 대시보드나 에이전트가 읽는다.

```
   [실패가 눈에 보이는 경우]
   배치 실패 → 빨간불 → 알림 → 사람이 본다  ✅

   [이 경우]
   배치 성공 → 초록불 → 알림 없음
        │
        └─▶ 그런데 주문 #1001 은 3일째 "배송중"이다
             (실제로는 배송완료된 지 3일 됨)
             아무도 모른다  💀
```

### 4) 더 안전한 방법 — 고수위(watermark) 방식

시간 창을 고정하는 대신, **"마지막으로 성공한 시점 이후 전부"** 를 읽는 방식이 있다. 이걸 **고수위 표시(high watermark)** 방식이라고 한다.

```
   [고정 시간 창]                      [고수위]
   ─────────────────                  ────────────────────────────
   WHERE 수정시각                      WHERE 수정시각 > (마지막 성공 시점)
     BETWEEN 오늘 00시                                    │
         AND 오늘 07시                                    └─ 컨트롤 테이블에 저장
        │
        └─ 상류 스케줄에 대한             ✅ 상류가 언제 돌든 상관없다
           암묵적 계약이 코드에 박힘       ✅ 배치를 하루 걸러도 자동 복구
        ❌ 상류가 바뀌면 조용히 깨짐        ✅ 낮에 수정돼도 다음 실행에 잡힌다
```

고수위 방식이 구조적으로 우월한 이유는 **"놓친 것이 다음 실행에서 자동으로 따라잡힌다"** 는 점이다. 고정 창은 한 번 놓치면 영영 놓치지만, 고수위는 워터마크를 갱신하지 않는 한 계속 재시도한다.

여기에 실무에서 꼭 얹는 장치가 둘 있다.

**① 되돌아보기 여유(lookback buffer)**

```
   WHERE 수정시각 > (마지막 성공 시점 - 1시간)
                                      └─ 일부러 겹치게 읽는다
```

왜? **경계에서의 유실을 막기 위해서**다. 트랜잭션이 커밋되는 시점과 `수정시각` 컬럼에 찍히는 시점이 미세하게 다르면, 정확히 경계에 걸린 행이 새어나갈 수 있다. 겹쳐 읽으면 그런 행도 잡힌다.

**그리고 겹쳐 읽어도 안전한 이유가 바로 merge다.** 같은 행을 다시 읽어 같은 값으로 덮어써도 결과가 같기 때문이다. 이게 앞의 표에서 본 **"merge는 구조적으로 멱등"** 이라는 성질의 실전 활용이다. (append 테이블에 같은 짓을 하면 중복이 생긴다. 그래서 append 쪽은 겹쳐 읽는 대신 **경계를 명확히 하거나 중복 제거 로직이 필요**하다.)

**② 주기적 전체 대조(reconciliation)**

증분 방식은 아무리 잘 짜도 **드리프트가 누적된다.** 그래서 주기적으로 — 주 1회나 월 1회 — 전체를 다시 읽어 맞춰본다.

```
   매일:   증분 MERGE           (빠르다)
   매주:   전체 재동기화 or 건수·해시 비교   (안전망)
             └─ 어긋난 게 있으면 알림
```

**증분은 성능 최적화이고, 전체 대조는 그 최적화의 보험**이다. 보험 없는 최적화는 언젠가 청구서가 온다.

### 5) 상태 테이블 MERGE에서 흔히 나는 사고 하나

덤으로, 상태 테이블을 merge할 때 초보자가 자주 만드는 버그를 하나 적어둔다.

```
   원천에서 같은 주문이 하루에 3번 상태가 바뀌었다
   → 증분 조회 결과에 주문 #1001 이 3행 들어 있다

   MERGE 대상 테이블 USING (그 3행) ON 주문번호 일치
        ↓
   💥 에러 또는 비결정적 결과
      "여러 소스 행이 같은 대상 행에 매칭됨"
```

**MERGE는 소스에 키가 유일해야 한다.** 그래서 증분 추출 후에 **키별로 가장 최신 행 하나만 남기는 단계**가 반드시 필요하다.

```sql
-- 키별 최신 1건만 남기기
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (
             PARTITION BY 주문번호 ORDER BY 수정시각 DESC) AS rn
  FROM 증분조회결과
) WHERE rn = 1
```

**"최종 상태만 원한다"는 설계 결정이 코드 레벨에서 이 한 단계로 나타나는 것**이다. 이 단계가 없으면 하루에 여러 번 바뀌는 주문이 나올 때 배치가 깨진다. 그리고 그런 주문은 평소엔 없다가 프로모션 날에 갑자기 생긴다.

> **핵심 통찰 1 — "증분 추출의 조건은 코드가 아니라 상류와의 계약이다"**
>
> `WHERE 수정시각 BETWEEN 00시 AND 07시` 라는 한 줄은 겉보기에 그냥 필터다. 그런데 이 한 줄이 실제로 주장하는 것은 훨씬 크다 — **"상류 시스템은 이 시간대 밖에서 이 테이블을 절대 건드리지 않는다."**
>
> 이건 **다른 팀의 행동에 대한 약속**이다. 그런데 그 약속이 어디에도 문서화돼 있지 않고, 상류 팀은 그런 약속을 한 적도 없으며, 우리 코드 안에만 암묵적으로 존재한다. 상류가 배치 시간을 30분 늦추는 순간 우리 데이터가 조용히 틀어지는데, **상류 팀은 자기가 뭘 깼는지조차 모른다.**
>
> 그래서 이런 상수를 볼 때 물어야 할 질문은 "이 숫자가 맞나"가 아니라 **"이 숫자는 무엇에 대한 가정인가, 그 가정이 깨지면 누가 알게 되나"** 다. 답이 "아무도 모른다"면, 그 코드는 지금 작동하는 게 아니라 **아직 안 깨진 것**이다.

> **핵심 통찰 2 — "적재 방식의 선택은 멱등성의 선택이고, 멱등성은 운영 절차의 자유도를 정한다"**
>
> merge와 append는 흔히 "데이터가 갱신되냐 아니냐"로 설명되지만, 실제로 운영에서 더 크게 체감되는 차이는 **다시 돌려도 되느냐**다.
>
> merge는 같은 데이터를 열 번 넣어도 결과가 같다. 그래서 겹쳐 읽어도 되고, 실패한 배치를 그냥 다시 돌려도 되고, 의심스러우면 어제 것까지 포함해서 다시 읽어도 된다. **"일단 다시 돌려보자"가 안전한 선택지가 된다.**
>
> append는 그렇지 않다. 다시 돌리면 중복이 생기므로, 재실행 전에 **"어디까지 들어갔는지"를 먼저 확인해야 한다.** 새벽 3시에 이 확인을 정확히 해낼 확률은 높지 않다.
>
> 그래서 적재 방식은 데이터 모델링 결정처럼 보이지만 **운영 결정**이다. 그리고 append를 쓸 수밖에 없다면 — 사실 테이블은 대부분 그렇다 — **멱등성을 다른 방식으로 확보해야 한다.** 날짜 파티션 단위 덮어쓰기가 가장 흔한 답이다.

### 내가 확인할 것

- [ ] 상류 ETL의 실제 수행 시간대. **그리고 그게 지연될 때 우리에게 통지되는 경로가 있는지**
- [ ] 시간 창 계산이 어느 타임존 기준인지. 상류가 쓰는 타임존과 일치하는지 (Q6과 직결된다)
- [ ] 상류가 배치 시간을 바꿀 때 우리가 알 수 있는 방법이 있는지. 없다면 **고수위 방식으로 바꾸는 게 맞지 않은지**
- [ ] MERGE 전에 키별 중복 제거 단계가 있는지. 없다면 하루에 여러 번 바뀌는 키에서 깨지지 않는지
- [ ] 상태 전이 이력이 업무적으로 필요해질 가능성이 있는지. 있다면 **원천에 이력이 남아 있는지** (우리가 Type 1로 덮어쓰면 우리 쪽엔 안 남는다)
- [ ] 주기적 전체 대조가 있는지. 없다면 드리프트를 발견할 방법이 무엇인지

## Q4. dbt의 새 엔진과 기존 엔진 중 우리는 무엇을 쓰나요?

dbt가 최근 **Rust로 다시 쓴 새 실행 엔진**을 내놓으면서 메이저 버전이 올라갔다는 걸 알고 있었다. 그런데 그 새 엔진에서 **Databricks 커넥터(어댑터)는 아직 미리보기 단계**라는 이야기도 들었다. 그래서 물었다. "우리는 새 버전을 쓰나요, 기존 버전을 쓰나요?"

### 들은 답

> 현재 번들 초기화 템플릿을 쓰면 **기존 버전으로 연결**되는데, **새 버전이 안정적이게 되면 그쪽으로 연결될 것**이다. **Databricks에서 알아서 한다.**

실용적으로는 맞는 답이다. 다만 **"알아서 한다"에 기대면 안 되는 부분이 하나 있고**, 그게 이 질문에서 제일 배울 만한 지점이다. 먼저 배경부터.

### 1) 기초 — dbt가 하는 일과 "엔진"이 무엇인지

dbt를 처음 보는 사람을 위해 한 문단으로 요약하면 이렇다.

**dbt는 SQL 파일들을 의존 순서대로 실행해주는 도구다.**

```
   내가 쓰는 것                      dbt 가 하는 것
   ────────────────                 ─────────────────────────────
   models/orders.sql                ① SQL 안의 참조 함수를 실제 테이블명으로 치환
   models/daily_sales.sql           ② 참조 관계로부터 DAG(실행 순서)를 자동 계산
   models/monthly_sales.sql         ③ 순서대로 CREATE TABLE AS / MERGE 실행
        │                           ④ 테스트 실행, 문서 생성, 리니지 그림
        └─ 각 파일은 SELECT 문 하나
```

여기서 중요한 건 **"각 모델은 SELECT 문 하나이고, DDL은 내가 안 쓴다"** 는 것이다. 테이블을 만들지 뷰를 만들지, 전체를 다시 만들지 증분으로 붙일지는 **설정으로 지정**하고, 실제 DDL은 dbt가 생성한다.

그럼 "엔진"은 뭘 하나?

```
   dbt 실행 엔진이 하는 일
   ─────────────────────────────────────
   프로젝트 파일 파싱 (수백~수천 개 SQL/YAML)
   템플릿 렌더링
   DAG 계산
   각 데이터 플랫폼에 맞는 SQL 생성  ← 여기가 "어댑터"
   실행 및 결과 수집
```

기존 엔진은 **Python**으로 구현돼 있다. 새 엔진은 이걸 **Rust**로 다시 쓴 것이고, 목표는 두 가지다.

| 목표 | 무슨 뜻 |
|---|---|
| **속도** | 수천 개 모델짜리 프로젝트의 파싱 시간을 수십 초 → 1초 미만으로 |
| **SQL 이해** | 기존 엔진은 SQL을 "문자열"로만 다뤘다. 새 엔진은 **SQL을 실제로 파싱해서 이해**한다 |

두 번째가 사실 더 큰 변화다. SQL을 이해한다는 건 **실행하기 전에 컬럼 수준의 오류를 잡을 수 있다**는 뜻이다.

```
   [기존]  없는 컬럼을 참조하는 SQL 작성
             ↓
           dbt run 실행 → 웨어하우스에 쿼리 전송 → 에러 반환
             ↓
           몇 분 후에야 알게 됨 (그리고 웨어하우스 비용 발생)

   [새 엔진]  SQL 을 파싱해서 컬럼 레벨로 검증
             ↓
           IDE 에서 빨간 줄. 실행 전에 안다.  ★
```

### 2) 어댑터가 왜 병목인가

여기가 내 질문의 핵심이었다. **엔진이 새로 나왔다고 모든 데이터 플랫폼에서 바로 쓸 수 있는 게 아니다.**

```
        dbt 엔진 (공통)
             │
    ┌────────┼────────┬────────┬────────┐
    ▼        ▼        ▼        ▼        ▼
 어댑터A  어댑터B  어댑터C  어댑터D  어댑터E
    │        │        │        │        │
    ▼        ▼        ▼        ▼        ▼
  플랫폼별로 SQL 방언·타입 체계·기능이 전부 다르다
```

어댑터가 하는 일은 생각보다 많다.

- **SQL 방언 차이 흡수** — 같은 "문자열 자르기"도 플랫폼마다 함수명이 다르다
- **타입 체계 매핑** — 각 플랫폼의 데이터 타입을 엔진의 타입 모델로 변환
- **증분 전략 구현** — merge, insert-overwrite, replace-where 등 플랫폼이 지원하는 방식
- **메타데이터 조회** — 테이블·컬럼 정보를 어떻게 가져올지
- **인증·연결** — 접속 방식

그리고 **새 엔진은 "SQL을 이해한다"는 목표 때문에 어댑터에 요구하는 것이 더 많다.** 기존 엔진은 SQL을 그냥 문자열로 던지면 됐지만, 새 엔진은 그 플랫폼의 타입 체계와 함수 시그니처를 정확히 알아야 컬럼 수준 검증을 할 수 있다. **그래서 어댑터 포팅이 오래 걸리고, 플랫폼마다 시차가 생긴다.**

> ⚠️ **각 플랫폼 어댑터가 지금 미리보기인지 정식인지는 시점에 따라 계속 바뀐다.** 이건 몇 달 단위로 움직이는 정보라서, 이 글에 특정 상태를 적어두면 금방 거짓이 된다. **판단이 필요한 시점에 공식 문서에서 직접 확인하는 게 유일하게 맞는 방법이다.**

### 3) ⚠️ "Databricks에서 알아서 한다"에 기대면 안 되는 부분

이제 이 질문에서 제일 중요한 지점이다.

번들 초기화 템플릿이 dbt 프로젝트 뼈대를 만들어주는 건 맞다. 그런데 **거기서 만들어지는 것 중에 "어떤 dbt 버전을 쓸지"를 결정하는 파일이 있고, 그 파일은 우리 리포에 있다.**

일반적으로 이런 모양이다.

```
   [프로젝트 안]

   requirements 파일 또는 잡 정의의 라이브러리 선언
   ┌──────────────────────────────────────┐
   │  dbt-databricks>=1.0.0,<2.0.0        │  ← ★ 이 한 줄이 버전을 정한다
   └──────────────────────────────────────┘
              │
              └─ 잡이 실행될 때 이 사양대로 패키지를 설치한다
```

**"버전 2 미만"이라는 상한선이 명시적으로 박혀 있다.** 즉 새 메이저 버전이 나와도 자동으로 올라가지 않는다. 이건 사고가 아니라 **의도된 설계**다.

```
   [상한선이 없다면]

   어제:  잡 실행 → dbt 1.9.x 설치 → 정상 동작
   오늘:  잡 실행 → dbt 2.0.0 출시됨 → 자동 설치 → 💥

          우리는 코드를 한 줄도 안 바꿨는데 배치가 깨졌다
```

**이게 재현 가능한 빌드(reproducible build)라는 개념이다.** 같은 코드는 언제 실행해도 같은 결과를 내야 하는데, 의존성 버전이 실행 시점마다 달라지면 그게 성립하지 않는다.

그래서 정확히 말하면 이렇다.

> **"Databricks가 알아서 한다"가 맞는 부분:** 템플릿의 기본값, 어댑터의 성숙도, 플랫폼 통합 방식.
>
> **우리가 해야 하는 부분:** 실제로 설치되는 버전은 **우리 리포의 파일에 적혀 있고, 그걸 올리는 건 우리가 PR을 올려서 하는 일**이다. 자동으로 올라가지 않는다 — 그리고 자동으로 올라가면 안 된다.

이걸 모르면 반년 뒤에 이런 일이 생긴다. "새 엔진이 정식 출시됐다는데 우리는 왜 안 바뀌었죠?" **아무도 안 바꿨기 때문이다.**

### 4) 그래서 언제, 어떻게 올리나

메이저 버전 업그레이드는 "새 버전이 나왔으니 올린다"가 아니라 판단이 필요한 일이다. 기준은 세 가지다.

| 기준 | 확인할 것 |
|---|---|
| **어댑터 성숙도** | 우리가 쓰는 플랫폼의 어댑터가 정식 지원인가. 미리보기라면 **운영 배치에 쓰면 안 된다** |
| **기능 동등성** | 지금 쓰는 기능(증분 전략, 매크로, 패키지)이 새 버전에서 다 되는가 |
| **얻는 것의 크기** | 모델이 수십 개면 파싱 속도 개선의 체감이 없다. **수백~수천 개일 때 의미가 커진다** |

그리고 올릴 때의 절차는 정해져 있다.

```
   ① 개발 환경에서만 버전을 올려본다  (운영 설정은 그대로)
   ② 같은 입력으로 양쪽을 돌린다
   ③ 결과 테이블을 비교한다 — 행 수, 체크섬, 샘플 값
        ↑ ★ 여기가 핵심. "돌아간다"와 "같은 결과가 나온다"는 다르다
   ④ 차이가 없으면 운영에 반영
```

**③번을 빼먹는 게 가장 흔한 실수다.** 업그레이드 후에 잡이 초록불로 끝나면 성공했다고 생각하는데, SQL 생성 방식이 미묘하게 달라져서 **결과가 조금 다른데 에러는 안 나는** 경우가 있다. 데이터 파이프라인에서 "에러 없음"은 "정확함"을 뜻하지 않는다.

> **핵심 통찰 1 — "플랫폼이 대신해주는 것과 리포에 남는 것을 구분해야 한다"**
>
> 관리형 플랫폼을 쓰면 "알아서 되는" 영역이 넓어진다. 클러스터 프로비저닝, 드라이버 관리, 런타임 패치 — 실제로 신경 안 써도 된다. 그래서 자연스럽게 **"이것도 알아서 되겠지"** 라는 기대가 번진다.
>
> 그런데 경계는 생각보다 선명하다. **플랫폼이 관리하는 건 "실행 환경"이고, 우리가 관리하는 건 "그 환경 위에서 무엇을 설치하고 실행할지"** 다. 라이브러리 버전 사양은 후자다. 우리 리포의 파일에 적혀 있고, 우리가 커밋했고, 우리가 안 바꾸면 영원히 안 바뀐다.
>
> 그래서 관리형 플랫폼을 쓸 때 물어야 할 질문은 **"이건 자동인가?"** 가 아니라 **"이 값이 어디에 적혀 있나?"** 다. 리포 안에 있으면 자동이 아니다. 예외 없다.

> **핵심 통찰 2 — "미리보기(Preview)는 '거의 다 됐다'가 아니라 '깨져도 항의할 수 없다'는 뜻이다"**
>
> "미리보기 단계"라는 말을 들으면 초보자는 완성도로 이해한다. 90% 정도 됐다는 느낌으로. 실제 의미는 완성도가 아니라 **약속**이다.
>
> 정식 지원(GA)이란 **하위 호환을 지키겠다, 문제가 생기면 지원하겠다, 사전 공지 없이 없애지 않겠다**는 약속이다. 미리보기에는 그 약속이 없다. 그래서 잘 돌아가더라도 다음 릴리스에서 동작이 바뀔 수 있고, 그때 우리는 대응할 뿐 항의할 수 없다.
>
> 그러니 판단 기준은 **"지금 잘 되나"** 가 아니라 **"깨졌을 때 감당 가능한가"** 다. 개발자 개인의 실험이라면 미리보기를 써도 좋다. **새벽에 도는 운영 배치라면, 잘 되더라도 쓰지 않는 게 맞다.**

### 내가 확인할 것

- [ ] 리포에서 dbt 관련 버전 사양이 적힌 파일이 정확히 어디인지, 상한선이 어떻게 걸려 있는지
- [ ] 그 버전이 잡 실행 시 매번 설치되는지, 아니면 이미지에 포함돼 있는지 (설치 시간과 안정성에 영향)
- [ ] 우리 프로젝트의 모델 개수. **수십 개라면 새 엔진의 속도 이득이 거의 없다** — 서두를 이유가 없다는 뜻
- [ ] dbt 실행 결과를 검증하는 테스트가 있는지. **없다면 버전을 올릴 때 "같은 결과인지" 확인할 방법이 없다**
- [ ] 우리가 쓰는 dbt 패키지·매크로 중에 새 엔진에서 아직 안 되는 게 있는지

## Q5. Lakehouse Federation도 결국 내부는 JDBC 아닌가요?

원천 데이터베이스에 연결하는 방법으로 **JDBC 직접 연결**과 **Lakehouse Federation** 두 가지가 있다고 들었다. 그런데 Federation도 결국 관계형 DB에 붙는 거니까 **내부적으로는 JDBC 드라이버를 쓸 텐데**, 그럼 둘이 뭐가 다른 건지 궁금했다.

### 들은 답

> JDBC 구성이 복잡하기 때문에, **Lakehouse Federation은 관리형·최적화된 JDBC라고 생각하면 된다.** 그러나 프로젝트 중에 불가피하게 JDBC를 써야 하는 경우가 있을 수도 있다.

**내 추측 자체는 맞았다.** Federation은 실제로 내부적으로 JDBC 드라이버를 사용한다. 그런데 **"내부 구현이 같다"와 "같은 것이다"는 다르다.** 그 차이가 어디서 나오는지가 이 질문의 답이다.

### 1) 먼저 — JDBC 직접 연결이 실제로 어떻게 생겼나

"구성이 복잡하다"가 얼마나 복잡한지 보는 게 빠르다.

```python
df = (spark.read
      .format("jdbc")
      .option("url", "jdbc:...://호스트:포트/DB명")
      .option("driver", "드라이버 클래스명")
      .option("user", 사용자)
      .option("password", 비밀번호)
      .option("dbtable", "(SELECT ... FROM ... WHERE ...) AS t")
      # ↓ 여기부터가 진짜 난이도
      .option("partitionColumn", "id")     # 무엇을 기준으로 쪼갤지
      .option("lowerBound", "1")           # 그 컬럼의 최솟값
      .option("upperBound", "10000000")    # 최댓값
      .option("numPartitions", "8")        # 몇 개로 쪼갤지
      .option("fetchsize", "10000")        # 한 번에 몇 행씩 가져올지
      .load())
```

아래 다섯 줄이 왜 어려운지 설명이 필요하다.

**병렬 읽기의 원리.** 위 옵션들이 없으면 Spark는 **단일 연결로 전부 읽는다.** 클러스터에 워커가 10대 있어도 한 대만 일한다.

```
   [옵션 없음]
   Spark 워커 1대 ──── 하나의 JDBC 연결 ────▶ DB
   나머지 9대는 논다. 1억 행이면 몇 시간

   [파티션 옵션 있음]  numPartitions=4, partitionColumn=id, 1~10000000
   워커1 ── WHERE id <  2500000 ──┐
   워커2 ── WHERE id >= 2500000 ──┤
           AND id <  5000000      ├──▶ DB   ← 동시에 4개 쿼리
   워커3 ── WHERE id >= 5000000 ──┤
           AND id <  7500000      │
   워커4 ── WHERE id >= 7500000 ──┘
```

**Spark가 알아서 쪼개는 게 아니라, 내가 알려준 범위를 산술적으로 나눠 WHERE 절을 붙이는 것뿐이다.** 그래서 여기 지뢰가 여럿이다.

| 실수 | 결과 |
|---|---|
| `partitionColumn`에 인덱스가 없음 | 4개 쿼리가 전부 풀스캔 → **원래보다 느려짐** |
| 값이 균등하지 않음 (앞쪽에 몰려 있음) | 파티션 1개만 오래 걸림 (데이터 스큐) |
| `numPartitions`를 크게 잡음 | **원천 DB에 동시 연결이 폭증 → 원천이 죽는다** 💥 |
| `lowerBound`/`upperBound`를 잘못 잡음 | 범위 밖 데이터가 양 끝 파티션에 몰림 |
| 문자열/날짜 컬럼을 파티션 컬럼으로 | 균등 분할이 안 됨 |

**그리고 이 모든 걸 테이블마다 따로 정해야 한다.** 30개 테이블이면 30번 판단해야 한다. PM님이 "구성이 복잡하다"고 하신 건 이 이야기다.

여기에 더해 **접속 정보를 코드가 직접 들고 있다는 문제**도 있다.

```
   노트북 A ──┐
   노트북 B ──┼── 각자 시크릿을 읽어 접속 문자열을 조립한다
   노트북 C ──┘        ↓
                 · 원천 접속 권한이 "시크릿 접근 권한"과 같아진다
                 · 누가 어느 테이블을 읽었는지 중앙에서 알 수 없다
                 · 접속 정보가 바뀌면 모든 노트북이 영향
```

### 2) Federation이 실제로 무엇을 바꾸나

Federation은 접속을 **카탈로그 객체로 만든다.**

```
   [한 번만] 관리자가 커넥션과 외부 카탈로그를 등록

      커넥션 객체 "원천DB"  ←── 접속 정보·자격증명이 여기 한 곳에
             │
             ▼
      외부 카탈로그 "source_db"
             │
             └─▶ 카탈로그 안에 원천의 스키마·테이블이 그대로 보인다


   [그 후] 사용자는 그냥 SQL 을 쓴다

      SELECT * FROM source_db.public.orders WHERE 주문일자 = '2026-08-09'
                  └─── 평범한 3단계 이름. JDBC 라는 단어가 안 나온다 ───┘
```

**연결이라는 개념이 코드에서 사라지고 카탈로그 이름으로 바뀌었다.** 이게 표면적 변화고, 그 아래에서 실제로 달라지는 건 네 가지다.

| | **JDBC 직접** | **Federation** |
|---|---|---|
| 접속 정보 | **코드마다** 시크릿 읽어 조립 | **커넥션 객체 한 곳** |
| 권한 관리 | 시크릿 접근 권한 = 사실상 DB 전체 권한 | **카탈로그 권한 체계로 테이블·컬럼 단위 제어** |
| 사용 이력 | 추적 어려움 | **누가 무엇을 조회했는지 감사 로그에 남음** |
| 리니지 | 끊김 | **원천 테이블까지 이어짐** |
| 병렬·튜닝 | **내가 전부 지정** | 플랫폼이 처리 |
| 푸시다운 | 내가 직접 쿼리에 넣어야 | **필터·프로젝션·집계 등을 자동으로 원천에 밀어냄** |

**"관리형 JDBC"라는 PM님의 표현이 정확한 요약이다.** 다만 관리형이 뜻하는 게 "설정을 대신 해준다"만이 아니라 **"거버넌스 체계 안으로 들어온다"** 는 것까지 포함한다는 게 중요하다. 아래 세 줄(권한·감사·리니지)은 편의성이 아니라 **통제**의 문제고, 이게 사실 더 큰 이득이다.

### 3) 푸시다운 — 성능의 핵심이자 함정

Federation의 성능은 **푸시다운(pushdown)** 에 달려 있다. "이 작업을 어느 쪽에서 할 것인가"의 문제다.

```
   SELECT 지역, SUM(금액)
   FROM source_db.public.orders
   WHERE 주문일자 = '2026-08-09'
   GROUP BY 지역


   [푸시다운이 될 때]
   원천에 이런 쿼리를 보낸다:
     SELECT 지역, SUM(금액) FROM orders
     WHERE 주문일자='2026-08-09' GROUP BY 지역
        ↓
   돌아오는 것: 지역 수만큼의 행 (수십 행)   ✅


   [푸시다운이 안 될 때]
   원천에 이런 쿼리를 보낸다:
     SELECT * FROM orders
        ↓
   돌아오는 것: 전체 테이블 (수억 행)
        ↓
   네트워크로 다 끌어와서 우리 쪽에서 필터·집계  💥
   느리고, 비싸고, 원천에도 부하
```

**같은 SQL 한 줄인데 뒤에서 벌어지는 일이 100배 차이 난다.** 그리고 겉으로는 구분이 안 간다 — 그냥 "좀 느리네" 정도로 보인다.

푸시다운이 안 되는 대표적 경우들:

- 원천이 지원하지 않는 함수를 쓸 때
- 복잡한 표현식이나 사용자 정의 함수
- 특정 종류의 조인이나 윈도우 함수
- 소스 종류에 따라 지원 범위가 다름

**그래서 Federation을 쓸 때는 "실행 계획을 확인하는 습관"이 필요하다.** 무엇이 원천으로 내려갔는지 실행 계획에 나오고, 그걸 안 보면 조용히 전체 스캔을 하고 있어도 모른다.

### 4) 그럼에도 JDBC가 필요한 경우 — "불가피하게"의 실제 내용

PM님이 여지를 두신 부분이다. 구체적으로 어떤 경우인지 정리해둔다.

| 상황 | 왜 Federation으로 안 되나 |
|---|---|
| **지원 목록에 없는 소스** | Federation은 지원하는 데이터베이스 종류가 정해져 있다 |
| **쓰기가 필요할 때** | Federation은 기본적으로 **읽기 전용**이다 |
| **극단적 대용량 초기 적재** | 병렬도·페치 크기를 직접 조절해야 할 때가 있다 |
| **특수한 인증·네트워크 구성** | 커넥션 객체가 지원하지 않는 인증 방식 |
| **드라이버 고유 옵션이 필요할 때** | 특정 드라이버의 세밀한 옵션 |
| **권한이 없을 때** | 커넥션·외부 카탈로그 생성은 관리자 권한이 필요하다 |

마지막 항목이 현실에서 꽤 크다. **Federation은 "우리가 쓰기로 결정"해서 되는 게 아니라 "관리자가 등록해줘야" 되는 것**이다. 등록 요청이 며칠 걸리는 조직에서는 개발자가 그냥 JDBC로 짜버리게 된다.

### 5) ★ 그런데 진짜 질문은 "복사할 것인가"다

여기서 한 걸음 물러설 필요가 있다. JDBC냐 Federation이냐는 **"어떻게 연결하나"** 의 문제인데, 배치 파이프라인을 설계할 때 그보다 먼저 정해야 할 게 있다.

```
   [복사한다 (배치 적재)]
   원천 ──매일 1회──▶ 우리 테이블 ──▶ 이후 모든 조회는 우리 것을 본다

   ✅ 원천에 부하가 하루 1회만
   ✅ 원천이 죽어도 우리는 산다
   ✅ "어제 받은 그 데이터"가 남아 재현이 된다
   ❌ 신선도 지연이 있다


   [복사 안 한다 (연합 조회)]
   원천 ◀──조회할 때마다──── 우리 쿼리

   ✅ 항상 최신
   ✅ 저장 비용 없음
   ❌ 조회할 때마다 원천에 부하
   ❌ 원천이 죽으면 우리도 죽는다
   ❌ 같은 쿼리를 두 번 돌리면 결과가 다를 수 있다 (재현 불가)
```

**정기 배치의 입력으로는 대체로 "복사"가 맞다.** 이유는 위의 ❌ 세 줄이다. 특히 **재현 불가능**이 크다. 어제 배치 결과를 오늘 다시 만들어야 할 때, 원천 데이터가 이미 바뀌어 있으면 같은 결과가 안 나온다.

그리고 여기서 흔한 오해를 하나 정리해두는 게 좋다.

> **"복사본은 중복이니까 나쁜 것"** — 애플리케이션 개발에서는 대체로 맞는 직관이지만, **데이터 파이프라인에서는 자주 틀린다.** 복사본은 중복이 아니라 **시간의 스냅샷**이다. 원천은 "지금"만 보여주지만, 우리 복사본은 "그때"를 보존한다. 그게 배치 재현성의 기반이다.

그래서 실무 배치는 대개 이렇게 간다. **Federation으로 편하게 읽되, 읽은 것을 우리 테이블로 복사해 저장한다.** Federation은 "복사를 안 하는 방법"이 아니라 **"복사를 쉽게 하는 방법"** 으로 쓰는 게 대부분이다.

> **핵심 통찰 1 — "관리형 서비스의 가치는 편의가 아니라, 판단해야 할 것의 개수를 줄이는 데 있다"**
>
> "Federation이 JDBC보다 편하다"는 설명은 절반만 맞다. 진짜 차이는 **내가 내려야 하는 결정의 개수**다.
>
> JDBC 직접 연결은 테이블 하나당 최소 대여섯 개의 결정을 요구한다 — 파티션 컬럼, 경계값, 병렬도, 페치 크기, 푸시다운할 필터. 그리고 **각 결정이 틀려도 에러가 안 난다.** 그냥 느리거나, 원천에 부하를 주거나, 데이터가 한쪽에 몰릴 뿐이다. 30개 테이블이면 180번의 조용히 틀릴 수 있는 결정이 생긴다.
>
> 관리형 서비스는 그중 대부분을 기본값으로 흡수한다. 기본값이 최적은 아닐 수 있지만, **"틀리게 설정된 값"보다는 거의 항상 낫다.** 그래서 관리형을 고를 때의 질문은 "성능이 더 좋은가"가 아니라 **"내가 이 결정들을 근거를 갖고 내릴 수 있는가"** 다. 답이 "아니오"라면, 관리형의 평범한 기본값이 내 추측보다 낫다.

> **핵심 통찰 2 — "추상화는 아래층을 숨기지만, 아래층의 비용까지 없애지는 않는다"**
>
> Federation이 좋은 이유는 SQL 한 줄로 원천을 조회할 수 있다는 것이다. 그런데 바로 그게 위험한 이유이기도 하다. **`SELECT * FROM 원천테이블` 이라고 쓰는 순간 내부에서는 남의 운영 DB에 쿼리가 나간다.** 그런데 문법상으로는 우리 테이블을 읽는 것과 구별되지 않는다.
>
> 그래서 대시보드에 연결하거나, 반복 조회하는 코드에 넣거나, 조인의 한쪽에 놓으면 — **원천 시스템 담당자가 어느 날 "누가 우리 DB를 하루 3만 번 조회하고 있냐"고 찾아온다.**
>
> 일반화하면 이렇다. **추상화의 위험은 "쉬워지는 것" 자체가 아니라, 쉬워진 것과 비싼 것이 겉보기에 똑같아지는 것**이다. 그래서 좋은 추상화를 쓸 때일수록 **그 아래에서 실제로 무슨 일이 일어나는지 한 번은 확인해봐야 한다.** 실행 계획을 읽는 습관이 그 확인이다.

### 내가 확인할 것

- [ ] 우리가 원천을 읽는 방식이 실제로 무엇인지 (JDBC 직접 / Federation / 언로드 파일 경유)
- [ ] JDBC라면 파티션 옵션이 어떻게 잡혀 있고, 그 값들의 근거가 무엇인지. **원천 DB에 동시 연결이 몇 개까지 허용되는지**
- [ ] Federation이라면 우리 쿼리에서 무엇이 원천으로 푸시다운되는지 실행 계획으로 확인해보기
- [ ] Federation으로 읽은 것을 우리 테이블에 복사하는지, 아니면 조회 시마다 원천에 가는지
- [ ] 커넥션·외부 카탈로그를 만들 권한이 우리 팀에 있는지, 아니면 요청해야 하는지 (리드타임 포함)

## Q6. 왜 시간을 UTC로 변환하나요?

배치 코드에 **타임스탬프를 UTC로 변환하는 단계**가 명시적으로 들어 있었다. 원천에서 읽어온 시각 컬럼을 변환한 뒤에 저장한다. 왜 이 단계가 필요한지 물었다.

### 들은 답

- 원천에 **타임존이 없는 타임스탬프(NoTimeZone Timestamp)** 가 있는데, 그걸 원천 ETL 단계에서 바꿨어야 했다. 그런데 **고객사에서 그렇게 하지 않았다.** 그래서 우리 쪽으로 가져오는 배치에서 변환한다.
- **표준은 원천 DB에서부터 UTC로 저장하고, 마지막에 보여줄 때만 KST로 바꾸는 것**이 정석이다.

두 번째 문장이 이 질문의 정답이고, 첫 번째 문장이 **왜 정답대로 못 하고 있는지**에 대한 설명이다. 순서대로 푼다.

### 1) 기초 — 타임스탬프에 두 종류가 있다는 것

이게 시작점이다. 많은 사람이 "시각은 시각이지"라고 생각하지만, 데이터베이스에는 **의미가 근본적으로 다른 두 종류**가 있다.

```
   [1] 벽시계 값 (타임존 없음)

       "2026-08-10 09:00:00"

       이건 그냥 숫자 6개다. 지구상의 특정 순간을 가리키지 않는다.
       서울의 09시인지 뉴욕의 09시인지 알 수 없다.
       (SQL 표준의 TIMESTAMP WITHOUT TIME ZONE)


   [2] 시점 (타임존 있음 / UTC 기준)

       "2026-08-10 00:00:00 UTC"

       이건 지구상의 특정 순간이다.
       서울에서는 09시, 뉴욕에서는 전날 20시로 보이지만 같은 순간이다.
       (SQL 표준의 TIMESTAMP WITH TIME ZONE)
```

**둘의 차이는 "정보가 하나 더 있느냐"** 다. 벽시계 값에는 **어느 지역의 시계인지**가 빠져 있다. 그리고 그 정보 없이는 두 값을 비교할 수 없다.

```
   서울 서버 로그:   2026-08-10 09:00:00   (타임존 없음)
   뉴욕 서버 로그:   2026-08-09 20:00:00   (타임존 없음)

   Q. 어느 쪽이 먼저 일어난 일인가?
   A. 알 수 없다. (사실은 정확히 같은 순간이다)
```

**이게 타임존 없는 타임스탬프의 본질적 결함이다.** 값 하나만 봐서는 무엇을 가리키는지 알 수 없고, "어디서 만들어졌는지"라는 **데이터 밖의 지식**이 있어야만 해석된다.

### 2) 플랫폼별로 어떻게 다루나

각 시스템이 이 두 종류를 어떻게 취급하는지 알아야 변환이 이해된다.

| | 타임존 있는 타입 | 타임존 없는 타입 |
|---|---|---|
| **일반 관계형 DB** | `TIMESTAMPTZ` 등 | `TIMESTAMP` (기본값인 경우가 많다 ⚠️) |
| **Spark / Databricks** | `TIMESTAMP` — 내부적으로 UTC 기준 시점으로 저장하고, **표시할 때 세션 타임존을 적용** | `TIMESTAMP_NTZ` — 타임존 개념 없음 |

여기에 함정이 하나 있다. **이름이 반대로 겹친다.**

```
   원천 DB 의 TIMESTAMP        =  타임존 없음  (벽시계 값)
   Databricks 의 TIMESTAMP     =  타임존 있음  (UTC 기준 시점)
                    ↑
        같은 이름인데 의미가 다르다  💥
```

그래서 **원천의 `TIMESTAMP` 컬럼을 아무 생각 없이 Databricks의 `TIMESTAMP`로 받으면, "타임존이 없던 값"이 "UTC 값"으로 해석되어 버린다.** 실제로는 KST 벽시계 값이었는데 UTC로 취급되므로 **9시간이 틀어진다.**

이게 PM님이 말씀하신 상황이다.

```
   원천에 저장된 값:   2026-08-10 09:00:00   (실제로는 KST 벽시계, 타입은 타임존 없음)
                          ↓ 그대로 받으면
   우리 쪽 해석:       2026-08-10 09:00:00 UTC
                          ↓ KST 로 표시하면
   화면에 보이는 값:   2026-08-10 18:00:00   ← 9시간 뒤로 밀렸다 💥
```

**그래서 "UTC로 변환"이라고 부르는 그 단계가 실제로 하는 일은 이것이다.**

> **"이 값은 KST 벽시계 값이다"라는, 데이터 밖에만 있던 지식을 데이터 안으로 집어넣는 것.**

변환이 아니라 **의미 부여**에 가깝다. 그리고 이 지식은 원천 시스템 담당자의 머릿속에만 있던 것이라, 언젠가는 잃어버린다. 그 전에 데이터에 새겨두는 것이다.

### 3) ⚠️ 여기서 가장 자주 나는 버그 — 변환 방향

이 변환에서 초보자가 100% 한 번은 틀리는 지점이 있다. **함수 이름이 직관과 반대로 읽히기 때문이다.**

```
   to_utc_timestamp(값, "Asia/Seoul")
   ─────────────────────────────────
   의미: "이 값을 서울 시각으로 해석해서, UTC 로 바꿔라"
   09:00 → 00:00   (9시간 뺀다)

   ✅ 우리가 필요한 것: 원천의 KST 벽시계 값을 진짜 시점으로 만들기


   from_utc_timestamp(값, "Asia/Seoul")
   ─────────────────────────────────
   의미: "이 값을 UTC 로 해석해서, 서울 시각으로 바꿔라"
   09:00 → 18:00   (9시간 더한다)

   ✅ 필요한 곳: 마지막에 사람에게 보여줄 때
```

**두 번째 인자가 "결과의 타임존"이 아니라, 함수마다 다른 역할을 한다는 게 혼동의 원인이다.** 외우는 방법은 이렇다.

```
   to_utc_timestamp    →  결과가 UTC 다      (입력이 지역시)
   from_utc_timestamp  →  입력이 UTC 다      (결과가 지역시)
              ↑
   "to/from" 이 가리키는 게 UTC 쪽이다
```

그리고 **틀렸을 때 에러가 안 난다.** 9시간 틀린 값이 조용히 저장될 뿐이다. 그래서 반드시 검증해야 한다.

```
   검증 방법
   ────────────────────────────────────────────
   원천에서 최근 행 하나를 눈으로 확인한다
   그 값이 실제로 언제 일어난 일인지 업무 담당자에게 확인한다
   변환 후 우리 테이블에서 같은 행을 KST 로 표시해본다
   → 원천 화면의 값과 같아야 한다  ★
```

**"9시간 차이"는 눈에 잘 띄지만, 하루 이내라서 날짜 경계에서만 표가 난다.** 0~9시 사이에 생긴 데이터가 전날로 밀리거나 다음날로 넘어가는 식이다. 그래서 **일별 집계에서만 이상하게 나오고 평소엔 멀쩡해 보인다.** 발견이 늦어지는 전형적인 버그다.

### 4) 왜 UTC가 표준인가 — 한국만 쓰는데도?

"우리는 한국에서만 서비스하고, 한국은 서머타임도 없는데 왜 UTC를 써야 하나?" 는 합리적인 질문이다. 이유가 네 가지 있다.

**① 서머타임(DST)이 있는 지역과 섞이는 순간 지역시는 깨진다**

한국은 DST가 없지만, 데이터가 한국에서만 오지 않는다. 클라우드 리전, 외부 API, 파트너사 데이터 — 어느 하나라도 DST 지역이면 문제가 시작된다.

```
   DST 가 있는 지역의 지역시로 저장하면

   [봄, 시계를 앞으로]  02:00 → 03:00 으로 점프
        → 02:30 이라는 시각이 그 날 존재하지 않는다 (없는 시각)

   [가을, 시계를 뒤로]  02:00 → 01:00 으로 되돌림
        → 01:30 이 그 날 두 번 있다 (모호한 시각)
        → "01:30 에 일어난 두 사건" 중 어느 게 먼저인가? 알 수 없다  💥

   UTC 에는 이런 일이 없다. 절대 되돌아가지 않고 절대 건너뛰지 않는다
```

**② 시각 연산이 안전해진다**

지역시로 저장하면 "두 시각의 차이"가 틀릴 수 있다. UTC는 단조 증가하므로 뺄셈이 항상 맞다.

**③ 시스템 간 대조가 가능해진다**

장애 분석할 때 애플리케이션 로그, DB 로그, 클라우드 로그를 나란히 놓고 봐야 하는데 — **클라우드 인프라 로그는 거의 항상 UTC다.** 우리만 KST면 매번 머릿속으로 9를 더하고 빼야 하고, 그러다 틀린다.

**④ 확장 시 이미 늦는다**

나중에 다른 나라 데이터가 들어오면 그때 바꿀 수 있을까? **못 바꾼다.** 이미 쌓인 수억 행이 어느 타임존 기준인지 확실히 알 수 없기 때문이다. 심지어 **시기마다 다를 수도 있다.**

그래서 원칙은 짧다.

```
   ┌────────────────────────────────────────────┐
   │  저장은 UTC. 표시할 때만 지역시.           │
   │  변환은 가장 바깥층(화면)에서 딱 한 번.    │
   └────────────────────────────────────────────┘
```

이 원칙의 이름이 있다면 **"경계에서 변환하기"** 다. 소프트웨어 설계 전반에 나오는 패턴 — 시스템 안쪽은 하나의 표준 표현만 쓰고, 바깥과 만나는 지점에서만 변환한다. 인코딩(내부는 UTF-8), 단위(내부는 SI), 통화(내부는 최소 단위 정수) 전부 같은 구조다.

### 5) ⚠️ "표준은 원천 DB부터 UTC"에 대한 정직한 보충

PM님 말씀이 원칙적으로 맞다. 다만 실무에서 조금 더 정확히 말하면 이렇다.

**원천이 반드시 "UTC로 변환해서" 저장해야 하는 건 아니다. 타임존 정보를 가진 타입으로 저장하면 된다.** 타임존이 있는 타입을 쓰면 DB가 내부적으로 UTC로 관리하고, 조회하는 세션의 타임존에 맞춰 보여준다. 값이 무엇을 가리키는지가 데이터 자체에 들어 있으므로 모호함이 없다.

진짜 문제는 **타임존 없는 타입을 쓰면서 "이건 KST야"라는 규칙을 사람의 머릿속에만 두는 것**이다. 그 규칙은:

- 문서에 없고
- 코드 주석에 없고
- 아는 사람이 퇴사하면 사라지고
- 심지어 **시기에 따라 달랐을 수도 있다** (시스템 이관 전후로 기준이 바뀌었는데 아무도 기록 안 함)

**우리 배치의 변환 단계는 이 사라질 지식을 데이터에 새기는 작업이고, 그래서 가치가 있다.** 상류가 안 해줘서 어쩔 수 없이 하는 뒤처리이기도 하지만, **하고 나면 우리 쪽 데이터는 모호함이 없어진다.**

다만 대가도 정확히 알아야 한다.

| 남는 위험 | 내용 |
|---|---|
| **가정이 코드에 박힌다** | "원천 값은 KST"라는 가정이 우리 변환 코드에만 있다. 원천이 어느 날 UTC로 바꾸면 **우리가 9시간 더 틀어진다** |
| **과거 데이터의 기준이 다를 수 있다** | 특정 시점 이전 데이터는 다른 기준이었을 가능성 |
| **원천의 다른 컬럼은?** | 한 테이블 안에서도 컬럼마다 기준이 다를 수 있다 |
| **경계 데이터 검증이 필요** | 자정 근처 데이터로 반드시 확인해야 한다 |

그리고 **가장 좋은 해결은 여전히 상류를 고치는 것**이다. 우리가 뒤에서 보정하는 한, 원천을 쓰는 다른 소비자들은 계속 틀린 해석을 하고 있을 것이기 때문이다. **우리만 맞는 것과 모두가 맞는 것은 다르다.**

> **핵심 통찰 1 — "타임존이 없는 타임스탬프는 값이 아니라 반쪽짜리 값이다"**
>
> `2026-08-10 09:00:00` 을 보면 시각처럼 보인다. 그런데 이건 **시각이 아니라 시각을 계산하기 위한 재료**다. "어느 지역의 시계인가"라는 정보가 있어야만 비로소 지구상의 한 순간을 가리킨다.
>
> 그리고 그 나머지 절반은 어디 있나? **데이터 안에 없다.** 시스템을 만든 사람의 기억 속에, 부서의 관행 속에, "우리 회사는 원래 한국 시간으로 저장해요"라는 구전 속에 있다. **데이터베이스 밖에 있는 정보에 의존하는 데이터는, 그 정보가 사라지는 순간 해석 불가능해진다.**
>
> 그래서 타입 선택은 저장 공간이나 성능의 문제가 아니라 **"이 데이터가 자기 자신을 설명할 수 있는가"** 의 문제다. 자기 설명적인 데이터는 10년 뒤에도 읽히고, 그렇지 않은 데이터는 10년 뒤에 고고학이 된다.

> **핵심 통찰 2 — "상류의 부채는 사라지지 않고, 하류로 내려오면서 여러 벌로 복제된다"**
>
> 원천이 타임존 정보를 안 남긴 건 한 번의 결정이다. 그런데 그 결과는 한 곳에서 끝나지 않는다.
>
> ```
>    원천의 결정 1개
>         ├─▶ 우리 배치에 보정 코드
>         ├─▶ B 팀의 리포트에 보정 코드
>         ├─▶ C 서비스에 보정 코드
>         └─▶ 어딘가에는 보정을 안 한 곳  ← 그리고 아무도 모른다
> ```
>
> **같은 지식이 여러 곳에 복사되면, 언젠가 반드시 갈라진다.** 원천이 기준을 바꾸는 날, 네 곳 중 몇 곳이 제때 고쳐질까? 그리고 안 고쳐진 곳은 에러 없이 9시간 틀린 숫자를 계속 내놓는다.
>
> 그래서 하류에서 하는 보정은 **응급처치이지 치료가 아니다.** 해야 하지만, 하면서 **"이건 상류에서 고쳐야 할 일"이라는 사실을 코드 주석과 이슈 트래커에 남겨야 한다.** 남기지 않으면 몇 달 뒤에는 그 보정 코드가 "원래 그런 것"이 되고, 아무도 왜 9시간을 빼는지 모르게 된다. **부채는 갚지 않으면 사라지는 게 아니라 정체를 잃는다.**

### 내가 확인할 것

- [ ] 원천 컬럼의 실제 타입이 타임존 있는 타입인지 없는 타입인지, 컬럼별로 확인
- [ ] 변환 방향이 맞는지 검증 — **자정 직후(00~09시) 데이터로 원천 화면과 우리 값을 대조**
- [ ] 우리 테이블의 저장 타입이 무엇인지. 세션 타임존 설정이 클러스터/웨어하우스마다 다르지 않은지
- [ ] "원천은 KST"라는 가정이 **과거 데이터 전 구간에 대해** 성립하는지 (시스템 이관 이력 확인)
- [ ] 이 보정이 필요한 이유가 코드 주석과 이슈로 남아 있는지. **없다면 지금 남기기**
- [ ] 상류에 타입 개선을 요청하는 경로가 있는지, 요청했다면 진행 상태

## 오늘의 정리

### 여섯 개의 답을 한 줄씩

1. **비어 있던 테이블 생성 노트북** — 정말 빈 노트북이고, 초기 테이블은 **CTAS로 수동 생성**했다. 한 번만 하는 일을 자동화하지 않은 건 합리적이다. 다만 **"자동 실행하지 않는 것"과 "코드로 남기지 않는 것"은 다른 문제**이고, DDL은 리포에 남아 있어야 재현·리뷰·이력이 가능하다. 그리고 이름 붙은 빈 껍데기는 다음 사람에게 거짓 약속을 한다 — 지우거나 한 줄 설명을 남기는 게 맞다.
2. **시크릿의 출처** — 시크릿 스코프. 파라미터와 갈리는 기준은 민감도가 아니라 **"실행 이력·로그에 남아도 되는가"** 다. 스코프 생성·값 입력은 **CLI/API가 표준 경로**이고(UI에서 값을 타이핑하는 흐름은 일반적이지 않다), "admin만"은 플랫폼 제약이라기보다 **자격증명을 한 곳에 모으기 위한 조직의 규율**이다. UC 쪽으로 옮겨가는 흐름의 핵심은 **"안전하게 읽기"에서 "아예 읽지 않기"** 로의 이동이다.
3. **상태 테이블의 시간 창** — 상태 테이블은 **최종 상태만 필요하니 이력을 안 남긴다(SCD Type 1)** 는 게 첫 번째 이야기고, 이건 전적으로 맞다. 두 번째 이야기인 "ETL 시간만 잡히면 된다"에는 **"상류가 그 시간대 밖에서는 절대 안 건드린다"는 무언의 계약**이 깔려 있다. 그 계약은 문서에 없고, 깨져도 에러가 안 나고, **조용히 오래된 상태가 남는다.** 고수위 방식 + 되돌아보기 여유 + 주기적 전체 대조가 구조적으로 안전하다.
4. **dbt 버전** — 템플릿 기본이 기존 버전이고 새 엔진이 성숙하면 옮겨가는 흐름은 맞다. 다만 **"Databricks가 알아서 한다"가 아니다.** 실제로 설치되는 버전은 **우리 리포의 버전 사양 파일**에 상한선과 함께 박혀 있고, 그걸 올리는 건 우리가 PR로 하는 일이다. 그리고 **미리보기는 완성도가 아니라 약속의 부재**를 뜻하므로, 운영 배치에는 잘 되더라도 쓰지 않는다.
5. **JDBC vs Federation** — 내부적으로 JDBC를 쓴다는 추측은 맞다. **"관리형·최적화 JDBC"라는 요약이 정확**하다. 다만 관리형이 주는 건 편의만이 아니라 **거버넌스(권한·감사·리니지)** 이고 이게 더 크다. 핵심 성능 변수는 **푸시다운**이고, 되고 안 되고가 겉으로 구별되지 않으므로 실행 계획을 봐야 한다. 그리고 더 앞선 질문은 **"복사할 것인가"** 인데, 배치 입력은 대개 복사가 맞다 — **복사본은 중복이 아니라 시간의 스냅샷**이다.
6. **UTC 변환** — 원천의 **타임존 없는 타임스탬프**를 시점으로 만드는 작업이다. 이건 변환이라기보다 **"데이터 밖에만 있던 지식(이 값은 KST다)을 데이터 안에 새기는 일"** 이다. 변환 방향을 틀려도 에러가 안 나고 **날짜 경계에서만 표가 나므로** 반드시 검증해야 한다. 원칙은 **저장은 UTC, 표시할 때만 지역시, 변환은 가장 바깥층에서 한 번.** 다만 하류의 보정은 응급처치라, **왜 하는지를 남겨두지 않으면 몇 달 뒤 "원래 그런 것"이 된다.**

### 오늘 여섯 개를 관통한 하나의 주제

정리하고 보니 여섯 개 중 다섯 개가 같은 이야기를 하고 있었다.

> **"어디에도 안 적혀 있는데 시스템이 그것에 의존하고 있는 것"**

- **Q1** — 초기 DDL이 어디에도 없다. 스키마가 왜 이런지 아는 건 사람뿐
- **Q2** — 스코프를 만들고 권한을 준 절차가 코드에 없으면, 새 환경을 세울 수 없다
- **Q3** — "상류는 00~07시에만 갱신한다"는 계약이 우리 코드 안에만 암묵적으로 존재한다
- **Q4** — "버전은 Databricks가 알아서"라는 믿음이 실제 파일과 어긋난다
- **Q6** — "이 컬럼은 KST 기준"이라는 지식이 원천 담당자 머릿속에만 있다

전부 **지금은 잘 돌아간다.** 그리고 전부 **깨질 때 에러를 안 낸다.** 조용히 틀린 값이 나오거나, 새 환경을 세우려는 순간 아무도 방법을 모르게 되거나, 몇 달 뒤에 "왜 9시간을 빼는 거죠?"라는 질문에 답할 사람이 없어진다.

그래서 온보딩 중인 지금 가장 값진 행동은 코드를 잘 짜는 게 아니라 **"안 적혀 있는데 의존하고 있는 것"을 발견할 때마다 적어두는 것**이다. 지금은 물어볼 사람이 옆에 있고, 반년 뒤에는 없을 수도 있다.

### 질문하면서 배운 것 (내용 말고 방법)

- **"비어 있다"를 발견했을 때 바로 물은 게 맞았다.** 빈 노트북을 보고 "아직 안 만들었나 보다" 하고 넘어갔으면, 나중에 그 노트북에 코드를 채워 넣는 사람이 될 뻔했다. **없는 것에 대해 묻는 게 있는 것에 대해 묻는 것보다 답이 빠르게 나온다** — 있는 것은 읽으면 알 수 있지만, 없는 것은 물어야만 알 수 있기 때문이다.
- **"둘이 어떻게 다른가요"보다 "둘이 결국 같은 것 아닌가요"가 답을 깊게 끌어낸다.** Q5에서 "Federation도 내부는 JDBC 아닌가요"라고 물으니, 단순 비교표가 아니라 **"관리형이라는 게 무슨 뜻인가"** 라는 층위의 답이 돌아왔다. **내 가설을 틀리게 만들어 달라고 요청하는 형태**가 좋다.
- **"왜 이 숫자인가요"는 항상 물을 가치가 있다.** Q3의 00~07시가 그랬다. 답 자체는 짧았지만, 그 숫자가 **다른 팀의 배치 스케줄에 대한 가정**이라는 걸 알게 된 게 소득이었다. **코드에 박힌 상수는 대부분 누군가와의 약속이고, 그 약속은 대개 문서화돼 있지 않다.**
- **한 문장짜리 답이 사실 두 개의 답일 때가 있다.** Q3이 그랬다. "최종 상태만 원하니까 이력이 필요 없다"와 "ETL 시간만 잡히면 된다"는 붙어 있었지만 **층위가 다른 이야기**였다 — 앞은 데이터 모델링, 뒤는 증분 추출. 그리고 조건이 붙는 건 뒤쪽뿐이었다. **답을 받아 적고 나서 "이게 몇 개의 주장인가"를 세어보면**, 통째로 받아들였을 때 놓쳤을 조건이 드러난다.
- **답이 "알아서 된다"일 때는 한 번 더 파야 한다.** Q4가 그랬다. 큰 흐름은 맞지만, **"알아서"의 경계가 정확히 어디인지**는 리포의 파일을 직접 열어봐야 알 수 있었다. 관리형 플랫폼을 쓸수록 이 경계가 흐려지고, 흐려진 채로 두면 아무도 관리하지 않는 영역이 생긴다.

### 다음에 물어볼 것

- **초기 DDL이 어딘가에 남아 있나요?** 없다면 지금 현재 스키마를 덤프해서 리포에 넣어도 될까요?
- **상류 ETL이 지연되면 우리가 알 수 있는 경로가 있나요?** 없다면 증분 조건을 고수위 방식으로 바꾸는 게 어떨까요?
- **상태 테이블의 상태 전이 이력이 원천에는 남아 있나요?** 나중에 필요해질 때 복원할 수 있는지가 궁금합니다.
- **원천의 시각 컬럼 중 KST 기준이 아닌 게 섞여 있을 가능성이 있나요?** 시스템 이관 전후로 기준이 바뀐 이력이 있는지.
- **커넥션·외부 카탈로그를 우리 팀이 만들 수 있나요?** 요청해야 한다면 리드타임이 어느 정도인지.

**타임존**

- [TIMESTAMP_NTZ type (Databricks 공식)](https://docs.databricks.com/aws/en/sql/language-manual/data-types/timestamp-ntz-type) — 타임존 없는 타입이 언제 필요하고 언제 위험한지.
- [`to_utc_timestamp` / `from_utc_timestamp` (Databricks 공식)](https://docs.databricks.com/aws/en/sql/language-manual/functions/to_utc_timestamp) — 변환 방향을 헷갈릴 때마다 열어볼 것. 예제 하나만 봐도 방향이 확정된다.
