## Q1. 내부망에는 어떻게 배포되나요? 하나의 GitLab 레포에서 외부망·내부망 CI가 전부 되나요?

고객사 환경이 외부망과 내부망으로 갈려 있다. 개발은 외부망에서 하는데 실제 운영 대상 중 일부는 내부망에 있다. 그러면 코드는 어디에 있고, 배포는 누가 실행하며, 두 망에 같은 것이 올라간다는 걸 무엇이 보장하는지가 궁금했다.

### 들은 답

> - **하나의 레포에서 CI로 된다.** GitLab이 내부와 외부 둘 다 된다.
> - GitLab의 **runner가 컨테이너를 실행**해서, **외부망 workspace와 내부망 workspace 모두에 validate·deploy** 할 수 있다.

맞는 답이다. 그런데 이 두 문장에는 **"어떻게"가 빠져 있다.** 그리고 그 "어떻게"가 폐쇄망 CI에서 실제로 시간을 잡아먹는 부분 전부다. 하나씩 뜯는다.

### 1) 기초 — GitLab CI는 세 조각으로 되어 있다

CI/CD를 "GitLab이 알아서 해주는 것"으로 뭉뚱그리면 폐쇄망 이야기를 할 수 없다. 실제로는 서로 다른 세 개가 있다.

```
   ┌─────────────────────────────────────────────────────────┐
   │  ① GitLab 서버                                         │
   │     - 레포지토리, MR, 파이프라인 정의(.gitlab-ci.yml)   │
   │     - "이 job을 실행해야 한다"는 목록을 들고 있다       │
   │     - 직접 실행하지는 않는다                    ★       │
   └─────────────────────────────────────────────────────────┘
                        ▲
                        │  ② Runner가 GitLab에 "일 있나요?"
                        │     주기적으로 물어본다 (아웃바운드)
                        │     GitLab이 Runner에 접속하지 않는다  ★★
                        │
   ┌─────────────────────────────────────────────────────────┐
   │  ② GitLab Runner                                       │
   │     - 어딘가에 설치된 데몬 프로세스                     │
   │     - job을 받아와서 ③에게 실행을 시킨다               │
   └─────────────────────────────────────────────────────────┘
                        │
                        ▼
   ┌─────────────────────────────────────────────────────────┐
   │  ③ Executor                                            │
   │     - shell / docker / kubernetes ...                   │
   │     - docker executor면 job마다 컨테이너를 새로 띄운다  │
   │     - PM님이 말한 "runner가 컨테이너를 실행해서"가 이것 │
   └─────────────────────────────────────────────────────────┘
```

★★ 표시한 줄이 **폐쇄망에서 GitLab CI가 성립하는 이유**다. Runner는 GitLab 서버에 **자기가 먼저 접속해서** 일감을 가져온다(long polling). GitLab 서버가 Runner에게 접속을 거는 게 아니다.

그래서 **인바운드 포트를 열지 않고도** 내부망 안에 Runner를 둘 수 있다. 내부망 Runner가 밖으로 나가서 GitLab에 물어보고, 받아온 job을 내부망 안에서 실행하고, 결과 로그만 다시 밖으로 올린다. 방화벽 정책이 "내부망에서 밖으로 나가는 것 중 GitLab 주소만 허용"이면 끝난다.

> **핵심 통찰 — "폐쇄망 CI가 가능한 건 Runner가 pull 모델이기 때문이다"**
>
> push 모델(중앙 서버가 대상 서버에 접속해서 배포)이면 내부망에 인바운드 구멍을 뚫어야 한다. 그건 망분리의 존재 이유를 부정하는 일이라 보안 심의를 통과하기 어렵다.
>
> pull 모델은 방향이 반대다. **"안에 있는 것이 밖을 향해 물어본다"** 는 형태는 대부분의 망분리 정책에서 허용 가능한 범위 안에 있다. Runner, 에이전트 기반 배포 도구, GitOps가 전부 이 형태를 취하는 건 우연이 아니다.

### 2) "하나의 레포에서 두 망" 이 성립하는 방식은 두 가지다 — 어느 쪽인지 확인해야 한다

여기가 오늘 답에서 가장 애매하게 남은 부분이다. "runner가 두 workspace 모두에 deploy할 수 있다"는 말은 **구조가 다른 두 가지**를 다 가리킬 수 있다.

```
   [구조 A] 하나의 Runner가 두 망 모두에 도달한다

        GitLab 서버 (외부)
              ▲
              │
        ┌─────┴──────┐
        │   Runner   │  ← 이 머신이 외부망 workspace와
        │  (경계에)  │     내부망 workspace 양쪽에 접속 가능
        └──┬──────┬──┘
           │      │
           ▼      ▼
      외부망 WS  내부망 WS

      → 편하다. 그런데 이 Runner 머신 자체가 두 망을 잇는 통로다.
        여기서 실행되는 컨테이너는 임의의 코드다(= MR을 올린 사람의 코드).
        보안 관점에서 이건 "망분리 예외 지점"이다.


   [구조 B] 망마다 Runner를 따로 두고 tag로 라우팅한다

        GitLab 서버 (외부)
              ▲            ▲
              │            │  둘 다 아웃바운드
        ┌─────┴────┐  ┌────┴─────┐
        │ Runner   │  │ Runner   │
        │ tag:     │  │ tag:     │
        │ external │  │ internal │
        └────┬─────┘  └────┬─────┘
             ▼             ▼
        외부망 WS      내부망 WS

      → 각 Runner는 자기 망 안에서만 논다. 망을 잇는 건 GitLab 서버뿐이고,
        그마저도 코드와 로그만 오간다.
```

`.gitlab-ci.yml`에서 이 라우팅은 `tags` 한 줄로 표현된다.

```yaml
# .gitlab-ci.yml
stages: [validate, deploy]

.dab: &dab
  image: registry.internal.example.com/ci/databricks-cli:0.280.0   # 사내 레지스트리 이미지
  before_script:
    - databricks --version

validate:external:
  <<: *dab
  stage: validate
  tags: [external]                      # ← 외부망 Runner가 집어간다
  script:
    - databricks bundle validate -t prod_external

validate:internal:
  <<: *dab
  stage: validate
  tags: [internal]                      # ← 내부망 Runner가 집어간다
  script:
    - databricks bundle validate -t prod_internal

deploy:internal:
  <<: *dab
  stage: deploy
  tags: [internal]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"   # main에서만
      when: manual                      # 그리고 사람이 눌러야 나감
  environment:
    name: internal-prod                 # 배포 이력이 GitLab에 남는다
  script:
    - databricks bundle deploy -t prod_internal
```

그리고 DAB 쪽에서는 이게 `targets` 로 표현된다. **리소스 정의는 한 벌이고, 망 차이는 타깃 오버라이드로만 흡수한다.**

```yaml
# databricks.yml
bundle:
  name: our_pipeline

include:
  - resources/*.yml          # 잡·파이프라인 정의는 여기 한 벌만 존재

targets:
  dev:
    mode: development
    default: true
    workspace:
      host: https://ext-workspace.cloud.databricks.com

  prod_external:
    mode: production
    workspace:
      host: https://ext-workspace.cloud.databricks.com
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    run_as:
      service_principal_name: ${var.deploy_sp}

  prod_internal:
    mode: production
    workspace:
      host: https://int-workspace.example.internal      # ← 여기만 다르다
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    run_as:
      service_principal_name: ${var.deploy_sp}
```

> ⚠️ **"두 망에 같은 것이 올라간다"를 보장하는 건 레포가 하나라는 사실이 아니다.** 같은 커밋에서 배포됐다는 사실이다.
>
> 레포가 하나여도, 외부망은 `main`에서 자동 배포되고 내부망은 사람이 수동으로 다른 시점에 누른다면 **두 망은 언제든 다른 상태**일 수 있다. 그리고 그건 정상이다 — 내부망을 먼저 검증 없이 올리는 게 더 위험하다.
>
> 중요한 건 **"지금 내부망에 올라가 있는 게 어느 커밋인가"를 알 수 있느냐**다. `environment:` 를 쓰면 GitLab이 환경별 배포 커밋 이력을 남겨준다. 이게 없으면, 장애가 났을 때 "내부망 코드가 뭐였는지" 를 사람 기억에 의존해야 한다.

### 3) ★ 폐쇄망에서 실제로 터지는 건 배포가 아니라 **의존성**이다

지금까지는 구조 이야기였다. 실무에서 하루를 날리는 건 여기다.

컨테이너를 띄운다는 건 **어딘가에서 이미지를 받아온다**는 뜻이다. 그리고 CI 스크립트는 보통 무언가를 설치한다. 폐쇄망에서는 이 전부가 막힌다.

| 밖에서는 그냥 되는 것 | 내부망에서 벌어지는 일 | 대응 |
|---|---|---|
| `image: python:3.11` (Docker Hub) | 이미지 pull 실패 | 사내 컨테이너 레지스트리에 미러링 |
| `pip install databricks-cli` (PyPI) | 설치 실패 | 사내 PyPI 미러(Nexus/Artifactory), 또는 CLI를 **이미지에 미리 구워둔다** |
| `dbt deps` (hub.getdbt.com) | **패키지가 없어도 실패할 수 있다** | 아래 참고 |
| 잡의 `libraries: pypi:` 설치 | 클러스터가 PyPI에 못 나감 | Volume에 올린 wheel 또는 사내 인덱스 |
| DAB의 Terraform 프로바이더 다운로드 | 다운로드 실패 | **direct 배포 엔진 사용** |

이 중 두 개는 따로 설명이 필요하다.

**(a) `dbt deps` 는 의존성이 없어도 밖으로 나가려 한다**

dbt는 `packages.yml`에 hub 패키지가 하나도 없어도 패키지 허브에 접속을 시도하는 동작이 보고되어 있다. 오프라인 환경에서 이것 때문에 `dbt deps`가 타임아웃으로 멈추는 이슈가 dbt-core에 올라와 있다. 회피책은 세 가지다.

```yaml
# packages.yml — 폐쇄망에서 쓸 수 있는 형태
packages:
  # ① 로컬 경로 (레포 안에 벤더링해서 커밋)
  - local: ../vendor/dbt_utils

  # ② 사내 git 레포 (내부망에서 도달 가능한 주소)
  - git: "https://gitlab.internal.example.com/data/dbt-utils.git"
    revision: 1.3.0
```

가장 확실한 건 **`dbt_packages/` 디렉터리 자체를 CI 이미지에 미리 구워두고, 내부망 job에서는 `dbt deps`를 아예 건너뛰는 것**이다. 재현성 관점에서도 이 편이 낫다 — 배포 때마다 외부에서 뭔가를 받아오는 파이프라인은, 그 외부가 바뀌면 어제와 다른 결과를 낸다.

**(b) DAB의 배포 엔진**

DAB가 Terraform 기반으로 동작하던 시절에는 배포 시점에 Terraform 프로바이더 바이너리를 받아와야 했다. 폐쇄망에서는 이게 그 자체로 장애물이었다. **direct 배포 엔진**은 이 외부 의존을 없앤 것이라, 폐쇄망에서는 선택이 아니라 사실상 전제다.

> **핵심 통찰 — "폐쇄망 CI의 난이도는 배포 로직이 아니라 의존성 그래프에서 나온다"**
>
> `databricks bundle deploy` 한 줄은 어디서 실행하든 똑같이 동작한다. 문제는 그 한 줄에 도달하기까지 컨테이너 이미지, CLI 바이너리, Python 패키지, dbt 패키지, 프로바이더 바이너리가 각각 어딘가에서 내려와야 한다는 것이다.
>
> 그래서 폐쇄망 CI를 설계할 때 첫 작업은 파이프라인을 짜는 게 아니라 **"이 job이 네트워크로 무엇을 가져오는지 전부 나열하기"** 다. 나열하고 나면 대응은 기계적이다 — 미러링하거나, 이미지에 굽거나, 레포에 벤더링한다. 나열을 안 하면 job이 실패할 때마다 하나씩 발견하게 되고, 매번 인프라 팀에 방화벽 요청을 넣게 된다.

### 4) 인증 — 무엇으로 두 workspace에 접속하나

CI가 workspace에 접속하려면 자격증명이 필요하다. 선택지는 셋이고, 폐쇄망에서 고려사항이 갈린다.

| 방식 | 형태 | 폐쇄망에서 |
|---|---|---|
| PAT(개인 토큰) | `DATABRICKS_TOKEN` 변수 | 동작은 하지만, **만료·회수·소유자 퇴사**가 전부 장애 요인. 감사 로그에 그 사람 이름이 찍힌다 |
| 서비스 프린시펄 + OAuth(M2M) | client id / secret | 무난한 기본값. 시크릿을 GitLab CI 변수(masked·protected)에 둔다 |
| OIDC 워크로드 아이덴티티 페더레이션 | 시크릿 없음 | 가장 안전. **단, GitLab이 발급한 토큰을 Databricks가 검증할 수 있어야 한다** |

> ⚠️ **OIDC는 폐쇄망에서 한 번 더 확인이 필요하다.** 이 방식은 Databricks 쪽이 GitLab의 OIDC 발급자(issuer)를 신뢰하도록 페더레이션 정책을 등록하는 구조다. 내부망 workspace가 GitLab 서버의 공개키 엔드포인트에 도달할 수 없으면 검증이 성립하지 않는다.
>
> 즉 **"CI에서 시크릿을 없애는 최선의 방법"이 하필 폐쇄망에서 가장 먼저 막힐 수 있다.** 내부망은 서비스 프린시펄 + 시크릿, 외부망은 OIDC — 이렇게 갈리는 것도 충분히 정상적인 결론이다.

그리고 배포용과 실행용은 나누는 게 원칙이다.

```
   배포용 서비스 프린시펄        실행용 서비스 프린시펄
   ─────────────────────        ─────────────────────
   잡·파이프라인을 만들 권한      데이터를 읽고 쓸 권한
   데이터 접근 권한은 최소         워크스페이스 관리 권한은 없음
        │                              │
        └─ CI가 쓴다                   └─ run_as 에 지정한다
```

이유는 단순하다. **CI 자격증명은 파이프라인 로그와 여러 사람의 MR을 통과한다.** 그게 곧 데이터 접근 권한이면, 파이프라인에 임의 코드를 넣을 수 있는 사람은 누구나 데이터에 접근할 수 있다.

### 내가 확인할 것

- [ ] 내부망 Runner는 **어디에 설치돼 있나** — 구조 A(경계 머신 하나)인가 구조 B(망별 Runner)인가. `.gitlab-ci.yml`의 `tags` 를 보면 바로 나온다.
- [ ] 내부망 job이 쓰는 **컨테이너 이미지의 출처** — 사내 레지스트리인가, 외부인가. 외부라면 어떻게 나가고 있나.
- [ ] `dbt deps` 를 내부망에서 어떻게 처리하고 있나 — 미러? 벤더링? 아니면 아직 안 부딪혔나(=아직 dbt가 내부망에 안 갔다).
- [ ] 배포 엔진이 **direct** 인지 확인. 폐쇄망이면 이건 사실상 필수다.
- [ ] 인증 방식 — PAT / SP+시크릿 / OIDC 중 무엇이며, 외부망과 내부망이 다른가.
- [ ] 내부망 배포가 **자동인가 수동 승인인가**, 그리고 **현재 배포된 커밋을 어디서 확인**하나.
- [ ] `targets` 이름 규칙 — 실수로 내부망 타깃에 외부망 호스트가 들어가는 걸 무엇이 막나. (`bundle validate`는 호스트 오타를 못 잡는다. 접속이 되면 그냥 성공한다.)

## Q2. `databricks bundle init dbt-sql`에서 어떤 SQL warehouse를 골라야 하나요?

`databricks bundle init` 을 `dbt-sql` 템플릿으로 실행하면 초반에 SQL warehouse를 고르라고 나온다. 목록에 `Shared Warehouse (serverless)` 와 `Shared Pro Warehouse (pro)` 가 있었다.

### 들은 답

> **Serverless로 `Shared Warehouse` 를 사용한다.**

결론은 이걸로 확정이다. 그런데 이 선택이 **정확히 어디에 어떻게 박히는지**를 모르면, 나중에 "prod에서도 이 웨어하우스를 쓰고 있었네" 를 뒤늦게 발견하게 된다. 실제로 템플릿 코드를 뜯어보니 그럴 소지가 있었다.

### 1) 기초 — SQL warehouse는 세 종류고, 차이는 성능만이 아니다

| | **classic** | **pro** | **serverless** |
|---|---|---|---|
| Photon | ✅ | ✅ | ✅ |
| Predictive IO | ❌ | ✅ | ✅ |
| Intelligent Workload Management | ❌ | ❌ | ✅ |
| 기동 시간 | 약 4분 | 약 4분 | **4~6초** |
| 컴퓨트가 사는 곳 | 우리 계정 | 우리 계정 | **Databricks 계정** |
| 우리 VPC 안 리소스 접속 | 가능 | 가능 | 별도 네트워크 설정 필요 |

여기서 **가장 중요한 줄은 성능이 아니라 "컴퓨트가 사는 곳"** 이다.

```
   [classic / pro]                    [serverless]

   ┌──────────────────┐              ┌──────────────────┐
   │ Databricks 계정  │              │ Databricks 계정  │
   │  - UI, 스케줄러  │              │  - UI, 스케줄러  │
   │  - Unity Catalog │              │  - Unity Catalog │
   └──────────────────┘              │  - ★ SQL 실행     │
            │                        └──────────────────┘
            ▼                                 │
   ┌──────────────────┐                       ▼
   │ 우리 계정 VPC    │              ┌──────────────────┐
   │  - ★ SQL 실행    │              │ 우리 계정 S3     │
   │  - S3 데이터     │              │  - 데이터        │
   └──────────────────┘              └──────────────────┘

   VPC 안의 온프렘 DB, 사설 엔드포인트에      데이터는 여전히 우리 것이지만,
   그냥 도달한다                             실행 주체는 경계 밖에 있다
```

Databricks 문서가 pro를 권하는 조건이 정확히 이것이다 — **"serverless를 쓸 수 없는 리전이거나, 커스텀 네트워크를 정의해 두고 클라우드/온프렘의 DB에 접속해야 할 때."**

> ⚠️ **이 조건이 Q1(내부망)과 정면으로 만난다.**
>
> 외부망 workspace에서 serverless를 고르는 건 당연히 맞다. 그런데 **내부망 workspace에도 serverless SQL warehouse가 있는가**는 별개 문제다. 폐쇄망 구성에서는 serverless가 아예 제공되지 않거나, NCC/PrivateLink 설정이 선행되어야 하는 경우가 흔하다.
>
> 그리고 뒤에서 보겠지만, 템플릿은 **dev와 prod 프로파일에 같은 `http_path` 값을 넣는다.** 망이 다르면 웨어하우스 ID도 당연히 다르므로, 이 값은 반드시 **타깃별로 갈라야 한다.** 지금 안 갈라두면 내부망 첫 배포에서 "warehouse를 찾을 수 없다"로 터진다.

### 2) ★ 이 선택은 실제로 어디에 박히나 — 템플릿을 뜯어봤다

`dbt-sql` 템플릿이 물어보는 것은 순서대로 여섯 개다.

```
1. project_name        프로젝트 이름
2. http_path           "Select a SQL warehouse to use during development
                        (you can change this in databricks.yml later)"   ← 이것
3. default_catalog     초기 카탈로그
4. personal_schemas    사용자별 개인 스키마를 쓸지 (기본 yes)
5. shared_schema       (personal_schemas=no일 때만) 공용 스키마
6. serverless          서버리스 컴퓨트를 쓸지 (기본 yes)               ← 이건 다른 것!
```

**여기서 항목 2와 항목 6은 서로 다른 컴퓨트를 가리킨다.** 이게 이 템플릿에서 가장 헷갈리는 지점이다. 뒤에서 자세히 본다.

먼저 항목 2에서 고른 값이 어디로 가는지 보자. 생성된 프로젝트에서 그 값은 **두 파일**에 들어간다.

```
my_dbt_project/
├── databricks.yml              ← 여기엔 http_path 가 없다  ⚠️
├── dbt_project.yml
├── profile_template.yml        ← ① 로컬 개발용 (dbt init 이 참조)
├── dbt_profiles/
│   └── profiles.yml            ← ② 배포된 job 이 참조     ★
├── requirements-dev.txt        ← dbt-databricks>=1.8.0,<2.0.0
├── resources/
│   └── my_dbt_project.job.yml  ← dbt task 정의
└── src/
    ├── models/
    ├── seeds/
    └── macros/
```

②번 파일의 실제 내용은 이렇게 생겼다.

```yaml
# dbt_profiles/profiles.yml — 배포된 잡이 사용하는 프로파일
my_dbt_project:
  target: dev
  outputs:

    dev:
      type: databricks
      method: http
      catalog: my_catalog
      schema: "{{ var('dev_schema') }}"        # 사용자별 개인 스키마
      http_path: /sql/1.0/warehouses/abc123    # ← init 에서 고른 값
      host:  "{{ env_var('DBT_HOST') }}"       # Databricks 가 주입
      token: "{{ env_var('DBT_ACCESS_TOKEN') }}"

    prod:
      type: databricks
      method: http
      catalog: my_catalog
      schema: default
      http_path: /sql/1.0/warehouses/abc123    # ← ★ prod 도 같은 값이다
      host:  "{{ env_var('DBT_HOST') }}"
      token: "{{ env_var('DBT_ACCESS_TOKEN') }}"
```

> ⚠️ **프롬프트 문구를 그대로 믿으면 안 되는 지점이 두 개 있다.**
>
> **첫째, "use during development" 라고 하지만 prod 프로파일에도 같은 값이 들어간다.** 개발용으로 아무거나 고른다는 마음으로 넘어가면, 그게 그대로 운영 웨어하우스가 된다.
>
> **둘째, "you can change this in databricks.yml later" 라고 하지만 이 값은 `databricks.yml`에 없다.** `dbt_profiles/profiles.yml` 에 있다. 프롬프트 안내문이 템플릿 구조 변경을 따라가지 못한 것으로 보인다. `databricks.yml`을 아무리 뒤져도 안 나온다고 당황할 필요 없다.
>
> 그래서 **init 직후 가장 먼저 할 일은 이 파일을 열어서 dev/prod를 갈라놓는 것**이다.

타깃별로 웨어하우스를 가르는 건 이렇게 한다.

```yaml
# databricks.yml — 변수로 뽑는다
variables:
  warehouse_http_path:
    description: dbt 가 SQL 을 실행할 웨어하우스의 HTTP path

targets:
  dev:
    variables:
      warehouse_http_path: /sql/1.0/warehouses/DEV_ID
  prod_external:
    variables:
      warehouse_http_path: /sql/1.0/warehouses/EXT_PROD_ID
  prod_internal:
    variables:
      warehouse_http_path: /sql/1.0/warehouses/INT_PROD_ID   # 내부망은 다른 웨어하우스
```

그리고 잡 정의에서 이 변수를 환경변수로 dbt에 넘긴 뒤, `profiles.yml` 에서 `env_var()` 로 받는다. `host`/`token`이 이미 그 방식으로 주입되고 있으니 같은 패턴을 하나 더 쓰는 것뿐이다.

```yaml
# dbt_profiles/profiles.yml
      http_path: "{{ env_var('DBT_HTTP_PATH') }}"
```

### 3) ★ 컴퓨트가 두 개다 — 이걸 모르면 비용도 네트워크도 잘못 본다

`dbt-sql` 번들에서 하나의 dbt 실행에는 **컴퓨트가 두 개** 관여한다.

```
   ┌───────────────────────────────────────────────────────────┐
   │  ① dbt 프로세스가 도는 곳  =  Job compute                │
   │     (init 항목 6의 "serverless" 가 정하는 것)             │
   │                                                           │
   │     여기서 하는 일:                                       │
   │       - dbt deps / seed / run 명령 실행                   │
   │       - Jinja 렌더링, DAG 계산, SQL 문자열 생성           │
   │       - 사실상 Python 프로세스 하나. 무겁지 않다          │
   │                                                           │
   │     기본값은 서버리스 환경이고, 아니면 단일 노드 클러스터 │
   │     (num_workers: 0, spark.master local[*,4])             │
   └────────────────────────┬──────────────────────────────────┘
                            │  생성된 SQL을 JDBC/HTTP 로 전송
                            │  (http_path 가 가리키는 곳)
                            ▼
   ┌───────────────────────────────────────────────────────────┐
   │  ② SQL 이 실제로 실행되는 곳  =  SQL warehouse           │
   │     (init 항목 2의 http_path 가 정하는 것)                │
   │                                                           │
   │     여기서 하는 일:                                       │
   │       - CREATE TABLE AS / MERGE / INSERT 전부             │
   │       - 스캔, 조인, 셔플, 쓰기                            │
   │       - 무거운 건 전부 여기다                        ★    │
   └───────────────────────────────────────────────────────────┘
```

이 구분을 알면 세 가지가 정리된다.

**(a) 비용.** ①은 dbt가 도는 내내 켜져 있지만 하는 일이 거의 없다. ②는 쿼리가 갈 때만 바쁘다. 그런데 **①이 켜져 있는 시간 = 전체 dbt run 시간**이므로, 모델이 200개인데 순차 실행이면 ①도 그만큼 오래 과금된다. `threads` 를 올려서 전체 시간을 줄이는 건 ②의 병렬성뿐 아니라 ①의 과금 시간도 줄인다.

**(b) 네트워크.** dbt가 원천에 접속하는 게 아니다. **②가 접속한다.** 그래서 "웨어하우스가 어느 망에 있는가"가 문제지, dbt 프로세스가 어디서 도는지는 데이터 접근 관점에서 중요하지 않다.

**(c) 왜 SQL warehouse인가.** dbt가 만드는 건 결국 SQL 문자열이다. 범용 클러스터로도 돌릴 수 있지만, SQL warehouse는 SQL 실행에 최적화돼 있고 auto-stop이 짧다. dbt처럼 **짧은 쿼리를 다발로 던지고 끝나는** 워크로드에는 기동이 빠른 쪽이 압도적으로 유리하다. serverless의 4~6초 vs pro의 4분 차이는, 하루 한 번 도는 배치에서도 개발 반복에서는 매번 체감된다.

> **핵심 통찰 — "serverless가 맞는 이유는 성능이 아니라 기동 시간이다"**
>
> Photon이나 Predictive IO 같은 성능 기능은 pro에도 있다. serverless만 가진 건 Intelligent Workload Management와 **4~6초 기동**이다.
>
> dbt 개발은 "모델 한 줄 고치고 `dbt run --select my_model`" 을 하루에 수십 번 반복하는 일이다. 이때 매번 4분을 기다리면 개발 속도가 아니라 **개발 방식이 바뀐다.** 사람은 기다림이 길면 여러 변경을 모아서 한 번에 실행하게 되고, 그러면 실패했을 때 원인이 되는 변경을 특정하지 못한다.
>
> 즉 기동 시간은 편의 문제가 아니라 **디버깅 단위의 크기를 정하는 변수**다.

### 4) "Shared" 라는 이름이 뜻하는 것

목록의 두 웨어하우스는 이름이 둘 다 `Shared` 로 시작한다. 팀 공용이라는 뜻이고, 그러면 **동시성 경합**이 따라온다.

```
   dbt run --threads 8

   dbt 프로세스                    Shared Warehouse
   ┌──────────┐                   ┌────────────────────┐
   │ model A  │──┐                │ 다른 팀의 대시보드 │
   │ model B  │──┤                │ 다른 팀의 애드혹   │
   │ model C  │──┼───→ 8개 동시 ─→│ 우리 dbt 8개       │
   │ ...      │──┤                │                    │
   │ model H  │──┘                │ → 큐잉 발생        │
   └──────────┘                   └────────────────────┘
```

serverless는 Intelligent Workload Management로 이 상황에서 자동 스케일링이 가장 민첩한 타입이긴 하다. 그래도 **`threads` 를 무작정 올리면 남의 대시보드가 느려진다.** 템플릿 기본값은 4다. 모델 수가 많아지면 올리되, 공용 웨어하우스라는 걸 알고 올려야 한다.

### 내가 확인할 것

- [ ] init 직후 `dbt_profiles/profiles.yml` 을 열어 **dev/prod의 `http_path` 가 같은지** 확인하고, 다르게 갈라둔다.
- [ ] **내부망 workspace에 serverless SQL warehouse가 존재하는가.** 없으면 내부망 타깃은 pro여야 하고, 그건 `http_path` 를 반드시 타깃 변수로 빼야 한다는 뜻이다.
- [ ] init 항목 6(`serverless` = dbt 프로세스가 도는 컴퓨트)이 **내부망에서도 되는지**. 안 되면 잡 정의에 단일 노드 클러스터 스펙이 필요하고, 그 클러스터가 `dbt-databricks` 를 PyPI에서 받을 수 있어야 한다(→ Q1의 의존성 문제와 같은 지점).
- [ ] 공용 웨어하우스의 **현재 부하와 auto-stop 설정**. 우리 배치 시간대에 다른 팀 워크로드가 겹치나.
- [ ] `threads` 값을 몇으로 둘지 — 모델 개수와 웨어하우스 크기를 보고 정한다.

## Q3. 데이터 모델링은 기존 것 그대로 가나요?

새 파이프라인을 만드는 것이지 새 데이터 웨어하우스를 설계하는 것은 아니다. 그런데 옮기다 보면 "이건 이렇게 하는 게 나은데" 가 계속 눈에 밟힌다. 어디까지가 우리 재량인지 물었다.

### 들은 답

> - **원칙은 그대로 가는 것이다.**
> - 그래도 **꼭 필요한 경우라면 고객사와 협의해서 변경**한다.

짧지만 이건 마이그레이션 프로젝트에서 가장 중요한 원칙 중 하나다. 왜 그런지를 제대로 이해해두면, 나중에 "이건 협의 대상인가 그냥 하면 되는가" 를 스스로 판단할 수 있다.

### 1) 왜 "그대로" 가 원칙인가 — 변수를 하나만 바꾼다

마이그레이션의 성공 판정 기준은 단 하나다. **새 파이프라인의 결과가 기존과 같은가.**

```
   [변수를 하나만 바꿨을 때]

   기존 엔진 + 기존 모델  ──→  결과 A
   새 엔진   + 기존 모델  ──→  결과 B

   A ≠ B  →  원인은 반드시 "엔진 차이" 안에 있다.   ✅
             범위가 좁으므로 반나절이면 찾는다.


   [변수를 둘 바꿨을 때]

   기존 엔진 + 기존 모델  ──→  결과 A
   새 엔진   + 새 모델    ──→  결과 B

   A ≠ B  →  엔진 때문인가?  모델을 바꿔서인가?
             모델을 바꾼 게 맞는데 엔진이 또 틀린 건가?
             ─────────────────────────────────────
             구별할 방법이 없다.                    💥
             그리고 "새 모델이니까 값이 다른 게 당연하다"는
             변명이 성립하는 순간, 진짜 버그가 그 뒤에 숨는다.
```

두 번째 상황의 진짜 위험은 시간이 더 걸린다는 게 아니다. **검증이 불가능해진다는 것**이다. 값이 달라도 "모델을 바꿨으니까" 로 설명이 되어버리면, 아무도 그 차이를 끝까지 파고들지 않는다.

> **핵심 통찰 — "마이그레이션에서 '그대로 간다'는 보수적인 선택이 아니라, 검증을 가능하게 만드는 유일한 선택이다"**
>
> "기존 모델이 완벽해서 그대로 간다"가 아니다. 기존 모델에 개선할 점이 있다는 걸 알면서도 그대로 가는 것이다. 이유는 **개선과 이전을 동시에 하면 둘 다 검증할 수 없기 때문**이다.
>
> 개선은 이전이 끝나고 "기존과 값이 같다"가 증명된 다음에 한다. 그때는 새 파이프라인이 기준선이 되어주므로, 개선의 효과만 따로 볼 수 있다.
>
> 이건 리팩터링의 기본 규칙과 같다 — **동작을 바꾸는 커밋과 구조를 바꾸는 커밋을 섞지 않는다.** 마이그레이션은 그 규칙을 파이프라인 단위로 확대한 것뿐이다.

### 2) 그런데 "그대로"가 물리적으로 불가능한 지점들이 있다

여기가 실무에서 부딪히는 부분이다. **"모델을 그대로 간다"는 논리 모델(엔티티, 키, 관계, 컬럼의 의미)을 그대로 간다는 뜻이지, 물리 모델(타입, 정렬, 분산, 인덱스)까지 같다는 뜻이 될 수 없다.** 엔진이 다르면 물리 모델은 개념 자체가 다르기 때문이다.

| 기존(Redshift 계열) 개념 | 새 환경(Databricks/Delta)에서 | 성격 |
|---|---|---|
| `DISTKEY` / `DISTSTYLE` | 대응 개념 없음 (파일 기반, 셔플은 실행 시 결정) | **번역 불가 — 버린다** |
| `SORTKEY` | Liquid Clustering / Z-ORDER / 파티셔닝 | **다른 것으로 대체** |
| `ENCODE` (컬럼 압축) | Parquet/Delta가 자동 처리 | **번역 불가 — 버린다** |
| `VARCHAR(n)` 길이 제약 | `STRING` (길이 제약 없음) | 제약이 사라진다 ⚠️ |
| `NUMERIC(p,s)` | `DECIMAL(p,s)` | 대체로 대응되지만 **정밀도 한계가 다르다** |
| `IDENTITY` 컬럼 | Delta의 `GENERATED ... AS IDENTITY` | 동작하지만 **값의 연속성 보장 범위가 다르다** |
| 식별자 대소문자 | 엔진마다 규칙이 다르다 | **조용히 다르게 동작** ⚠️ |
| 문자열 비교 시 후행 공백 | 엔진마다 규칙이 다르다 | **조용히 다르게 동작** ⚠️ |
| `NULL` 정렬 순서 | `ORDER BY` 기본 위치가 다를 수 있다 | **조용히 다르게 동작** ⚠️ |

⚠️ 표시한 넷이 위험하다. **에러가 안 나고 값만 달라지기 때문이다.**

특히 `VARCHAR(n)` → `STRING` 은 함정이 반대 방향이다. 기존에는 길이 초과가 **에러로 잡혔는데**, 새 환경에서는 그냥 들어간다. 즉 기존 시스템이 데이터 품질 게이트 역할을 하던 걸 잃는다. 그게 중요한 컬럼이면 dbt 테스트로 되살려야 한다.

```yaml
# src/models/silver/_silver__models.yml
models:
  - name: silver_member
    columns:
      - name: member_no
        tests:
          - not_null
          - unique
      - name: member_grade_cd
        tests:
          # 기존 VARCHAR(2) 제약을 테스트로 되살린다
          - dbt_utils.expression_is_true:
              expression: "length(member_grade_cd) <= 2"
```

> ⚠️ **"그대로 간다"가 만드는 착시 하나.** 물리 모델을 번역할 수 없다는 건 **테이블 성능 특성이 반드시 달라진다**는 뜻이다. 기존에 `SORTKEY` 덕분에 빠르던 조회가 새 환경에서는 전체 스캔이 될 수 있다.
>
> 그러니 "모델을 그대로 간다"고 해서 **성능까지 그대로 갈 거라고 기대하면 안 된다.** 오히려 마이그레이션 후 성능 이슈는 대부분 여기서 나온다. 원래 정렬 키였던 컬럼 목록은, 새 환경에서 클러스터링 키 후보 목록이다. 버리지 말고 옮겨 적어둬야 한다.

### 3) 그래서 "협의"라는 말의 실제 무게

SI에서 "고객사와 협의해서 변경한다"는 절차상의 예의가 아니다. **데이터 모델은 계약의 일부**이기 때문이다.

```
   데이터 모델을 바꾼다는 것이 실제로 건드리는 것들

   컬럼 하나를 바꾼다
        │
        ├─→ 그 컬럼을 쓰는 대시보드
        ├─→ 그 컬럼을 쓰는 리포트 정의서
        ├─→ 그 컬럼을 쓰는 다른 팀의 쿼리
        ├─→ 산출물 문서(테이블 정의서, 매핑 정의서)
        ├─→ 검수 기준 (= 대금 지급 조건)
        └─→ 운영 이관 시 인수인계 범위
```

우리가 "이게 더 낫다"고 판단해서 바꾼 것은, 검수 시점에 **"요구사항과 다르다"** 로 돌아온다. 기술적으로 옳아도 계약적으로는 결함이다.

그래서 변경이 필요할 때의 실무 절차는 이렇게 된다.

1. **변경 없이 되는 방법을 먼저 찾는다.** 대부분 된다.
2. 안 되면 **무엇이 왜 불가능한지**를 기록한다 (엔진 차이? 데이터 문제? 성능?).
3. **선택지를 두 개 이상** 만들어 각각의 영향 범위를 적는다.
4. 협의하고, **결정을 문서에 남긴다.**

3번이 핵심이다. "이렇게 바꿔야 합니다" 는 협의가 아니라 통보다. "A안은 이런 영향이 있고 B안은 저런 영향이 있는데, 어느 쪽으로 가시겠습니까" 가 협의다.

### 내가 확인할 것

- [ ] 기존 모델의 **테이블 정의서·매핑 정의서가 존재하는가**, 그리고 그게 실제 테이블과 일치하는가. (자주 어긋나 있고, 어긋난 걸 발견하는 것 자체가 초기에 해야 할 일이다.)
- [ ] 기존 테이블의 **정렬 키/분산 키 목록**을 뽑아둔다. 그대로 못 옮기지만, 클러스터링 후보로는 그게 최선의 정보다.
- [ ] 타입 매핑 규칙을 **한 장으로 정리**한다. 사람마다 다르게 매핑하면 그것 자체가 값 차이의 원인이 된다.
- [ ] 새 환경에서 **조용히 다르게 동작하는 것들**(NULL 정렬, 후행 공백, 대소문자)을 실제 데이터로 한 번씩 확인한다.
- [ ] 변경 요청이 생겼을 때 **어디에 기록하는지** — Jira? 별도 이슈 관리 대장? 채널에서 구두로 끝나면 검수 때 근거가 없다.

## Q4. dbt로 MTV(Metric View)까지 다 만들어야 하나요?

새로 만드는 dbt 파이프라인의 **범위**를 확인하고 싶었다. silver·gold 테이블까지인가, 그 위에 얹히는 Metric View까지인가.

### 들은 답

> **MTV는 dbt로 안 되고, 따로 job을 만들어야 한다.**

**우리 프로젝트에서의 결론은 이게 맞을 가능성이 높다.** 다만 이유가 "dbt가 원리적으로 못 해서" 는 아니고, **어댑터 버전**에 달린 이야기다. 그리고 버전 문제와 별개로 **따로 두는 게 설계상 더 나은 이유**가 따로 있다. 순서대로 본다.

### 1) 기초 — Metric View는 일반 view와 무엇이 다른가

Metric View는 SQL이 아니라 **YAML로 정의하는 view**다. Unity Catalog 안에 있는 semantic layer 객체다.

```sql
CREATE OR REPLACE VIEW orders_metrics WITH METRICS LANGUAGE YAML AS $$
version: 1.1
comment: '주문 관련 KPI'
source: samples.tpch.orders
joins:
  - name: customer
    source: samples.tpch.customer
    'on': source.o_custkey = customer.c_custkey
filter: source.o_orderdate > '1990-01-01'
fields:                                   # 차원 (그룹핑·필터 대상)
  - name: Order Month
    expr: DATE_TRUNC('MONTH', source.o_orderdate)
  - name: Market Segment
    expr: customer.c_mktsegment
measures:                                 # 측정값 (집계식)
  - name: Order Count
    expr: COUNT(1)
  - name: Total Revenue
    expr: SUM(source.o_totalprice)
$$
```

일반 view와의 결정적 차이는 이거다.

```
   [일반 view]
   집계 단위가 정의 안에 박혀 있다.
        SELECT month, SUM(price) FROM orders GROUP BY month
        → 월별로만 볼 수 있다.
        → 세그먼트별로 보려면 view를 하나 더 만든다.
        → 그러다 보면 같은 지표의 view가 열 개가 되고,
          그중 두 개가 미묘하게 다른 정의를 갖게 된다.   💥

   [metric view]
   측정값 정의와 집계 단위가 분리돼 있다.
        measures 에 "Total Revenue = SUM(o_totalprice)" 만 정의
        → 조회할 때 GROUP BY 를 사용자가 정한다.
        → 월별로도, 세그먼트별로도, 둘 다로도 볼 수 있다.
        → 정의는 한 곳이다.                              ✅
```

그리고 이게 단순한 편의가 아닌 이유는 **잘못된 집계를 구조적으로 막아주기 때문**이다.

```
   비율 지표를 사전 집계해두면 벌어지는 일

   지점 A: 주문 100건 중 성공 90건 → 성공률 90%
   지점 B: 주문   4건 중 성공  1건 → 성공률 25%

   전체 성공률을 "지점별 성공률의 평균"으로 구하면
        (90 + 25) / 2 = 57.5%     ← 틀렸다

   올바른 값은
        (90 + 1) / (100 + 4) = 87.5%

   metric view 는 measures 에 분자·분모의 집계식을 갖고 있으므로
   어떤 단위로 그룹핑하든 원자료에서 다시 계산한다.
```

이 오류는 사전 집계 테이블을 여러 벌 만들어 쓰는 조직에서 **정말 자주** 나온다. 그리고 발견이 어렵다 — 값이 그럴듯하기 때문이다.

### 2) 왜 dbt와 궁합이 나쁜가

dbt 모델의 기본 계약은 **"파일 하나 = SELECT 문 하나"** 다. dbt는 그 SELECT를 받아 `CREATE TABLE AS` 나 `CREATE VIEW AS` 로 감싼다.

```
   dbt 모델 파일               dbt 가 만드는 것
   ──────────────              ───────────────────────────
   SELECT ... (SQL)     →      CREATE TABLE x AS SELECT ...
                               CREATE VIEW  x AS SELECT ...

   metric view 정의            필요한 것
   ──────────────              ───────────────────────────
   version/source/             CREATE VIEW x WITH METRICS
   fields/measures (YAML)      LANGUAGE YAML AS $$ ... $$
                                          ▲
                                          └─ SELECT 문이 아니다
```

바디가 SQL이 아니라 YAML이므로, 이걸 만들려면 **어댑터에 전용 materialization이 있어야 한다.** 없으면 dbt는 이 객체를 만들 방법이 없다.

### 3) ⚠️ 사실 확인 — dbt-databricks 1.12.0부터는 된다

`dbt-databricks` 변경 이력을 확인한 결과는 이렇다.

| 버전 | 날짜 | 내용 |
|---|---|---|
| 1.11.8 | 2026-05-11 | **카탈로그에 metric view가 있으면 `dbt run` 이 실패하던 버그 수정** |
| **1.12.0** | **2026-05-18** | **`materialized='metric_view'` 추가 — metric view를 materialization으로 지원** |
| 1.12.1 | 2026-06-10 | 관련 버그 수정 |
| 1.12.4 | 2026-08-12 | (최신) |

1.11.8 항목이 상황을 잘 보여준다. **그 전에는 "만들 수 없다"가 아니라 "카탈로그에 있기만 해도 dbt가 깨졌다".** `metric_view` 라는 관계 타입 자체를 어댑터가 몰랐기 때문이다. 그러니 "dbt로 안 된다"는 답은 그 시절 기준으로는 정확한 정도가 아니라 온화한 표현이다.

1.12.0의 지원 형태는 이렇다.

```sql
-- src/models/semantic/orders_metrics.sql
{{ config(materialized='metric_view') }}

version: 1.1
source: {{ ref('gold_orders') }}
fields:
  - name: Order Month
    expr: DATE_TRUNC('MONTH', source.o_orderdate)
measures:
  - name: Total Revenue
    expr: SUM(source.o_totalprice)
```

어댑터가 `CREATE OR REPLACE VIEW ... WITH METRICS LANGUAGE YAML` 을 발행한다. `databricks_tags`, `tblproperties`, `grants` 를 지원하고, `view_update_via_alter=true` 를 켜면 전체 교체 대신 `ALTER VIEW AS` 로 갱신한다.

> ⚠️ **그렇다고 "PM님 답이 틀렸다"가 아니다. 조건이 붙는 답이다.**
>
> 되려면 최소 세 가지가 동시에 참이어야 한다.
> 1. **dbt-databricks가 1.12.0 이상**이어야 한다. 우리 리포는 버전 사양 파일에 값을 고정해두고 있어서, 새 버전이 나와도 자동으로 올라가지 않는다. 고정된 값이 1.12 미만이면 진짜로 안 된다.
> 2. **Databricks Runtime 16.4 이상**에서 생성 가능하고, materialization을 걸려면 **17.3 이상**이 필요하다. 개별 YAML 기능도 각각 최소 런타임이 다르다.
> 3. **폐쇄망에서 그 버전을 설치할 수 있어야 한다.** 사내 PyPI 미러에 1.12가 없으면 논의 자체가 무의미하다. (→ Q1의 의존성 문제)
>
> 그래서 이 답은 **"안 된다"가 아니라 "우리 버전에서는 안 된다"** 로 적어두는 게 맞다. 둘의 차이는 반년 뒤에 드러난다. 전자로 적어두면 아무도 다시 확인하지 않는다.

### 4) 버전과 무관하게, 따로 두는 게 나은 이유

버전이 올라가서 dbt로 만들 수 있게 되더라도, **일배치 dbt run의 DAG에 metric view를 넣는 게 좋은 설계인지는 별개 문제**다. 이유는 **라이프사이클이 다르기 때문**이다.

```
   silver / gold 테이블                metric view
   ────────────────────                ────────────────────
   매일 데이터가 바뀐다                 정의가 바뀔 때만 바뀐다
   실행 = 데이터 적재                   실행 = 정의 등록
   실패하면 데이터가 없다               실패하면 정의가 옛날 것이다
   재실행에 시간이 든다                 재실행이 즉시다
   ────────────────────                ────────────────────
   하루 1회 실행                        분기에 한 번 바뀔 수도 있다
```

**데이터가 아니라 정의를 다루는 객체를, 데이터 적재 주기에 맞춰 매일 재생성할 이유가 없다.** 오히려 섞으면 이런 일이 생긴다.

```
   [섞었을 때]
   dbt run
     ├─ silver 40개 적재  ✅ (25분)
     ├─ gold 12개 적재    ✅ (10분)
     └─ metric view 5개   ❌ 정의 오타
   → 잡 전체가 실패로 표시된다.
   → 알림이 울린다. 새벽에 사람이 깬다.
   → 실제로는 데이터 적재는 다 끝났고, 문제는 view 정의 한 줄이다.
     실패 반경이 실제 손상 범위보다 훨씬 크다.       💥

   [나눴을 때]
   job: daily_load      → 데이터. 실패하면 진짜 문제.
   job: semantic_deploy → 정의. 정의가 바뀔 때만 실행.
   → 알림의 의미가 명확해진다.
```

여기에 materialization까지 붙으면 이유가 하나 더 생긴다. Metric View에 materialization을 걸면 Databricks가 **관리형 파이프라인(SDP)을 만들어서** 사전 집계 MV를 유지하고, 쿼리 시점에 옵티마이저가 자동으로 매칭해준다. 즉 그때부터는 **갱신 주체가 dbt가 아니라 플랫폼**이다. dbt가 매일 `CREATE OR REPLACE` 를 날리면, 플랫폼이 관리하던 것을 매일 흔드는 셈이 된다.

> **핵심 통찰 — "dbt의 경계는 '데이터가 매일 바뀌는 곳'까지다"**
>
> dbt는 **데이터를 만드는 도구**다. 정의·권한·의미 계층은 데이터가 아니라 메타데이터고, 이것들은 배포 주기가 다르다.
>
> 좋은 기준선은 이거다 — **"매일 실행되어야 하는가?"** 예면 dbt. 아니면 별도.
>
> 이 기준으로 나누면 잡의 실패 알림이 정확해진다. 그리고 실패 알림이 정확하면 사람이 알림을 무시하지 않게 된다. **알림 피로는 알림이 많아서가 아니라, 알림과 실제 문제가 대응되지 않아서 생긴다.**

그래서 우리 파이프라인의 경계는 이렇게 그려진다.

```
   ┌──────────────── dbt 가 담당 ────────────────┐
   │                                             │
   │  source (기존 ODS/Mart)                     │
   │       │                                     │
   │       ▼                                     │
   │  staging  ──→  silver  ──→  gold            │
   │  (정규화)     (정제·표준)   (업무 집계)     │
   │                                             │
   │  매일 실행. 데이터가 바뀐다.                │
   └──────────────────┬──────────────────────────┘
                      │
   ┌──────────────────▼───── 별도 job ───────────┐
   │  Metric View (semantic layer)               │
   │  - YAML 정의                                │
   │  - 정의가 바뀔 때만 배포                    │
   │  - materialization 은 플랫폼이 관리         │
   └──────────────────┬──────────────────────────┘
                      ▼
              Genie / BI / 애드혹 분석
```

### 내가 확인할 것

- [ ] **우리 리포에 고정된 `dbt-databricks` 버전**이 몇인지. 1.12 미만이면 "안 된다"가 맞고, 이상이면 "안 하기로 한 것"이다. 둘은 다른 이야기다.
- [ ] 우리가 쓸 **SQL warehouse의 런타임 버전**. metric view 생성에 16.4+, materialization에 17.3+가 필요하다.
- [ ] 기존에 **MTV가 몇 개 있고 어떻게 만들어져 있나** — 노트북? SQL 스크립트? 수동? 이게 곧 "따로 만들 job"의 형태를 정한다.
- [ ] metric view가 **gold 테이블을 참조하므로, gold가 준비되기 전에 배포되면 깨진다.** 별도 job이라도 순서 의존은 남는다. 이걸 어떻게 처리할지.
- [ ] MTV의 **정의 원본이 어디에 버전 관리되는지.** 별도 job으로 뺀다고 해서 YAML을 Git 밖에 두면, DAB로 얻으려던 것(설정의 코드화)을 여기서 잃는다.

## Q5. `for_each_task`로 돌던 것을 dbt에서는 어떻게 하나요?

기존 파이프라인은 테이블 목록을 배열로 넘겨서 `for_each_task` 한 개가 N번 돌게 되어 있다. 잡 정의는 짧고 테이블이 늘어도 배열에 한 줄만 추가하면 된다. 이 구조를 dbt에서 어떻게 재현하는지 물었다.

### 들은 답

> **하나씩 다 dbt로 만들어야 한다.**

맞다. 그리고 이건 "dbt가 부족해서 어쩔 수 없이" 가 아니라 **dbt의 설계 원리상 그럴 수밖에 없고, 그 대가로 얻는 게 있는** 거래다. 그 거래의 내용을 알아야 N개 파일을 만드는 게 삽질이 아니라 투자로 느껴진다.

### 1) 기초 — 두 방식은 DAG를 만드는 시점이 다르다

```
   [for_each_task]

   잡 정의 (배포 시점)              실행 시점
   ──────────────────              ────────────────────────
   task: load_all                   inputs 배열을 읽는다
     for_each_task:                   → ["member","order","asset", ...]
       inputs: {{job.parameters}}    반복 횟수가 여기서 결정된다  ★
       concurrency: 10
       task:                         iteration 1: member
         notebook_task: load.py      iteration 2: order
                                     iteration 3: asset
   ──────────────────              ────────────────────────
   정의에는 "무엇을" 이 없다        런타임에 "무엇을" 이 정해진다


   [dbt]

   모델 파일 (커밋 시점)            실행 시점
   ──────────────────              ────────────────────────
   silver_member.sql                파싱 → DAG 확정  ★
   silver_order.sql                 → 노드 3개, 의존관계 확정
   silver_asset.sql                 → 그대로 실행
   ──────────────────              ────────────────────────
   정의에 "무엇을" 이 전부 있다     런타임에 구조가 안 바뀐다
```

dbt는 **파싱 시점에 정적 DAG를 확정**한다. `ref()` 를 전부 읽어서 노드와 간선을 만들고, 그 다음에야 실행이 시작된다. 그래서 dbt는 실행 전에 "이번에 무엇이 만들어지고, 무엇이 무엇에 의존하는지" 를 전부 안다.

**런타임에 테이블 목록을 조회해서 모델을 동적으로 만드는 건 이 계약을 깨는 일이다.** dbt에 `for_each` 가 없는 건 기능이 빠진 게 아니라, 있으면 dbt가 dbt가 아니게 되기 때문이다. 실제로 dbt-core 쪽 논의에서도 "동적으로 모델을 정의하는 방법은 없다 — 모델은 파일 하나에 하나" 로 정리돼 있고, 대안은 전부 **파일을 미리 생성하는** 방향이다.

### 2) ★ 그래서 무엇을 잃고 무엇을 얻나

| | `for_each_task` | dbt 모델 N개 |
|---|---|---|
| 테이블 추가 | 배열에 한 줄 | 파일 하나 (+ yml 몇 줄) |
| 잡 정의 길이 | 짧다 | 길다 |
| **리니지** | **없다.** 잡 하나가 N개 테이블을 만든다 | 테이블마다 노드. 상류·하류가 보인다 |
| **한 개만 재실행** | 배열을 바꿔서 다시 돌린다 (원본 수정) | `dbt run --select silver_order` |
| **실패한 것만 재실행** | 어느 iteration이 실패했는지 로그에서 찾는다 | `dbt retry` |
| **테이블별 테스트** | 노트북 안에 직접 짜 넣는다 | yml에 선언 |
| **문서** | 별도로 관리 | 모델과 같은 파일에 산다 |
| **의존 순서** | 사람이 잡 순서로 표현 | `ref()` 로 자동 |
| **PR 리뷰** | 배열 한 줄 변경. 무엇이 바뀌는지 안 보인다 | 파일 diff로 로직이 보인다 |
| **일부만 다른 로직** | if/else 분기가 노트북 안에 쌓인다 ⚠️ | 그 모델만 다르게 쓴다 |

마지막 줄이 시간이 지날수록 결정적이다.

```
   for_each 노트북의 수명 주기

   1개월차:  def load(table): ...                    깔끔하다
   3개월차:  if table == "order": 특수 처리
   6개월차:  if table in ("order","asset"): ...
             if table == "member": 컬럼 하나 더
   12개월차: if 문 열두 개.
             어느 테이블이 어떤 경로를 타는지
             코드를 끝까지 읽어야 알 수 있다.       💥
             그리고 아무도 수정하려 하지 않는다.
```

**for_each는 "모든 대상이 똑같다"는 가정 위에 서 있다.** 그 가정은 거의 항상 시간이 지나면서 깨진다. 깨진 뒤에도 구조를 유지하려면 분기를 넣는 수밖에 없고, 분기는 쌓인다.

dbt의 N개 파일은 처음엔 중복처럼 보이지만, **"이 테이블만 다르다"가 생겼을 때 그 파일만 고치면 된다.** 다른 39개는 영향을 받지 않는다. 그리고 diff에 그 사실이 그대로 드러난다.

> **핵심 통찰 — "for_each는 정의를 짧게 만들고, dbt는 정의를 명시적으로 만든다"**
>
> 둘 다 정당한 목표지만 양립하지 않는다. 그리고 **데이터 파이프라인에서는 명시성이 대체로 이긴다.**
>
> 이유는 데이터 파이프라인의 주된 작업이 "새로 만들기"가 아니라 **"틀린 값의 출처 추적하기"** 이기 때문이다. 값이 이상할 때 필요한 건 짧은 정의가 아니라, **이 테이블이 무엇에서 어떤 로직으로 나왔는지**다.
>
> for_each 구조에서는 그 질문에 답하려면 노트북 코드를 읽고 분기를 따라가야 한다. dbt에서는 모델 파일 하나를 열면 끝난다.

### 3) 그렇다고 N개 파일을 손으로 쓰라는 뜻은 아니다

"하나씩 다 만들어야 한다"가 "하나씩 다 타이핑해야 한다"는 아니다. 세 단계로 나눠 접근한다.

**(a) 공통 로직은 macro로 뺀다 → 모델 파일은 몇 줄이 된다**

```sql
-- src/macros/build_silver.sql
{% macro build_silver(source_name, table_name, pk, ts_col) %}

    select
        {{ dbt_utils.star(from=source(source_name, table_name)) }},
        -- 공통으로 붙는 것들
        from_utc_timestamp({{ ts_col }}, 'Asia/Seoul')  as {{ ts_col }}_kst,
        current_timestamp()                              as _loaded_at
    from {{ source(source_name, table_name) }}
    where {{ ts_col }} >= dateadd(day, -1, current_date())

    {% if is_incremental() %}
      and {{ ts_col }} > (select coalesce(max({{ ts_col }}), '1900-01-01') from {{ this }})
    {% endif %}

{% endmacro %}
```

```sql
-- src/models/silver/silver_member.sql   ← 실제 모델 파일은 이게 전부
{{ config(materialized='incremental', unique_key='member_no') }}
{{ build_silver('ods', 'tb_member', 'member_no', 'reg_dtm') }}
```

```sql
-- src/models/silver/silver_order.sql
{{ config(materialized='incremental', unique_key='order_no') }}
{{ build_silver('ods', 'tb_order', 'order_no', 'ord_dtm') }}
```

**중복은 파일 개수에 있는 거지 로직에 있는 게 아니다.** 로직은 매크로 한 곳에 있다. 그리고 "order만 특수 처리" 가 생기면 `silver_order.sql` 만 매크로를 안 쓰고 직접 쓰면 된다 — 나머지는 그대로다.

**(b) 파일 생성 자체는 스크립트로 한다 — 단, 결과물은 커밋한다**

40개 파일을 손으로 만들 필요는 없다. 메타 정보(테이블 목록, PK, 타임스탬프 컬럼)가 이미 어딘가에 있다면 그걸로 파일을 찍어내면 된다.

```python
# tools/gen_silver_models.py — 1회성 생성기. CI에서 돌리지 않는다.
import csv, pathlib

TEMPLATE = """{{{{ config(materialized='incremental', unique_key='{pk}') }}}}
{{{{ build_silver('ods', '{src}', '{pk}', '{ts}') }}}}
"""

out = pathlib.Path("src/models/silver")
for row in csv.DictReader(open("tools/table_catalog.csv")):
    (out / f"silver_{row['name']}.sql").write_text(
        TEMPLATE.format(src=row["source_table"], pk=row["pk"], ts=row["ts_col"])
    )
```

> ⚠️ **핵심은 "생성 시점"이다.** 이 스크립트는 **개발 중에 한 번 돌리고, 생성된 파일을 Git에 커밋**한다. CI에서 매번 돌리면 안 된다.
>
> CI에서 생성하면 결국 for_each와 같은 문제로 돌아간다 — **레포를 봐도 무엇이 만들어지는지 알 수 없다.** 그리고 "이 테이블만 예외" 를 손으로 고치는 순간, 다음 생성에서 덮여 사라진다.
>
> 생성기는 **초기 부트스트랩 도구**지 파이프라인의 일부가 아니다.

**(c) 반복되는 설정은 디렉터리 단위로 준다**

```yaml
# dbt_project.yml
models:
  our_project:
    silver:
      +materialized: incremental
      +incremental_strategy: merge
      +on_schema_change: append_new_columns
      +tags: ['silver', 'daily']
      +full_refresh: false        # ← prod 에서 실수로 날리는 것 방지 (기타 1 참고)
    gold:
      +materialized: table
      +tags: ['gold', 'daily']
```

이러면 개별 모델의 `config()` 블록에서 반복이 사라진다.

### 4) ⚠️ 전환하면서 실제로 달라지는 운영 특성

**(a) 동시성의 주체가 바뀐다**

```
   for_each_task                      dbt
   ────────────────                   ────────────────
   concurrency: 10  ← 잡이 제어        threads: 8       ← dbt 가 제어
   (기본 1, 최대 100)                  (템플릿 기본 4)
   iteration 마다 태스크 실행           SQL warehouse 에 동시 쿼리
```

`threads` 를 올리면 공용 웨어하우스에 그만큼 동시 쿼리가 간다. **for_each의 concurrency 값을 그대로 옮기면 안 된다.** 저쪽은 태스크 슬롯이고 이쪽은 웨어하우스 동시 쿼리다.

**(b) 실패의 모양이 바뀐다**

for_each는 iteration 하나가 실패해도 잡 전체가 실패로 뜨고, 어느 것이 실패했는지 보려면 로그를 뒤져야 한다. dbt는 **부분 실패가 명시적**이다.

```bash
# 실패한 모델과 그 하류만 다시
dbt retry

# 특정 모델과 그 하류 전부
dbt run --select silver_order+

# 실패하면 즉시 중단 (하류가 잘못된 데이터로 도는 걸 막는다)
dbt build --fail-fast
```

특히 `dbt build` 는 `run` + `test` + `seed` + `snapshot` 을 **DAG 순서대로 섞어서** 실행한다. 즉 **어떤 모델의 테스트가 실패하면 그 하류 모델이 실행되지 않는다.** for_each 구조에서는 이런 게 자동으로 되지 않는다.

**(c) 잡 정의는 오히려 짧아진다**

역설적이지만, dbt로 옮기면 **Databricks 잡 정의는 태스크 하나로 줄어든다.** 40개 모델이든 400개든 잡은 `dbt run` 하나다. 복잡도가 잡에서 dbt DAG로 옮겨간 것이고, dbt DAG는 잡 정의보다 훨씬 좋은 표현 수단이다.

### 내가 확인할 것

- [ ] 기존 `for_each_task`의 **입력 배열이 어디서 오는지** — 잡 파라미터 하드코딩? 메타 테이블 조회? 후자면 그 메타 테이블이 곧 모델 생성기의 입력이다.
- [ ] 그 배열의 **테이블 수**. 그리고 그중 **특수 처리(if 분기)를 받는 것이 몇 개**인지. 이게 매크로 하나로 끝날지 아닐지를 정한다.
- [ ] 기존 노트북 안에 **분기 로직이 얼마나 쌓여 있는지.** 여기가 마이그레이션 공수의 실제 크기다.
- [ ] `threads` 를 몇으로 둘지 — 공용 웨어하우스 부하를 보고 정한다.
- [ ] `dbt run` 이 아니라 **`dbt build`** 를 쓸지. 테스트를 DAG에 끼워 넣을 거면 build가 맞다.

## 기타 1. 초기 적재는 신경 쓰지 말고 1일치만

> - dbt로 만들 때 **초기 적재는 신경쓰지 말고 1일치 받아오는 것**으로 한다.
> - 초기 적재는 **이미 만들어져 있는 것에서 `select insert` 하는 게 제일 빠르다.**

이건 실용적으로 정확한 판단이다. 그리고 여기엔 **dbt를 쓸 때만 나타나는 함정**이 하나 숨어 있어서, 그걸 모르면 백필해둔 데이터를 한 번에 날릴 수 있다.

### 1) 왜 백필과 증분을 분리하는 게 옳은가

```
   백필(초기 적재)                    증분(일배치)
   ────────────────                   ────────────────
   1회성                              영구
   대량 (수년치)                       소량 (1일치)
   한 번 맞으면 끝                     매일 맞아야 한다
   성능이 전부                         정확성·재실행 안전성이 전부
   ────────────────                   ────────────────
   → 최적화 대상이 완전히 다르다
```

**하나의 코드로 둘 다 하려고 하면 양쪽 다 어중간해진다.** 백필용으로 짜면 매일 도는 로직이 필요 이상으로 복잡해지고, 증분용으로 짜서 백필을 돌리면 며칠이 걸린다.

그리고 `select insert` 백필이 빠른 이유는 명확하다.

```
   [dbt 로 백필]                       [select insert 백필]

   원천/Mart 재조회                    이미 적재된 테이블에서 읽는다
        │                                   │
   Federation 또는 JDBC                 같은 플랫폼 안
        │                                   │
   네트워크 왕복                        스캔 + 쓰기만
        │                                   │
   Jinja 렌더링, 모델별 순차            단일 SQL 문
        │                                   │
   ▼                                    ▼
   수 시간 ~ 수 일                       수 분 ~ 수십 분
```

원천을 다시 건드리지 않는다는 점도 크다. 운영 중인 원천 DB에 수년치 풀스캔을 거는 건 그 자체로 위험 작업이다.

### 2) ★ 함정 — dbt의 `--full-refresh` 가 백필을 지운다

여기가 오늘 정리 중 가장 위험한 지점이다.

dbt의 incremental 모델은 이렇게 생겼다.

```sql
{{ config(materialized='incremental', unique_key='order_no') }}

select *
from {{ source('ods', 'tb_order') }}
where ord_dtm >= dateadd(day, -1, current_date())    -- ← 1일치만

{% if is_incremental() %}
  and ord_dtm > (select max(ord_dtm) from {{ this }})
{% endif %}
```

`is_incremental()` 은 **테이블이 이미 존재하고, `--full-refresh` 가 아닐 때** 참이다. 그래서 동작은 이렇게 갈린다.

```
   ┌─────────────────────────────────────────────────────────┐
   │ 첫 실행 (테이블 없음)                                   │
   │   is_incremental() = false                              │
   │   → CREATE TABLE AS (WHERE 1일치만 적용)                │
   │   → 테이블에 1일치만 생긴다   ← 의도한 대로             │
   └─────────────────────────────────────────────────────────┘
                            ↓
   ┌─────────────────────────────────────────────────────────┐
   │ select insert 로 3년치 백필                             │
   │   → 테이블에 3년치 + 1일치                              │
   └─────────────────────────────────────────────────────────┘
                            ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 매일 dbt run                                            │
   │   is_incremental() = true → MERGE 로 1일치 추가/갱신    │
   │   → 정상                                                │
   └─────────────────────────────────────────────────────────┘
                            ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 누군가 dbt run --full-refresh                           │
   │   is_incremental() = false                              │
   │   → CREATE OR REPLACE TABLE AS (WHERE 1일치만)          │
   │                                                         │
   │   → 3년치 백필이 사라지고 1일치만 남는다      💥💥💥     │
   │   → 에러도 안 난다. 잡은 성공으로 끝난다.               │
   │   → 발견은 누군가 과거 데이터를 조회할 때.              │
   └─────────────────────────────────────────────────────────┘
```

`--full-refresh` 는 스키마가 바뀌었을 때 흔히 쓰는 명령이다. 실제로 dbt-databricks에서 materialized view나 streaming table의 정의를 바꾸면 `--full-refresh` 를 쓰라는 안내가 나온다. **즉 정상적인 운영 과정에서 자연스럽게 실행될 수 있는 명령이다.**

방어는 세 겹으로 건다.

```yaml
# ① dbt_project.yml — prod 에서 아예 못 하게 막는다
models:
  our_project:
    silver:
      +full_refresh: false      # --full-refresh 를 줘도 무시된다
```

```sql
-- ② 모델 안에서 명시적으로 막는다
{{ config(
     materialized='incremental',
     unique_key='order_no',
     full_refresh=false
) }}
```

```
③ 문서화 — 모델 yml의 description 에 "이 테이블은 외부 백필로 적재된
   과거 데이터를 포함한다. full-refresh 금지." 를 적는다.
   나중에 이 모델을 처음 보는 사람에게 필요한 정보다.
```

> **핵심 통찰 — "dbt 밖에서 채운 데이터는 dbt에게 보이지 않는다"**
>
> dbt는 자기가 만든 테이블을 **자기 모델 정의로 언제든 다시 만들 수 있다**고 전제한다. 그게 dbt의 멱등성 모델이다.
>
> 백필을 dbt 밖에서 하면 그 전제가 깨진다. **테이블의 내용이 모델 정의에서 도출되지 않는 상태**가 되는 것이다. dbt는 이 상태를 알 방법이 없으므로 경고도 못 한다.
>
> 그래서 이 결정 — "백필은 밖에서, 증분만 dbt로" — 은 편의를 위한 지름길이면서 동시에 **dbt의 안전장치 하나를 끄는 것**이다. 끄기로 했으면 대신 방어를 명시적으로 걸어야 한다. `+full_refresh: false` 한 줄이 그 대가다.

### 3) ⚠️ 백필과 증분이 같은 결과를 내는지 확인해야 한다

백필 SQL과 dbt 모델은 서로 다른 코드다. 그러면 경계에서 값이 갈릴 수 있다.

```
        백필 구간              │  증분 구간
   ────────────────────────────┼─────────────────
   select insert 로 채움       │  dbt 가 채움
   컬럼 순서: A B C            │  컬럼 순서: A C B      ⚠️
   타임스탬프: 원본 그대로     │  타임스탬프: KST 변환   ⚠️
   NULL 처리: 원본 그대로      │  NULL 처리: coalesce    ⚠️
   ────────────────────────────┴─────────────────
                       ▲
                이 경계에서만 값이 튄다.
                그리고 경계는 딱 하루치라 눈에 잘 안 띈다.
```

가장 확실한 방법은 **백필 SQL을 dbt 모델의 컴파일 결과에서 뽑는 것**이다.

```bash
# 모델을 컴파일하면 실제 실행될 SQL 이 나온다
dbt compile --select silver_order
cat target/compiled/our_project/models/silver/silver_order.sql
```

이 SQL에서 `where ord_dtm >= dateadd(day,-1,current_date())` 부분만 전체 기간으로 바꾸면, 그게 백필 SQL이다. 손으로 새로 쓰는 것보다 훨씬 안전하다.

그리고 백필 직후에 한 번 검증한다.

```sql
-- 컬럼 스키마가 같은가
DESCRIBE TABLE catalog.silver.silver_order;

-- 경계 며칠을 겹쳐 넣고 중복이 없는지
SELECT order_no, COUNT(*) c
FROM catalog.silver.silver_order
GROUP BY order_no HAVING c > 1;
```

`unique_key` 를 지정한 incremental 모델은 MERGE를 쓰므로 겹치는 구간을 넣어도 중복이 안 생긴다. **백필 범위를 dbt 증분 시작 시점과 하루 이틀 겹치게 잡는 것**이 오히려 안전하다. 빈틈이 생기는 것보다 낫다.

## 기타 2. 기존 ODS를 볼 수 있게 조치해두었다

> **기존 ODS와 dbt로 만든 silver를 비교하면서 분석할 수 있도록, 기존 ODS를 볼 수 있게 조치해놨다.**

이 한 줄이 프로젝트 성패에 미치는 영향이 생각보다 크다. **마이그레이션에서 정답지가 있느냐 없느냐의 차이**이기 때문이다.

```
   [정답지가 없을 때]
   새 파이프라인 결과: 회원 수 1,203,411
        → 이게 맞나?
        → 확인하려면 업무 담당자에게 물어본다
        → "대략 120만쯤 됩니다"
        → 411명 차이는? 알 수 없다.
        → 결국 "그럴듯하니까 맞겠지" 로 넘어간다.        💥

   [정답지가 있을 때]
   기존:   1,203,411
   신규:   1,203,408
        → 3건 차이. 어느 3건인지 SQL 한 줄로 나온다.
        → 원인을 특정할 수 있다.                        ✅
```

### 1) 비교는 네 단계로 하고, 각 단계가 잡는 버그가 다르다

| 단계 | 무엇을 보나 | 여기서 잡히는 버그 |
|---|---|---|
| ① 행 수 | `COUNT(*)` | 필터 조건 오류, 조인으로 인한 행 증식, 날짜 범위 어긋남 |
| ② 키 집합 | PK의 차집합 (양방향) | **어떤 레코드가** 빠졌는지/늘었는지 |
| ③ 컬럼 값 | PK로 조인 후 컬럼별 비교 | 타입 변환, 타임존, 반올림, NULL 처리 |
| ④ 집계 값 | 업무 지표의 합계 | 위에서 다 통과했는데도 지표가 다른 경우 (= 로직 차이) |

**①만 보고 넘어가면 안 된다.** 행 수가 같아도 내용이 다를 수 있고, 실제로 그런 경우가 더 위험하다.

### 2) 실제로 쓰는 SQL

**① 행 수와 ② 키 집합**

```sql
-- 양방향 차집합. 한 방향만 보면 절반을 놓친다.
SELECT '기존에만 있음' AS side, member_no FROM legacy_ods.tb_member
EXCEPT
SELECT '기존에만 있음',        member_no FROM catalog.silver.silver_member

UNION ALL

SELECT '신규에만 있음',        member_no FROM catalog.silver.silver_member
EXCEPT
SELECT '신규에만 있음',        member_no FROM legacy_ods.tb_member;
```

**③ 컬럼별 값 비교**

```sql
WITH j AS (
  SELECT
    l.member_no,
    l.member_nm  AS l_nm,  n.member_nm  AS n_nm,
    l.grade_cd   AS l_gr,  n.grade_cd   AS n_gr,
    l.reg_dtm    AS l_dt,  n.reg_dtm    AS n_dt
  FROM legacy_ods.tb_member l
  JOIN catalog.silver.silver_member n USING (member_no)
)
SELECT
  COUNT(*)                                                          AS total,
  SUM(CASE WHEN l_nm IS DISTINCT FROM n_nm THEN 1 ELSE 0 END)       AS diff_nm,
  SUM(CASE WHEN l_gr IS DISTINCT FROM n_gr THEN 1 ELSE 0 END)       AS diff_gr,
  SUM(CASE WHEN l_dt IS DISTINCT FROM n_dt THEN 1 ELSE 0 END)       AS diff_dt
FROM j;
```

`IS DISTINCT FROM` 을 쓰는 이유는 **`=` 는 NULL끼리 비교하면 NULL을 내기 때문**이다. `NULL = NULL` 이 참이 아니므로, 양쪽 다 NULL인 정상 케이스가 "다름"으로도 "같음"으로도 집계되지 않고 조용히 빠진다.

**패키지를 쓰면 이 전부가 매크로 한 줄**

`dbt-audit-helper` 는 이런 비교를 위해 만들어진 dbt Labs 패키지다.

```sql
-- src/analyses/audit_silver_member.sql
{{ audit_helper.compare_relations(
     a_relation = source('legacy_ods', 'tb_member'),
     b_relation = ref('silver_member'),
     primary_key = 'member_no'
) }}
```

행 단위·컬럼 단위 비교를 해서 일치율(%)과 어느 컬럼이 얼마나 다른지를 돌려준다. `compare_column_values`, `compare_queries` 같은 매크로도 있다.

> ⚠️ **폐쇄망이면 이 패키지도 `dbt deps` 대상이다.** 내부망에서 쓰려면 벤더링하거나 사내 git에 미러링해야 한다(→ Q1). 안 되면 위의 raw SQL을 매크로로 직접 만들어 쓰는 것도 충분하다.

### 3) ⚠️ 비교 전에 반드시 정규화해야 하는 것들

비교에서 나오는 "차이"의 상당수는 진짜 버그가 아니라 **표현 차이**다. 이걸 걸러내지 않으면 노이즈에 파묻혀서 진짜 차이를 못 본다.

| 정규화 대상 | 예 | 처리 |
|---|---|---|
| 타임존 | KST vs UTC | 한쪽으로 통일하고 비교 |
| 소수 스케일 | `10.00` vs `10.000` | `CAST(x AS DECIMAL(18,4))` |
| 후행 공백 | `'ABC '` vs `'ABC'` | `TRIM()` |
| NULL vs 빈 문자열 | `NULL` vs `''` | `NULLIF(x, '')` |
| 대소문자 | `'kr'` vs `'KR'` | `UPPER()` |
| 날짜 타입 | `DATE` vs `TIMESTAMP` | `CAST(x AS DATE)` |

그리고 하나 더 — **시점 문제**다.

```
   기존 파이프라인:  02:00 실행 → 그 시점의 원천 스냅샷
   새 파이프라인:    05:00 실행 → 그 시점의 원천 스냅샷
                                    ▲
              그 사이 3시간에 원천이 바뀌었으면
              두 결과는 당연히 다르다. 버그가 아니다.
```

그래서 비교는 반드시 **기준일(파티션)을 고정해서** 한다. 이미 마감된 과거 날짜를 대상으로 비교해야 원천 변동이 개입하지 않는다.

> **핵심 통찰 — "기존 시스템을 볼 수 있게 해둔 것은 편의가 아니라 검증 인프라다"**
>
> 마이그레이션 프로젝트에서 가장 비싼 순간은 **"값이 다른데 어느 쪽이 맞는지 모를 때"** 다. 이때는 결국 업무 담당자를 붙잡고 원천부터 하나하나 따라가는 수밖에 없고, 여기서 며칠이 날아간다.
>
> 두 결과를 **같은 SQL 엔진 안에서 조인해서 비교할 수 있다**는 건, 이 며칠짜리 작업을 쿼리 한 번으로 바꾼다는 뜻이다.
>
> 그래서 이건 개발 편의 조치가 아니라 **프로젝트의 검증 방법론 자체**다. 그리고 이 접근이 가능한 동안에 최대한 많이 비교해두는 게 맞다 — 기존 시스템은 언젠가 내려간다. 내려간 뒤에는 정답지가 없다.

## 기타 3. VS Code 확장의 Remote Folder Sync

> - VS Code의 Databricks 확장 프로그램으로 **`Remote Folder` 에서 Sync**할 수 있다. (실시간)
> - **매번 validate, deploy하지 않아도 되는 기능.**

맞다. 다만 "매번 deploy 안 해도 된다"는 말에는 **범위 조건**이 붙는다. 그 범위를 정확히 알아야, 어느 날 "고쳤는데 왜 반영이 안 되지"로 한 시간을 쓰지 않는다.

### 1) 이게 정확히 무엇인가

확장의 Configuration 뷰에 있는 `Remote Folder` 옆 동기화 아이콘을 누르면 시작된다. 동작은 이렇다.

```
   로컬 VS Code 프로젝트          Databricks 워크스페이스 폴더
   ─────────────────────          ────────────────────────────
   src/models/silver_order.sql
        │  파일 저장
        │
        ▼  자동 감지
   ═══════════════════════════▶  /Workspace/.bundle/.../files/
        단방향                          src/models/silver_order.sql
        (로컬 → 원격만)  ★
```

CLI로는 `databricks sync --watch` 에 해당하고, DAB 문맥에서는 `databricks bundle sync --watch` 다. 확장은 번들 설정의 `workspace.file_path` 를 보고 대상 폴더를 정한다.

**중요한 성질 두 가지가 문서에 명시돼 있다.**

1. **단방향이다.** 로컬 → 원격만 간다. 원격에서 바뀐 건 로컬로 안 온다.
2. **확장이 만든 워크스페이스 디렉터리만 쓸 수 있다.** 기존에 있던 임의의 디렉터리를 대상으로 지정할 수 없다.

### 2) ★ 무엇을 대신해주고, 무엇을 대신해주지 않나

이게 핵심이다.

| 내가 바꾼 것 | Sync로 반영되나 | 이유 |
|---|---|---|
| dbt 모델 SQL | ✅ | 파일이다 |
| 노트북/Python 코드 | ✅ | 파일이다 |
| 매크로, 시드 파일 | ✅ | 파일이다 |
| `dbt_project.yml` | ✅ | 파일이다 |
| **잡 정의(`resources/*.yml`)** | ❌ | **워크스페이스의 잡 객체를 바꿔야 한다** |
| **스케줄 변경** | ❌ | 위와 같음 |
| **클러스터 스펙 / 환경 의존성** | ❌ | 위와 같음 |
| **잡 파라미터, 태스크 추가** | ❌ | 위와 같음 |
| **`targets` / 변수 변경** | ❌ | 배포 시점에 해석된다 |

```
   bundle deploy 가 하는 일 = 두 가지

   ┌───────────────────────────┐   ┌───────────────────────────┐
   │ ① 파일을 워크스페이스로  │   │ ② YAML 을 REST API 호출로 │
   │    올린다                 │   │    바꿔서 잡/파이프라인/  │
   │                           │   │    권한 객체를 만든다     │
   └───────────────────────────┘   └───────────────────────────┘
              ▲                                 ▲
              │                                 │
        Sync 가 대신해준다               Sync 는 못 한다  ★
        (그것도 실시간으로)              deploy 가 필요하다
```

> **핵심 통찰 — "Sync는 배포를 대체하는 게 아니라, 배포에서 파일 전송 부분만 실시간으로 떼어낸 것이다"**
>
> DAB의 본질은 **설정의 코드화**다. `resources/*.yml` 이 워크스페이스의 잡 객체가 되는 게 배포의 핵심이고, 그건 REST API 호출이라 파일 복사로는 대체되지 않는다.
>
> 그래서 실무 규칙은 이렇게 정리된다.
> - **코드만 고쳤다 → Sync로 충분.** 즉시 반영.
> - **YAML(리소스 정의)을 고쳤다 → `bundle deploy` 필요.**
>
> 그리고 헷갈릴 때의 판단 기준은 **"내가 바꾼 게 워크스페이스 UI에서 보이는 설정인가"** 다. 잡 화면에서 보이는 것(스케줄, 클러스터, 태스크 구성)은 전부 deploy 대상이다.

### 3) ⚠️ 단방향이라서 생기는 사고

```
   [흔한 시나리오]

   1. Sync 켜둠
   2. 워크스페이스 UI에서 노트북을 열어 디버깅하다가 코드를 고침
   3. 잘 되네! 하고 만족
   4. 로컬에서 다른 파일 하나 저장
   5. → Sync 가 로컬 상태를 밀어넣으면서 2번의 수정이 사라짐   💥
```

단방향 동기화는 **로컬이 항상 진실**이라는 전제 위에서 동작한다. 그 전제를 깨는 순간(=워크스페이스에서 편집) 작업물이 조용히 사라진다.

**규칙: Sync를 켠 동안에는 워크스페이스 UI에서 편집하지 않는다.** 디버깅으로 뭔가를 고쳤으면, 그 변경을 로컬에 옮겨 적은 다음에 계속한다.

### 4) dbt 개발에서 이게 실제로 얼마나 유용한가

솔직하게 말하면, **dbt 개발에서는 Sync보다 로컬 실행이 더 빠르다.**

```
   [경로 A] 로컬에서 직접 실행 — 가장 빠르다
   VS Code
     │  dbt run --select silver_order
     ▼
   로컬 dbt 프로세스
     │  ~/.dbt/profiles.yml 의 http_path 로 접속
     ▼
   SQL Warehouse (원격)
     → 잡을 거치지 않는다. 몇 초.


   [경로 B] Sync + 워크스페이스에서 실행
   VS Code → Sync → 워크스페이스 파일 → 잡 실행
     → 잡 기동 시간이 붙는다.


   [경로 C] bundle deploy + 잡 실행
   VS Code → deploy → 잡 실행
     → 가장 느리다. 대신 실제 배포 형태와 동일하다.
```

`dbt-sql` 템플릿이 `profile_template.yml` 을 따로 두는 이유가 이거다 — **로컬 개발은 `~/.dbt/profiles.yml` 로 직접 웨어하우스에 붙어서 하고, 배포된 잡만 `dbt_profiles/profiles.yml` 을 쓴다.** 두 프로파일이 나뉘어 있는 게 실수가 아니라 의도다.

그러면 Sync는 언제 쓰나. **"잡 안에서만 재현되는 문제"** 를 디버깅할 때다.

- 서비스 프린시펄 권한으로만 나는 오류
- 잡 환경의 패키지 버전이 로컬과 달라서 나는 오류
- `env_var()` 로 주입되는 값이 잡에서만 존재할 때
- 잡 컴퓨트의 네트워크 경계에서만 나는 접속 오류

이런 건 로컬에서 재현이 안 된다. 그때 `bundle deploy` 를 매번 돌리는 대신 Sync로 코드만 밀어 넣으면서 반복하면 사이클이 훨씬 짧아진다.

## 오늘의 정리

### 다섯 질문은 두 개의 축 위에 있었다

오늘 물은 것들은 표면적으로는 제각각인데, 정리하고 보니 축이 둘이었다.

```
   [축 1] 하나의 정의를 여러 환경에 어떻게 흘려보내는가

   Q1 내부망 배포     →  하나의 레포 / 두 개의 망 / targets 로 흡수
   Q2 warehouse 선택  →  하나의 http_path / dev·prod / 갈라야 한다
   Q3 데이터 모델링   →  하나의 논리 모델 / 두 개의 엔진 / 물리는 못 옮긴다
   기타1 초기 적재    →  하나의 테이블 / 백필과 증분 / 다른 코드
   기타3 Sync         →  하나의 코드 / 로컬과 원격 / 단방향

   → 공통 질문: "무엇을 공유하고, 무엇을 환경별로 가르는가"


   [축 2] dbt 의 경계는 어디인가

   Q4 MTV            →  데이터가 아니라 정의 → dbt 밖
   Q5 for_each       →  런타임 동적 구조    → dbt 밖 (= 파일로 펼친다)
   기타1 백필         →  1회성 대량 적재     → dbt 밖
   기타2 기존 ODS 비교 →  검증              → dbt 안(테스트)으로 넣을 수 있다

   → 공통 질문: "매일 실행되며 데이터를 만드는가?"
      예 → dbt.  아니오 → 다른 것.
```

### 항목별 한 줄

| # | 들은 답 | 내가 덧붙여야 할 조건 |
|---|---|---|
| Q1 | 하나의 레포, runner가 양쪽에 배포 | Runner가 망별로 나뉘어 있는지 확인. 실제 난관은 배포가 아니라 **의존성**(이미지·PyPI·dbt 패키지) |
| Q2 | Serverless Shared Warehouse | `http_path` 는 **dev·prod에 같은 값이 박히고, `databricks.yml` 이 아니라 `dbt_profiles/profiles.yml` 에 있다.** 내부망은 serverless가 없을 수 있다 |
| Q3 | 원칙은 그대로, 필요시 협의 | "그대로"는 **논리 모델**까지다. 물리 모델(정렬·분산)은 번역 불가 |
| Q4 | MTV는 dbt로 안 됨, 별도 job | **dbt-databricks 1.12.0(2026-05-18)부터는 된다.** 우리 고정 버전 확인 필요. 다만 **별도로 두는 게 설계상 더 낫다** |
| Q5 | 하나씩 다 dbt로 | 맞다. **손으로 쓰라는 뜻은 아니다** — 매크로 + 1회성 생성기 |
| 기타1 | 초기 적재는 select insert | **`--full-refresh` 가 백필을 지운다.** `+full_refresh: false` 를 걸어야 한다 |
| 기타2 | 기존 ODS 조회 가능 | 비교는 **4단계**로. 비교 전 **정규화**와 **기준일 고정** 필수 |
| 기타3 | Sync로 실시간 반영 | **파일만** 간다. YAML(리소스 정의)은 여전히 `bundle deploy` |

### 질문하면서 배운 것 (내용 말고 방법)

- **"안 된다"는 답은 조건과 함께 적어야 한다.** Q4가 그 사례였다. 조건 없이 적으면 반년 뒤에 아무도 다시 확인하지 않는 잘못된 전제가 된다.
- **프롬프트 안내 문구를 믿지 말고 생성물을 열어봐야 한다.** Q2에서 `bundle init` 이 "databricks.yml에서 나중에 바꿀 수 있다"고 안내했지만 실제 값은 다른 파일에 있었다. 도구의 안내문은 도구 구조 변경을 항상 따라가지는 않는다.
- **"하나로 된다"는 답을 들으면 "그 하나가 어떻게 둘에 도달하나"를 되물어야 한다.** Q1이 그랬다. 레포가 하나라는 사실은 두 망이 같은 상태라는 걸 보장하지 않는다.

> **토론거리**
>
> 1. **내부망과 외부망의 배포 시점을 일치시켜야 하는가?** 항상 같은 커밋이 올라가 있어야 한다면 자동화해야 하고, 그러면 내부망에 검증되지 않은 코드가 바로 간다. 반대로 수동 승인을 두면 두 망이 갈린다. 어느 쪽 위험이 더 큰가 — 그리고 그 답은 이 시스템이 무엇을 하느냐에 따라 달라지는가?
>
> 2. **Metric View를 dbt 안에 넣을 것인가 밖에 둘 것인가.** 어댑터 버전이 올라가면 기술적으로는 가능해진다. 그때도 밖에 두는 게 맞을까? "라이프사이클이 다르다"는 이유는 충분한가, 아니면 **모든 정의가 한 도구의 DAG 안에 있는 것**의 가치가 더 큰가?
>
> 3. **for_each 구조를 N개 모델로 펼치는 결정을, 테이블이 200개일 때도 유지할 것인가.** 40개면 명시성의 이득이 명확하지만, 200개 파일이 되면 리뷰도 탐색도 부담이 된다. 어느 규모에서 판단이 뒤집히나 — 그리고 그때의 대안은 무엇인가?
>
> 4. **기존 ODS와의 비교를 언제까지 유지할 것인가.** 기존 시스템은 결국 내려간다. 내려가기 전에 "값이 같다"를 어느 수준까지 증명해둬야 안심하고 내릴 수 있는가? 그 기준을 누가 정하나?
