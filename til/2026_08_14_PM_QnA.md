## Q1. `targets` 중 `prod`만 내부망인데, 외부망 `prod-public`은 어떤 역할인가요?

`databricks.yml` 을 열어보니 타깃이 다섯 개였다. `dev-local`, `dev`, `qa` 는 외부망 workspace URL을 `host` 로 쓰는데, `prod` 만 내부망 URL이었다. 그리고 외부망 쪽에 `prod-public` 이 따로 있었다.

배포 파이프라인을 이해하려면 이 다섯 개가 무엇을 기준으로 갈린 건지부터 알아야 했다. 이름만 보면 `dev → qa → prod` 라는 익숙한 한 줄로 보이는데, 실제로는 그렇지 않았다.

### 들은 답

> - **데이터는 외부망에 없고 내부망에 있다.** 그래서 `prod` 는 내부망이다.
> - 외부망 `prod-public` 이 있는 이유는 **외부망에서도 AI agent를 사용해야 하기 때문**이다.

맞는 답이고, 두 문장 모두 프로젝트의 구조를 정확히 요약한다. 다만 **"왜 하필 AI만 밖에 있어야 하나"** 가 빠져 있다. 그리고 그 이유를 알아야 `prod-public` 에 무엇을 배포하고 무엇을 배포하지 말아야 하는지가 정해진다.

### 1) 기초 — `targets` 는 "환경"이 아니라 "좌표"다

DAB(Databricks Asset Bundles)에서 `targets` 를 처음 보면 대개 `dev / staging / prod` 라는 **수명주기 단계**로 읽는다. 그런데 DAB 문법상 타깃이 실제로 담는 건 그게 아니다.

```
   하나의 target 이 정하는 것

   ┌──────────────────────────────────────────────┐
   │  workspace.host      어느 워크스페이스인가   │ ← 물리적 위치
   │  workspace.root_path 어디에 올리는가         │
   │  mode                development / production│ ← 동작 규칙
   │  run_as              누구 권한으로 도는가    │
   │  variables           값 오버라이드           │
   │  resources.*         리소스 부분 오버라이드  │
   └──────────────────────────────────────────────┘
```

즉 타깃은 **"이 번들을 어디에, 어떤 값으로 펼칠 것인가"** 를 지정하는 좌표지, 수명주기 단계 그 자체가 아니다. 보통은 좌표축이 하나(수명주기)라서 이름과 의미가 일치하는데, 우리 프로젝트는 **축이 두 개**다.

```
                    │  외부망(public)        │  내부망(internal)
   ─────────────────┼────────────────────────┼──────────────────
   개발             │  dev-local, dev        │  (없음)
   검증             │  qa                    │  (없음)
   운영             │  prod-public      ★    │  prod        ★
   ─────────────────┴────────────────────────┴──────────────────

   → dev / qa / prod 는 "수명주기" 축
   → public / internal 은 "망" 축
   → prod 와 prod-public 은 단계가 다른 게 아니라 ★ 망이 다른 것이다
```

이걸 알고 나면 이름의 어색함이 설명된다. `prod-public` 은 `prod` 의 앞 단계도 뒷 단계도 아니다. **같은 등급의 운영 환경이 두 망에 각각 하나씩 있는 것**이다. 그리고 이 둘은 하는 일이 다르다.

> ⚠️ **이름이 두 축을 섞고 있으면, 신규 인원은 반드시 한 번 잘못 이해한다.**
>
> `dev-local` / `dev` / `qa` / `prod` 만 보면 `prod` 가 마지막 단계로 보이고, `prod-public` 은 "prod의 공개 버전" 처럼 읽힌다. 실제로는 반대에 가깝다 — 데이터가 있는 진짜 운영은 `prod`(내부망)이고, `prod-public` 은 **데이터가 없는 쪽의 운영**이다.
>
> 축이 둘이면 이름도 둘을 드러내는 게 안전하다. `prod-internal` / `prod-public` 처럼 양쪽에 망을 붙이면, `prod` 라는 이름이 암묵적으로 "기본 = 내부망" 을 뜻하는 상태가 사라진다. 지금 당장 바꾸자는 뜻은 아니고, **`prod` 에 망 표시가 없다는 사실 자체가 사고 지점**이라는 걸 알고 있어야 한다는 뜻이다.

### 2) 왜 데이터가 내부망에 있고, 그게 왜 배포 구조를 결정하는가

"데이터가 내부망에 있다"는 한 문장이 나머지를 거의 다 결정한다. 이유는 **데이터 중력(data gravity)** 이다.

```
   데이터를 컴퓨트로 옮기기            컴퓨트를 데이터로 옮기기
   ────────────────────────            ────────────────────────
   TB 단위 전송                        코드 몇 MB 배포
   망 경계를 데이터가 통과             망 경계를 코드가 통과
   전송 중 암호화·감사 필요            배포 이력만 관리
   원본과 사본이 둘 다 존재  💥        원본은 하나
   → 규제 대상이 두 곳이 된다          → 규제 대상은 한 곳
```

개인정보나 규제 대상 데이터가 있는 시스템에서 **사본이 하나 더 생긴다**는 건 기술 문제가 아니라 컴플라이언스 문제다. 사본이 생기는 순간 그 사본의 접근 통제·보관 기간·파기 절차를 전부 따로 증명해야 한다.

그래서 원칙은 항상 같다 — **데이터는 안 움직이고, 코드가 움직인다.** 운영 파이프라인이 내부망에 있는 건 선택이 아니라 이 원칙의 결과다.

> **핵심 통찰 — "데이터가 있는 곳이 운영이다. 나머지 환경은 전부 그 사실을 중심으로 배치된다"**
>
> 망분리 프로젝트에서 환경 구조를 그릴 때 첫 질문은 "몇 단계로 나눌까"가 아니라 **"진짜 데이터는 어디에 있나"** 다. 그 자리가 `prod` 이고, 나머지는 그 주위에 배치되는 것이다.
>
> 그래서 개발 환경이 외부망에 있다는 건 **"운영 데이터로 개발할 수 없다"** 는 제약을 이미 받아들였다는 뜻이기도 하다. 외부망 `dev`/`qa` 의 데이터는 실제 데이터가 아니거나(합성·마스킹), 일부 비민감 서브셋이다. 이 제약은 개발 편의의 문제가 아니라 **테스트가 잡아낼 수 있는 버그의 종류를 제한**한다 — 실제 데이터의 분포·이상치·인코딩 문제는 내부망에 가서야 처음 만난다.

### 3) ★ 그럼 데이터가 없는 외부망 운영은 무엇을 하나 — AI가 서버리스이기 때문이다

여기가 오늘 답에서 가장 중요한 부분이고, 이유를 한 겹 더 파야 한다.

"외부망에서도 AI agent를 써야 해서" 라는 답은 **"AI를 쓰고 싶으니까 밖에 둔다"** 가 아니다. 순서가 반대다. **Databricks의 AI 기능들이 구조적으로 서버리스여서, 폐쇄망에 있을 수 없거나 있기 매우 어렵다.**

| 기능 | 컴퓨트 형태 | 폐쇄망에서 |
|---|---|---|
| AI/BI Genie | **Pro 또는 Serverless SQL warehouse 필요** | pro가 있으면 가능성은 있으나 serverless 권장 |
| Mosaic AI Model Serving | **완전 서버리스** (Databricks 계정에서 실행) | 리전·네트워크 구성에 따라 아예 불가 |
| Vector Search | 서버리스 | 위와 같음 |
| Foundation Model API | 서버리스 + 외부 모델 호출 | 위와 같음 |

서버리스가 왜 문제인지는 컴퓨트가 어디서 도는지를 보면 바로 나온다.

```
   [classic / pro warehouse]              [serverless / model serving]

   ┌────────────────────┐                 ┌──────────────────────┐
   │ Databricks 계정    │                 │ Databricks 계정      │
   │  - UI, 스케줄러    │                 │  - UI, 스케줄러      │
   │  - Unity Catalog   │                 │  - Unity Catalog     │
   └────────────────────┘                 │  - ★ 실제 실행       │
            │                             └──────────────────────┘
            ▼                                      │
   ┌────────────────────┐                          ▼
   │ 고객사 계정 VPC    │                 ┌──────────────────────┐
   │  - ★ 실제 실행     │                 │ 고객사 계정 스토리지 │
   │  - 데이터          │                 │  - 데이터            │
   └────────────────────┘                 └──────────────────────┘

   실행 주체가 경계 안에 있다              실행 주체가 경계 밖에 있다
                                          → 망분리 심의에서 걸린다
```

**내부망의 존재 이유가 "경계 밖에서 실행되는 것을 허용하지 않는다" 인데, 서버리스는 정의상 경계 밖에서 실행된다.** 그래서 AI 기능을 내부망에 넣으려면 망분리 정책 자체를 손대야 하고, 그건 보통 협상 대상이 아니다.

결론적으로 `prod-public` 은 **"AI를 위해 만든 환경"** 이 아니라, **"서버리스가 필요한 것들이 갈 수 있는 유일한 자리"** 다.

> **핵심 통찰 — "망분리 환경에서 아키텍처를 가르는 기준은 기능이 아니라 컴퓨트의 위치다"**
>
> "이 기능을 내부망에서 쓸 수 있나"를 판단할 때 기능 이름으로는 답이 안 나온다. 물어야 할 건 하나다 — **"이게 실행될 때 코드는 어느 계정의 어느 네트워크에서 도나?"**
>
> 우리 VPC 안이면 대체로 된다. Databricks 계정에서 돌면 대체로 안 되거나, 별도 네트워크 구성(PrivateLink, NCC)이 선행되어야 한다.
>
> 이 기준 하나로 SQL warehouse 타입 선택, Model Serving 가능 여부, Genie 배치, dbt Python 모델의 컴퓨트 선택(→ Q3)까지 전부 같은 방식으로 판단할 수 있다. 기능 목록을 외우는 것보다 이 질문 하나를 갖고 있는 게 낫다.

### 4) ⚠️ 그러면 외부망 AI agent는 무슨 데이터를 보나 — 여기가 진짜 확인할 지점이다

`prod-public` 에 AI agent가 있다는 건 좋다. 그런데 **AI agent가 답을 하려면 데이터가 있어야 한다.** 데이터는 내부망에 있다고 했다. 이 둘이 어떻게 만나는지가 설계상 가장 중요한 미확인 사항이다. 가능한 형태는 셋이고, 각각 함의가 완전히 다르다.

```
   [형태 A] 메타데이터만 본다
        외부망에 스키마·테이블 정의·설명만 있고 실제 행은 없다.
        AI agent는 "SQL을 만들어주는 것"까지만 한다.
        → 실행은 사람이 내부망에서.
        → 가장 안전하지만, agent의 유용성은 제한적이다.

   [형태 B] 비민감 서브셋을 외부망에 복제한다
        마스킹·집계된 데이터만 외부망으로 내보낸다.
        → agent가 실제로 답을 낼 수 있다.
        → ⚠️ "무엇이 비민감인가"를 정의하고 유지하는 게 프로젝트가 된다.
          그리고 집계값도 조합하면 재식별이 되는 경우가 있다.

   [형태 C] 외부망에서 내부망 데이터를 참조한다
        Delta Sharing / Lakehouse Federation 등.
        → ⚠️ 이건 망 경계를 데이터가 통과한다는 뜻이다.
          대부분의 망분리 정책에서 가장 먼저 막히는 형태다.
```

우리가 어느 쪽인지에 따라 `prod-public` 타깃에 배포해야 할 리소스가 완전히 달라진다. 형태 A면 dbt 파이프라인을 배포할 이유가 아예 없고, 형태 B면 **마스킹·서브셋 추출 파이프라인이라는 별도 잡**이 있어야 한다.

### 5) 하나의 번들을 두 망에 배포할 때의 실무 함정

`include: resources/*.yml` 로 리소스를 한 벌만 두고 타깃으로 오버라이드하는 게 DAB의 기본 형태다. 그런데 이 구조는 **"모든 타깃에 모든 리소스가 배포된다"** 를 전제한다.

```
   resources/
   ├── ingest_job.yml        내부망에만 필요 (원천이 내부망)
   ├── transform_job.yml     내부망에만 필요
   └── agent_endpoint.yml    외부망에만 필요 (서버리스)

   그냥 배포하면:
     prod(내부망)     → agent_endpoint 도 배포 시도 → 서버리스 없어서 실패 💥
     prod-public(외부) → ingest_job 도 배포됨 → 매일 원천 없이 실행되어 실패 💥
```

DAB에는 타깃에서 리소스를 **깔끔하게 제거하는 문법이 없다시피 하다.** 그래서 실무 대응은 셋 중 하나가 된다.

```yaml
# 대응 1) 타깃별로 스케줄만 꺼둔다 — 배포는 되지만 돌지 않는다
targets:
  prod-public:
    resources:
      jobs:
        ingest_job:
          schedule:
            pause_status: PAUSED     # 객체는 존재, 실행은 안 함

# 대응 2) include 를 타깃과 무관한 공통분과 망 전용으로 나눈다
#         (번들을 둘로 쪼개는 것에 가깝다)

# 대응 3) 애초에 번들을 둘로 분리한다
#         파이프라인 번들 / AI 서빙 번들
```

대응 1이 가장 간단하지만 **"쓰지 않는 잡 객체가 워크스페이스에 남는다"** 는 부작용이 있다. 운영 인계 시점에 "이건 왜 있고 왜 꺼져 있냐"는 질문을 반드시 받는다. 문서에 미리 적어두는 게 낫다.

> **핵심 통찰 — "번들을 하나로 유지하는 이득과, 타깃마다 필요한 리소스가 다르다는 현실은 정면으로 충돌한다"**
>
> DAB의 매력은 **정의를 한 벌만 두는 것**이다. 그런데 환경 축이 두 개가 되는 순간(수명주기 × 망), "모든 환경에 모든 것이 필요하다"는 전제가 깨진다.
>
> 판단 기준은 **오버라이드로 흡수 가능한 차이인가**다. 호스트·카탈로그·웨어하우스 ID처럼 **값만 다른 것**은 타깃 변수로 충분하다. 반면 **리소스의 존재 여부 자체가 다른 것**은 값이 아니라 구조의 차이라, 오버라이드로 밀어붙이면 `pause_status` 같은 우회가 쌓인다.
>
> 우회가 세 개를 넘어가면 번들을 쪼개는 게 맞다. "하나의 레포"와 "하나의 번들"은 별개다 — 레포는 하나여도 번들은 둘일 수 있다.

### 내가 확인할 것

- [ ] `prod-public` 에 **실제로 무엇이 배포되고 있나.** dbt 파이프라인까지 가나, 아니면 서빙 엔드포인트만 가나.
- [ ] 외부망 AI agent가 **어떤 데이터를 보나** — 형태 A/B/C 중 무엇인가. B라면 마스킹·서브셋 파이프라인이 어디에 정의돼 있나.
- [ ] `prod-public` 에서 **자동 배포인가**, 그리고 내부망 `prod` 와 **같은 커밋을 유지해야 하는 관계인가**. 두 운영 환경이 서로 다른 커밋일 때 문제가 되는 리소스가 있는지.
- [ ] `dev-local` 과 `dev` 의 차이 — 호스트가 같다면 `root_path` / 카탈로그 / 개인 스키마로 갈리는 구조일 텐데, 정확히 무엇이 다른지.
- [ ] 내부망 `prod` 에서 **serverless SQL warehouse가 존재하는가.** 없으면 dbt 잡의 컴퓨트 지정이 타깃별로 갈려야 한다.
- [ ] 타깃 이름에 망 표시가 없는 것(`prod`)이 실제로 사고를 낸 적이 있는지, 팀 내 합의된 읽는 법이 있는지.

## Q2. dbt 리니지와 Unity Catalog 리니지는 역할이 겹치나요?

dbt를 도입하면 `dbt docs` 로 리니지 그래프가 나온다. 그런데 Unity Catalog에도 리니지 화면이 있다. 둘 다 유지하는 게 중복 아닌가 싶었다.

### 들은 답

> - **결론은 같이 써야 한다.**
> - **Unity Catalog**: 단점은 전체가 한 번에 안 보인다. 장점은 **bronze 앞, gold 뒤까지 전부 보인다.**
> - **dbt**: 단점은 bronze 앞·gold 뒤가 안 보인다. 장점은 **전체를 한 눈에 볼 수 있다.** 개발 관점에서 보기 좋다.

이 답은 관찰로서 정확하다. 실제로 두 화면을 열어보면 딱 그렇게 느껴진다. 여기에 **"왜 그렇게 되는가"** 를 붙이면, 앞으로 새로운 상황에서도 어느 쪽을 봐야 할지 스스로 판단할 수 있게 된다. 그리고 그 이유는 단 하나에서 나온다.

### 1) 기초 — 두 리니지는 생성 시점이 다르다. 나머지는 전부 여기서 파생된다

```
   [dbt 리니지]  =  선언에서 만든다 (컴파일 타임)

   models/gold_order.sql
     SELECT ... FROM {{ ref('silver_order') }}
                        └────┬────┘
                             │  dbt 가 파일을 파싱한다
                             ▼
                    엣지: silver_order → gold_order
                             │
                             ▼
                       manifest.json  (DAG)

   → 실행하지 않아도 존재한다. 코드가 근거다.


   [Unity Catalog 리니지]  =  실행에서 만든다 (런타임)

   실제로 돌아간 쿼리
     CREATE TABLE gold_order AS SELECT ... FROM silver_order
                             │
                             │  Spark 실행 계획에서 추출
                             ▼
                    엣지: silver_order → gold_order (컬럼 단위 포함)

   → 실행되어야 존재한다. 실행 이력이 근거다.
```

**dbt는 "이렇게 하겠다"를 그리고, UC는 "이렇게 했다"를 그린다.** 이 한 줄에서 PM님이 말한 장단점이 전부 따라 나온다.

| | **dbt 리니지** | **Unity Catalog 리니지** |
|---|---|---|
| 생성 시점 | 컴파일 타임 | 런타임 |
| 근거 | `ref()` / `source()` 코드 | Spark 실행 계획 |
| 안 돌려도 보이나 | ✅ 보인다 | ❌ 안 보인다 |
| 범위 | **dbt 프로젝트 안쪽만** | **메타스토어 전체**(워크스페이스 횡단) |
| 노트북·잡·대시보드 | 안 보임 (`exposures` 로 수동 등록) | **자동으로 노드가 된다** |
| 컬럼 레벨 | 도구/버전에 따라 다름 | **자동, 기본 제공** |
| 보는 방식 | **DAG 전체를 한 장으로** | 한 객체에서 상·하류로 **펼쳐 나가며** |
| 삭제된 코드 | 즉시 사라짐 | 과거 실행 기록은 남음 |
| 이름 변경 시 | 코드가 진실이므로 유지 | **리니지가 끊긴다** (문서 명시 한계) |

"전체가 한 눈에 안 보인다"는 UC의 단점은 버그가 아니라 **관측 기반이라는 성격의 필연**이다. UC는 프로젝트라는 개념을 모른다. UC가 아는 건 "테이블과 테이블 사이에 이런 실행이 있었다"는 사실의 집합이고, 그걸 한 장으로 그리려면 어디까지가 한 덩어리인지를 알아야 하는데 그 정보가 UC에는 없다. 그래서 노드 하나에서 출발해 펼치는 UI가 된다.

반대로 dbt는 "프로젝트"라는 경계가 처음부터 있다. 그 경계 안이 곧 DAG이므로 한 장에 그릴 수 있다. 그리고 같은 이유로 **경계 밖은 못 본다.**

> **핵심 통찰 — "dbt 리니지는 의도이고, UC 리니지는 증거다"**
>
> 의도와 증거는 대체 관계가 아니다. 코드 리뷰가 테스트를 대체하지 못하고, 테스트가 코드 리뷰를 대체하지 못하는 것과 같다.
>
> - 무언가를 **바꾸기 전에** 봐야 하는 건 의도다. 아직 실행되지 않았으니 증거는 없다.
> - 무언가가 **잘못된 뒤에** 봐야 하는 건 증거다. 코드가 어떻든 실제로 흐른 건 증거뿐이다.
>
> 그래서 "같이 쓴다"는 절충이 아니라, 서로 다른 시점의 질문에 답하는 두 도구를 각각 쓰는 것이다.

### 2) 각각의 사각지대를 구체적으로 — 여기를 알아야 잘못 믿지 않는다

**dbt가 못 보는 것**

```
   [Glue / Airflow]  →  bronze  →  silver  →  gold  →  [대시보드/Genie]
   └──── 안 보임 ────┘  └──────── dbt 가 보는 범위 ────┘  └── 안 보임 ──┘
                        (source() 부터 시작)
```

- `source()` **이전** — 원천에서 bronze로 넣는 적재 과정. Glue든 Airflow든 dbt는 모른다. dbt에게 source는 "이미 거기 있는 것"이다.
- gold **이후** — 대시보드, Genie, 노트북, 사람들의 애드혹 쿼리. `exposures` 로 수동 등록하면 DAG 끝에 매달 수 있지만, 등록하지 않으면 없다.
- ⚠️ **`ref()` 를 안 쓰고 테이블명을 하드코딩한 모델.** 이게 가장 위험하다. SQL은 정상 컴파일되고 실행도 되는데, **DAG에서만 그 엣지가 사라진다.** 그러면 dbt는 실행 순서를 보장하지 않고, `--select model+` 로 하류를 고를 때도 빠진다. 조용히 틀린다.

```sql
-- ❌ 동작은 한다. 그러나 dbt 는 이 의존을 모른다.
select * from my_catalog.silver.silver_order

-- ✅ 이렇게 써야 DAG 에 엣지가 생긴다
select * from {{ ref('silver_order') }}
```

**UC가 못 보는 것** (문서에 명시된 한계 중 우리에게 걸릴 것들)

- 이름을 바꾸면(카탈로그/스키마/테이블/컬럼) **리니지가 끊긴다.**
- **UDF를 통과하면 컬럼 매핑이 흐려진다.** → Q3의 Python UDF와 직결된다.
- 경로(path)로 참조한 소스는 **컬럼 리니지가 안 잡힌다.**
- `runs submit` API·`spark submit` 태스크는 잡히지 않는다.
- 글로벌 임시 뷰, RDD는 잡히지 않는다.
- 카탈로그 탐색기 화면은 2024-09-01 이후 데이터를 계속 보관하지만, **리니지 시스템 테이블은 1년 롤링 윈도우**다. 즉 쿼리로 뽑아 분석하려면 1년치까지다.
- 그리고 가장 중요한 것 — **아직 안 돌아본 경로는 존재하지 않는다.** 분기 배치 하나가 아직 안 돌았으면, UC 리니지상 그 의존은 없는 것처럼 보인다.

> ⚠️ **"UC 리니지에 안 나온다 = 의존이 없다" 가 아니다.**
>
> 테이블을 지워도 되는지 UC 리니지로 판단할 때 흔히 나오는 사고다. 아직 안 돌아간 월배치·분기배치가 그 테이블을 쓰고 있으면, 지운 뒤 한 달 있다가 터진다.
>
> 이 판단만큼은 **UC 리니지(실행된 것) + dbt DAG(선언된 것) + 잡 정의**를 다 봐야 한다.

### 3) ★ 두 리니지가 어긋나는 지점이 곧 문제 탐지기다

여기가 "같이 쓴다"의 진짜 실용적인 이득이다. 둘을 나란히 놓으면 **불일치 자체가 정보**가 된다.

```
                      UC 에 있다              UC 에 없다
                  ┌───────────────────┬────────────────────────┐
   dbt 에 있다    │  정상             │  ⚠️ 그 모델이 한 번도  │
                  │                   │    안 돌았거나 실패 중 │
                  ├───────────────────┼────────────────────────┤
   dbt 에 없다    │  ⚠️ dbt 밖에서    │  (해당 없음)           │
                  │    만든 테이블,   │                        │
                  │    또는 ref() 대신│                        │
                  │    하드코딩 ★     │                        │
                  └───────────────────┴────────────────────────┘
```

**오른쪽 위**: 선언은 했는데 실행 흔적이 없다. 배포는 됐는데 스케줄이 안 걸렸거나, 매번 실패하는데 알림이 안 온 경우다.

**왼쪽 아래**: 이게 거버넌스 관점에서 제일 자주 나오는 구멍이다. 누군가 노트북으로 테이블을 만들어 두고 그걸 대시보드가 쓰고 있다. dbt DAG에는 없으니 코드 리뷰 대상이 아니고, 재현도 안 되고, 그 사람이 나가면 아무도 모른다.

UC 리니지는 시스템 테이블로 쿼리할 수 있으므로, 이 대조를 자동화할 수 있다.

```sql
-- UC 가 관측한 엣지 (시스템 테이블, 1년 롤링)
select
  source_table_full_name,
  target_table_full_name,
  max(event_time) as last_seen
from system.access.table_lineage
where target_table_catalog = 'my_catalog'
  and event_time >= current_date() - interval 30 days
group by 1, 2
```

여기서 나온 엣지 목록을 dbt의 `manifest.json` 에서 뽑은 엣지 목록과 대조하면, 위 사분면이 그대로 나온다. **정기적으로 돌리는 리포트로 만들 만한 가치가 있다.**

> **핵심 통찰 — "두 시스템이 같은 것을 관리할 때, 진짜 가치는 각각의 정확도가 아니라 둘의 차이에 있다"**
>
> 리니지가 두 개라서 중복 같아 보이지만, 하나만 있으면 **틀렸다는 걸 알 방법이 없다.** dbt DAG만 있으면 "선언대로 돌고 있다"를 확인할 수 없고, UC만 있으면 "선언과 다르게 돌고 있다"를 확인할 수 없다.
>
> 이건 리니지에 국한된 이야기가 아니다. 오늘 다섯 질문이 전부 이 모양이다 — 두 망, 두 리니지, 두 언어, 두 포맷, 두 권한 모델. **둘이 있을 때는 "어느 쪽이 맞나"보다 "둘이 어긋나면 무엇을 알 수 있나"를 먼저 설계하는 게 낫다.**

### 4) 둘을 실제로 이어붙이는 방법 세 가지

"같이 쓴다"를 화면 두 개를 번갈아 보는 것으로 끝내지 않으려면, 붙일 수 있는 지점이 있다.

**(a) dbt → UC : `persist_docs` 로 설명을 UC 코멘트로 밀어넣는다**

dbt의 `schema.yml` 에 쓴 description은 기본적으로 dbt 문서 안에서만 산다. `persist_docs` 를 켜면 그게 **Unity Catalog의 테이블/컬럼 COMMENT로 들어간다.**

```yaml
# dbt_project.yml
models:
  +persist_docs:
    relation: true
    columns: true
```

```yaml
# src/models/gold/_gold__models.yml
models:
  - name: gold_order_daily
    description: "일자별 주문 집계. 취소 주문은 제외한다."
    columns:
      - name: order_date
        description: "주문 기준일 (KST). 원천의 UTC 를 변환한 값."
      - name: net_amount
        description: "할인 적용 후 실결제액. 배송비 미포함."
```

- ⚠️ Databricks에서 **컬럼 코멘트는 `file_format: delta`(또는 v2 포맷)가 필요**하다.
- ⚠️ **대소문자가 섞인 컬럼명은 반영되지 않는다.** yml에서 소문자로 적거나 `quote: true` 를 붙여야 한다.

이게 왜 중요한가 — **Genie를 비롯한 AI 기능이 읽는 게 바로 UC의 COMMENT다.** 즉 `schema.yml` 을 잘 쓰는 건 문서 작업이 아니라 **AI의 입력을 만드는 작업**이다. (PM님이 "schema는 docs에서 쓰이니 잘 써야 한다"고 한 말의 사정거리가 생각보다 길다.)

**(b) UC 바깥 → UC : External Lineage (Bring Your Own Lineage, Public Preview)**

Glue, Airflow, Tableau 같은 Databricks 밖 시스템을 **external metadata object** 로 등록하고, UC 안의 테이블과 관계를 맺어줄 수 있다. 컬럼 단위 매핑도 지정 가능하다.

```
   [Glue Iceberg 테이블]  ──(수동 등록)──▶  bronze  →  silver  →  gold  ──(수동 등록)──▶  [Tableau]
    external metadata                        UC 가 자동으로 잡는 구간                      external metadata
```

⚠️ **자동이 아니다.** 등록과 관계 정의를 사람이 한다. 그래서 "bronze 앞·gold 뒤가 보인다"는 UC의 장점은, 정확히는 **"보이게 만들 자리가 있다"** 에 가깝다. Databricks 안에서 일어난 일은 자동, 밖은 수동이다.

**(c) dbt → BI : `exposures`**

dbt 쪽에서도 DAG 끝에 대시보드를 매달 수 있다.

```yaml
# src/models/exposures.yml
exposures:
  - name: sales_daily_dashboard
    type: dashboard
    maturity: high
    url: https://.../dashboards/abcd
    depends_on:
      - ref('gold_order_daily')
    owner:
      name: 영업기획팀
      email: ...
```

이러면 `gold_order_daily` 를 고칠 때 `dbt ls --select gold_order_daily+` 에 이 대시보드가 딸려 나온다. **영향 범위를 사람 기억이 아니라 명령어로 확인**할 수 있게 된다.

### 내가 확인할 것

- [ ] `persist_docs` 를 켤 것인가. 켠다면 **컬럼 코멘트가 필요한 포맷 조건**(delta)과 대소문자 규칙을 먼저 정한다.
- [ ] 우리 프로젝트에서 **Genie를 쓸 계획이 있는지.** 있다면 `schema.yml` description 품질이 곧 Genie 정확도가 되므로, 작성 기준(무엇을 반드시 쓰는가)을 초반에 정해야 한다.
- [ ] `ref()` 대신 테이블명을 하드코딩한 모델이 있는지 검사할 방법 — 리뷰 체크리스트나 간단한 lint.
- [ ] UC 리니지 시스템 테이블(`system.access.table_lineage`)에 **접근 권한이 있는지**, 그리고 내부망에서도 조회 가능한지.
- [ ] gold 뒤를 쓰는 소비자(대시보드·리포트)를 **exposures로 등록할지**, 아니면 UC external lineage로 등록할지. 둘 다 수동이므로 한 곳으로 정하는 게 낫다.
- [ ] 기존 시스템(Glue/Airflow)의 리니지를 external metadata로 등록할 계획이 있는지 — 마이그레이션 기간에는 "예전 건 어디서 오나"를 자주 묻게 된다.

## Q3. dbt는 SQL 파일로만 하는 것 같은데, Python으로 처리하는 경우도 있나요?

dbt를 공부하면 예제가 전부 `.sql` 이다. 그런데 실무에는 SQL로 표현하기 곤란한 처리가 반드시 나온다. dbt 안에서 해결이 되는지, 아니면 그건 dbt 밖으로 빼야 하는지 물었다.

### 들은 답

> - **dbt는 Python과 SQL 두 언어를 다 지원한다.**
> - **macro 안에서 Python으로 함수로 선언하면 된다.**

앞 문장은 맞다. 뒤 문장은 **받아 적으면서 두 개가 섞인 것 같다.** dbt에는 "Python으로 뭔가를 선언하는" 방법이 실제로 두 가지 있는데, 둘 다 macro는 아니다. 오히려 macro는 **정의상 Python이 들어갈 수 없는 자리**다. 하나씩 정리한다.

### 1) 기초 — macro는 Python이 들어갈 수 있는 자리가 아니다

macro는 **Jinja 템플릿**이다. Jinja가 하는 일은 딱 하나 — **SQL 문자열을 만드는 것**이다.

```
   dbt run 의 두 단계

   ┌──────────────────────────────────────────────┐
   │ ① 컴파일 (내 PC 또는 잡의 Python 프로세스)  │
   │    - Jinja 렌더링                            │
   │    - macro 호출이 SQL 문자열로 치환된다      │
   │    - 결과: 순수 SQL 텍스트                   │
   └───────────────────┬──────────────────────────┘
                       │  이 시점에 macro 는 사라진다  ★
                       ▼
   ┌──────────────────────────────────────────────┐
   │ ② 실행 (SQL warehouse / 클러스터)           │
   │    - 위에서 만든 SQL 문자열을 보낸다         │
   │    - 웨어하우스는 macro 라는 걸 모른다       │
   └──────────────────────────────────────────────┘
```

macro 안에서 Jinja의 `{% set %}`, 반복문, 조건문을 쓸 수는 있다. 그건 "Python 비슷한 문법"이지 Python이 아니고, **하는 일은 문자열 조립뿐**이다. 데이터를 못 만진다. macro 안에서 DataFrame을 다루거나 numpy를 부르는 건 개념적으로 불가능하다.

그리고 dbt 문서에는 반대 방향의 제약도 명시돼 있다 — **Python 모델은 macro 안에서 참조할 수 없다.**

### 2) 그럼 "Python으로 함수 선언"은 무엇이었나 — 후보가 둘이다

**후보 A) Python 모델 (`models/` 안의 `.py` 파일)**

이게 "dbt가 Python을 지원한다"의 본체다. macro와는 완전히 별개다.

```python
# src/models/silver/silver_order_enriched.py
def model(dbt, session):
    dbt.config(materialized="table")

    orders = dbt.ref("bronze_order")          # Spark DataFrame 을 돌려준다
    members = dbt.source("ods", "member")

    df = (
        orders.join(members, on="member_no", how="left")
              .withColumn("is_vip", ...)
    )
    return df                                  # DataFrame 을 반환하면 dbt 가 테이블로 만든다
```

규칙은 이렇다.

| 항목 | 내용 |
|---|---|
| 위치 | `models/` 안의 `.py` |
| 시그니처 | `def model(dbt, session)` — 정확히 이 이름 |
| 반환 | 단일 DataFrame (Databricks는 PySpark) |
| 지원 어댑터 | Snowflake, BigQuery, **Databricks** |
| 지원 materialization | `table`, `incremental` **만** |
| 불가 | `view`, `ephemeral` |
| 상류 참조 | `dbt.ref()`, `dbt.source()` |
| 하류에서 참조 | SQL 모델에서 `{{ ref('silver_order_enriched') }}` 로 **평소처럼** |
| Jinja | **렌더링되지 않는다.** `dbt.config.get()` 등 메서드로 접근 |
| 로그 | `print()` 출력이 dbt 로그에 안 보인다 ⚠️ |

핵심은 **Python 모델도 DAG의 정식 노드**라는 점이다. `dbt.ref()` 로 상류를 잡고, 하류 SQL 모델이 `{{ ref() }}` 로 이걸 다시 잡는다. SQL 모델과 Python 모델을 한 DAG 안에서 섞을 수 있다.

**후보 B) UDF 리소스 (`functions/` 디렉터리) — dbt Core 1.11+**

"Python으로 함수를 선언해서 SQL 안에서 쓴다"는 그림에 정확히 대응하는 건 이쪽이다. 비교적 최근에 dbt에 들어온 리소스 타입이다.

```python
# functions/is_positive_int.py
import re

def main(a_string):
    return 1 if re.search(r'^[0-9]+$', a_string or '') else 0
```

```yaml
# functions/is_positive_int.yml
functions:
  - name: is_positive_int
    description: 문자열이 양의 정수 표현이면 1
    config:
      schema: udf_schema
      runtime_version: "3.11"
      entry_point: main
    arguments:
      - name: a_string
        data_type: string
    returns:
      data_type: integer
```

```sql
-- models/silver/silver_x.sql
select
  raw_code,
  {{ function('is_positive_int') }}(raw_code) as is_numeric
from {{ ref('bronze_x') }}
```

- Databricks에서 **Python UDF는 Unity Catalog가 필요**하다.
- 이건 macro와 달리 **웨어하우스에 실제 함수 객체로 남는다.** 그래서 dbt 밖(BI, 노트북, 애드혹 쿼리)에서도 쓸 수 있다.

### 3) ★ macro / Python 모델 / UDF — 셋을 한 표로

이 셋을 헷갈리면 "왜 이건 되고 저건 안 되지"가 계속 생긴다.

| | **macro** | **Python 모델** | **UDF** |
|---|---|---|---|
| 언어 | Jinja(+SQL) | Python | SQL 또는 Python |
| 실행 시점 | **컴파일 타임** | 런타임 | 런타임 |
| 만드는 것 | SQL 문자열 | **테이블** | **함수 객체** |
| 웨어하우스에 남나 | ❌ 사라진다 | 테이블로 남는다 | ✅ 함수로 남는다 |
| dbt 밖에서 쓸 수 있나 | ❌ | (테이블은 가능) | ✅ BI·노트북에서 호출 |
| DAG 노드인가 | ❌ | ✅ | ✅ (1.11+) |
| 쓰는 이유 | 반복 SQL 제거, DDL 생성 | SQL로 표현 불가한 변환 | 재사용 가능한 비즈니스 로직 |

```
   같은 로직을 세 가지로 구현했을 때 무엇이 남는가

   macro            :  select ... (긴 SQL 이 그대로 펼쳐진 상태)   ← 함수 흔적 없음
   UDF              :  select udf_db.udf_schema.is_positive_int(x)  ← 함수 호출이 남음
   Python 모델      :  (테이블 자체가 결과물)
```

> **핵심 통찰 — "macro는 코드를 줄이고, UDF는 로직을 공유한다"**
>
> 둘 다 "중복 제거"로 보이지만 공유 범위가 다르다. macro로 뺀 로직은 **dbt 프로젝트 안에서만** 공유된다. 컴파일 후에는 흔적이 없으므로, BI 도구에서 같은 계산을 하려면 그쪽에 다시 구현해야 한다. 그리고 그 순간 **같은 지표의 두 번째 정의**가 생긴다.
>
> UDF는 웨어하우스에 남으니 BI도 노트북도 같은 함수를 부른다. 정의가 하나다.
>
> 그래서 판단 기준은 **"이 로직을 dbt 밖에서도 쓰는가"** 다. 쓴다면 macro가 아니라 UDF여야 하고, 안 쓴다면 macro가 가볍다.

### 4) ⚠️ 우리 프로젝트에서 진짜 중요한 제약 — SQL warehouse는 Python 모델을 실행하지 못한다

여기가 오늘 조사에서 가장 실무적으로 걸리는 부분이다.

dbt-databricks에서 SQL 모델은 `profiles.yml` 의 `http_path` 가 가리키는 **SQL warehouse**에서 실행된다. 그런데 **SQL warehouse는 Python을 실행할 수 없다.** Python 모델을 하나라도 넣는 순간, **컴퓨트가 하나 더 필요해진다.**

```
   SQL 모델만 있을 때                Python 모델이 섞였을 때

   dbt 프로세스                      dbt 프로세스
        │                                 │
        │ SQL                             ├── SQL ──▶ SQL warehouse
        ▼                                 │
   SQL warehouse                          └── Python ──▶ ★ 별도 컴퓨트가 필요
                                                        (클러스터 / 서버리스 잡)
   컴퓨트 1개                             컴퓨트 2종류
```

dbt-databricks가 제공하는 `submission_method` 는 네 가지다.

| `submission_method` | 필요한 것 | 성격 |
|---|---|---|
| `all_purpose_cluster` (기본) | `cluster_id` 또는 `http_path` | 반응이 빠르다. 클러스터를 미리 만들어 둬야 하고 비싸다. 개발용 |
| `job_cluster` | `job_cluster_config` | 모델마다 단명 클러스터. 기동 시간이 붙지만 저렴하다. 운영용 |
| `serverless_cluster` | 없음 | 관리 부담 없음. **서버리스가 있어야 한다** ⚠️ |
| `workflow_job` | 선택(없으면 서버리스) | 재사용 워크플로를 만든다. **dbt 밖에서도 실행 가능한 객체가 남는다** ⚠️ |

```python
def model(dbt, session):
    dbt.config(
        submission_method="job_cluster",
        job_cluster_config={
            "spark_version": "15.4.x-scala2.12",
            "node_type_id": "...",
            "num_workers": 2,
        },
        packages=["scikit-learn==1.5.0"],   # ⚠️ 폐쇄망이면 여기서 막힌다
    )
    ...
```

> ⚠️ **Python 모델 하나가 늘리는 것은 코드 파일 하나가 아니다.**
>
> 1. **컴퓨트가 하나 더 생긴다.** 클러스터 스펙을 정하고, 비용을 감시하고, 타깃별로 다르게 설정해야 한다.
> 2. **패키지 설치 경로가 생긴다.** `packages` 는 기본적으로 PyPI에서 받아온다. 내부망에서는 사내 인덱스(`index_url`)나 미리 구운 이미지가 필요하다.
> 3. **내부망에 서버리스가 없으면** `serverless_cluster` / `workflow_job`(서버리스 모드)은 선택지에서 빠진다.
> 4. **UC 리니지의 컬럼 매핑이 흐려질 수 있다.** UC 리니지는 UDF를 통과하면 컬럼 대응을 잃는 한계가 문서에 있고, DataFrame 변환도 실행 계획에서 컬럼 대응을 항상 깔끔하게 남기지는 않는다.
>
> 즉 "언어를 하나 더 쓴다"가 아니라 **"실행 경로를 하나 더 만든다"** 다. 그 값을 지불할 만한 처리인지 먼저 물어야 한다.

### 5) 그래서 언제 Python을 쓰나

**Python이 맞는 경우**

- ML 모델 추론 (학습된 모델을 불러와 배치 스코어링)
- SQL로 표현이 곤란한 복잡한 파싱·정규화 (중첩 JSON, 비정형 텍스트, 특수 인코딩)
- 통계 라이브러리가 필요한 계산 (이상치 탐지, 시계열 분해)
- 행 단위로 상태를 들고 가야 하는 알고리즘

**Python을 피해야 하는 경우**

- 조인, 집계, 윈도우 함수 — SQL이 더 빠르고 옵티마이저가 붙는다
- "Python이 익숙해서" — 팀의 유지보수 비용이 늘 뿐이다
- 외부 API 호출 — 파이프라인 안에서 네트워크에 나가는 건 재현성과 실패 처리를 동시에 망가뜨린다

> **핵심 통찰 — "dbt에서 Python을 쓸지 말지는 언어 취향이 아니라 컴퓨트 배치 결정이다"**
>
> SQL 모델은 웨어하우스 하나면 끝난다. Python 모델을 넣는 순간 컴퓨트, 패키지 공급 경로, 타깃별 설정, 비용 감시가 전부 따라온다.
>
> 그래서 판단 기준은 이렇게 두는 게 낫다 — **"SQL로 쓰면 읽을 수 없을 정도로 흉해지는가?"** 흉하기만 하면 SQL로 쓰고 주석을 잘 단다. **불가능**할 때만 Python으로 간다.
>
> 그리고 Python이 정말 필요하다면, 모델 전체를 Python으로 만들기 전에 **UDF 하나로 해결되는지**를 먼저 본다. UDF면 컴퓨트 구조를 안 건드리고, SQL 모델 안에서 호출만 하면 되며, dbt 밖에서도 재사용된다.

### 내가 확인할 것

- [ ] 현재 이관 대상 중 **SQL로 표현 불가한 처리가 실제로 있는지** 목록화. (있다고 생각했는데 없는 경우가 많다.)
- [ ] 있다면 **UDF로 되는지 먼저** 검토. 안 되면 Python 모델.
- [ ] Python 모델이 필요하다면 **내부망 `prod` 에서 어떤 `submission_method` 가 가능한지.** 서버리스가 없으면 `job_cluster` 이고, 그러면 클러스터 스펙을 타깃별로 관리해야 한다.
- [ ] 우리 `dbt-databricks` 버전이 **UDF 리소스(dbt Core 1.11+)를 쓸 수 있는 수준인지.**
- [ ] Python 모델의 패키지 의존성을 **폐쇄망에서 어떻게 공급하는지** — 사내 PyPI 인덱스가 있는지.

## Q4. 우리는 Iceberg를 쓰나요, Delta Lake를 쓰나요?

레이크하우스 이야기를 하다 보면 Iceberg와 Delta Lake가 계속 같이 나온다. 우리 스택에서 실제로 무엇이 쓰이는지, 그리고 그게 dbt로 넘어가면 어떻게 되는지 물었다.

### 들은 답

> - **Glue까지는 Iceberg로 되어 있다.**
> - **dbt를 Databricks에서 진행할 때는 자동으로 Delta Lake가 된다.**

둘 다 맞다. 그런데 이 답을 그대로 두면 **"우리 데이터는 중간에 포맷이 바뀐다"** 라는 사실만 남고, 그게 실무에서 무엇을 뜻하는지가 안 남는다. 정리하면 함의가 꽤 크다.

### 1) 기초 — 세 개의 층을 분리해야 혼란이 사라진다

"Iceberg냐 Delta냐"가 헷갈리는 이유는 서로 다른 세 개를 한 단어로 부르기 때문이다.

```
   ┌─────────────────────────────────────────────────────────┐
   │ ③ 카탈로그                                             │
   │    "어떤 테이블이 어디 있고 누가 볼 수 있나"            │
   │    → AWS Glue Data Catalog / Unity Catalog / Hive MS    │
   └─────────────────────────────────────────────────────────┘
   ┌─────────────────────────────────────────────────────────┐
   │ ② 테이블 포맷 (메타데이터 레이어)                      │
   │    "이 파일들이 모여서 하나의 테이블이고,               │
   │     지금 버전은 이것이며, 트랜잭션은 이렇게 처리한다"   │
   │    → Delta Lake (_delta_log) / Apache Iceberg (metadata)│
   └─────────────────────────────────────────────────────────┘
   ┌─────────────────────────────────────────────────────────┐
   │ ① 파일 포맷                                            │
   │    실제 데이터가 담긴 파일                              │
   │    → Parquet  ★ Delta 도 Iceberg 도 여기는 같다         │
   └─────────────────────────────────────────────────────────┘
```

**데이터 파일 자체는 둘 다 Parquet다.** 다른 건 그 위에 얹히는 메타데이터(어떤 파일들이 어느 스냅샷에 속하는가, 커밋을 어떻게 기록하는가)와, 그걸 어떤 엔진이 이해하느냐다.

이걸 알면 "포맷을 바꾼다"는 말의 무게가 정확해진다. 데이터를 전부 다시 쓰는 게 아니라 **메타데이터 레이어를 다시 쓰는 것**에 가깝다. (물론 항상 그런 건 아니다 — 아래 참고.)

### 2) "dbt를 Databricks에서 하면 자동으로 Delta" — 맞다, 그리고 이제는 선택지가 있다

dbt-databricks의 기본 `file_format` 은 `delta` 다. Unity Catalog 관리형 테이블의 기본도 Delta다. 그래서 아무것도 지정하지 않으면 Delta가 나온다. 여기까지가 답 그대로다.

그런데 **원하면 Iceberg로 만들 수 있다.** 그리고 그 "Iceberg"가 두 가지다.

```
   [1] Iceberg 읽기가 가능한 Delta 테이블  (구 UniForm)
       - 실체는 Delta 테이블이다
       - Delta 메타데이터 + Iceberg 메타데이터를 둘 다 생성
       - Parquet 파일은 다시 쓰지 않는다
       - DBR 14.3 LTS+
       → "Databricks 안에서는 Delta로, 밖에서는 Iceberg로 읽힌다"

   [2] 관리형 Iceberg 테이블 (Managed Iceberg)
       - 실체가 Iceberg 테이블이다
       - Unity Catalog 가 관리
       - DBR 16.4 LTS+
       → "진짜 Iceberg"
```

dbt에서는 이렇게 갈린다.

```sql
-- 모델 단위 설정
{{ config(
    materialized = 'table',
    table_format = 'iceberg'
) }}
```

- `table_format='iceberg'` 는 dbt-databricks 1.9+ 에서 지원한다.
- 어느 쪽이 만들어지는지는 **`use_managed_iceberg` 동작 플래그**가 정한다. 켜면 [2], 끄면 [1].
- 지원 materialization은 **`table` 과 `incremental` 뿐**이다.
- `table_format: iceberg` 일 때 `file_format` 은 `delta` 여야 한다.
- 관리형 Iceberg에서 **Iceberg v3는 아직 미지원**이다.

카탈로그 단위로 지정할 수도 있다.

```yaml
# catalogs.yml
catalogs:
  - name: unity_catalog
    type: unity
    table_format: iceberg
    config:
      databricks:
        location_root: s3://...
```

### 3) ★ 그래서 진짜 질문은 "우리는 뭘 쓰나"가 아니라 "경계에서 무엇이 오가나"다

우리 구조를 그리면 이렇게 된다.

```
   원천  →  Glue (Iceberg, S3)  →  ???  →  Databricks (Delta, Unity Catalog)
                                    ▲
                          여기가 실제 설계 지점이다
```

이 `???` 를 통과하는 방법이 셋이고, 각각 완전히 다른 결과를 낸다.

**(a) 복사 적재 — 읽어서 Delta로 다시 쓴다**

가장 흔하고, 우리도 이쪽일 가능성이 높다.

```
   Glue Iceberg 테이블  ──읽기──▶  bronze (Delta)  ──▶  silver  ──▶  gold
```

- 포맷 차이는 **읽는 순간에만** 존재한다. 그 뒤로는 전부 Delta다.
- 데이터 사본이 하나 생긴다 → 저장 비용, 그리고 **동기화 지연**이 생긴다.
- 증분 전략(어디까지 읽었는가)을 우리가 관리해야 한다.

**(b) 카탈로그 페더레이션 — Glue를 UC의 foreign catalog로 붙인다**

Unity Catalog는 AWS Glue, Hive Metastore, Snowflake Horizon 등을 페더레이션할 수 있다. 외부 Iceberg 테이블 거버넌스(Foreign Iceberg)도 지원한다.

- 사본이 안 생긴다. UC에서 바로 조회된다.
- ⚠️ **읽기 전용이다.** Lakehouse Federation으로 접근하는 foreign table에는 쓸 수 없다.
- ⚠️ 성능 특성이 다르다 — 우리 관리 하의 Delta 테이블처럼 최적화(liquid clustering, predictive optimization)를 걸 수 없다.

**(c) 반대 방향 — 외부에서 UC 테이블을 Iceberg로 읽는다**

UC의 Iceberg REST API 엔드포인트를 통해 외부 엔진이 UC 테이블을 Iceberg 클라이언트로 읽을 수 있다. AWS Glue Data Catalog 쪽에서도 UC를 페더레이션하는 기능이 나왔다.

- 우리가 만든 gold를 **다른 팀·다른 엔진에 개방**해야 할 때 쓰는 경로다.
- 이 요구가 있으면 gold를 `table_format='iceberg'` 로 만드는 게 의미를 갖는다.

> ⚠️ **"Glue까지는 Iceberg"라는 문장이 실제로 감추고 있는 결정.**
>
> 이 문장은 상태를 기술할 뿐, 그 경계를 **복사로 넘는지 페더레이션으로 넘는지**를 말하지 않는다. 그런데 그 선택이 증분 전략, 저장 비용, 데이터 신선도, 권한 모델을 전부 결정한다.
>
> 복사면 → "어디까지 읽었나"를 관리해야 하고, bronze가 원천의 사본이므로 재적재 절차가 필요하다.
> 페더레이션이면 → 쓰기가 불가하고, 성능이 원천 쪽에 달려 있으며, Glue 권한과 UC 권한이 이중으로 걸린다.
>
> "우리는 Delta다"라고 정리해두면 이 질문이 아예 안 떠오른다. 실제로 확인해야 하는 건 **경계를 넘는 방식**이다.

### 4) 왜 Databricks는 Delta가 기본이고, 그래도 Iceberg가 필요한 순간은 언제인가

```
   Delta Lake                          Apache Iceberg
   ──────────────────────────          ──────────────────────────
   Databricks 최적화와 직결            엔진 이식성이 넓다
    - Photon                            - Trino, Flink, Snowflake,
    - Liquid Clustering                   Spark, Athena, ...
    - Predictive Optimization          - 특정 벤더에 묶이지 않는다
    - Deletion Vectors
   → Databricks 안에서 가장 빠르다     → Databricks 밖에서 가장 잘 읽힌다
```

2026년 기준으로 이 대립은 상당히 누그러졌다. Unity Catalog가 Delta와 Iceberg를 **같은 거버넌스 평면에서 관리**하고, 관리형 Iceberg와 Foreign Iceberg가 정식 기능이 되면서, 포맷 선택은 진영 문제가 아니라 **워크로드 문제**가 됐다.

실무 판단 기준은 이렇게 압축된다.

```
   이 테이블을 Databricks 밖의 엔진이 읽는가?
       ├─ 아니다  →  Delta.  고민할 이유가 없다.
       └─ 그렇다  →  읽기만 하는가?
                       ├─ 읽기만  →  Iceberg 읽기 가능한 Delta 테이블 [1]
                       │             (파일 재작성 없이 양쪽 다 됨)
                       └─ 쓰기도  →  관리형 Iceberg [2] 또는 구조 재검토
```

> **핵심 통찰 — "테이블 포맷은 파일 형식이 아니라 쓰기 권한의 계약이다"**
>
> 테이블 포맷이 실제로 정하는 건 **"누가 이 테이블에 커밋할 수 있는가"** 다. Delta log와 Iceberg metadata는 각자의 방식으로 트랜잭션을 관리하는데, **한 테이블에 두 엔진이 각자의 방식으로 동시에 쓰면 깨진다.**
>
> 그래서 포맷 선택의 진짜 질문은 "어느 쪽이 좋은가"가 아니라 **"이 테이블의 쓰기 주체가 누구 하나인가"** 다. 쓰기 주체가 하나면 그 엔진이 편한 포맷을 쓰면 되고, 읽기 소비자가 여럿이면 읽기 호환만 열어주면 된다.
>
> 이 관점으로 보면 [1] "Iceberg 읽기가 가능한 Delta 테이블"이 왜 실용적인 기본값인지가 분명해진다 — **쓰기는 하나로 고정하고 읽기만 개방**하는 형태이기 때문이다.

### 5) ⚠️ 포맷을 나중에 바꾸는 건 설정 변경이 아니라 마이그레이션이다

`table_format` 을 나중에 바꾸면, dbt가 테이블을 다시 만들어야 하는 상황이 생길 수 있다. 그리고 포맷에 딸린 기능 차이가 조용히 있다.

- **컬럼 코멘트**(`persist_docs` 의 `columns: true`)는 Databricks에서 delta 같은 v2 포맷을 요구한다. → Q2의 문서화·Genie 이야기와 직결된다.
- **증분 전략**의 일부는 `file_format: delta` 를 요구한다 (`merge`, `replace_where`, `delete+insert`, `microbatch`).
- Liquid Clustering 등 최적화 기능도 포맷에 묶여 있다.

그래서 포맷은 **테이블 하나하나 고민할 게 아니라, 계층 단위로 초반에 정해두고 가는 게 맞다.**

```
   bronze  →  Delta          (우리만 쓴다. 최적화가 중요하다)
   silver  →  Delta          (우리만 쓴다)
   gold    →  Delta,
              필요하면 Iceberg 읽기 개방   ← 외부 소비자가 있을 때만
```

### 내가 확인할 것

- [ ] Glue Iceberg → Databricks 경계를 **복사로 넘는지 페더레이션으로 넘는지.** 이게 오늘 확인 항목 중 가장 중요하다.
- [ ] 복사라면 **증분 기준**이 무엇인지 (파티션? 타임스탬프? Iceberg 스냅샷 ID?).
- [ ] 우리 gold를 **Databricks 밖에서 읽는 소비자가 있는지.** 없으면 Iceberg 논의는 지금 안 해도 된다.
- [ ] `dbt-databricks` 버전이 `table_format` 을 지원하는지 (1.9+), 그리고 런타임이 관리형 Iceberg 요건(DBR 16.4 LTS+)을 만족하는지.
- [ ] `persist_docs` 로 컬럼 코멘트를 쓸 계획이라면 포맷 요건(delta)과 충돌하지 않는지.

## Q5. RBAC와 ABAC

권한 이야기가 나왔는데 키워드만 받아 적었다. 우리 프로젝트에 개인정보 컬럼이 있는 이상 언젠가 반드시 부딪힐 주제라, 처음부터 정리했다.

### 1) 기초 — RBAC: 목록을 관리하는 방식

Unity Catalog의 기본 권한 모델은 RBAC(Role-Based Access Control)다. **주체(사용자·그룹·서비스 프린시펄)에게 객체별 권한을 GRANT**한다.

```sql
GRANT USE CATALOG ON CATALOG my_catalog TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  my_catalog.gold TO `analysts`;
GRANT SELECT      ON TABLE   my_catalog.gold.order_daily TO `analysts`;
```

상속이 있다. 카탈로그에 준 권한은 하위 스키마·테이블에 내려간다. 그래서 실무에서는 대개 그룹 단위로 스키마 레벨에 걸어둔다.

**RBAC의 구조적 한계는 곱셈이다.**

```
   주체 M 개  ×  객체 N 개  =  관리해야 할 grant 조합

   그리고 진짜 문제는 크기가 아니라 시간이다:

   새 테이블이 생긴다  →  아무도 권한을 안 걸어준다
                          → 접근이 안 돼서 문의가 온다
                          → 급하게 넓게 걸어준다        💥
                          → 그 넓은 권한은 아무도 안 걷는다

   사람이 팀을 옮긴다  →  새 그룹에 추가된다
                          → 옛 그룹에서 빠지는 건 잊는다  💥
```

특히 **민감 컬럼**을 다룰 때 RBAC는 표현력이 부족하다. "주민번호 컬럼만 가리고 나머지는 보여주기"를 RBAC로 하려면 **뷰를 하나 더 만들어야** 한다. 그리고 그 뷰가 테이블마다, 대상 그룹마다 늘어난다.

### 2) ABAC — 규칙을 관리하는 방식

ABAC(Attribute-Based Access Control)는 접근 판단을 **객체에 붙은 속성**으로 한다. Unity Catalog에서 그 속성은 **거버넌스 태그(governed tag)** 다.

```
   [1] 계정 레벨에서 태그 체계를 정의한다
       sensitivity = pii | confidential | public
       domain      = sales | hr | finance

   [2] 객체에 태그를 붙인다
       카탈로그 / 스키마 / 테이블 / ★ 컬럼 / 모델 / 볼륨
       → 상위에서 하위로 상속된다 (단, 컬럼은 직접 부착 필요)

   [3] 정책을 카탈로그·스키마·테이블에 붙인다
       "sensitivity = pii 인 컬럼은 마스킹한다.
        단 pii_readers 그룹은 예외."

   [4] 평가는 조회 시점에 동적으로 일어난다
```

정책은 세 종류다.

| 정책 | 하는 일 | 형태 |
|---|---|---|
| **Row filter** | 조건에 맞는 행을 숨긴다 | UDF가 FALSE를 반환하면 제외 |
| **Column mask** | 컬럼 값을 가린다 | UDF로 마스킹된 값 반환 |
| **GRANT policy** (베타) | 태그 조건이 맞으면 권한을 준다 | UDF 없이 동적 부여 |

핵심 함수는 `has_tag()` / `has_tag_value()` 다. 정책은 붙인 지점의 **하위 전체**에 대해 평가되므로, Databricks는 **카탈로그 레벨에 붙이는 것을 권장**한다.

### 3) ★ 결정적 차이 — 새로 생긴 객체가 자동으로 보호되는가

```
   [RBAC]  새 테이블이 생긴다
             │
             ▼
        권한이 없다 (또는 상속으로 너무 넓게 열린다)
             │
             ▼
        사람이 GRANT 를 건다   ← 이 단계를 잊으면 사고
                                  (열어야 하는데 안 열려서 문의,
                                   또는 닫아야 하는데 열려서 유출)


   [ABAC]  새 테이블이 생긴다
             │
             ▼
        태그가 붙는다 (수동 또는 자동 분류)
             │
             ▼
        기존 정책이 ★ 이미 적용된다    ← 추가 작업 없음
```

이게 ABAC가 규모에서 이기는 이유다. RBAC는 **객체가 늘 때마다 작업이 는다.** ABAC는 **정책 개수만큼만 작업이 있다.**

```
   RBAC :  작업량  ∝  주체 × 객체       (곱셈)
   ABAC :  작업량  ∝  정책 개수 + 태깅  (덧셈)
```

그리고 Databricks는 여기에 **자동 데이터 분류(Data Classification)** 를 붙였다. 2026년에 ABAC 행 필터·컬럼 마스킹 정책, 거버넌스 태그, 자동 분류가 함께 GA가 되면서 이런 흐름이 완성됐다.

```
   자동 분류가 민감 컬럼을 찾는다
        ▼
   계정 레벨 거버넌스 태그가 붙는다
        ▼
   기존 ABAC 정책이 즉시 적용된다
        ▼
   사람은 정책만 관리한다
```

### 4) ⚠️ ABAC는 RBAC를 대체하지 않는다

여기가 가장 오해하기 쉬운 지점이다.

> **Row filter / column mask 정책은 접근을 부여하지 않는다. 이미 부여된 접근을 좁힌다.**

```
   ┌──────────────────────────────────────────────┐
   │ ① RBAC (GRANT)  — 문을 연다                 │
   │    "이 그룹은 이 스키마를 볼 수 있다"        │
   └──────────────────┬───────────────────────────┘
                      ▼
   ┌──────────────────────────────────────────────┐
   │ ② ABAC (row filter / column mask)           │
   │    — 창문을 가린다                           │
   │    "단, pii 태그가 붙은 컬럼은 마스킹"       │
   └──────────────────────────────────────────────┘

   ① 없이 ② 만 있으면?  →  아무것도 안 보인다.
                            정책이 좁힐 대상 자체가 없다.
```

그래서 실제 운영 형태는 **"RBAC로 큰 틀을 잡고 ABAC로 민감도를 다룬다"** 가 된다. 둘 중 하나를 고르는 문제가 아니다.

> **핵심 통찰 — "RBAC는 목록을 관리하고 ABAC는 규칙을 관리한다. 목록은 조용히 썩고, 규칙은 시끄럽게 틀린다"**
>
> RBAC의 실패 방식은 **누적**이다. 잘못 준 권한은 에러를 내지 않는다. 아무 일도 안 일어나고, 그냥 몇 년 뒤 감사에서 발견된다. 그래서 RBAC 환경의 권한은 시간이 지날수록 반드시 넓어진다 — 넓히는 데는 사유가 있지만 좁히는 데는 사유가 없기 때문이다.
>
> ABAC의 실패 방식은 **즉시**다. 정책이 잘못되면 여러 테이블이 한꺼번에 안 보이거나 한꺼번에 열린다. 크게 틀리지만, 바로 안다.
>
> 운영 관점에서는 **틀린 걸 바로 아는 쪽이 낫다.** 다만 그 대가로 ABAC는 **초기 설계(태그 체계)를 제대로 해야 한다.** 태그 체계가 엉성하면 정책도 엉성해지고, 그건 나중에 고치기가 매우 어렵다 — 이미 수천 개 객체에 붙어 있기 때문이다.

### 5) ⚠️ SI 프로젝트에서 ABAC를 쓸 때 미리 봐야 할 것

**(a) 역할 분리가 조직에 존재하는가**

ABAC 워크플로는 다섯 단계이고, 각 단계마다 필요한 권한이 다르다.

```
   ① 태그 체계 정의     →  거버넌스 담당 (계정 레벨 권한)
   ② 태그 부착          →  데이터 오너
   ③ 정책 작성          →  보안/거버넌스
   ④ 데이터 객체 생성   →  우리(개발)
   ⑤ 조회               →  최종 사용자
```

우리 프로젝트에서 ①②③을 할 사람이 정해져 있지 않으면, ABAC는 도입해도 굴러가지 않는다. 결국 개발자가 다 하게 되고, 그러면 **"보호 대상을 만드는 사람과 보호하는 사람이 같아지는"** 상태가 된다. 그건 통제가 아니다.

**(b) 감사 설명 가능성**

동적 평가는 편리하지만, **"작년 3월에 이 사람이 이 컬럼을 왜 볼 수 있었나"** 를 재현하기 어렵다. 그 시점의 태그 상태와 정책 상태를 알아야 하기 때문이다. RBAC는 grant 이력이 그대로 답이 된다.

규제 대상 시스템이라면 **태그·정책 변경 이력을 어떻게 남길 것인지**를 도입 전에 정해야 한다.

**(c) 태그와 dbt의 접점**

우리는 테이블을 dbt로 만든다. 그러면 태그는 누가 붙이나?

```yaml
# dbt 쪽에서 태그를 붙이는 형태 (dbt-databricks)
{{ config(
    materialized='table',
    databricks_tags={'sensitivity': 'pii'}
) }}
```

- 장점: 태그가 **코드와 함께 버전 관리**된다. 새 모델을 만들 때 태그를 안 붙이면 리뷰에서 잡힌다.
- ⚠️ 단점: 태그 체계를 개발팀이 들고 있게 된다. 위 (a)의 역할 분리와 충돌할 수 있다.
- ⚠️ 그리고 **컬럼 레벨 태그**는 이렇게 붙이기 어렵다. 컬럼 태그는 상속되지 않고 직접 부착해야 하는데, 개인정보 마스킹은 대부분 컬럼 단위다.

이건 정답이 있는 문제가 아니라 **협의해서 정해야 할 경계**다.

### 내가 확인할 것

- [ ] 고객사에 **거버넌스 태그 체계가 이미 있는지**, 아니면 우리가 제안해야 하는지.
- [ ] 개인정보 마스킹 요건이 **계약 산출물에 있는지**, 있다면 그 요건이 뷰 기반(RBAC)으로 명시돼 있는지 아니면 방식이 열려 있는지.
- [ ] 내부망 workspace에서 **ABAC 기능이 사용 가능한지** — 런타임 버전과 기능 활성화 여부.
- [ ] 태그를 **dbt에서 붙일 것인가, 별도 거버넌스 프로세스로 붙일 것인가.**
- [ ] 컬럼 레벨 태그를 붙여야 하는 컬럼 목록이 있는지 — 있으면 그건 데이터 모델 산출물과 함께 관리돼야 한다.
- [ ] ABAC 정책이 걸린 테이블을 dbt가 읽을 때, **서비스 프린시펄에도 마스킹이 적용되는지.** 적용되면 파이프라인이 마스킹된 값을 silver에 적재하게 된다. ⚠️ 이건 반드시 미리 확인해야 한다.

## dbt 기초 7개

질문 사이사이에 들은 dbt 기초를, 각각 한 겹씩 더 파서 정리한다.

### 1) macro — 공통 함수의 집합, "SQL 안에서 쓰는 사용자 정의 함수" (Jinja)

들은 설명은 감을 잡기에 좋은 비유다. 다만 **결정적으로 다른 점 하나**를 알고 있어야 한다.

> ⚠️ **macro는 데이터베이스에 남지 않는다.** 컴파일 시점에 SQL 문자열로 치환되고 사라진다. UDF는 웨어하우스에 함수 객체로 남는다. (자세한 비교는 Q3 참고.)

macro의 실제 쓰임은 셋이다.

```jinja
{# ① 반복되는 SQL 제거 #}
{% macro to_kst(ts_col) %}
    from_utc_timestamp({{ ts_col }}, 'Asia/Seoul')
{% endmacro %}

{# 사용 #}
select {{ to_kst('created_at') }} as created_at_kst from {{ ref('bronze_order') }}
```

```jinja
{# ② DDL/DML 생성 — 모델이 아닌 것을 만든다 #}
{% macro grant_select_to_analysts(schema) %}
  {% set sql %}
    grant select on schema {{ schema }} to `analysts`
  {% endset %}
  {% do run_query(sql) %}
{% endmacro %}
```

```jinja
{# ③ 어댑터 분기 — 여러 웨어하우스를 지원할 때 #}
{% macro date_diff_days(a, b) %}
  {{ return(adapter.dispatch('date_diff_days')(a, b)) }}
{% endmacro %}
```

> ⚠️ **macro를 많이 쓸수록 "쓴 SQL"과 "도는 SQL"이 멀어진다.**
>
> 문제가 생겼을 때 모델 파일만 봐서는 알 수 없게 된다. 그래서 macro를 쓰는 프로젝트에서는 **`target/compiled/` 아래의 컴파일 결과를 여는 습관**이 필수다. `dbt compile` 후 그 파일을 그대로 웨어하우스에 붙여넣으면 실제로 도는 쿼리를 볼 수 있다.
>
> 판단 기준 하나 — **macro가 SQL을 짧게 만드는가, 아니면 감추는가.** 같은 표현이 세 번 이상 나오면 macro가 맞다. 두 번이면 대개 그냥 두는 게 낫다.

### 2) 모델의 `schema` — docs에서 쓰인다. 그래서 잘 써야 한다

맞다. 그리고 **docs보다 더 멀리 간다.**

```yaml
# src/models/gold/_gold__models.yml
models:
  - name: gold_order_daily
    description: "일자별 주문 집계. 취소 주문 제외."
    config:
      contract:
        enforced: false
    columns:
      - name: order_date
        description: "주문 기준일 (KST)"
        data_type: date
        data_tests:
          - not_null
          - unique
      - name: net_amount
        description: "할인 후 실결제액. 배송비 미포함."
```

이 파일이 하는 일은 네 가지다.

| 역할 | 내용 |
|---|---|
| **문서** | `dbt docs generate` 의 원본 |
| **테스트** | `data_tests` 가 여기 붙는다. `dbt build` 가 실행한다 |
| **설정** | `config:` 로 materialization·태그 등을 지정 가능 |
| **★ 카탈로그 코멘트** | `persist_docs` 를 켜면 **Unity Catalog COMMENT로 들어간다** |

네 번째가 "잘 써야 한다"의 진짜 이유다. **description은 dbt 안에 머무는 문서가 아니라, Unity Catalog를 거쳐 Genie 같은 AI 기능의 입력이 된다.** 컬럼 설명이 부실하면 AI가 잘못된 SQL을 만든다.

> ⚠️ **`schema.yml` 에 컬럼을 적는다고 그 컬럼이 만들어지지는 않는다.**
>
> 이건 설명이지 계약이 아니다. SELECT에서 컬럼을 지우고 yml만 남겨두면, dbt는 조용히 넘어간다.
>
> 계약으로 만들려면 **model contracts** 를 명시적으로 켜야 한다(`contract: enforced: true`). 그러면 선언한 컬럼·타입과 실제 결과가 다를 때 빌드가 실패한다. 산출물로 테이블 정의서를 내야 하는 SI 프로젝트에서는 이 옵션을 진지하게 볼 만하다 — **정의서와 실물이 어긋나는 사고를 CI에서 잡을 수 있다.**

### 3) `~/.dbt/profiles.yml` — 내 설정과 토큰이 들어간다

> ⚠️ 파일명은 **`profiles.yml`**(복수형)이다. `profile.yml` 로 만들면 dbt가 못 찾는다.

```yaml
# ~/.dbt/profiles.yml
my_dbt_project:              # ← dbt_project.yml 의 profile: 과 일치해야 한다
  target: dev
  outputs:
    dev:
      type: databricks
      host: adb-xxxx.azuredatabricks.net
      http_path: /sql/1.0/warehouses/abc123
      token: "{{ env_var('DBT_TOKEN') }}"
      catalog: my_catalog
      schema: my_dev_schema
      threads: 4
```

dbt가 찾는 순서는 셋이고, **먼저 찾은 것을 쓴다.**

```
   ① --profiles-dir 플래그      (CI/CD 에서 지정)
   ② 프로젝트 루트 디렉터리
   ③ ~/.dbt/                    ← 권장
```

`~/.dbt/` 를 권장하는 이유는 단순하다 — **자격증명이 프로젝트 디렉터리 밖에 있으면 Git에 들어갈 일이 없다.**

> ⚠️ **로컬에서 되는데 배포된 잡에서 안 되는 사고의 상당수가 여기다.**
>
> 로컬 개발은 `~/.dbt/profiles.yml` 을 본다. 배포된 잡은 그 파일을 볼 수 없으므로 **번들 안의 별도 프로파일**(예: `dbt_profiles/profiles.yml`)을 본다.
>
> 두 파일이 다른 웨어하우스·다른 카탈로그를 가리키고 있으면, 로컬에서 통과한 것이 잡에서 실패한다. 그리고 이건 에러 메시지가 불친절하다 — 대개 "테이블이 없다"로 나온다.
>
> 그래서 문제가 생겼을 때 첫 질문은 **"지금 어느 프로파일을 보고 있나"** 여야 한다. `dbt debug` 가 그걸 알려준다.

### 4) `dbt deps` → `dbt build`

> ⚠️ 메모의 `dbt debs` 는 `dbt deps` 의 오타로 보인다. 참고로 `dbt debug` 라는 명령도 따로 있어서(연결 확인용) 헷갈리기 쉽다.

**`dbt deps`** — `packages.yml` 에 적힌 패키지를 `dbt_packages/` 에 내려받는다.

```
   packages.yml  ──dbt deps──▶  dbt_packages/
                                  ├── dbt_utils/
                                  └── ...
```

⚠️ `dbt_packages/` 는 **Git에 커밋하지 않는 게 관례**다(`.gitignore`). 그래서 **CI에서도, 배포된 잡에서도 매번 `dbt deps` 가 필요하다.** 폐쇄망에서 이게 문제가 된다.

**`dbt build`** — 시드·모델·스냅샷·테스트를 **DAG 순서로 섞어서** 실행한다. `dbt run` 후 `dbt test` 와 결정적으로 다르다.

```
   [dbt run  →  dbt test]

   모델 A 생성 → 모델 B 생성 → 모델 C 생성
                                   │
                                   ▼
                          테스트 A, B, C 를 나중에 한꺼번에
                                   │
                          A 가 실패했다는 걸 이제 안다.
                          그런데 B, C 는 이미 A 를 읽고 만들어졌다.  💥


   [dbt build]

   모델 A 생성 → 테스트 A
                    │
                    ├─ 통과 → 모델 B 생성 → 테스트 B → ...
                    │
                    └─ 실패 → ★ B, C 를 skip 한다
                              오염된 데이터가 하류로 안 흐른다  ✅
```

> **핵심 통찰 — "`dbt build` 를 쓰는 이유는 명령이 짧아서가 아니라, 실패가 전파되지 않게 하기 위해서다"**
>
> `dbt run` 다음 `dbt test` 는 **"다 만든 다음에 검사한다"** 는 순서다. 검사에서 걸리면 이미 잘못된 데이터가 gold까지 가 있다. 되돌리려면 다시 돌려야 하고, 그 사이 대시보드는 틀린 값을 보여준다.
>
> `dbt build` 는 **"만들면서 검사하고, 틀리면 거기서 멈춘다"** 는 순서다. 실패 반경이 실패 지점에 머문다.
>
> 그래서 운영 잡의 기본 명령은 `dbt build` 여야 한다. `dbt run` 은 개발 중 특정 모델만 빠르게 돌릴 때 쓰는 것이다.

일반적인 실행 순서는 이렇게 된다.

```bash
dbt deps          # 패키지 설치
dbt debug         # (선택) 연결 확인
dbt build         # 시드 → 모델 → 스냅샷 → 테스트를 DAG 순서로
```

### 5) hub.getdbt.com — pip 같은 느낌

비유가 정확하다. dbt 패키지 허브이고, `packages.yml` 에 적고 `dbt deps` 로 받는다.

```yaml
# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0
```

다만 pip와 **결정적으로 다른 점**이 하나 있다.

> ⚠️ **dbt 패키지는 라이브러리가 아니라 소스코드다.**
>
> pip는 라이브러리를 설치하고, 내가 부를 때만 실행된다. dbt 패키지는 `dbt_packages/` 에 **프로젝트 전체가 통째로** 들어가서, **내 프로젝트의 일부처럼 컴파일된다.**
>
> 그 말은 — **패키지 안에 모델이 들어 있으면, 그 모델이 내 웨어하우스에 테이블로 만들어질 수 있다.** `dbt_utils` 처럼 매크로만 있는 패키지는 상관없지만, 모델을 포함한 패키지를 넣을 때는 `dbt_project.yml` 에서 그 패키지의 모델을 비활성화할지 먼저 봐야 한다.

버전 고정은 `package-lock.yml` 로 관리된다(`dbt deps` 가 생성). 이건 **커밋해야 한다** — 재현성의 근거이기 때문이다.

폐쇄망에서는 허브에 못 나가므로 다른 형태를 쓴다.

```yaml
packages:
  - local: ../vendor/dbt_utils                          # 레포에 벤더링
  - git: "https://gitlab.internal.example.com/..."      # 사내 git
    revision: 1.3.0
```

### 6) snapshot — 테이블의 history를 관리해주는 기능

맞다. 정확히는 **SCD Type 2**를 구현해준다.

```
   원천 테이블 (덮어쓰기 방식)

   2026-08-12   order_1  status = 'pending'
   2026-08-13   order_1  status = 'shipped'   ← pending 이 사라졌다
   2026-08-14   order_1  status = 'delivered' ← shipped 도 사라졌다

   → "8월 12일 시점에 몇 건이 pending 이었나" 에 답할 수 없다.


   snapshot 테이블

   order_1  pending    dbt_valid_from=08-12  dbt_valid_to=08-13
   order_1  shipped    dbt_valid_from=08-13  dbt_valid_to=08-14
   order_1  delivered  dbt_valid_from=08-14  dbt_valid_to=NULL   ← 현재
```

전략은 둘이다.

```yaml
# snapshots/orders_snapshot.yml
snapshots:
  - name: orders_snapshot
    relation: ref('stg_orders')
    config:
      strategy: timestamp          # ← 권장
      unique_key: order_id
      updated_at: updated_at
```

| 전략 | 방식 | 특징 |
|---|---|---|
| **timestamp** (권장) | `updated_at` 컬럼 하나만 본다 | 컬럼이 추가/삭제돼도 영향 없다 |
| **check** | `check_cols` 에 적은 컬럼들을 비교 | 원천에 갱신 시각이 없을 때. 스키마 변경에 취약 |

자동으로 붙는 메타 컬럼은 넷이다 — `dbt_valid_from`, `dbt_valid_to`, `dbt_scd_id`, `dbt_updated_at`. (`hard_deletes: 'new_record'` 를 쓰면 `dbt_is_deleted` 도.)

> ⚠️ **snapshot은 소급이 불가능하다. 이게 가장 중요한 성질이다.**
>
> snapshot은 **실행된 시점의 원천 상태**만 기록한다. 어제 안 돌렸으면 어제 상태는 영원히 없다. 모델은 다시 돌리면 복구되지만 **snapshot은 복구되지 않는다.**
>
> 그래서 두 가지가 따라온다.
> 1. **snapshot을 시작하는 날이 곧 히스토리의 시작일이다.** 마이그레이션 프로젝트라면 "언제부터 이력을 남길 것인가"가 곧 배포 일정 문제가 된다.
> 2. **snapshot 잡의 실패는 다른 실패와 성격이 다르다.** 모델 실패는 다시 돌리면 되지만, snapshot 실패는 그날의 이력을 잃는 것이다. 알림 우선순위를 다르게 둘 이유가 있다.
>
> 그리고 기존 시스템에 이미 SCD2 테이블이 있다면, **그걸 snapshot으로 옮길지 그냥 일반 incremental 모델로 옮길지**는 별도 판단이다. 이미 이력이 있는 테이블을 snapshot으로 다시 만들면 과거 이력이 안 따라온다.

기타 제약: `snapshots/` 디렉터리에 따로 둬야 하고, 원천에서 컬럼이 사라져도 snapshot 테이블에서는 안 지워지며, 타입은 바뀌지 않는다.

### 7) `threads` — 동시 실행 수

맥락상 맞다. 정확히는 **dbt가 DAG에서 동시에 진행하는 경로의 수**다.

```yaml
# profiles.yml
outputs:
  dev:
    threads: 4        # 기본값 4
```

```bash
dbt build --threads 8    # 실행 시 덮어쓰기
```

```
   threads = 1                      threads = 4

   A ─▶ B ─▶ C ─▶ D                  A ─┐
   (하나씩)                          B ─┼─▶ 동시에 4개까지
                                     C ─┤
                                     D ─┘
```

여기서 두 가지를 구분해야 한다.

> ⚠️ **`threads` 는 "쿼리를 몇 개 동시에 던지는가"이지, "쿼리 하나가 얼마나 빨라지는가"가 아니다.**
>
> 1. **DAG가 직렬이면 threads를 올려도 안 빨라진다.** A→B→C→D 처럼 한 줄로 이어져 있으면 동시에 돌릴 게 없다. threads가 효과를 내려면 **독립적인 가지가 여럿**이어야 한다. (원천 테이블 여러 개를 각각 bronze로 당기는 구간이 정확히 그런 형태다 — 메모의 "Glue에서 당겨올 때 동시 실행 수"라는 표현이 이 구간을 가리킨 것으로 보인다.)
> 2. **상한이 두 개다.** dbt 쪽 `threads` 와, 웨어하우스가 실제로 동시에 처리할 수 있는 양. 공용 웨어하우스라면 threads를 올린 만큼 **다른 팀의 쿼리가 큐에 밀린다.**
>
> 그래서 threads는 "높을수록 좋다"가 아니라, **DAG 모양과 웨어하우스 크기를 보고 정하는 값**이다. 올렸는데 안 빨라졌다면 DAG가 직렬이거나 웨어하우스가 이미 포화 상태다.

## 오늘의 정리

### 다섯 질문은 전부 같은 모양이었다

```
   Q1  두 개의 망        →  무엇이 어느 망에 있어야 하나
                            (기준: 컴퓨트가 어디서 도는가)

   Q2  두 개의 리니지    →  각각 무엇을 근거로 그리나
                            (기준: 선언인가 관측인가)

   Q3  두 개의 언어      →  실은 두 개의 컴퓨트다
                            (기준: SQL warehouse 로 되는가)

   Q4  두 개의 포맷      →  실은 쓰기 주체가 누구인가의 문제다
                            (기준: 이 테이블에 누가 커밋하나)

   Q5  두 개의 권한 모델 →  목록을 관리할까 규칙을 관리할까
                            (기준: 객체가 늘 때 작업이 느는가)

   ─────────────────────────────────────────────────────────
   공통 질문:  "둘 중 뭐가 맞나" 가 아니라
               "둘의 경계가 어디이고, 어긋나면 무엇을 알 수 있나"
```

그리고 Q2에서 나온 결론 — **두 시스템이 어긋나는 지점이 곧 문제 탐지기** — 는 나머지 넷에도 그대로 적용된다.

- 두 망에 다른 커밋이 올라가 있다 → 배포 프로세스에 구멍이 있다
- dbt DAG와 UC 리니지가 다르다 → `ref()` 를 안 쓴 모델이 있다
- SQL 모델은 도는데 Python 모델만 실패한다 → 컴퓨트가 없거나 패키지가 없다
- Glue와 Databricks의 행 수가 다르다 → 경계를 넘는 방식(복사/페더레이션)의 문제
- 권한은 줬는데 값이 마스킹돼 있다 → ABAC 정책이 서비스 프린시펄에도 걸려 있다

### 항목별 한 줄

| # | 들은 답 | 내가 덧붙여야 할 조건 |
|---|---|---|
| Q1 | 데이터가 내부망이라 `prod` 는 내부망, `prod-public` 은 AI agent용 | AI가 밖에 있는 건 **서버리스라서**다. 그리고 **외부망 agent가 무슨 데이터를 보는지**가 미확인 |
| Q2 | 둘 다 써야 한다. UC는 넓게, dbt는 한눈에 | 차이의 근원은 **선언 vs 관측**. 그리고 **둘의 불일치가 탐지기**다 |
| Q3 | Python·SQL 둘 다 지원, macro 안에서 Python 함수 선언 | ⚠️ **macro가 아니다.** Python 모델(`models/*.py`) 또는 UDF(`functions/`, dbt 1.11+). 그리고 **SQL warehouse는 Python을 못 돌린다** |
| Q4 | Glue까지 Iceberg, Databricks dbt는 자동 Delta | 맞다. 다만 `table_format='iceberg'` 로 바꿀 수 있고, **진짜 질문은 경계를 복사로 넘는지 페더레이션으로 넘는지** |
| Q5 | (키워드만) | ABAC는 RBAC를 **대체하지 않는다** — 문은 GRANT가 열고, ABAC는 창문을 가린다 |
| dbt 3 | `~/.dbt/profile.yml` | ⚠️ `profiles.yml`(복수). 그리고 **배포된 잡은 이 파일을 안 본다** |
| dbt 4 | `dbt debs` > `dbt build` | ⚠️ `dbt deps`. `build` 를 쓰는 이유는 **실패가 하류로 전파되지 않게** 하려는 것 |
| dbt 5 | hub.getdbt.com은 pip 같은 것 | ⚠️ 설치되는 게 라이브러리가 아니라 **소스코드**다 |
| dbt 6 | snapshot은 히스토리 관리 | ⚠️ **소급 불가.** 시작한 날이 이력의 시작일이고, 실패하면 그날은 영원히 없다 |
| dbt 7 | `threads` 는 동시 실행 수 | **DAG가 직렬이면 올려도 안 빨라진다.** 그리고 공용 웨어하우스면 남에게 영향 |

### 질문하면서 배운 것 (내용 말고 방법)

- **"A로 하면 된다"는 답을 들으면 A가 무엇의 하위 개념인지 확인해야 한다.** Q3이 그랬다. "macro 안에서 Python"이라고 적어뒀다면 계속 macro 문법을 뒤졌을 것이다. macro가 **Jinja이고 컴파일 타임에 사라진다**는 성질을 알고 있었으면, 받아 적는 그 자리에서 "그건 macro가 아닐 것 같은데" 라고 되물을 수 있었다.
- **"자동으로 X가 된다"는 답은 "X 말고 다른 선택지가 있나"를 같이 물어야 한다.** Q4가 그랬다. "자동으로 Delta"는 사실이지만, 그게 **선택지가 없다**는 뜻은 아니었다.
- **두 개가 있으면 "겹치나요"보다 "어긋나면 무슨 뜻인가요"가 더 나은 질문이다.** Q2에서 얻은 게 그거였다. 겹침 여부를 물으면 "같이 쓰세요"로 끝나는데, 어긋남을 물으면 실제 점검 절차가 나온다.

> **토론거리**
>
> 1. **`prod-public` 의 AI agent에게 데이터를 어디까지 열 것인가.** 메타데이터만 주면 안전하지만 agent가 별로 쓸모없고, 서브셋을 복제하면 쓸모 있지만 "무엇이 비민감인가"를 계속 판정해야 한다. 이 판정을 **누가, 어떤 주기로** 하는 게 맞는가? 그리고 그 판정 자체를 파이프라인으로 만들 수 있는가?
>
> 2. **dbt DAG와 UC 리니지의 불일치를 정기 점검 항목으로 만들 것인가.** 만들면 dbt 밖에서 만들어진 테이블을 계속 발견하게 되는데, 발견한 다음에 어떻게 할 것인가가 더 어려운 문제다. 전부 dbt로 흡수하는 게 맞는가, 아니면 "dbt 밖 테이블"이라는 범주를 인정하고 관리하는 게 맞는가?
>
> 3. **`schema.yml` 의 description을 어느 수준까지 강제할 것인가.** Genie를 쓴다면 이건 문서가 아니라 기능이 된다. 그런데 description 품질은 리뷰로 강제하기 어렵고, 자동 검사는 "있는가/없는가"까지만 가능하다. **AI가 읽을 문서의 품질**을 어떻게 담보할 것인가?
>
> 4. **ABAC를 도입한다면 태그를 dbt 코드에 둘 것인가, 별도 거버넌스 프로세스에 둘 것인가.** 코드에 두면 버전 관리가 되고 리뷰에서 잡히지만, 보호 대상을 만드는 사람이 보호 규칙도 정하게 된다. 이 역할 분리가 실제로 지켜지는 조직이 얼마나 되며, 안 지켜질 거라면 그걸 전제로 설계하는 게 맞는가?
>
> 5. **`dbt build` 의 "실패하면 하류 skip"이 항상 옳은가.** gold 하나가 테스트에 걸려서 나머지 gold 20개가 안 만들어지는 게 더 나쁜 상황일 수도 있다. 테스트 심각도(`severity: warn/error`)를 어떻게 나눌 것인가 — 그리고 그 기준을 누가 정하나?
