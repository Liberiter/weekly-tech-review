# 2026-08-18. Databricks 변환 최적화 — "읽지 않는 기술"과 그 세 세대

> dbt 모델 설정을 들여다보다가 손이 멈췄다. `partition_by`, `liquid_clustered_by`, `zorder`, `tblproperties`. 셋 다 "성능을 위한 것"이라는데, **셋이 서로 무엇이 다른지, 왜 셋이나 있는지, 내 모델에는 뭘 써야 하는지**가 하나도 안 잡혔다.
>
> 더 근본적인 질문이 있었다. **"최적화"라는 게 정확히 뭘 최적화하는 건가?** 쿼리가 빨라지는 건 알겠는데, 왜 빨라지는지 설명하지 못하면 설정값은 그냥 미신이 된다. 남이 쓴 걸 복사해 붙이고 "이게 좋다더라"로 끝난다.
>
> 이 글은 세 가지를 정리한다. **(1) 최적화가 실제로 줄이는 것이 무엇인가**, **(2) 파티셔닝·Z-ORDER·Liquid Clustering이 각각 무엇이고 어떤 순간에 쓰는가**, **(3) 이 셋 말고도 사실 최적화 손잡이는 훨씬 많다 — 그리고 대개 성능 문제의 진범은 이 셋이 아니다.**

## 1. 도입: "최적화해주세요"는 무엇을 해달라는 말인가

현장에서 "이 쿼리 최적화 좀 해주세요"라는 말을 들으면, 초심자는 보통 **SQL을 고치려 든다.** 서브쿼리를 CTE로 바꾸고, `DISTINCT`를 빼고, 조인 순서를 바꾼다.

그런데 Databricks 같은 레이크하우스에서 이건 대체로 **효과가 가장 작은 축**에 속한다. 이유는 단순하다. 쿼리 엔진이 이미 옵티마이저를 갖고 있어서 그 정도 재작성은 알아서 한다. 반면 엔진이 절대 알아서 못 하는 게 하나 있다.

> **디스크에 이미 어떤 모양으로 써 있는 데이터를, 쿼리 시점에 다시 배치할 수는 없다.**

10TB짜리 테이블에서 하루치를 뽑을 때, 그 하루치가 파일 100개에 모여 있으면 100개만 읽는다. 10만 개 파일에 흩뿌려져 있으면 10만 개를 다 읽는다. **같은 SQL, 같은 결과, 1000배 차이.** 그리고 이 차이는 SQL을 아무리 예쁘게 고쳐도 사라지지 않는다.

그래서 레이크하우스 최적화의 중심은 **"데이터가 파일에 어떻게 놓여 있는가(data layout)"**다. 파티셔닝·Z-ORDER·Liquid Clustering은 전부 이 하나의 질문에 대한 서로 다른 세대의 답이다. 셋이 병렬로 존재하는 대안이 아니라, **같은 문제를 푸는 1세대·2세대·3세대**에 가깝다.

다만 시작하기 전에 미리 못 박아둘 게 있다. 이 셋만 아는 상태로 현장에 나가면, **정작 가장 흔한 병목을 못 본다.** 실무에서 압도적으로 자주 만나는 성능 문제는 이 순서다.

```
1위. 작은 파일이 너무 많다 (small file problem)
2위. 매번 전체를 다시 계산한다 (증분화 안 됨)
3위. 조인이 셔플/스큐로 터진다
4위. ...그 다음에야 레이아웃(파티션/클러스터링) 문제
```

레이아웃은 4위다. 그런데 검색하면 1~3위보다 4위 이야기가 훨씬 많이 나온다. 이 글이 9장을 따로 두는 이유다.

## 2. 최적화의 정의 — 결국 네 가지 자원을 줄이는 게임

"최적화"를 한 문장으로 정의하면 이렇다.

> **같은 결과를 만들면서, 소비하는 자원을 줄이는 것.**

그럼 자원이 뭔가. 분산 쿼리 엔진에서 쿼리 한 번이 소비하는 건 딱 네 가지다.

| 자원 | 무엇 | 늘어나는 원인 | 줄이는 대표 수단 |
|---|---|---|---|
| **I/O (스캔)** | 스토리지에서 읽어 들인 바이트 | 필요 없는 파일·컬럼·행을 읽음 | 파일 스킵, 컬럼 프루닝, 레이아웃 |
| **네트워크 (셔플)** | 노드 간 이동한 바이트 | 조인·집계·정렬 시 재분배 | 브로드캐스트 조인, 사전 집계, AQE |
| **CPU** | 디코딩·필터·연산 | 압축 해제, 문자열 처리, UDF | Photon, 벡터화, 타입 선택 |
| **메모리** | 실행 중 상주 데이터 | 큰 셔플·스큐·윈도우 | 스필 회피, 파티션 크기 조정, 스큐 처리 |

여기서 두 가지를 짚고 가야 한다.

**첫째, 클라우드에서 성능은 곧 비용이다.** 온프레미스 시절에는 서버를 이미 샀으니 쿼리가 느려도 "기다리면 되는" 문제였다. 클라우드에서는 **쿼리가 2배 느리면 DBU를 2배 쓴다.** 최적화는 성능 튜닝이 아니라 원가 절감 활동이다. 이 프레이밍이 실무에서 중요한 이유는, "빠르게 해주세요"보다 **"이 잡의 월 비용을 40% 줄였습니다"**가 훨씬 잘 통하는 언어이기 때문이다.

**둘째, 네 자원 중 압도적 1위는 I/O다.** 클라우드 오브젝트 스토리지(S3, ADLS, GCS)는 로컬 디스크가 아니라 **네트워크 너머의 HTTP 서비스**다. 파일 하나 여는 데 수십 ms의 지연이 붙는다. 그래서 레이크하우스 최적화의 90%는 이 한 문장으로 요약된다.

> **가장 빠른 읽기는, 읽지 않는 것이다.**

> **핵심 통찰 — "최적화는 계산을 빠르게 하는 기술이 아니라, 읽지 않는 기술이다"**
>
> 전통 RDBMS 튜닝의 감각은 "인덱스를 타게 해서 조회를 빠르게 한다"였다. 레이크하우스는 인덱스가 없다(정확히는, B-tree 같은 행 단위 인덱스가 없다). 대신 **파일 단위로 "이 파일은 아예 안 봐도 된다"를 판정**한다.
>
> 이 차이가 실무에 뭘 바꾸느냐 — **최적화의 성공 지표가 "실행 시간"이 아니라 "읽은 파일 수 / 읽은 바이트"**가 된다. Databricks 쿼리 프로파일에서 `files pruned` vs `files read`를 먼저 보는 습관이 여기서 나온다. 시간은 클러스터 크기에 따라 흔들리지만, 스캔한 바이트는 레이아웃 품질을 정직하게 반영한다.
>
> 그리고 이 관점은 튜닝 순서를 정해준다. **읽는 양을 못 줄였는데 클러스터를 키우는 건, 새는 양동이에 물을 더 붓는 것**이다. 잠깐 빨라지고 비용만 늘어난다.

## 3. 모든 레이아웃 최적화의 뿌리: 파일 스킵

파티셔닝·Z-ORDER·Liquid Clustering을 이해하려면, 그 셋이 전부 봉사하는 **하나의 메커니즘**을 먼저 알아야 한다. 데이터 스킵(data skipping)이다.

### 3.1 Delta 테이블은 사실 "파일 목록 + 통계"다

Delta 테이블은 Parquet 파일 더미와, 그걸 설명하는 트랜잭션 로그(`_delta_log/`)로 되어 있다. 로그에는 파일을 추가할 때마다 이런 항목이 쌓인다.

```json
{"add": {
   "path": "part-00000-....snappy.parquet",
   "size": 268435456,
   "stats": "{
      \"numRecords\": 1200000,
      \"minValues\": {\"event_date\": \"2026-08-01\", \"customer_id\": 100003},
      \"maxValues\": {\"event_date\": \"2026-08-03\", \"customer_id\": 999871},
      \"nullCount\": {\"customer_id\": 0}
   }"
}}
```

핵심은 `stats`다. **파일을 열지 않고도 그 파일 안 값의 범위를 알 수 있다.**

이제 이런 쿼리가 들어온다.

```sql
SELECT * FROM events WHERE event_date = '2026-08-15'
```

플래너는 파일을 열기 전에 로그만 보고 판정한다.

```
파일 A: min=2026-08-01, max=2026-08-03  →  15일이 범위 밖   → 안 읽음 ✅
파일 B: min=2026-08-14, max=2026-08-16  →  15일이 범위 안   → 읽음
파일 C: min=2026-08-20, max=2026-08-22  →  범위 밖          → 안 읽음 ✅
```

이게 **파일 프루닝(file pruning)**이다. 실제로는 여기에 더해 3단 프루닝이 일어난다.

```
① 파티션 프루닝    디렉터리 경로만 보고 통째로 제외        (파티션이 있을 때만)
       ↓
② 파일 프루닝      트랜잭션 로그의 min/max로 파일 제외      ← 레이아웃 최적화가 겨냥하는 지점
       ↓
③ Parquet 내부     row group 통계로 블록 제외 + 필요한 컬럼만 읽음 (컬럼 지향 포맷의 기본 이득)
```

### 3.2 그런데 min/max는 데이터가 "몰려 있을 때만" 쓸모 있다

여기가 전부다. 같은 데이터, 같은 통계 구조인데 **파일에 담기는 순서**만 다르면 이렇게 갈린다.

```
[정렬되지 않은 테이블 — 날짜가 무작위로 섞여 파일에 들어감]

파일1  min=08-01  max=08-31   ← 8월 전체를 포함
파일2  min=08-01  max=08-31   ← 8월 전체를 포함
파일3  min=08-01  max=08-31   ← 8월 전체를 포함
...
WHERE event_date='2026-08-15'  →  모든 파일이 "가능성 있음"  →  스킵 0%
```

```
[날짜 기준으로 몰아둔 테이블]

파일1  min=08-01  max=08-03
파일2  min=08-04  max=08-06
...
파일11 min=08-14  max=08-16    ← 이것만 읽음
...
WHERE event_date='2026-08-15'  →  1/11만 읽음  →  스킵 91%
```

> **핵심 통찰 — "레이아웃 최적화의 세 방법은 전부 '같은 값을 같은 파일에 모으는' 방법의 변주다"**
>
> 파티셔닝은 **디렉터리로** 모으고, Z-ORDER는 **공간 채움 곡선 순서로 정렬해서** 모으고, Liquid Clustering은 **테이블 속성으로 선언해두고 쓰기·유지보수 때마다 자동으로** 모은다.
>
> 목표가 같으니 **비교 축도 같다.** "얼마나 잘 모으는가"가 아니라 **"모으는 규칙을 나중에 바꿀 수 있는가", "모으는 비용을 언제 내는가", "카디널리티가 높아도 견디는가"**가 실제 차이다. 알고리즘 자랑이 아니라 **운영 특성의 차이**로 봐야 선택이 쉬워진다.

### 3.3 통계에는 한계가 있다 (자주 놓치는 함정)

- **통계는 앞쪽 컬럼에만 잡힌다.** Unity Catalog 외부 테이블 기준 기본값은 **처음 32개 컬럼**(`delta.dataSkippingNumIndexedCols`). 33번째 컬럼으로 필터하면 데이터 스킵이 **아예 작동하지 않는다.** 넓은 테이블에서 조용히 성능이 죽는 전형적 원인이다. 필터에 쓰는 컬럼을 앞으로 옮기거나, `delta.dataSkippingStatsColumns`로 명시하면 된다.
- **긴 문자열은 잘린다.** 통계 수집 시 긴 문자열은 truncate된다. 본문·JSON 덩어리 같은 컬럼은 통계에서 빼는 게 낫다(수집 비용만 들고 프루닝엔 도움 안 됨).
- **함수를 씌우면 프루닝이 죽는다.** `WHERE date_format(ts,'yyyyMMdd') = '20260815'`는 min/max와 대조할 수 없다. `WHERE ts >= '2026-08-15' AND ts < '2026-08-16'`으로 써야 산다. **RDBMS의 "인덱스 컬럼에 함수 쓰지 마라"와 정확히 같은 규칙**이다.
- **UC 관리형 테이블은 예측 최적화가 통계 컬럼을 알아서 고른다.** 32컬럼 제한을 받지 않는다. 외부 테이블/관리형 테이블 구분이 여기서도 갈린다.

## 4. 최적화 계층 지도 — 우리가 아는 셋은 한 층에 불과하다

파티셔닝·Z-ORDER·Liquid Clustering은 **딱 한 층(L1)**의 이야기다. 전체 지도는 이렇다.

```
┌───────────────────────────────────────────────────────────────────────┐
│ L4  워크로드 설계    증분 처리 / MV / 캐시 / 컴퓨트 선택              │  ← 효과 最大
│                      "애초에 계산을 안 한다"                          │
├───────────────────────────────────────────────────────────────────────┤
│ L3  쿼리 실행        Photon / AQE / 동적 파일 프루닝 / 조인 전략      │
│                      "같은 데이터를 더 빨리 처리한다"                 │
├───────────────────────────────────────────────────────────────────────┤
│ L2  메타데이터·통계  ANALYZE·CBO / 데이터 스킵 통계 / Deletion Vector │
│                      "덜 읽을 수 있게 판단 재료를 준다"               │
├───────────────────────────────────────────────────────────────────────┤
│ L1  데이터 레이아웃  파티셔닝 / Z-ORDER / Liquid Clustering           │  ← 오늘의 주제
│                      + 파일 크기·컴팩션(OPTIMIZE)                     │
│                      "덜 읽도록 물리 배치를 바꾼다"                   │
├───────────────────────────────────────────────────────────────────────┤
│ L0  스토리지 포맷    Delta/Iceberg, Parquet, 압축(zstd/snappy), 타입  │
│                      "바이트 자체를 줄인다"                           │
└───────────────────────────────────────────────────────────────────────┘
```

읽는 법이 있다. **위로 갈수록 효과가 크고, 아래로 갈수록 손대기 쉽다.** 그래서 사람들은 아래(설정 한 줄)부터 만지고, 정작 효과가 큰 위(파이프라인 설계)는 건드리지 않는다. 이 글의 10장이 순서를 뒤집어 제안하는 이유다.

## 5. 방법 1: 파티셔닝 — 확실하지만 되돌릴 수 없다

### 5.1 무엇인가

파티션 컬럼의 값마다 **물리 디렉터리를 만들어** 데이터를 나눈다. Hive 시절부터 이어진 가장 오래된 방식이다.

```sql
CREATE TABLE events (
  event_id   BIGINT,
  event_date DATE,
  country    STRING,
  payload    STRING
)
USING DELTA
PARTITIONED BY (event_date);
```

실제 스토리지는 이렇게 생긴다.

```
/events/
  ├── event_date=2026-08-15/
  │     ├── part-0000.parquet
  │     └── part-0001.parquet
  ├── event_date=2026-08-16/
  │     └── part-0000.parquet
  └── _delta_log/
```

`WHERE event_date='2026-08-16'`이면 **디렉터리 하나만 보고 나머지는 목록 조회조차 안 한다.** 통계를 볼 필요도 없다. 프루닝이 가장 확실하고 가장 이해하기 쉬운 형태다.

### 5.2 장점

- **프루닝이 결정적이다.** min/max 추정이 아니라 경로 매칭이라, "될 수도 있고 안 될 수도" 같은 회색지대가 없다.
- **파티션 단위 대체 연산이 가능하다.** `INSERT OVERWRITE`로 특정 파티션만 통째 교체 → **재실행 안전성(멱등성)**을 얻기 쉽다. dbt의 `insert_overwrite` 전략이 정확히 이걸 쓴다.
- **파티션 단위 삭제/보존이 싸다.** "3년 지난 데이터 삭제", "특정 지역 데이터 분리 보관" 같은 요구가 파일 스캔 없이 처리된다. 규제 대응에서 실질적 가치가 있다.
- **레거시 호환성.** Hive metastore, 외부 엔진, 경로 규약에 의존하는 시스템이 그대로 읽는다.

### 5.3 단점 — 그리고 왜 지금은 비권장인가

**① 카디널리티 함정 = small file problem**

파티션 컬럼을 잘못 고르면 파티션이 수만~수백만 개가 된다. `customer_id`로 파티션? 고객 10만 명이면 디렉터리 10만 개다. 각 디렉터리에 몇 KB짜리 파일 몇 개. 결과는 **읽기도 쓰기도 메타데이터 처리에 짓눌린다.**

Databricks 가이드는 명시적이다. **파티션 하나당 최소 1GB.** 그보다 작아질 조합이면 파티셔닝하면 안 된다.

**② 스큐**

`country`로 파티션하면 KR 파티션은 500GB, LU 파티션은 2MB가 된다. 태스크 하나가 500GB를 처리하는 동안 나머지는 논다.

**③ 조합 폭발**

`PARTITIONED BY (year, month, day, country)` 같은 걸 하면 파티션 수 = 년×월×일×국가. 매력적으로 보이지만 거의 항상 재앙이다.

**④ 가장 치명적: 바꾸려면 전체를 다시 쓴다**

파티션 컬럼은 **테이블 정의의 일부이자 물리 디렉터리 구조**다. `event_date`로 나눴는데 6개월 뒤 실제 쿼리 대부분이 `customer_id` 필터더라 — 이걸 고치려면 **테이블 전체를 새로 만들어 데이터를 옮겨야 한다.** 수십 TB면 며칠짜리 작업에 다운타임 협의까지 붙는다.

**⑤ 파티션 컬럼이 아닌 필터에는 아무 도움이 안 된다**

`event_date`로 파티션한 테이블에 `WHERE customer_id = 123`이 들어오면 **전체 스캔**이다.

### 5.4 현재 Databricks의 공식 가이드

문서가 놀랄 만큼 직설적이다.

| 테이블 크기 | 권고 |
|---|---|
| **1TB 미만** | 파티션하지 마라 |
| **1TB ~ 100TB** | Liquid Clustering을 써라. 파티셔닝은 **도움보다 해가 될 가능성이 높다** |
| **100TB 이상** | 파티셔닝이 도움 될 수 있으나, **Liquid Clustering을 먼저 테스트**하라 |

그리고 한 문장 더 — *"대부분의 100TB 미만 테이블은 파티셔닝이 필요 없다."* 파티션이 없어도 Delta는 **수집 시간(ingestion time) 기준으로 자연스럽게 뭉쳐 쓰기** 때문에, 최근 데이터 조회에는 이미 어느 정도 프루닝이 걸린다.

### 5.5 그럼에도 파티셔닝을 쓰는 경우

비권장이라고 "쓰면 안 된다"는 아니다. 여전히 정당한 이유가 있다.

- **파티션 단위 라이프사이클 관리가 요구사항일 때** — 보존기간 만료 삭제, 파티션 단위 아카이빙/분리 보관.
- **`insert_overwrite` 기반 배치 재처리 패턴이 이미 표준일 때** — "그날 파티션을 통째로 다시 만든다"가 운영·감사 측면에서 이해하기 쉽다.
- **초대형(100TB+) 테이블에서 날짜 같은 저카디널리티 축이 확실할 때.**
- **Liquid Clustering을 쓸 수 없는 환경** — 구 런타임, 외부 클라이언트 호환성 제약, 관리형 테이블이 아닐 때.

> **핵심 통찰 — "파티셔닝의 진짜 비용은 성능이 아니라 비가역성이다"**
>
> 파티셔닝의 문제는 "느리다"가 아니다. 잘 고르면 지금도 빠르다. 문제는 **결정의 비대칭성**이다. 파티션 키를 고르는 데는 30초가 걸리고, 되돌리는 데는 3일이 걸린다.
>
> 그런데 프로젝트 초기는 **쿼리 패턴을 가장 모르는 시점**이다. 가장 모를 때 가장 되돌리기 힘든 결정을 강요하는 구조 — 이게 파티셔닝이 밀려난 진짜 이유다. 성능 경쟁에서 진 게 아니라 **운영 유연성에서 졌다.**
>
> 실무에 주는 규칙: **되돌리기 비싼 결정은 정보가 쌓인 뒤로 미룬다.** 초기에는 파티션 없이 시작하고, 실제 쿼리 로그가 쌓인 뒤 레이아웃을 정하는 게 거의 항상 낫다.

## 6. 방법 2: Z-ORDER — 상태가 아니라 사건이다

### 6.1 문제의식: 두 컬럼으로 동시에 필터하고 싶다

파티셔닝은 축 하나(혹은 소수의 저카디널리티 축)에만 잘 듣는다. 그런데 현실 쿼리는 이렇다.

```sql
WHERE event_date BETWEEN '2026-08-01' AND '2026-08-07'
  AND customer_id = 481920
```

날짜로 파티션했으니 7일치는 걸러진다. 하지만 그 7일치 안에서 `customer_id`는 무작위로 흩어져 있어 **전부 읽어야 한다.**

"그럼 `ORDER BY event_date, customer_id`로 정렬해두면?" — 이게 안 되는 이유가 Z-ORDER 존재 이유다.

```
[일반 정렬: ORDER BY a, b]

a로 먼저 완전 정렬 → a 필터는 잘 듣는다
b는 a 그룹 안에서만 정렬 → b 단독 필터는 거의 안 듣는다

  파일1: a=1,   b=1..1000    ← b=500을 찾으려면
  파일2: a=1,   b=1001..2000    a=1..N의 모든 그룹에서
  파일3: a=2,   b=1..1000       해당 구간 파일을 다 봐야 함
  ...                            → 첫 컬럼만 이득
```

**정렬은 본질적으로 1차원**이라, 여러 컬럼에 이득을 나눠주지 못한다.

### 6.2 Z-order 곡선: 다차원을 1차원으로 접는다

Z-ORDER는 **공간 채움 곡선(space-filling curve)**을 쓴다. 2차원(혹은 N차원) 좌표를 하나의 순서로 사상하되, **원래 공간에서 가까운 점들이 그 순서에서도 대체로 가깝게** 되도록 만든다. Z-order(Morton order)는 각 좌표의 비트를 번갈아 끼워 넣는(bit interleaving) 방식이다.

```
좌표 (x=3, y=5)
  x = 011
  y = 101
  비트 인터리빙 → y2 x2 y1 x1 y0 x0 = 1 0 0 1 1 1 = 39
```

시각화하면 격자를 이렇게 훑는다.

```
      x→ 0    1    2    3
   y↓  ┌────┬────┬────┬────┐
    0  │ 0  → 1  │ 4  → 5  │       Z자를 그리며 채우고,
       │  ↙      │  ↙      │       그 Z가 다시 큰 Z를 이룬다
    1  │ 2  → 3  │ 6  → 7  │
       ├────┼────┼────┼────┤
    2  │ 8  → 9  │12 →13   │       → 어느 축으로 잘라도
       │  ↙      │  ↙      │         결과 구간이 완전히
    3  │10 →11   │14 →15   │         흩어지지는 않는다
       └────┴────┴────┴────┘
```

이 순서대로 데이터를 파일에 담으면, **어느 컬럼으로 필터해도 "고르게 나쁘고 고르게 좋은"** 프루닝을 얻는다. 첫 컬럼만 잘 듣는 정렬과의 결정적 차이다.

### 6.3 쓰는 법

```sql
OPTIMIZE events
WHERE event_date >= '2026-08-01'         -- 파티션 술어로 범위 한정(선택)
ZORDER BY (customer_id, product_id);
```

dbt에서는 모델 config로도 걸 수 있다.

```sql
{{ config(materialized='incremental', file_format='delta',
          zorder=['customer_id', 'product_id']) }}
```

### 6.4 단점 — 여기가 핵심이다

**① Z-ORDER는 테이블의 "상태"가 아니라 "사건"이다**

이게 가장 자주 오해되는 지점이다. `PARTITIONED BY`는 테이블 정의에 남지만, `ZORDER BY`는 **그 순간 실행된 명령**일 뿐이다. 테이블에 "나는 Z-order된 테이블"이라는 지속 속성이 붙지 않는다.

```
월요일  OPTIMIZE ... ZORDER BY (customer_id)   →  잘 정렬됨 ✅
화요일  하루치 신규 데이터 append              →  새 파일들은 정렬 밖 ❌
수요일  또 append                              →  더 나빠짐 ❌❌
        ...
        → 매번 다시 OPTIMIZE ZORDER를 돌려야 유지된다
```

**② 비멱등(non-idempotent)이며 비싸다**

일반 `OPTIMIZE`(bin-packing)는 멱등이다 — 두 번 돌리면 두 번째는 할 일이 없다. 반면 **`ZORDER BY`는 멱등이 아니다.** 문서도 "여러 번 실행해도 더 빨라진다는 보장이 없다"고 명시한다. 그리고 대상 범위의 파일을 **다시 씀**. 큰 테이블이면 매일 밤 수 시간짜리 잡이 하나 늘어난다.

**③ 컬럼이 늘면 효과가 급감한다**

축이 늘어날수록 각 축의 프루닝 능력이 희석된다. 실무 기준 **2~3개까지**. 4개 이상 넣는 건 대개 "아무거나 넣어봤다"의 신호다.

**④ 통계가 없는 컬럼에는 무효**

3.3절의 32컬럼 제한과 직결된다. 통계가 안 잡힌 컬럼을 Z-ORDER해봐야 파일 스킵 판정에 못 쓴다. **비용만 내고 이득이 0.**

**⑤ Liquid Clustering과 병용 불가**

같은 테이블에서 둘을 같이 쓸 수 없다. 배타 선택이다.

> **핵심 통찰 — "Z-ORDER는 명령이고, Liquid Clustering은 선언이다"**
>
> 둘의 차이를 "알고리즘 성능"으로 이해하면 계속 헷갈린다. 실제 차이는 **운영 모델**이다.
>
> Z-ORDER = **명령형(imperative)**. "지금 이 데이터를 이렇게 재배치해라." 그래서 누군가가 **주기적으로 다시 명령해야** 하고, 그 스케줄과 비용을 사람이 관리한다. 관리 주체가 사라지면 레이아웃도 서서히 무너진다.
>
> Liquid Clustering = **선언형(declarative)**. "이 테이블은 이 키로 뭉쳐 있어야 한다." 어떻게·언제 그 상태를 만들지는 플랫폼이 맡는다.
>
> 이 전환은 낯선 게 아니다. **Terraform이 배포 스크립트를 대체하고, dbt가 ETL 절차 코드를 대체한 것과 같은 방향**이다. 데이터 레이아웃 영역에서도 같은 이동이 일어났다고 보면 정확하다.

## 7. 방법 3: Liquid Clustering — 결정을 되돌릴 수 있게 만든 것

### 7.1 무엇인가

테이블에 **클러스터링 키를 속성으로 선언**해두면, 이후 쓰기와 유지보수 작업이 그 키 기준으로 데이터를 계속 뭉쳐 준다. 디렉터리는 만들지 않는다.

```sql
-- 신규 테이블
CREATE TABLE events (
  event_id BIGINT, event_date DATE, customer_id BIGINT, payload STRING
)
CLUSTER BY (event_date, customer_id);

-- 기존(파티션 없는) 테이블에 적용
ALTER TABLE events CLUSTER BY (event_date, customer_id);

-- 키 변경 — 메타데이터 변경이다. 데이터를 즉시 재작성하지 않는다
ALTER TABLE events CLUSTER BY (customer_id, product_id);

-- 소급 적용이 필요하면 (DBR 16.4+)
OPTIMIZE events FULL;
```

### 7.2 무엇이 근본적으로 다른가

**① 키 변경이 메타데이터 연산이다**

파티셔닝의 5.3-④와 정면으로 대비된다. `ALTER TABLE ... CLUSTER BY`는 **선언만 바꾼다.** 기존 데이터는 그대로 두고, **이후 쓰기와 `OPTIMIZE`부터 새 키를 적용**한다. 과거 데이터까지 소급하려면 `OPTIMIZE FULL`을 명시적으로 돌린다(대형 테이블에선 몇 시간이 걸릴 수 있다).

즉 **"일단 정하고, 틀리면 바꾼다"가 가능해졌다.** 이게 이 기능의 실질적 가치다.

**② `OPTIMIZE`가 증분적이다**

Z-ORDER는 돌릴 때마다 대상 범위를 다시 썼다. Liquid Clustering의 `OPTIMIZE`는 **이미 잘 클러스터된 파일은 건드리지 않고, 새로 들어온·정리가 필요한 파일만** 재배치한다. 매일 밤 전체 재작성 → 증분 정리로 유지비 곡선이 완전히 달라진다.

**③ 고카디널리티와 스큐에 강하다**

디렉터리를 만들지 않으니 `customer_id`, `device_id` 같은 고카디널리티 컬럼을 키로 써도 small file problem이 생기지 않는다. 파티셔닝이 가장 못 하던 영역이다.

**④ 동시 쓰기에 강하다**

deletion vector + row tracking이 켜져 있으면(신규 테이블 기본) **행 수준 동시성(row-level concurrency)**이 작동해 동시 쓰기 충돌이 줄어든다. 여러 dbt 모델·스트리밍 잡이 같은 테이블에 쓰는 구조에서 실질적인 이득이다.

### 7.3 자동 Liquid Clustering (`CLUSTER BY AUTO`)

한 걸음 더 나간 형태다. **키를 사람이 안 고른다.**

```sql
CREATE TABLE events (...) CLUSTER BY AUTO;
ALTER TABLE events CLUSTER BY AUTO;
```

예측 최적화(Predictive Optimization)가 **쿼리 이력을 분석해 실제 필터에 쓰이는 컬럼을 파악하고**, 클러스터링 키를 스스로 고른다. 그리고 **예상 이득이 비용을 넘을 때만** 실제로 재배치한다. 쿼리 패턴이 바뀌면 키도 따라 바뀐다.

- Unity Catalog **관리형** Delta 테이블 + **DBR 15.4 LTS 이상**
- 현재 선택된 키는 `DESCRIBE TABLE` / `SHOW TBLPROPERTIES`의 `clusterByAuto`, `clusteringColumns`로 확인
- Iceberg v3 관리형 테이블은 DBR 18.0+

> **핵심 통찰 — "레이아웃 결정이 '설계 산출물'에서 '운영 지표'로 내려왔다"**
>
> 파티션 키는 **설계 단계에 정하고 문서에 적어 결재받는** 항목이었다. 바꾸기 어려우니 그럴 수밖에 없었다.
>
> `CLUSTER BY AUTO`는 그 결정을 **런타임 관측(쿼리 이력)에 기반한 자동 조정**으로 내려버린다. 사람이 회의실에서 추측하던 것을, 시스템이 실제 워크로드를 보고 정한다.
>
> 실무에 뭘 바꾸나 — **"파티션 키를 뭘로 할까요"라는 회의가 없어진다.** 대신 질문이 바뀐다. *"우리 테이블이 관리형인가? 예측 최적화가 켜져 있나? 이 자동 결정이 어떤 근거로 내려졌는지 감사(audit)할 수 있나?"* 튜닝 역량이 **결정하는 능력에서 위임하고 검증하는 능력으로** 이동한다. SI 관점에서는 이게 산출물 목록에도 영향을 준다.

### 7.4 제약과 주의사항

만능은 아니다. 도입 전에 확인해야 할 목록이다.

| 항목 | 내용 |
|---|---|
| **키 개수** | 최대 **4개** |
| **타입 제한** | Struct/Map/Array 등 복합 타입 자체는 불가(중첩 필드는 점 표기로 가능). Date, Timestamp, String, 정수/실수/Decimal 등 지원 |
| **병용 불가** | 파티셔닝·Z-ORDER와 **같이 못 쓴다** |
| **런타임** | 읽기/쓰기 최소 **DBR 13.3 LTS**, Delta 정식(GA)은 **15.4 LTS** |
| **프로토콜 업그레이드** | reader v3 / writer v7로 올라간다 → **이 프로토콜을 모르는 외부 클라이언트는 테이블을 못 읽는다** |
| **클러스터-온-라이트 임계치** | 쓰기 시점 자동 클러스터링은 일정 데이터 크기(대략 64MB~1GB, 컬럼 수·테이블 종류에 따라 다름) 이상일 때 작동. 소량 append는 `OPTIMIZE` 때 정리된다 |
| **소급 적용 비용** | `OPTIMIZE FULL`은 대형 테이블에서 몇 시간 단위 |
| **DataFrame API 제약** | append 모드로 쓰면서 클러스터링 키를 바꿀 수 없다 → SQL `ALTER TABLE` 사용 |
| **자동 클러스터링 범위** | `CLUSTER BY AUTO`는 UC **관리형** 테이블 한정 |

특히 **프로토콜 업그레이드**는 SI 현장에서 실제로 문제가 된다. 고객사의 다른 시스템(구버전 Spark, 자체 Delta 리더, 일부 BI 커넥터)이 같은 테이블을 직접 읽고 있다면, Liquid Clustering을 켜는 순간 그쪽이 깨진다. **"이 테이블을 우리 말고 누가 직접 읽는가"를 먼저 확인**해야 한다.

## 8. 세 방법 정면 비교

| 축 | 파티셔닝 | Z-ORDER | Liquid Clustering |
|---|---|---|---|
| **물리 구조** | 디렉터리 분할 | 파일 내부 배치 순서 | 파일 내부 배치 순서 |
| **테이블에 남는가** | 정의의 일부 (영구) | 안 남음 (일회성 명령) | 테이블 속성 (영구) |
| **운영 모델** | 선언형(단, 불변) | **명령형** | **선언형** |
| **키 변경 비용** | 전체 재작성 (치명적) | 다음 OPTIMIZE에 반영 | **메타데이터만** (소급은 OPTIMIZE FULL) |
| **유지 방식** | 쓰기 시 자동 | **주기적 재실행 필요** | 쓰기 + 증분 OPTIMIZE |
| **재실행 비용** | — | 대상 범위 **전체 재작성** | **증분** (필요한 파일만) |
| **고카디널리티** | ❌ small file 폭발 | ⭕ 가능 | ⭕⭕ 강점 |
| **저카디널리티** | ⭕ 적합 | △ | ⭕ |
| **다중 컬럼 필터** | △ (첫 축 위주) | ⭕ (2~3개) | ⭕ (최대 4개) |
| **스큐 내성** | ❌ 약함 | △ | ⭕ 강함 |
| **동시 쓰기** | 파티션 단위 충돌 | OPTIMIZE와 충돌 잦음 | ⭕ 행 수준 동시성 |
| **파티션 단위 삭제/교체** | ⭕⭕ 고유 강점 | — | △ (`replace_where`로 대체) |
| **외부 호환성** | ⭕ 가장 넓음 | ⭕ (Delta 표준) | △ 프로토콜 업그레이드 |
| **지금 고르라면** | 특수 요구사항일 때만 | 신규엔 비권장 | **기본값** |

**한 문장 결론:** *신규 테이블은 Liquid Clustering을 기본으로 하고, 파티셔닝은 "파티션 단위 라이프사이클 관리"라는 고유 요구가 있을 때만, Z-ORDER는 Liquid를 못 쓰는 환경에서만.*

**선택 흐름:**

```
테이블을 만든다
  │
  ├─ 1TB 미만이고 특별한 필터 패턴 없음?
  │     → 아무것도 안 함. 파일 크기만 관리 (수집 순서 클러스터링으로 충분)
  │
  ├─ Unity Catalog 관리형 + DBR 15.4+ ?
  │     ├─ 쿼리 패턴을 아직 모름     → CLUSTER BY AUTO
  │     └─ 주 필터 컬럼이 명확함     → CLUSTER BY (col1, col2)   ← 기본 답
  │
  ├─ 파티션 단위 삭제/보존/교체가 요구사항?
  │     → 그 축만 PARTITIONED BY.  (나머지 축은 포기하거나 별도 검토)
  │
  └─ 외부 테이블 / 구 런타임 / 외부 클라이언트 호환 필요?
        → 파티셔닝 + 주기적 OPTIMIZE ZORDER BY (2~3 컬럼)
```

## 9. 나머지 최적화들 — 진범은 대개 여기 있다

여기부터가 "3가지 말고 더 있나요?"에 대한 답이다. 결론부터: **훨씬 많고, 실무 효과는 대체로 이쪽이 더 크다.**

### 9.1 파일 크기와 컴팩션 — 실무 1위 문제

**증상:** 쿼리는 단순한데 이상하게 느리다. 데이터 양 대비 태스크 수가 비정상적으로 많다.

**원인:** 파일이 너무 작고 너무 많다. 스트리밍 수집이나 잦은 증분 배치는 실행마다 작은 파일을 남긴다. 하루 1440번(분당) 도는 잡이 매번 파일 4개를 남기면 **하루 5760개**다.

작은 파일이 비싼 이유:

```
파일 1개를 읽는 실제 비용
  = 스토리지 요청 지연(수십 ms)     ← 파일 수에 비례
  + 메타데이터 처리                  ← 파일 수에 비례
  + Parquet 푸터 파싱                ← 파일 수에 비례
  + 실제 데이터 읽기                 ← 데이터 양에 비례

→ 1GB를 4MB 파일 256개로 읽으면, 고정비를 256번 낸다
```

**대처:**

```sql
-- ① 수동 컴팩션(bin-packing). 멱등이라 안전하게 반복 가능
OPTIMIZE events;
OPTIMIZE events WHERE event_date >= '2026-08-01';   -- 범위 한정

-- ② 쓰기 단계에서 미리 크게 쓰기 / 자동 압축
ALTER TABLE events SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',
  'delta.autoOptimize.autoCompact'   = 'auto'
);

-- ③ 목표 파일 크기 직접 지정(특수한 경우만)
ALTER TABLE events SET TBLPROPERTIES ('delta.targetFileSize' = '256mb');
```

알아둘 기본 동작:

- **자동 튜닝**: 테이블 2.56TB 미만 → 목표 **256MB**, 2.56TB~10TB → 256MB에서 1GB로 선형 증가, 10TB 이상 → **1GB**. 대개 이 자동값이 정답이라 `targetFileSize`를 직접 만질 일은 드물다.
- **optimized writes**는 `MERGE`, 서브쿼리를 쓴 `UPDATE`/`DELETE`에서 이미 기본 활성. UC + DBR 13.3+ 파티션 테이블의 `CTAS`/`INSERT`에도 자동 적용.
- **auto compact**는 `auto` 권장(목표 크기 동적 조정). `true`는 128MB로 고정.

> **핵심 통찰 — "클러스터링 키를 고민하기 전에 파일 개수를 세라"**
>
> 레이아웃 최적화는 **"읽어야 할 파일을 줄이는"** 일이다. 그런데 파일이 애초에 5760개로 잘게 쪼개져 있으면, 잘 골라내도 여전히 수백 개를 연다. **분모를 안 고치고 분자만 손보는 셈**이다.
>
> 실무 순서는 그래서 명확하다. **컴팩션 → 그 다음 클러스터링.** 그리고 대개 컴팩션만으로 체감 개선의 상당 부분이 나온다. 화려하지 않아서 덜 이야기될 뿐이다.

### 9.2 통계와 CBO

```sql
ANALYZE TABLE events COMPUTE STATISTICS FOR ALL COLUMNS;
```

데이터 스킵용 min/max와는 **다른 층**이다. 이건 옵티마이저(CBO)가 **조인 순서와 조인 전략**을 고르는 재료다. 통계가 없으면 옵티마이저가 카디널리티를 잘못 추정해서, 브로드캐스트하면 될 테이블을 셔플 조인으로 처리하는 식의 사고가 난다. UC 관리형 테이블은 예측 최적화가 `ANALYZE`를 자동으로 돌려준다.

### 9.3 Deletion Vectors — dbt `merge` 전략과 직결

기본적으로 Delta는 **copy-on-write**다. 1억 행짜리 파일에서 한 행을 지우려면 파일 전체를 새로 쓴다.

**Deletion vector**는 이걸 **merge-on-read**로 바꾼다. "이 파일의 37번째 행은 삭제됨"을 메타데이터에 기록하고, 읽을 때 그 정보를 적용해 걸러낸다.

- `DELETE`, `UPDATE`, `MERGE`가 크게 빨라진다 → **dbt의 `merge` 증분 전략이 직접 이득을 본다.**
- 대가: **읽을 때 벡터를 해석하는 비용**이 붙고, 누적되면 읽기가 느려진다.
- 정리: `OPTIMIZE`나 자동 압축이 물리적으로 반영한다. 규정 대응 등으로 물리 삭제를 확실히 해야 하면 `REORG TABLE ... APPLY (PURGE)` 후 `VACUUM`.

```sql
REORG TABLE events APPLY (PURGE);
VACUUM events;
```

**주의:** deletion vector를 켜면 Delta 프로토콜이 올라간다. Liquid Clustering과 마찬가지로 외부 리더 호환성 확인이 필요하다.

### 9.4 동적 파일 프루닝 (Dynamic File Pruning, DFP)

스타 스키마에서 결정적인 기능이다.

```sql
SELECT f.*
FROM fact_sales f
JOIN dim_store s ON f.store_id = s.store_id
WHERE s.region = 'Seoul'        -- 필터는 차원 테이블에 걸려 있다
```

정적 프루닝은 여기서 무력하다. 팩트 테이블에 대한 필터 술어가 문법적으로 존재하지 않기 때문이다. DFP는 **차원 테이블을 먼저 처리해 실제 `store_id` 목록을 얻은 뒤, 그 값을 런타임에 팩트 스캔으로 밀어 넣어** 파일을 걸러낸다.

- 기본 활성(`spark.databricks.optimizer.dynamicFilePruning=true`)
- 발동 임계치: 테이블 **10GB 이상**, 파일 **10개 이상**
- `MERGE`/`UPDATE`/`DELETE`에서의 DFP는 **Photon 필요**. `SELECT`는 Photon 없이도 되지만, Photon일 때 더 넓고 안정적으로 적용된다
- **효과는 팩트 테이블이 조인 키 기준으로 잘 뭉쳐 있을수록 커진다** → 조인 키를 클러스터링 키에 넣는 근거

### 9.5 Photon과 AQE

**Photon** — Spark 실행 엔진을 C++로 다시 쓴 벡터화 엔진. DBU 단가 배수가 붙지만, 스캔·필터·조인·집계가 많은 워크로드에서는 **총 실행 시간이 더 크게 줄어 총비용이 내려가는** 경우가 많다. 단, UDF가 많은(특히 Python UDF) 워크로드는 Photon이 처리하지 못해 이득이 적다. **"켜고 같은 잡을 두 번 돌려 비용을 비교"**가 유일하게 정직한 판단법이다.

**AQE (Adaptive Query Execution)** — 런타임 통계로 계획을 고쳐 쓴다. 기본 활성이며 세 가지를 한다.

1. **셔플 파티션 자동 병합** — `spark.sql.shuffle.partitions=200` 같은 고정값이 만드는 작은 파티션 문제를 줄인다
2. **조인 전략 전환** — 실제 크기를 보고 소트머지 조인을 브로드캐스트 조인으로 바꾼다
3. **스큐 조인 분할** — 특정 키에 데이터가 몰리면 그 파티션을 쪼갠다

AQE 덕에 옛날 Spark 튜닝 지식(`shuffle.partitions` 수동 조정 등)은 상당 부분 필요 없어졌다. **오래된 블로그를 보고 수동 설정을 넣는 게 오히려 AQE를 방해하는 경우**가 있다.

### 9.6 조인과 셔플

- **브로드캐스트 조인**: 작은 쪽 테이블을 모든 노드에 복사해 셔플을 없앤다. 임계치는 `spark.sql.autoBroadcastJoinThreshold`(기본 10MB 수준)이고, AQE가 런타임에 판단해 확장 적용한다. 명시적으로는 `/*+ BROADCAST(dim) */` 힌트.
- **스큐**: 특정 키(예: `customer_id = 0`, `'UNKNOWN'`)에 행이 몰리면 태스크 하나가 전체를 붙잡는다. AQE의 스큐 처리가 상당 부분 해결하지만, **더미 키를 쓰는 데이터 모델 자체가 원인**이면 모델을 고치는 게 맞다.
- **스필(spill)**: 메모리가 모자라 디스크로 밀려나는 것. 쿼리 프로파일에 스필이 크게 잡히면 **레이아웃이 아니라 메모리/파티션 크기 문제**다.

### 9.7 증분 처리 — dbt에서 가장 큰 손잡이

**모든 최적화 중 효과가 가장 큰 것은, 애초에 계산하지 않는 것이다.**

3년치 10TB 테이블을 매일 전체 재생성하는 dbt 모델이 있다고 하자. 클러스터링 키를 아무리 잘 잡아도 **10TB를 읽고 10TB를 쓴다.** 증분으로 바꿔 하루치 10GB만 처리하면 **1000배**다. Liquid Clustering으로는 절대 얻을 수 없는 배수다.

dbt-databricks의 증분 전략 선택:

| 전략 | 동작 | 언제 쓰나 | 주의 |
|---|---|---|---|
| `append` | `INSERT INTO` | 순수 append 로그, 중복 없음 보장 | 재실행 시 **중복 발생** — 멱등하지 않다 |
| `merge` | `unique_key`로 upsert | 갱신되는 디멘션, SCD Type 1 | Delta 전용. deletion vector 이득을 받음 |
| `insert_overwrite` | 파티션 통째 교체 | 파티션된 시계열 재처리 | `partition_by` 전제 |
| `replace_where` | 술어로 지정한 범위 교체 | 파티션 없이 시간창 재처리 | **컬럼 순서 기반 삽입** 주의 |
| `delete+insert` | 삭제 후 삽입 | 레코드 전체 교체 | `unique_key` 필수 |
| `microbatch` | 시간창 단위 `replace_where` | 지연 도착이 있는 이벤트 스트림 | `event_time` 지정 필요 |

**Liquid Clustering과의 조합에서 특히 중요한 점:** 파티션이 없어도 `replace_where`로 "특정 시간창만 원자적으로 교체"가 된다. 예전에는 이게 파티셔닝을 유지하는 주요 이유 중 하나였는데, 이제 그 이유가 하나 줄었다.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='replace_where',
    incremental_predicates="event_date >= date_sub(current_date(), 3)",
    liquid_clustered_by=['event_date', 'customer_id']
) }}
```

### 9.8 캐싱과 사전 계산

- **디스크 캐시(Delta cache)**: 워커 로컬 SSD에 원격 파일을 캐시. 같은 데이터를 반복 조회하는 BI 워크로드에서 크다. 대부분 자동.
- **머티리얼라이즈드 뷰**: 자주 쓰는 집계를 미리 계산해 증분 갱신. **"쿼리를 최적화"하는 대신 "쿼리를 없애는"** 접근.
- **결과 캐시**: 같은 쿼리·같은 데이터면 재실행 없이 반환.

### 9.9 유지보수 자동화 — 예측 최적화

지금까지 나온 `OPTIMIZE`, `VACUUM`, `ANALYZE`를 언제 얼마나 돌릴지는 사실 성가신 운영 문제다. **예측 최적화(Predictive Optimization)**가 이걸 대신한다.

- 대상: **Unity Catalog 관리형 테이블** (Delta, Iceberg). **외부 테이블은 제외**
- 수행: `OPTIMIZE`(+ Liquid Clustering 증분 클러스터링), `VACUUM`, `ANALYZE`. **`ZORDER`는 하지 않는다** — Z-ORDER를 쓰면 유지 스케줄을 여전히 사람이 져야 한다는 뜻
- 기본값: **2024년 11월 11일 이후 생성된 계정은 기본 활성.** 기존 계정도 순차 적용 중(2026년 8월 완료 목표)
- 상속: 계정 → 카탈로그 → 스키마 → 테이블. 각 단계에서 재정의 가능
- 비용: 서버리스 잡 SKU로 과금

> **핵심 통찰 — "관리형 테이블이냐 외부 테이블이냐가 최적화 가능 범위를 가른다"**
>
> `CLUSTER BY AUTO`, 예측 최적화, 통계 컬럼 자동 선택(32컬럼 제한 면제) — **최신 자동화 기능은 대체로 Unity Catalog 관리형 테이블 전용**이다.
>
> 그래서 "관리형이냐 외부냐"는 단순한 저장 위치 문제가 아니라 **어떤 최적화를 자동으로 받을 수 있느냐를 결정하는 선택**이다. 외부 테이블을 고르면 `OPTIMIZE` 스케줄, `VACUUM` 보존 정책, 통계 컬럼 지정을 **전부 사람이 설계하고 운영**해야 한다.
>
> SI 프로젝트라면 이건 **운영 인수인계 범위와 직결된다.** 관리형이면 "플랫폼이 알아서 합니다"로 끝나는 항목이, 외부 테이블이면 유지보수 잡·스케줄·모니터링이라는 산출물로 늘어난다. 아키텍처 결정 회의에서 이 비용을 같이 얹어 이야기해야 한다.

## 10. 그래서 무엇부터 하나 — 실무 의사결정 순서

### 10.1 0단계: 측정 없이 손대지 않는다

가장 흔한 실패는 **증상을 안 보고 처방부터 하는 것**이다. 느린 쿼리를 만나면 Databricks 쿼리 프로파일에서 다음을 먼저 본다.

| 지표 | 의미 | 크면 의심할 것 |
|---|---|---|
| **files read / files pruned** | 프루닝이 되고 있나 | 레이아웃(클러스터링/파티션), 필터에 함수 씌움 |
| **bytes read** | 실제 스캔량 | 위와 동일 + 컬럼 프루닝 |
| **files read 대비 rows output** | 파일을 열고 거의 안 쓰는가 | 레이아웃, 통계 미수집 컬럼 |
| **평균 파일 크기** | 작은 파일 문제 | 컴팩션(9.1) |
| **shuffle bytes** | 데이터 재분배량 | 조인 전략, 사전 집계 |
| **spill (disk)** | 메모리 부족 | 파티션 크기, 스큐, 클러스터 사양 |
| **task 시간 분포** | 스큐 | 스큐 키, 파티션 불균형 |

**"어느 자원이 병목인가"를 먼저 특정하고, 그 자원을 줄이는 수단을 고른다.** 스필이 문제인데 클러스터링 키를 바꾸는 건 아무 소용이 없다.

### 10.2 실행 순서

```
1. 파일 크기부터 본다              평균 파일이 수 MB → OPTIMIZE + optimizeWrite/autoCompact
                                   (효과 대비 비용이 가장 좋음. 위험도 거의 0)
       ↓
2. 계산 범위를 줄인다              전체 재생성 중이면 증분화(merge/replace_where/microbatch)
                                   (배수가 가장 큰 개선)
       ↓
3. 레이아웃을 정한다               CLUSTER BY (주 필터 컬럼 1~4개)
                                   패턴을 모르면 CLUSTER BY AUTO
       ↓
4. 통계·조인을 손본다              ANALYZE, 필터 컬럼을 앞 32개 안으로,
                                   조인 키를 클러스터링 키에 포함(DFP 이득)
       ↓
5. 컴퓨트를 조정한다               Photon 켜고 비용 비교, 워크로드에 맞는 인스턴스
       ↓
6. 그래도 부족하면 사전 계산       MV, 집계 테이블(gold), 결과 캐시
```

**이 순서를 거꾸로 하는 것이 전형적인 실수다.** 클러스터를 먼저 키우고(5번), 레이아웃을 만지고(3번), 정작 1·2번은 손대지 않는다. 1·2번이 배수가 가장 크고 비용이 가장 싼데도.

## 11. dbt에서의 실제 코드

### 11.1 신규 대형 팩트 테이블 (권장 기본형)

```sql
-- models/gold/fct_orders.sql
{{ config(
    materialized='incremental',
    file_format='delta',
    incremental_strategy='merge',
    unique_key='order_id',
    liquid_clustered_by=['order_date', 'customer_id'],
    tblproperties={
        'delta.autoOptimize.optimizeWrite': 'true',
        'delta.autoOptimize.autoCompact': 'auto'
    }
) }}

select
    order_id,          -- 필터에 쓰는 컬럼은 앞쪽에 (통계 32컬럼 제한)
    order_date,
    customer_id,
    store_id,          -- 조인 키 → DFP 이득
    amount,
    payload            -- 긴 문자열은 뒤로
from {{ ref('stg_orders') }}
{% if is_incremental() %}
where order_date >= (select max(order_date) - interval 3 days from {{ this }})
{% endif %}
```

포인트 넷:
- 레이아웃은 `liquid_clustered_by` — 나중에 바꿔도 재작성이 없다
- 증분은 `merge` + `unique_key` — 재실행해도 결과가 같다(멱등)
- 컬럼 순서가 성능에 영향을 준다 (통계 수집 범위)
- 3일 룩백으로 지연 도착 데이터를 흡수

### 11.2 쿼리 패턴을 아직 모를 때

```sql
{{ config(
    materialized='incremental',
    file_format='delta',
    incremental_strategy='merge',
    unique_key='event_id',
    auto_liquid_cluster=True     -- liquid_clustered_by와 함께 쓰지 않는다
) }}
```

**프로젝트 초기에 특히 합리적이다.** 아무도 실제 쿼리 패턴을 모르는 시점에 키를 추측해 박아 넣는 것보다, 쿼리 이력이 쌓이면서 시스템이 조정하게 두는 편이 낫다. (UC 관리형 + DBR 15.4+ 필요)

### 11.3 파티셔닝이 정당한 경우 — 보존 정책이 있는 로그

```sql
{{ config(
    materialized='incremental',
    file_format='delta',
    incremental_strategy='insert_overwrite',
    partition_by=['event_date']      -- 파티션 단위 삭제/교체가 요구사항일 때
) }}
```

`insert_overwrite`는 "그날 파티션을 통째로 다시 만든다"라서 **재처리 로직이 단순하고 감사에 설명하기 쉽다.** 다만 파티션당 1GB 이상이 나오는지 먼저 확인해야 한다. 하루 데이터가 50MB짜리 테이블에 날짜 파티션을 걸면 안 된다.

### 11.4 프로젝트 기본값을 폴더 단위로 못 박기

```yaml
# dbt_project.yml
models:
  my_project:
    +file_format: delta
    +tblproperties:
      delta.autoOptimize.optimizeWrite: 'true'
      delta.autoOptimize.autoCompact: 'auto'
    silver:
      +materialized: incremental
      +incremental_strategy: merge
    gold:
      +materialized: table
```

모델마다 config를 반복하지 않고 **팀 표준을 한 곳에** 둔다. 개별 모델은 필요할 때만 재정의한다.

### 11.5 OPTIMIZE를 누가 돌릴 것인가

dbt-databricks는 `liquid_clustered_by`가 설정된 모델을 만든 뒤 **자동으로 `OPTIMIZE`를 호출**한다. 예측 최적화가 켜진 UC 관리형 테이블이라면 이게 중복 작업이 될 수 있다.

```sql
{{ config(
    liquid_clustered_by=['order_date'],
    skip_optimize=True      -- 유지보수는 예측 최적화에 위임
) }}
```

실행 단위로 끄려면 환경변수 `DATABRICKS_SKIP_OPTIMIZE=true`.

**주의 하나:** `tblproperties`를 나중에 바꾸면 증분 모델에서는 `--full-refresh`가 필요하다. 조용히 반영 안 되는 상태로 몇 주가 지나는 사고가 여기서 난다.

## 12. 정리 & SI 관점의 시사점

**정리:**

- **최적화란 "같은 결과를 더 적은 자원으로"**이며, 자원은 **I/O·네트워크(셔플)·CPU·메모리** 네 가지다. 클라우드에서는 성능이 곧 비용이므로, 최적화는 튜닝이 아니라 **원가 활동**이다.
- 레이크하우스 최적화의 핵심은 **"읽지 않는 기술"**이다. Delta 트랜잭션 로그의 **min/max 통계로 파일을 열기 전에 제외**하는 것이 전부이고, 레이아웃 최적화는 그 통계가 쓸모 있도록 **같은 값을 같은 파일에 모으는** 일이다.
- **파티셔닝**은 디렉터리로 물리 분할한다. 프루닝이 확실하고 **파티션 단위 삭제·교체**라는 고유 강점이 있지만, **고카디널리티에서 small file로 붕괴**하고 **키를 바꾸려면 전체 재작성**이다. 현재 가이드는 **1TB 미만 비파티션, 파티션당 최소 1GB, 대부분의 100TB 미만 테이블은 불필요**.
- **Z-ORDER**는 공간 채움 곡선으로 다차원을 접어 **여러 컬럼에 고른 프루닝**을 준다. 하지만 **테이블 속성이 아니라 일회성 명령**이고, **비멱등**이며, 새 데이터가 들어올 때마다 **전체 재작성 비용**을 다시 낸다. 컬럼 2~3개를 넘기면 효과가 급감하고, **통계가 없는 컬럼에는 무효**다.
- **Liquid Clustering**은 클러스터링 키를 **테이블 속성으로 선언**하고 유지는 플랫폼이 맡는다. 결정적 차이는 **키 변경이 메타데이터 연산**(소급은 `OPTIMIZE FULL`)이고 **`OPTIMIZE`가 증분적**이라는 것. 고카디널리티·스큐·동시 쓰기에 강하다. **키 최대 4개, 파티셔닝/Z-ORDER와 병용 불가, 프로토콜 업그레이드(reader v3/writer v7)** 주의. `CLUSTER BY AUTO`는 **쿼리 이력을 보고 키를 자동 선택**한다(UC 관리형 + DBR 15.4+).
- **하지만 이 셋은 전체 지도의 한 층일 뿐이다.** 실무 효과가 큰 순서는 **① 파일 크기·컴팩션 ② 증분 처리 ③ 조인/셔플/스큐**이고, 레이아웃은 그 다음이다. 여기에 **Deletion Vector(merge-on-read), 동적 파일 프루닝, Photon, AQE, MV·캐시, 예측 최적화**가 각자의 층에서 작동한다.
- **자동화 기능 대부분은 Unity Catalog 관리형 테이블 전용**이다. 관리형/외부 선택이 곧 **자동으로 받을 수 있는 최적화의 범위**를 결정한다.
- dbt에서 실제로 만지는 손잡이는 **`liquid_clustered_by` / `auto_liquid_cluster` / `partition_by` / `zorder` / `tblproperties` / `incremental_strategy`**이며, 이 중 **가장 효과가 큰 것은 레이아웃이 아니라 `incremental_strategy`**다.

**우리 SI 프로젝트에 주는 시사점 (토론 포인트):**

- **레이아웃 표준을 프로젝트 초기에 한 장으로 정하되, "되돌릴 수 있는 쪽"으로 정하자.** 실무 기본값을 *"신규 테이블은 파티션 없이 시작, 필터 패턴이 뚜렷하면 `CLUSTER BY`, 아니면 `CLUSTER BY AUTO`, 파티셔닝은 예외 승인제"* 정도로 못 박아두면, 개발자 20명이 제각각 판단하는 상황을 막을 수 있다. 파티션 키는 잘못 정하면 나중에 전체 재작성 협의가 필요한 항목이라, **초기에 정하지 않는 것 자체가 설계 결정**이다.
- **테이블 종류(관리형/외부) 결정을 성능·운영 비용과 묶어서 논의하자.** 외부 테이블을 고르면 `OPTIMIZE`/`VACUUM`/`ANALYZE` 스케줄, 통계 컬럼 지정, Liquid Clustering 유지가 **전부 우리 운영 산출물이 된다.** 견적과 인수인계 문서 분량이 달라지는 항목인데, 보통 "저장 위치 문제"로만 다뤄지고 이 비용이 누락된다.
- **성능 개선 요청을 받으면 "쿼리 프로파일 먼저"를 팀 규칙으로 만들자.** 현장에서 튜닝 요청은 대개 "느려요"로만 온다. 파일 수·스캔 바이트·셔플·스필 중 **무엇이 큰지 확인하기 전에는 어떤 설정도 건드리지 않는다**는 규칙 하나가, 근거 없는 설정 변경이 코드베이스에 쌓이는 걸 막는다. 검증 없이 들어간 설정은 나중에 **지우지도 못한다** — 왜 넣었는지 아무도 모르기 때문이다.
- **증분화를 성능 과제가 아니라 설계 과제로 다루자.** 전체 재생성 모델을 증분으로 바꾸는 건 클러스터링 키 변경과 달리 **멱등성·지연 도착·백필 정책**을 같이 정해야 하는 일이다. 개발 후반에 "성능이 안 나와서" 급하게 하면 재처리 정확성이 흔들린다. 모델링 단계에서 **각 테이블의 갱신 전략(append/merge/replace_where)과 룩백 창**을 미리 정해두는 편이 안전하다.
- **프로토콜 업그레이드 영향도를 도입 전에 확인하자.** Liquid Clustering과 deletion vector는 Delta 프로토콜 버전을 올린다. 고객사의 다른 시스템(구버전 Spark, 자체 리더, 일부 BI 커넥터, 외부 반출 파이프라인)이 같은 테이블을 **직접** 읽고 있으면 그쪽이 깨진다. **"이 테이블을 우리 말고 누가 직접 읽는가"**를 도입 체크리스트에 넣어야 한다. 이건 되돌리기 번거로운 종류의 사고다.
- **최적화 효과를 "빨라졌다"가 아니라 숫자로 남기자.** *스캔 바이트, 파일 수, 실행 시간, DBU 비용* 네 가지를 개선 전후로 기록하면, 그 자체가 고객 보고 자료이자 다음 프로젝트의 근거 자료가 된다. SI에서 튜닝 작업은 **눈에 안 보여서 인정받기 어려운** 대표적 활동인데, 비용 절감액으로 환산하면 이야기가 달라진다.

> **토론거리:** 우리 프로젝트에서 **레이아웃 결정을 사람이 할 것인가, `CLUSTER BY AUTO`에 위임할 것인가?** 위임하면 튜닝 공수가 줄지만, "왜 이 키로 클러스터링되어 있나요"라는 질문에 **우리가 설명하지 못하는 상태**가 된다 — 고객 인수인계에서 이걸 어떻게 다룰 것인가. 그리고 **유지보수(OPTIMIZE/VACUUM)를 예측 최적화에 맡길 것인가, 우리 잡으로 명시적으로 돌릴 것인가?** 전자는 편하지만 비용이 서버리스 SKU로 따로 잡히고 실행 시점을 우리가 통제하지 못한다. 마지막으로, **성능 SLA를 계약/합의에 넣을 것인가?** "이 대시보드는 5초 이내" 같은 약속은 데이터가 커지면 지키기 어려워지는데, 그때 비용을 더 쓸지 요건을 조정할지의 판단 주체를 미리 정해두지 않으면 프로젝트 후반의 분쟁 지점이 된다.
