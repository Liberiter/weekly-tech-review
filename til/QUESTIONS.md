# PM님께 드릴 질문 목록

> 프로젝트 투입 초기, "질문하라"는 말은 들었는데 무엇을 물어야 할지 모를 때 쓰는 문서.
> **레벨 0(용어)부터 레벨 6(커리어)까지** 깊이순으로 정리했다. 위에서부터 순서대로 쓰는 게 아니라, **레벨 2(우리 프로젝트)를 가장 먼저** 소진하는 게 맞다 — 그게 당장 일하는 데 필요한 정보이자, 문서로는 절대 못 찾는 정보이기 때문이다.
>
> 답을 들으면 이 파일에 그대로 적어둔다. 3개월 뒤 이 문서가 곧 온보딩 자료가 된다.

## 먼저: 좋은 질문을 만드는 법

### 1) "질문"이 아니라 "확인"으로 던진다

초심자가 가장 많이 하는 실수는 **열린 질문**이다.

- ❌ "Unity Catalog가 뭔가요?" → 문서에 있다. 상대의 시간을 쓰고 내가 얻는 건 문서와 같은 답.
- ✅ "**제가 이해하기로는** Unity Catalog가 `카탈로그.스키마.테이블` 3단으로 권한을 관리해서, 워크스페이스가 여러 개여도 권한을 한 곳에서 본다는 건데 — **맞나요?** 그리고 실제 프로젝트에서 카탈로그를 나누는 기준은 보통 뭔가요?"

두 번째가 압도적으로 낫다. 이유가 셋이다.

- **내 이해도가 드러난다.** 상대가 어느 수준에서 설명할지 조준할 수 있다.
- **틀렸으면 정확히 그 지점만 교정된다.** "아니야, 그건 워크스페이스 단위가 아니라 메타스토어 단위야" 같은 답이 온다.
- **뒤에 붙인 두 번째 문장이 진짜 질문이다.** 문서에 없는 것 — 실무 판단 기준.

**공식: `[내가 이해한 것] + [맞나요?] + [문서에 없는 실무 질문]`**

### 2) 문서에 있는 것과 없는 것을 구분한다

PM님의 시간은 **문서에 없는 정보**에 써야 한다.

| 문서로 해결 (혼자 찾기) | 현직자에게만 있는 것 (질문하기) |
|---|---|
| 기능의 정의, 문법, 옵션 목록 | **왜 이 프로젝트에서 그걸 선택했는가** |
| "무엇을 할 수 있나" | **"실제로는 뭘 하나, 뭘 안 하나"** |
| 공식 베스트 프랙티스 | **그 베스트 프랙티스가 깨지는 경우** |
| 제품 비교표 | **고객이 실제로 겪은 실패 사례** |
| 가격 정책 | **어디서 비용이 예상 밖으로 새는가** |
| 로드맵 공개 자료 | **지금 설계에 반영해야 할 만큼 임박한 변화** |

### 3) 질문에 유통기한이 있다

- **투입 첫 2주**: "이걸 왜 이렇게 했는지" 물어도 전혀 이상하지 않다. **지금이 가장 싼 질문 타이밍이다.**
- **한 달 뒤**: 같은 질문이 "아직도 모르나"가 된다.
- 그러니 **레벨 2를 지금 다 태워라.** 아키텍처 배경, 선택의 이유, 안 한 선택지 — 나중엔 물어보기 민망해진다.

### 4) 한 번에 하나씩, 메모하며

- 한 번에 5개를 쏟으면 답이 얕아진다. **1~2개씩, 대신 자주.**
- 들은 답은 **그 자리에서 적는다.** 적는 걸 보면 상대는 더 자세히 말해준다.
- 답이 이해 안 되면 **그 자리에서** "죄송한데 한 번만 더" 라고 한다. 나중에 다시 묻는 게 훨씬 비싸다.

### 5) 오늘 바로 쓸 수 있는 질문 5개

시간이 없으면 이것부터. 전부 레벨 2에서 뽑았다.

1. "우리 프로젝트의 **전체 데이터 흐름**을 한 장으로 보면 어떻게 되나요? 소스가 뭐고 최종 소비자가 누구인지부터 잡고 싶습니다."
2. "제가 맡을 부분은 그 그림에서 **어디인가요?** 그리고 제 **첫 산출물**은 뭐가 되어야 할까요?"
3. "지금 이 프로젝트에서 **가장 리스크가 큰 지점**은 어디라고 보시나요?"
4. "코드는 어디에 올리고, **어떤 규칙**(브랜치, 리뷰, 배포)을 따르면 되나요?"
5. "제가 **혼자 판단해도 되는 것**과 **반드시 물어봐야 하는 것**의 경계가 어디일까요?"

5번은 특히 강력하다. 이걸 초기에 합의해두면 이후 모든 질문의 빈도가 자동으로 조절된다.

## Level 0 — 용어 확인

> 회의에서 흘러가는 단어들. **한꺼번에 묻지 말고**, 회의 중 못 알아들은 걸 메모했다가 끝나고 1~2개씩.
> 이 레벨은 사실 대부분 문서로 해결되니, **문서를 먼저 보고 "이렇게 이해했는데 맞나요"로 확인**하는 게 낫다.

### 플랫폼 기본 구조

- 계정(Account) / 메타스토어 / 워크스페이스는 각각 무엇의 단위인가요? 우리 고객사는 **워크스페이스를 몇 개** 쓰나요?
- **DBU**가 정확히 무엇의 단위인가요? 클러스터 크기와 DBU 소모가 어떻게 연결되나요?
- **DBR(Databricks Runtime)** 버전을 고를 때 실무에서 보는 기준이 뭔가요? LTS만 쓰나요?
- **All-purpose 클러스터 / Job 클러스터 / SQL 웨어하우스 / 서버리스** — 이 넷은 각각 언제 쓰는 건가요? 비용 차이가 큰가요?
- **Photon**은 켜면 항상 이득인가요, 아니면 안 맞는 워크로드가 있나요?

### Unity Catalog / 데이터 객체

- `카탈로그.스키마.테이블` 3단 구조에서 **카탈로그를 나누는 축**이 보통 뭔가요? (환경별? 도메인별? 조직별?)
- **관리형 테이블(managed)과 외부 테이블(external)**의 실질적 차이가 뭔가요? 우리는 어느 쪽을 기본으로 쓰나요?
- **볼륨(Volume)**은 언제 쓰는 건가요? 그냥 클라우드 스토리지 경로를 직접 쓰는 것과 뭐가 다른가요?
- **외부 위치(External Location)와 스토리지 자격증명(Storage Credential)**은 누가 만들고 관리하나요? 우리 권한 범위 안인가요?

### 개발·실행 단위

- **Job과 Pipeline**은 언제 갈리나요? 둘 다 되는 경우엔 뭘 기준으로 고르나요?
- 노트북과 일반 `.py` 파일 중 우리 프로젝트는 뭘 기본으로 쓰나요? **노트북을 프로덕션에 쓰는 것**에 대해 어떻게 생각하시나요?
- **Databricks Connect / Spark Connect**를 로컬 개발에 쓰나요, 아니면 워크스페이스에서 직접 개발하나요?

### 자주 헷갈리는 이름들

- **Delta Lake / Delta table / Databricks** — 이 셋의 관계를 어떻게 설명하시나요? (고객에게 설명할 때 쓰는 표현이 궁금합니다)
- **DLT, Lakeflow Declarative Pipelines, Spark Declarative Pipelines** — 이름이 여러 개인데 현장에서는 뭐라고 부르나요?
- **Databricks Asset Bundles / Declarative Automation Bundles(DAB)** — 개명 이후 팀에서는 어떻게 부르시나요?

## Level 1 — 개념 관계 정리

> 개별 용어는 알겠는데 **서로 어떻게 맞물리는지**가 안 잡힐 때. 여기부터는 문서로 잘 안 나오는 영역이 섞인다.

### 도구 간 경계

- **DAB와 Terraform의 역할 분담**을 어떻게 가져가시나요? UC 카탈로그·외부 위치까지 DAB로 관리하시나요, 아니면 그건 인프라팀 Terraform 영역인가요?
- **dbt를 쓰는 프로젝트와 SDP(선언형 파이프라인)를 쓰는 프로젝트**가 갈리는 기준이 뭔가요? 둘을 같이 쓰기도 하나요?
- **Airflow(또는 외부 스케줄러)와 Databricks Jobs** 중 어느 쪽으로 오케스트레이션을 잡나요? 고객사에 이미 Airflow가 있으면 어떻게 하시나요?
- **Auto Loader와 Lakeflow Connect(관리형 커넥터)** 중 어느 쪽을 기본으로 제안하시나요?

### 아키텍처 패턴

- **Medallion(Bronze/Silver/Gold)은 항상 3단인가요?** 2단이나 4단으로 가는 경우는 언제인가요?
- Bronze를 **원본 그대로 보관**하는 게 원칙이라고 알고 있는데, 실제 프로젝트에서 이게 지켜지나요? 안 지켜지면 왜인가요?
- **Gold 층을 어디까지 만드나요?** BI 도구에서 직접 조인하게 두는 경우도 있나요?
- 차원 모델링(Star Schema)을 레이크하우스에서도 그대로 하시나요? **SCD Type 2를 실제로 쓰는 비율**이 어느 정도인가요?

### 처리 모델

- **스트리밍이 진짜로 필요했던 프로젝트**가 몇이나 되나요? 고객이 "실시간" 요구할 때 어떻게 대응하시나요?
- `availableNow` **증분 배치를 기본값으로** 가져가는 게 맞다고 보시나요, 아니면 그냥 배치로 시작하나요?
- **구체화 뷰(Materialized View)를 실무에서 얼마나 쓰나요?** 증분 갱신이 실제로 잘 도나요?

## Level 2 — 우리 프로젝트 ★가장 먼저

> **이 섹션이 이 문서의 핵심이다.** 문서·구글·AI 어디에도 없는 정보이고, 투입 초기에만 자연스럽게 물을 수 있다.
> 여기 답이 채워지기 전까지 다른 레벨로 넘어가지 말 것.

### 2.1 전체 그림

- 우리 프로젝트의 **데이터 흐름을 한 장**으로 그리면 어떻게 되나요? (소스 → 적재 → 변환 → 소비)
  - → 답을 들으면 **직접 다이어그램을 그려서 다시 확인받자.** "이렇게 이해했는데 맞나요?" 이게 초기에 할 수 있는 최고의 학습이다.
- **최종 소비자가 누구**인가요? (BI 대시보드? 현업 분석가? ML 모델? 외부 시스템?)
- 이 프로젝트가 **끝났을 때 고객에게 무엇이 남아야** 성공인가요?
- 지금 **어느 단계**인가요? (요구사항 / 설계 / 구축 / 안정화)

### 2.2 배경과 선택의 이유 ← 지금 아니면 못 묻는 것

- 고객이 **왜 Databricks를 선택**했나요? 비교 대상은 뭐였나요?
- 기존에 뭘 쓰고 있었나요? **마이그레이션**인가요, 신규 구축인가요?
- 아키텍처에서 **의도적으로 하지 않기로 한 선택**이 있나요? 그 이유는요?
  - → 이 질문이 특히 좋다. "왜 이렇게 했나"보다 **"왜 저렇게 안 했나"**에 진짜 맥락이 있다.
- 이미 **한 번 뒤집힌 결정**이 있나요? 뭐가 문제였나요?

### 2.3 데이터와 요구사항

- 소스 시스템이 몇 개고, 각각 **어떤 형태**로 오나요? (DB CDC / 파일 덤프 / API / 메시지 큐)
- 데이터 **규모**가 어느 정도인가요? (일 증분량, 전체 보관량)
- **신선도 요구(SLA)**가 어떻게 되나요? 구간별로 다른가요?
- **개인정보나 민감정보**가 포함되나요? 마스킹·암호화 요건이 있나요?
- 데이터 품질 이슈가 이미 알려진 게 있나요? (누락, 중복, 스키마 변경 잦음 등)

### 2.4 환경과 규약

- **워크스페이스가 환경별로 분리**돼 있나요, 아니면 하나에서 카탈로그로 나누나요?
- **개발 → 운영 배포 경로**가 어떻게 되나요? 승인 주체는 누구인가요?
- 코드 저장소는 어디고, **브랜치 전략**은 어떻게 되나요?
- **운영 잡의 실행 주체(서비스 프린시펄)**가 준비돼 있나요? 없으면 누구에게 요청하나요?
- 네이밍 규칙(테이블, 잡, 카탈로그·스키마)이 정해져 있나요? 문서가 있나요?
- **폐쇄망이나 프록시 환경**인가요? 외부 패키지 설치가 자유로운가요?

### 2.5 컴퓨트와 비용

- 우리가 쓸 수 있는 **컴퓨트 예산의 상한**이 있나요? 누가 모니터링하나요?
- **서버리스를 쓰나요, 클래식 클러스터를 쓰나요?** 그 결정의 이유가 뭔가요?
- 제가 **실수로 비용을 크게 쓸 수 있는 지점**이 어디인가요?
  - → 초심자가 꼭 해야 할 질문. 대형 클러스터 방치, 전체 스캔 쿼리 반복, 스트리밍 상시 가동 같은 게 나온다.

### 2.6 내 역할

- 제가 맡을 **범위가 정확히 어디까지**인가요? 옆 사람과의 경계는요?
- **첫 산출물**로 뭘 만들면 될까요? 언제까지가 적절한가요?
- 제가 **혼자 판단해도 되는 것**과 **반드시 확인받아야 하는 것**의 경계가 어디인가요?
- **고객과 직접 커뮤니케이션**하는 상황이 생기나요? 그때 주의할 점이 있나요?
- 막혔을 때 **누구에게 먼저** 물어야 하나요? (PM님? 옆 개발자? 채널?)

### 2.7 팀과 고객

- 고객 측 **키맨**이 누구인가요? 각자 뭘 중요하게 생각하나요?
- 고객사 인프라·보안팀과의 **협조가 필요한 일**은 뭐가 있나요? 리드타임이 얼마나 걸리나요?
- 우리 팀 안에서 **각자 강한 영역**이 어떻게 되나요? (누구에게 뭘 물어야 하는지)

## Level 3 — 현장 감각

> 문서에 절대 안 나오는 것들. **현직자의 경험치가 그대로 이전되는 질문**이라 가성비가 가장 높다.

### 실패와 사고

- 지금까지 하신 Databricks 프로젝트에서 **가장 자주 터진 사고 유형** 세 가지를 꼽으면 뭔가요?
- **PoC에서는 잘 되는데 프로덕션에서 무너지는** 전형적인 패턴이 있나요?
- **비용이 예상 밖으로 튀는 지점**은 주로 어디인가요? 청구서 보고 놀란 경험이 있으신가요?
- 새벽에 전화 받으신 적이 있다면, 그 원인은 보통 뭐였나요?
- **롤백해야 했던 경험**이 있나요? Databricks에서 롤백은 실제로 어떻게 하나요?

### 시간이 어디로 가는가

- 마이그레이션 프로젝트에서 **실제로 가장 오래 걸리는 구간**이 어디인가요? (보통 예상과 다르다고 들었습니다)
- 견적을 낼 때 **과소평가하기 쉬운 작업**이 뭔가요?
- **기술이 아니라 사람·조직 때문에** 지연되는 경우가 얼마나 되나요?

### 고객 대응

- 고객이 Databricks에 대해 **가장 많이 오해하는 것**이 뭔가요?
- "이건 안 됩니다" 또는 "그건 필요 없습니다"를 어떻게 설득하시나요?
- 고객이 **요구사항을 바꾸는** 전형적 시점과 이유가 있나요?
- 인수인계 후에 고객이 **실제로 운영을 못 하는** 경우가 있나요? 뭐가 부족해서인가요?

### 습관과 요령

- 새 프로젝트에 들어가면 **처음 일주일에 반드시 하시는 것**이 뭔가요?
- 파이프라인 리뷰할 때 **가장 먼저 보는 지점**이 어디인가요?
- 문제가 생겼을 때 **어디부터 보시나요?** (쿼리 히스토리? Spark UI? 이벤트 로그? 클러스터 로그?)
- Databricks에서 디버깅할 때 **의외로 유용한데 잘 안 알려진 기능**이 있나요?

---

## Level 4 — 설계 판단

> 어느 정도 개념이 잡힌 뒤에 물을 것. **"무엇을"이 아니라 "언제/왜"를 묻는 질문들**이다.

### 저장·성능

- **파티셔닝을 언제 하나요?** Liquid Clustering이 나온 뒤에 판단 기준이 바뀌었나요?
- **Z-Ordering / Liquid Clustering / 파티셔닝** 중에 뭘 기본으로 가나요?
- **OPTIMIZE와 VACUUM을 언제, 얼마나 자주** 돌리나요? 자동화하시나요?
- 성능 튜닝을 **언제부터** 시작하나요? "일단 돌게 만들고 나중에"가 맞나요, 아니면 처음부터 잡아야 하나요?
- **작은 파일 문제**가 실제로 문제가 되기 시작하는 규모가 어느 정도인가요?

### 거버넌스

- **카탈로그를 나누는 축**을 환경(dev/prod)으로 하나요, 도메인으로 하나요? 둘 다면 어느 쪽이 상위인가요?
- 권한을 **개인이 아니라 그룹**으로 준다는 건 알겠는데, 그룹 체계를 어떻게 설계하시나요?
- **행·열 수준 보안(row filter, column mask)**을 실제로 많이 쓰나요? 성능 부담은 없나요?
- 데이터 리니지를 고객이 실제로 **보나요?** 아니면 만들어만 두나요?

### 처리 모델

- 스트리밍 파이프라인을 **고객에게 넘길 때** 무엇을 함께 합의하시나요? (24/7 운영 책임, 모니터링, 장애 대응)
- **상태(state)가 큰 스트리밍**을 운영해보신 적이 있나요? 뭐가 제일 힘드셨나요?
- **CDC 파이프라인**을 구축할 때 가장 신경 쓰는 부분이 뭔가요? (순서 보장, 삭제 처리, 초기 적재)
- **재처리(백필)** 시나리오를 처음부터 설계에 넣으시나요? 어떻게 하나요?

### 개방형 포맷

- **Delta와 Iceberg** 중 고객이 선택을 요구하면 어떻게 설명하시나요?
- Unity Catalog의 **Iceberg 상호운용**을 실제 프로젝트에서 써보셨나요?
- 고객이 **"벤더 종속이 걱정된다"**고 할 때 어떤 논리로 답하시나요?
  - → 이 답이 특히 궁금하다. 영업 논리가 아니라 **기술적으로 어디까지 진짜인지**.

### 품질과 테스트

- 데이터 품질 검증을 **파이프라인 안**에 넣나요, 별도 단계로 빼나요?
- 파이프라인의 **단위 테스트를 실제로 작성**하시나요? 어디까지 하나요?
- 스키마 변경이 상류에서 발생했을 때 **어떻게 감지**하나요?

---

## Level 5 — 제품·시장·전략

> **Databricks 코리아 현직자에게만 물을 수 있는 것.** 여기에 이 분의 고유한 가치가 있다.

### 한국 시장

- 한국에서 Databricks가 **잘 팔리는 산업/유스케이스**가 어디인가요? 미국과 다른 패턴이 있나요?
- **금융·공공** 프로젝트에서 특유의 제약이 뭔가요? (망분리, 클라우드 이용 규정, 데이터 국외 이전)
- 한국 고객이 **특히 자주 요구하는 것** 중에 제품이 잘 못 맞추는 게 있나요?
- **온프레미스 하둡에서 넘어오는** 고객이 아직 많나요? 그 마이그레이션의 난점이 뭔가요?

### 경쟁

- **Snowflake와 경합**할 때 실제 승부처가 어디인가요? 기능표 비교가 아니라 진짜 결정 요인이요.
- 고객이 Databricks를 **탈락시키는** 이유는 보통 뭔가요?
- 클라우드 벤더 자체 서비스(예: BigQuery, Synapse, Redshift)와는 어떻게 갈리나요?

### 제품 방향

- 최근 제품 변화 중에 **현장에서 체감이 큰 것**이 뭔가요?
- 반대로 **마케팅은 요란한데 실제로는 잘 안 쓰는** 기능이 있나요?
  - → 솔직한 답이 오면 아주 값지다. 초심자가 문서만 보면 절대 알 수 없는 정보.
- **로드맵상 곧 바뀔 것** 중에, 지금 우리 설계에 미리 반영해둬야 할 게 있나요?
- **서버리스로의 전환**이 실제로 얼마나 진행되고 있나요? 클래식 클러스터는 언제까지 쓰게 될까요?
- Genie·Assistant 같은 **AI 기능을 고객이 실제로 쓰나요?** 반응이 어떤가요?

### 지원 체계

- 제품 버그나 이상 동작을 만났을 때 **에스컬레이션 경로**가 어떻게 되나요?
- 한국에 **기술 지원 인력**이 있나요? 응답 속도가 어느 정도인가요?
- 공식 문서에 없는 걸 알아야 할 때 어디를 보시나요? (내부 채널, 커뮤니티, 소스코드)

## Level 6 — 커리어와 성장

> 분기에 한 번 정도. 자주 물으면 부담스럽다.

- 제가 **지금 시점에 가장 깊게 파야 할 것** 하나를 고르면 뭘까요?
- 반대로 **지금은 몰라도 되는 것**은 뭔가요? (범위를 좁혀주면 학습 효율이 크게 오른다)
- **자격증(Data Engineer Associate/Professional)**이 실무에 도움이 되나요, 아니면 형식적인가요?
- 6개월 뒤에 제가 **어떤 상태가 되어 있으면** 이 프로젝트에서 제 몫을 한다고 볼 수 있을까요?
- PM님은 **어떤 경로**로 지금 위치까지 오셨나요? 결정적이었던 경험이 있나요?
- 이 분야에서 **오래 가는 사람과 그렇지 않은 사람**의 차이가 뭐라고 보시나요?

## 주제별 심화 — DAB (Declarative Automation Bundles)

> 특정 주제를 막 공부한 직후에 쓰는 섹션. **배운 직후가 질문이 가장 날카로운 시점**이다.
> 아래는 DAB 편. 다른 주제를 공부하면 같은 형식으로 섹션을 추가한다.

### D-0. 묻기 전에 30분만 직접 해볼 것

질문의 질이 달라진다. **"안 해보고 묻는 질문"과 "해보다 막혀서 묻는 질문"은 돌아오는 답의 깊이가 완전히 다르다.**

```bash
databricks bundle init default-python    # 샘플 번들 생성 (로컬에 만들어만 봄)
```

그리고 만들어진 걸 **읽기만** 해본다.

- [ ] `databricks.yml`을 열어 최상위 키가 뭐뭐 있는지 눈으로 확인
- [ ] `resources/` 안의 잡 정의 YAML을 읽고, 어떤 필드가 UI의 어떤 설정에 대응하는지 짐작해보기
- [ ] `targets` 아래 dev/prod가 각각 뭘 다르게 하고 있는지 찾아보기
- [ ] `databricks bundle validate -t dev` — **배포는 아직 하지 말고** 검증만
- [ ] `databricks --version`으로 내 CLI 버전 확인 (질문할 때 필요하다)

여기까지 하면 아래 질문들이 **"제가 해봤는데 이 부분이 이해가 안 됩니다"**로 바뀐다.

> ⚠️ **`deploy`는 아직 치지 말 것.** 어느 워크스페이스로 나가는지, 내 계정에 무슨 권한이 있는지 모르는 상태에서 배포하는 건 위험하다. **D-2의 첫 질문이 바로 이걸 허락받는 질문**이다.

---

### D-1. 기본 개념 확인 (레벨 0~1)

> 공식: `[내가 이해한 것] + [맞나요?] + [실무 질문]`. 아래 질문들도 그 형태로 다듬어 쓰면 좋다.

- **번들 하나의 단위**가 뭔가요? 저장소당 하나인가요, 파이프라인/도메인 단위로 여러 개인가요?
  - → 이게 첫 질문이어야 한다. 이 답에 따라 저장소 구조가 통째로 달라진다.
- `databricks bundle deploy`를 하면 **워크스페이스의 어느 경로**에 뭐가 올라가나요? UI에서 어디를 보면 확인되나요?
- 제가 이해하기로는 **코드 파일은 워크스페이스로 동기화되고, 잡·파이프라인 같은 리소스는 API로 생성**되는 것 같은데 — 맞나요? 둘이 다른 메커니즘인가요?
- **로컬 CLI 인증**은 어떻게 설정하나요? 개인 액세스 토큰인가요, OAuth인가요? 우리 프로젝트 표준이 있나요?
- `.databricks/` 폴더에 생기는 **상태 파일**은 Git에 올리나요, 무시하나요? (`.gitignore`에 들어가 있는 것 같은데 그럼 다른 사람은 상태를 어떻게 아나요?)
  - → 상태가 워크스페이스에도 동기화된다는 걸 알게 되는 좋은 질문.
- **`bundle validate`와 `bundle plan`의 차이**가 뭔가요? 둘 다 매번 돌려야 하나요?
- 노트북을 UI에서 수정하고 저장하면, 그건 **번들과 무슨 관계**가 되나요? 다음 배포 때 사라지나요?

---

### D-2. 지금 당장 필요한 것 ★

> **가장 먼저 물을 것.** 실습을 시작하려면 이 답들이 있어야 한다.

- 제가 **로컬에서 dev 타깃으로 배포해봐도 되나요?** 어느 워크스페이스로 나가나요?
- 제 dev 배포가 **다른 팀원 것과 안 겹치나요?** (`mode: development`가 이름에 사용자 접두사를 붙인다고 이해했는데, 우리 설정도 그렇게 돼 있나요?)
- 제가 만든 dev 리소스는 **언제 어떻게 정리**하나요? `bundle destroy`를 제가 쳐도 되나요, 아니면 그냥 두나요?
- **제가 절대 치면 안 되는 명령**이 뭔가요? (`destroy -t prod`, `--force` 같은 것)
  - → 초심자가 반드시 해야 할 질문. 이걸 먼저 물으면 신뢰가 쌓인다.
- 배포가 실패하면 **로그를 어디서** 보나요? 에러 메시지가 불친절할 때 어디를 확인하시나요?
- 저는 **어느 타깃까지 배포 권한**이 있나요? staging이나 prod는 CI만 하나요?
- 우리 저장소를 클론한 다음 **제가 처음 쳐야 할 명령**이 뭔가요? (인증 설정 → validate → deploy 순서)

---

### D-3. 우리 프로젝트의 DAB 운영

- 우리 프로젝트는 **DAB를 쓰나요?** 안 쓴다면 그 이유가 뭔가요? (안 쓴다는 답도 아주 중요한 정보다)
- **타깃이 몇 개**고 각각 어떤 용도인가요? dev/prod 2단인가요, staging이 있나요?
- 워크스페이스가 환경별로 분리돼 있나요, 아니면 **한 워크스페이스에서 카탈로그로만** 나뉘나요? 후자라면 타깃을 어떻게 안전하게 설계하셨나요?
- `resources/` 아래 **파일을 쪼개는 기준**이 뭔가요? 잡 하나당 파일 하나인가요, 도메인별인가요?
- **환경차를 `variables`로 빼는 기준**이 있나요? 어디까지 변수화하고 어디부터 타깃 오버라이드로 가나요?
- **CI가 붙어 있나요?** PR을 올리면 뭐가 자동으로 도나요? (validate? plan? 테스트?)
- **운영 배포는 누가, 어떤 절차**로 하나요? 승인 단계가 있나요?
- 운영 잡의 **`run_as`가 서비스 프린시펄**로 돼 있나요? 아니면 개인 계정인가요?
- 우리는 **direct 엔진**을 쓰나요, Terraform 엔진을 쓰나요? 아직 Terraform이면 전환 계획이 있나요?
- 이미 UI로 만들어져 있던 잡들이 있나요? 있었다면 **`generate` + `bind`로 인수**하셨나요, 아니면 다시 만드셨나요?

---

### D-4. 현직자에게만 들을 수 있는 것 (레벨 3)

> 여기가 이 섹션의 알짜다. 문서에 없고, 겪어본 사람만 아는 것들.

**도입과 저항**

- DAB를 처음 도입할 때 **팀이 가장 저항하는 지점**이 뭔가요? (YAML 학습? UI를 못 쓰게 되는 것?)
- **"DAB가 관리하는 리소스는 UI에서 고치지 않는다"** 규칙이 실제로 지켜지나요? 안 지켜지면 어떻게 대응하시나요?
  - → 제가 읽은 자료에서 이게 최대 실패 원인이라고 하던데, 실제로도 그런가요?
- 고객사 담당자가 **YAML을 읽고 고칠 수 있나요?** 인수인계 때 이게 문제가 되나요?
- DAB를 **프로젝트 중간에 도입**해보신 적 있나요? 처음부터 한 것과 얼마나 차이가 나나요?

**사고와 복구**

- **`destroy`로 사고 난 사례**를 보거나 들으신 적 있나요? 어떻게 막고 계신가요?
- **상태 파일이 꼬인 적**이 있나요? 그럴 때 어떻게 복구하시나요?
- 누군가 UI에서 고친 게 **다음 배포에 덮어써져서** 문제가 된 적이 있나요?

**규모와 성장**

## 운영 메모

- 질문은 **레벨 2 → 3 → 1/0 → 4 → 5 → 6** 순으로 소진하는 게 실용적이다. 레벨 0·1은 문서로 먼저 시도하고 막힌 것만 남긴다.
- 물어본 질문은 **체크 표시**를 하거나 지운다. 같은 걸 두 번 묻지 않기 위해서.
- 답을 듣고 **새로 생긴 질문**은 바로 해당 레벨에 추가한다. 이 문서는 줄어드는 게 아니라 **바뀌면서 유지되는** 문서다.
- 레벨 3·4에서 좋은 답을 들었다면, 그건 **TIL 한 편으로 정리할 가치가 있는 내용**일 가능성이 높다.
- **주제를 하나 공부할 때마다 「주제별 심화」 섹션을 하나씩 추가한다.** 배운 직후가 질문이 가장 날카롭다. 각 섹션은 `0. 묻기 전에 직접 해볼 것 → 기본 확인 → 지금 당장 필요한 것 → 우리 프로젝트 → 현직자에게만 → 깊은 설계 → 내가 모르는 것` 형식을 따른다.
